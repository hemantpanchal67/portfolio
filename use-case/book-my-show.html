BookMyShow System Design

Design a movie and event booking platform where thousands of people pick seats on the same show and nobody pays for a seat that is already gone.

Requirements

Browsing is easy. The hard part is many people fighting for the same seat on a Friday-night blockbuster.

High-level architecture

clientedge / protectionservicedata storequeue / streamsolid arrow = sync call · dashed = async event

Flow

  1. User picks a city. Catalog serves movies, theatres and shows from a city-level cache backed by Elasticsearch.
  2. User opens a show. Seat service returns the seat map: booked, held, free.
  3. User taps seats. Seat service tries an atomic multi-seat lock in Redis (10 minutes).
  4. Booking creates a pending booking and calls Payment.
  5. On success: write confirmed seats to the DB, emit an event, Ticket service creates the QR e-ticket, Notifier sends it.
  6. Other viewers of the same show get live updates so seats turn grey without refreshing.

Deep dive 1: seat locking

Which locking strategy fits an interactive seat map with a payment step?

OptionGoodBad
DB row lockSimple, correctHeld during payment = blocked rows, deadlocks
Optimistic versionNo locksUsers lose the race after choosing and paying
Redis lock + TTLFast, auto-expires, fairNeeds a DB guard for safety
atomic multi-seat hold (Lua, all-or-nothing)
-- KEYS = seat:{show}:{seatId} ...   ARGV = userId, ttlSeconds
for i = 1, #KEYS do
  if redis.call('EXISTS', KEYS[i]) == 1 then return 0 end   -- any seat taken -> fail
end
for i = 1, #KEYS do
  redis.call('SET', KEYS[i], ARGV[1], 'EX', ARGV[2])
end
return 1
Final guard: UNIQUE (show_id, seat_id) on confirmed bookings. If Redis loses data, the DB still refuses a duplicate sale.

Deep dive 2: a blockbuster opens

Waiting roomAdmit users in batches so the booking tier stays within capacity.
Pre-warm cachesLoad seat maps and show lists into Redis before booking opens.
Shard by showPartition Redis and DB by show_id, so a hot show does not hurt others.
Cap seats per userMax 6 seats per hold. Stops hoarding and bot abuse.
  • Live seat updates: WebSocket or Server-Sent Events push seat state changes. Fall back to polling every few seconds.
  • Release on abandon: TTL expiry frees the seats and pushes an update to everyone watching.
  • Bots: captcha at hold time, per-account and per-device rate limits.
6

Deep dive 3: payment and timeouts

  1. Hold seats, then create a payment with an idempotency key.
  2. Payment success webhook arrives → if the hold is still valid, confirm.
  3. If the hold expired but payment succeeded, try to re-acquire the same seats. If taken, auto-refund.
  4. A nightly reconciliation compares gateway records against bookings.
Never confirm a seat from the browser's 'success' redirect alone. The server-side webhook is the source of truth.

Interview cheat-sheet

Why not lock the DB row during payment?

Payments take minutes. Held row locks block others and invite deadlocks. A TTL lock in Redis frees itself, and the DB constraint protects the final write.

How do you hold several seats atomically?

A Lua script that checks all seat keys and sets them only if none are taken. Redis runs it as a single atomic step.

How do other users see seats change live?

Push events over WebSocket or SSE from the seat service, with short polling as a fallback.

What if payment succeeds after the hold expired?

Try to re-acquire the seats. If someone else took them, refund automatically.
