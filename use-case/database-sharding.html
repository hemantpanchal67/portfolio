Database Sharding Scenario

One database has hit its limit on writes and size. The answer: shard it, and pick the shard key carefully.

The scenario

Scenario question
An e-commerce platform stores 800 million orders (12 TB) on one PostgreSQL primary. CPU is at 90%, writes hit 20,000/sec, and bigger hardware is no longer enough. 95% of queries filter by customer_id. How do you scale the database?

Clues in the question that point to this answer

single DB at its limitwrite throughput is the bottleneckdata too big for one machinequeries have a clear key (customer_id)scale-up already tried
Think first: what would you answer?

Try to name the pattern and one reason for each clue above. Then read on.

Answer in one line: Database sharding: split the data horizontally across many databases by customer_id, with a router in front.

Architecture

How it works

  1. Pick a shard key: customer_id. All of a customer's orders live together, so most queries hit one shard.
  2. The router hashes the key and consults the shard map to find the right database.
  3. Each shard has replicas for reads and failover.
  4. Cross-shard questions (reports, search) are served from a separate analytics store fed by CDC, not by scatter-gather on production.
  5. New row ids come from a global ID generator, since auto-increment is no longer unique across shards.
4

Choosing the shard key

Hash of keyEven distribution. Range queries on the key become scatter-gather. Best default.
Range of keyEasy range scans but risk of hot shards (e.g. latest date).
Directory (lookup table)Flexible: move any tenant anywhere. Extra lookup and a new single point of failure.
Geo / tenantWhole tenant or country on one shard. Good for isolation and residency, risk of uneven size.
A good key has high cardinality, even spread, and appears in most queries. Never shard by a low-cardinality column like status or country alone.
routing with virtual shards
VIRTUAL_SHARDS = 1024                       # many more than physical servers
vshard = hash(customer_id) % VIRTUAL_SHARDS
server = shard_map[vshard]                  # e.g. vshard 0..341 -> shard1
# Resharding = move some virtual shards to a new server; no re-hash of data

Cross-shard joinsDenormalise, co-locate related tables on the same key, or use CDC into an analytics store

6

Alternatives

  • Distributed SQL (CockroachDB, Spanner, YugabyteDB) shard automatically and keep SQL. Fewer manual headaches, different cost and latency profile.
  • NoSQL (DynamoDB, Cassandra) are built around partition keys. Great when access patterns are simple and known.
  • Application-level sharding gives full control but every team must understand it. A router or proxy hides that.
7

Follow-up questions

Sharding vs partitioning?

Partitioning splits a table inside one database. Sharding splits data across many databases or servers. See the partitioning scenario.

How do you add a shard without downtime?

Use virtual shards. Copy the chosen virtual shards to the new server, dual-write briefly, verify, then flip the shard map entry.

What if a query does not include the shard key?

It becomes scatter-gather to all shards. Avoid on hot paths. Add a secondary lookup or use the search / analytics store.

Why not shard on order_id?

Orders of one customer would spread across shards, so 'my orders' becomes scatter-gather. Shard by the entity you query by.
