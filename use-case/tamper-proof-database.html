Tamper-Proof Database Scenario

Regulators want proof that records were never altered, even by admins. The answer: an append-only, hash-chained ledger with externally anchored roots.

append-only ledger, hash chain, Merkle anchoring

The scenario

Scenario question
A bank must keep an audit trail of every balance change. Regulators demand proof that records have not been altered or deleted, even by a privileged DBA or by the bank's own engineers, and that the bank can prove this to an outsider. How do you design the database?

Clues in the question that point to this answer

Think first: what would you answer?

Try to name the pattern and one reason for each clue above. Then read on.

Answer in one line: A tamper-evident, append-only ledger: every entry is hash-chained and signed, batches are rolled into a Merkle tree, and the root hash is anchored outside the database.
2

Tamper-proof vs tamper-evident

No database can make an admin physically unable to touch disks. What we can do is make any change detectable and provable.

GoalTechnique
Prevent updates and deletesInsert-only table, revoke UPDATE / DELETE, triggers that reject changes
Detect edits to old rowsHash chain: each row stores the hash of the previous row
Detect deleted rowsSequence numbers with no gaps, plus the chain
Prove it to outsidersMerkle root published to something the bank cannot rewrite
Prove who wrote itDigital signatures with keys in an HSM
Keep copies safeWORM (write once read many) storage, object lock, replicas in other accounts

Architecture

How it works

  1. The application calls an append-only API. There is no update or delete endpoint.
  2. The ledger writer computes hash = SHA-256(prev_hash + payload + timestamp) and signs it with an HSM key.
  3. The entry is inserted into the ledger table. Database permissions allow INSERT and SELECT only.
  4. Every N seconds the Merkle batcher builds a Merkle tree over new entries and produces one root hash.
  5. The root hash is anchored in write-once storage and an external notary (a trusted timestamp service or a public ledger).
  6. A verifier job recomputes the chain and roots, and compares them with the anchors. Any difference raises an alert.
4

Implementation

hash-chained, insert-only ledger (PostgreSQL)
CREATE TABLE ledger (
  seq        bigint      PRIMARY KEY,          -- strictly increasing, no gaps
  account_id bigint      NOT NULL,
  payload    jsonb       NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  prev_hash  bytea       NOT NULL,
  row_hash   bytea       NOT NULL,             -- SHA-256(prev_hash || payload || created_at)
  signature  bytea       NOT NULL              -- signed by HSM key
);

REVOKE UPDATE, DELETE, TRUNCATE ON ledger FROM app_user, dba_user;

CREATE FUNCTION no_change() RETURNS trigger AS $$
BEGIN RAISE EXCEPTION 'ledger is append-only'; END $$ LANGUAGE plpgsql;
CREATE TRIGGER ledger_no_update BEFORE UPDATE OR DELETE ON ledger
  FOR EACH ROW EXECUTE FUNCTION no_change();
verification
for each row in ledger order by seq:
    assert row.seq == expected_seq                      # no deleted rows
    assert row.prev_hash == previous.row_hash           # chain unbroken
    assert row.row_hash == sha256(row.prev_hash + row.payload + row.created_at)
    assert verify_signature(row.signature, row.row_hash, public_key)
compare merkle_root(block) with the anchored copy       # catches full-chain rewrites
A clever insider could rewrite every row and recompute the whole chain. Only the externally anchored roots expose that. That is why anchoring matters.

Operational must-haves

  • Separate duties: the people who run the database cannot hold the signing keys or the anchor store credentials.
  • Corrections are new entries. Never edit. Reverse with a compensating entry that references the original.
  • Privacy: do not put raw PII in an immutable store (GDPR erasure). Store a hash or a pointer, or encrypt per subject and destroy the key.
  • Time: use a trusted timestamp so the anchored time is believable.
  • Performance: chain per account or per shard so writers do not serialise on one global chain.
7

Follow-up questions

Can't the DBA just rewrite the whole chain?

Yes, within the database. That is why root hashes are anchored in write-once storage and an external notary, and why signing keys sit in an HSM the DBA cannot use.

How do you prove one entry is genuine without sharing the whole ledger?

Give the auditor a Merkle proof (the sibling hashes up to the anchored root). They verify it without seeing other rows.

How do you handle a mistake?

Append a correcting entry that references the original. History stays intact, current balance is derived from all entries.

Hash chain vs blockchain?

A hash chain with anchoring gives tamper evidence for one organisation. A blockchain adds consensus between parties who do not trust each other.
