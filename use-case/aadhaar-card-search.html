Aadhaar Card Search System Design

Design a national-scale identity system: look up a person by number, search by name and DOB, and dedupe biometrics, all without leaking a single record.

High-level architecture

Request flow (verify an identity)

  1. Agency calls the Secure Gateway over mTLS with a signed request and a registered licence key.
  2. Rate limit + consent check: is this agency allowed, and did the person consent for these fields?
  3. Lookup validates the checksum, converts the number to a token, and reads the encrypted record from the right shard.
  4. Auth sends an OTP, or runs biometric matching, and returns only yes / no plus the consented fields.
  5. Every call is written to the audit stream and ends up in write-once storage.
4

Deep dive 1: lookup by Aadhaar number

  • Validate first. The 12th digit is a Verhoeff checksum. Reject typos without touching a database.
  • Tokenise. A token vault (backed by an HSM) maps the real number to an internal token. All other systems only see the token.
  • Shard by hash. shard = hash(token) mod N with consistent hashing, so adding shards moves little data. Each shard has replicas in two data centres.
  • Field-level encryption. Name, address and DOB are encrypted with per-record keys wrapped by the HSM.
  • Cache tokens, not PII. Never cache decrypted demographics in shared caches.
lookup path
verify(number):
  if !verhoeff(number): return INVALID
  token = vault.tokenize(number)          # HSM-backed
  shard = ring.locate(token)
  rec   = shard.get(token)                # encrypted blob
  return mask(decrypt(rec, allowedFields))  # e.g. XXXX XXXX 1234

Deep dive 2: demographic (fuzzy) search

Authorised agencies sometimes search by name + DOB + locality when the number is unknown. Names are messy: spellings, transliteration, initials.

Blocking keysDOB year + first letters + pincode shrink 1.4B to a few thousand candidates before any fuzzy work.
Phonetic + n-gramIndic-aware phonetic codes and character n-grams match Sharma / Sarma, Mohammad / Mohd.
ScoringWeighted score on name, DOB, address, gender. Return top-k with scores, never a single guess.
No raw PII in indexIndex holds hashed / tokenised tokens plus the record token. Details are fetched from the vault only after authorisation.
Search is the enumeration risk. Cap results (e.g. max 5), require consent or legal basis, and rate limit per agency and per user.

Deep dive 3: biometric dedup (1:N)

At enrolment, the new person's fingerprints, iris and face are compared against everyone, to make sure the same person is not enrolled twice.

  1. Extract templates (compact feature vectors) from raw biometrics.
  2. Prune candidates using demographics such as gender and age band. This can cut the search space by 5–10×.
  3. Scatter-gather across template shards held in memory. Each shard returns its best matches with scores.
  4. Fuse modalities (finger + iris + face) into one score. Multi-modal fusion lowers false matches.
  5. Above threshold → possible duplicate, routed to manual adjudication. Below → enrol.
1:1 authentication (is this the person who owns this number?) is far cheaper than 1:N dedup. Keep them as separate services.

Trade-offs and failure handling

  • Consistency over availability for identity writes. A duplicate identity is worse than a slow enrolment.
  • Reads degrade gracefully. If biometrics are down, fall back to OTP; if OTP fails, fall back to a retry window.
  • Active-active reads, single-writer per shard across regions, with synchronous replication inside a region.
  • Hot shards are unlikely because tokens are hashes, but one agency can be hot, so rate-limit per agency.

Interview cheat-sheet

How do you search 1.4B records quickly?

Number lookup is a hash to shard to key read. Fuzzy search uses blocking keys and phonetic n-grams to shrink candidates before scoring.

How do you protect the numbers if the DB leaks?

Tokenise, encrypt per record with HSM-wrapped keys, keep the token vault separate, and never store raw numbers in logs or indexes.

Why is biometric dedup hard?

It is 1:N across billions with probabilistic scores. We prune with demographics, shard templates in memory, fuse modalities, and use thresholds plus manual review.

How do you stop someone enumerating all numbers?

Checksum validation, per-requester rate limits, result caps, consent, and anomaly detection on query patterns.
