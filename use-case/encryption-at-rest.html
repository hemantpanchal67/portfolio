Encryption at Rest Scenario

Auditors ask what happens if a disk, snapshot or backup leaks. The answer: envelope encryption with layered keys, and field-level encryption for the crown jewels.

The scenario

Scenario question
A healthcare and payments platform stores patient records and card data in the cloud. Auditors (PCI DSS, HIPAA, GDPR) ask: if a disk, snapshot or backup is stolen, or a DBA browses the tables, can the attacker read customer data? You also need key rotation and the ability to revoke a customer's data. What do you design?

Clues in the question that point to this answer

stolen disk / snapshot / backupcompliance (PCI, HIPAA, GDPR)insider with DB accesskey rotation requiredper-customer data revocation
Think first: what would you answer?

Try to name the pattern and one reason for each clue above. Then read on.

Answer in one line: Encryption at rest with envelope encryption: data keys protect the data, a KMS / HSM-held master key protects the data keys, plus field-level encryption for the most sensitive columns.

Architecture

clientedge / protectionservicedata storequeue / streamsolid arrow = sync call · dashed = async event

Key hierarchy (envelope encryption)

  1. Root key lives in an HSM and never leaves it.
  2. KMS master key (KEK) is protected by the root key. Apps cannot read it, they can only ask KMS to wrap or unwrap.
  3. A data key (DEK) is generated per tenant, table or record. It encrypts the actual data with AES-256-GCM.
  4. The DEK is stored next to the data, encrypted by the KEK. To read, the app asks KMS to unwrap the DEK, decrypts, then discards the plaintext key.
Why envelope? KMS only encrypts small keys, so big data is never sent to KMS. Rotating the KEK only re-wraps small DEKs, not terabytes of data.

Implementation

envelope encryption (pseudo-code)
encrypt(plaintext, tenantId):
  dek        = kms.generateDataKey(keyId = "tenant/" + tenantId)   # returns plaintext + wrapped
  nonce      = random(12 bytes)
  ciphertext = AES_256_GCM.encrypt(dek.plaintext, nonce, plaintext, aad = tenantId)
  wipe(dek.plaintext)
  return { wrappedDek: dek.wrapped, nonce, ciphertext }     # store all three

decrypt(record, tenantId):
  dek = kms.unwrap(record.wrappedDek, context = tenantId)    # audited, policy-checked
  return AES_256_GCM.decrypt(dek, record.nonce, record.ciphertext, aad = tenantId)
Layered encryptionVolume/TDE for everything, field-level for card numbers, national IDs, health data.
Key per tenantDelete or disable a tenant key and their data becomes unreadable (crypto-shredding, helps GDPR erasure).
RotationRotate KEK on a schedule (e.g. yearly), re-wrap DEKs. Rotate DEKs when data is rewritten.
BYOK / HYOKCustomers bring or hold their own key. They can cut access by revoking it.
5

How do you search encrypted columns?

  • Exact match: store a blind index = HMAC(secret, normalized_value) next to the ciphertext. Query by the HMAC.
  • Prefix / last-4 digits: store a separate, low-sensitivity derived column (e.g. last 4 of card).
  • Range / LIKE / sort: not possible on strong ciphertext. Either avoid encrypting that column, tokenise it, or search a separate secured index.
  • Never use deterministic encryption for low-entropy values without understanding the leakage (equal values look equal).
6

Operational must-haves

  • Least privilege on keys: the app can use a key to encrypt and decrypt, but cannot export it or change its policy. Separate key admins from data admins.
  • Audit every key use and alert on unusual decrypt volumes.
  • Encrypt backups and replicas with keys available in the DR region.
  • Test restores, including key availability. An encrypted backup you cannot decrypt is no backup.
  • Protect logs and caches: plaintext copies in logs, caches or search indexes defeat the design.
  • Performance: AES uses hardware acceleration. Cache unwrapped DEKs briefly in memory to avoid a KMS call per row.
7

Follow-up questions

TDE vs application-level encryption?

TDE encrypts files on disk transparently and defends against stolen media. Application-level encryption also defends against DB admins and some injection, but costs searchability and needs key handling in the app.

What if KMS is down?

Cache unwrapped DEKs for a short time in memory, run KMS in multiple regions, and design degraded modes for read-only access.

How do you erase one customer's data from backups (GDPR)?

Use a per-customer key. Destroying the key makes every copy, including backups, unreadable (crypto-shredding).

Why AES-GCM?

It provides encryption and integrity together (authenticated encryption). Never reuse a nonce with the same key.
