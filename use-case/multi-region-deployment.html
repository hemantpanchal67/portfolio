Multi-Region Deployment Scenario

A global app must survive a whole-region outage, serve users fast everywhere and keep EU data in the EU. The answer: multi-region deployment.

The scenario

Scenario question
A fintech app serves users in India, Europe and the US. The business wants 99.99% availability, EU customer data must stay in the EU, latency should be under 200 ms for everyone, and a complete region outage must not stop the app. How do you deploy it?

Clues in the question that point to this answer

users in many continentsregional outage must be surviveddata residency (EU)low latency worldwide99.99% SLA
Think first: what would you answer?

Try to name the pattern and one reason for each clue above. Then read on.

Answer in one line: Active-active multi-region deployment with geo-routing, stateless regional stacks, and data placed by home region plus cross-region replication for disaster recovery.

Why multi-region?

Multi-region is expensive. Use it when availability, latency or residency demand it, not by default. A multi-AZ setup in one region already survives a data-centre failure.

Architecture

clientedge / protectionservicedata storequeue / streamsolid arrow = sync call · dashed = async event

How a request flows

  1. User hits global routing (GeoDNS or Anycast). It picks the nearest healthy region.
  2. The regional stack (stateless app + cache) serves the request. Sessions live in a regional store or in signed tokens.
  3. Reads and writes go to the user's home-region database.
  4. Changes replicate asynchronously to other regions for DR. EU data replicates only to approved EU locations.
  5. If a region fails, health checks remove it and users are routed to the next region, which already holds their replica.
4

The hard part: data

Home-region (partition by user)Each user has one home region that accepts writes. No write conflicts, and residency is satisfied. Best default.
Active-active writesAny region accepts writes. Needs conflict resolution (last-write-wins, CRDTs). Use for low-risk data like preferences.
Global tablesReference data (currencies, product catalogue) replicated everywhere. Read local, write rarely.
Async vs sync replicationSync across oceans adds 100+ ms to every write. Choose async and accept a small RPO, or sync only for critical ledgers.
TermMeaningTarget here
RTOHow long until service is back< 1 minute (automatic failover)

5

Failover and operations

  • Health checks at multiple layers: DNS health, load balancer health, synthetic transactions. Avoid flapping with sensible thresholds.
  • Capacity headroom: if one of three regions dies, the other two must absorb its traffic. Plan ~50% spare per region.
  • Promote carefully: when a home region fails, promote its replica in another region. Fence the old primary so it cannot accept writes when it returns (avoid split-brain).
  • Caches and sessions: keep them regional and rebuildable. Never depend on a cross-region cache call in the hot path.
  • Deployments: roll out region by region (canary first). One bad release must not hit every region at once.
  • Game days: regularly simulate a region loss to prove RTO and RPO.

Follow-up questions

What if two regions update the same record?

Prefer home-region ownership so only one region writes a given record. For shared data, use a conflict rule (last-write-wins with timestamps) or CRDTs.

How do you keep EU data in the EU?

Pin each EU user's home region to the EU, replicate only to EU locations, and keep analytics and logs that contain PII in-region too.

How do you prevent split-brain after failover?

Use a fencing token or epoch number. A returning old primary with an older epoch is read-only until resynced.

Is multi-region the same as multi-AZ?

No. AZs are separate data centres in one region (low latency, synchronous). Regions are far apart (high latency, usually asynchronous).
