IRCTC Ticket Booking System Design

Design a railway ticketing platform that handles millions of searches and a violent 10 AM booking spike without ever selling a seat twice.

Requirements

Think of IRCTC as a very large inventory system with a brutal traffic spike: Tatkal opens at 10:00 and 11:00 and everyone shows up in the same minute.

High-level architecture

Booking flow

  1. User passes CDN + WAF + captcha. Bots and scripts are filtered here.
  2. During Tatkal the user enters a waiting room. The gateway admits users at a rate the backend can handle.
  3. Search reads trains from Elasticsearch and cached availability. It never touches the inventory DB directly.
  4. Booking places a seat hold in Redis (TTL ~10 min), then calls Payment.
  5. On payment success, Booking commits the seat in the Inventory DB and emits a Kafka event.
  6. Workers send the ticket (SMS / email / push) and run waitlist promotion when seats free up.
4

Deep dive 1: seat inventory without double booking

A train runs A → B → C → D. A seat sold for A→C must stay available for C→D. So inventory is per segment, not per seat.

segment bitmap per seat
train 12951, date 2026-11-20, class 3A, coach B2, seat 41
stops:   A    B    C    D
legs:      A-B  B-C  C-D
bitmap:     1    1    0     (seat is taken for A->C, free for C->D)

booking(from=B, to=D) needs legs B-C and C-D free:
  (bitmap & mask(B..D)) == 0  ->  seat is allocatable
Pessimistic lockSELECT ... FOR UPDATE SKIP LOCKED on candidate seats. Simple and correct, but hot trains create lock contention.
Optimistic versionUpdate with WHERE version = ?. Great when conflicts are rare, wasteful in a Tatkal rush.
Single writer per trainPartition Kafka by train_id. One consumer allocates seats for a train, so no contention at all. Best for Tatkal.
Redis holdSET hold:{train}:{seat} user NX EX 600 reserves the seat while the user pays. TTL releases it automatically.
Final guard: a unique constraint on (train, date, class, seat, leg) in the DB. Even if Redis or app logic fails, the DB refuses a second sale.
5

Deep dive 2: booking + payment as a saga

Payment is slow and external. Do not hold a DB transaction open while waiting for the bank.

  1. Hold seat in Redis (10 minutes).
  2. Create a payment intent with an idempotency key (booking id).
  3. Redirect to bank / UPI. Result arrives through a webhook and a polling fallback.
  4. Success → commit seat, generate PNR, send ticket.
  5. Failure or timeout → release hold (compensation).
  6. A reconciliation job compares bank statements with bookings. Money debited but no ticket means auto-refund.
Duplicate webhooks and double-clicks are normal. The idempotency key makes the second call a no-op.
6

Deep dive 3: waitlist, RAC and Tatkal

  • Waitlist is a per-train, per-class queue ordered by booking time. A cancellation emits an event and the waitlist worker promotes the head of the queue.
  • RAC (Reservation Against Cancellation) gives a shared berth first, then upgrades to a full berth.
  • Tatkal is a separate quota with its own opening time. Treat it as its own inventory pool, so one rush does not lock general-quota seats.
  • Waiting room + token bucket admit only as many users as the booking tier can serve. Everyone else sees a calm queue page, not an error.

Trade-offs and failure handling

ChoiceWhyCost
Strong consistency for inventoryMoney and seats are involvedLower write throughput, so we queue per train
Cached, stale availability on searchSearch is 100× heavier than bookingUser may see 'available' then get 'sold out'
Waiting roomProtects backendSome users wait a few minutes

  • Redis down: fall back to DB-based holds with a short hold_until column.
  • Payment gateway slow: extend hold slightly, show a 'confirming' screen, and reconcile later.
  • Region failure: active-passive DR for inventory DB, since active-active writes risk double sales.
9

Interview cheat-sheet

How do you stop two users getting the same seat?

Hold in Redis with NX, serialise allocation per train through a partitioned queue, and keep a DB unique constraint as the final guard.

How do you survive the 10:00 Tatkal rush?

CDN + WAF + captcha, a waiting room with a token bucket, cached search, and a queue in front of booking. Scale reads horizontally, serialise writes per train.

What if payment succeeds but the user's session dies?

Webhook still reaches Booking, which confirms the seat if the hold is alive. If the hold expired, we try to re-allocate, else auto-refund via reconciliation.

Why not a microservice per class?

Booking is one transaction across a train's inventory. Splitting by class adds cross-service transactions with no real benefit.
