Database Partitioning Scenario

One giant time-series table is slow to query and impossible to purge. The answer: partition it by date.

range partitions, pruning, retention

The scenario

Scenario question
A payments system writes 5 billion rows to a single transactions table. Almost every query asks for the last 7 days. Monthly reports scan one month. Regulations say delete data older than 2 years, and the DELETE job locks the table for hours. Indexes no longer fit in memory. What do you do?

Clues in the question that point to this answer

one huge tablequeries filter by dateregular purge of old datadelete is slow and bloatsindex too big for RAM
Think first: what would you answer?

Try to name the pattern and one reason for each clue above. Then read on.

Answer in one line: Range partition the table by date (monthly). Queries touch only recent partitions, and retention becomes DROP PARTITION.
2

What partitioning gives you

Partition pruningA query with a date filter scans only matching partitions, not 5B rows.
Small, hot indexesEach partition has its own small index that fits in memory.
Instant retentionDROP / DETACH a month in milliseconds. No bloat, no long DELETE.
Cheap archivingDetach old partitions and move them to cheaper storage or Parquet files.
Partitioning splits data inside one database. It does not add more CPU or write capacity beyond that server. That is what sharding is for.

How it works

  1. The parent table holds no rows. Rows are stored in child partitions, one per month.
  2. Inserts are routed to the current month partition automatically.
  3. Queries with a created_at filter hit only the partitions that match (pruning).
  4. A scheduled job creates next month's partition ahead of time.
  5. Partitions older than 2 years are detached and archived, then dropped.

Implementation (PostgreSQL)

declarative range partitioning
CREATE TABLE transactions (
  id          bigint       NOT NULL,
  account_id  bigint       NOT NULL,
  amount      numeric(18,2),
  created_at  timestamptz  NOT NULL,
  PRIMARY KEY (id, created_at)          -- partition key must be in the PK
) PARTITION BY RANGE (created_at);

CREATE TABLE transactions_2026_11 PARTITION OF transactions
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

CREATE INDEX ON transactions (account_id, created_at);   -- created per partition
retention in milliseconds
-- instead of: DELETE FROM transactions WHERE created_at < now() - interval '2 years';
ALTER TABLE transactions DETACH PARTITION transactions_2024_10;
-- archive it (COPY to Parquet / object storage), then:
DROP TABLE transactions_2024_10;
check pruning
EXPLAIN SELECT * FROM transactions
WHERE created_at >= now() - interval '7 days';
-- plan should list only the current (and maybe previous) partition

  • Keep the partition count sensible (hundreds, not hundreds of thousands).
  • Always include the partition key in queries, otherwise every partition is scanned.
  • Unique constraints must include the partition key.

Follow-up questions

Partitioning vs sharding?

Partitioning: one database, many tables on the same server, for manageability and pruning. Sharding: many servers, for write and size scale.

Is partitioning enough when writes grow 10x?

No. It does not add CPU or disk bandwidth. Add read replicas, then shard when one primary can no longer take the writes.

What if a query lacks the date filter?

It scans all partitions and may be slower than before. Make date filters mandatory in the API or add a covering index.

Can I combine them?

Yes. Shard by customer across servers, and inside each shard partition by month. Common in large systems.
