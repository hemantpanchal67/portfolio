1. What is a Subnet?

A subnet (sub-network) is a range of IP addresses inside your VPC. You divide the VPC address space into subnets so that you can place resources in the right network segment, apply different routing and firewall rules to each, and spread them across Availability Zones. Each subnet lives in exactly one AZ and cannot span zones, so for high availability you create one subnet per tier per AZ.

Subnets are not secure or insecure by themselves. What matters is the route table associated with them. Calling a subnet public or private only describes whether its route table sends internet traffic to an Internet Gateway.

Features and benefits

Subnets give you segmentation (web, application and data tiers), control through per-subnet route tables and network ACLs, high availability by spreading across AZs, and organisation of address space. They are free: you pay only for the resources inside them and for gateways such as NAT.

Problems

The common problems are running out of IP addresses because subnets were sized too small, wrong route table association that makes a private subnet accidentally public, forgetting that a subnet is zonal and building a single-AZ design, and overlapping CIDR ranges that cannot be fixed without recreating the subnet, because the CIDR of an existing subnet cannot be changed.

aws ec2 create-subnet --vpc-id vpc-123 --cidr-block 10.0.1.0/24 --availability-zone ap-south-1a \
    --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=public-a}]'
aws ec2 describe-subnets --filters Name=vpc-id,Values=vpc-123 \
    --query "Subnets[].[SubnetId,CidrBlock,AvailabilityZone,AvailableIpAddressCount,MapPublicIpOnLaunch]" --output table

2. Public, Private & Isolated Subnets

A public subnet has a route 0.0.0.0/0 to an Internet Gateway. It hosts internet-facing resources: load balancers, NAT Gateways and sometimes a bastion host. A private subnet has no route to an IGW. Its resources are not reachable from the internet, but they can start outbound connections through a NAT Gateway in a public subnet. An isolated subnet goes further and has no route to the internet at all, not even through NAT. It is used for databases and other sensitive data, reached from the application tier and from AWS services through VPC endpoints. A VPN-only subnet routes to a virtual private gateway for connection to an on-premises network.

SubnetDefault routeTypical resourcesReachable from internet?
Public0.0.0.0/0 → Internet GatewayALB, NAT Gateway, bastionYes, if resource has a public IP and rules allow
Private0.0.0.0/0 → NAT GatewayApp servers, containers, LambdaNo
IsolatedLocal only (+ endpoints)RDS, ElastiCacheNo, and no outbound
VPN-only→ Virtual private gatewayHybrid workloadsNo

Marking a subnet public needs four things to line up: the route to the IGW, a public IP on the instance (auto-assign or Elastic IP), a security group that allows the traffic and a network ACL that allows it in both directions. If any is missing, the instance is not reachable.

resource "aws_route_table" "public"  { vpc_id = aws_vpc.main.id  route { cidr_block = "0.0.0.0/0" gateway_id     = aws_internet_gateway.igw.id } }
resource "aws_route_table" "private" { vpc_id = aws_vpc.main.id  route { cidr_block = "0.0.0.0/0" nat_gateway_id = aws_nat_gateway.a.id } }
resource "aws_route_table" "isolated"{ vpc_id = aws_vpc.main.id }                                  # local route only
resource "aws_route_table_association" "pub_a" { subnet_id = aws_subnet.public_a.id  route_table_id = aws_route_table.public.id }
A subnet that you do not explicitly associate with a route table uses the VPC main route table. Keep the main route table private so new subnets are never accidentally public.

3. CIDR, Sizing & Reserved Addresses

Subnets are carved out of the VPC's CIDR block. The prefix length tells the size: the number of addresses is 2^(32 − prefix). A /24 has 256 addresses, a /20 has 4,096 and a /28, the smallest allowed, has 16. A subnet range must fit inside the VPC range, and ranges in one VPC cannot overlap.

In every subnet AWS reserves five addresses: .0 is the network address, .1 is the VPC router, .2 is the Amazon DNS resolver, .3 is reserved for future use and the last address is the broadcast address (not supported but reserved). So the usable count is 2^n − 5: a /24 gives 251, a /28 gives 11.

PrefixAddressesUsableGood for
/281611Tiny endpoints or test
/266459NAT and ALB subnets
/24256251General subnets
/221,0241,019Larger app tiers
/204,0964,091Containers and pods
/198,1928,187EKS with many pods
import ipaddress
vpc = ipaddress.ip_network("10.0.0.0/16")
subnets = list(vpc.subnets(new_prefix=24))                  # 256 subnets of /24
print(len(subnets), subnets[0], subnets[1])                 # 256 10.0.0.0/24 10.0.1.0/24
print(subnets[0].num_addresses - 5, "usable in a /24")      # 251

Planning tips

Plan the whole address space first, leave spare blocks for future subnets and secondary CIDRs, and give more addresses to tiers that scale. Remember that load balancers, VPC endpoints, NAT Gateways, Lambda in VPC and container pods also consume addresses through their network interfaces, so count interfaces, not just servers. Subnet CIDRs cannot be changed after creation, but you can add secondary CIDR blocks to the VPC and create new subnets in them.

4. Three-tier Design Across Availability Zones

The classic layout uses three tiers of subnets and repeats them in two or three AZs. The public tier holds the load balancer and NAT Gateways. The application tier holds the servers or containers in private subnets, and is usually the largest because it contains the most network interfaces. The data tier holds databases and caches in isolated subnets. With three tiers in three AZs you create nine subnets.

VPC 10.0.0.0/16
         AZ a              AZ b              AZ c
public   10.0.0.0/24       10.0.1.0/24       10.0.2.0/24        ALB nodes, NAT Gateway per AZ
app      10.0.16.0/20      10.0.32.0/20      10.0.48.0/20       EC2 / ECS / EKS pods
data     10.0.8.0/24       10.0.9.0/24       10.0.10.0/24       RDS, ElastiCache (isolated)
Route tables:  public → IGW   |   app-a/b/c → NAT in the same AZ   |   data → local only
locals { azs = ["ap-south-1a", "ap-south-1b", "ap-south-1c"] }
resource "aws_subnet" "app" {
  count = 3  vpc_id = aws_vpc.main.id  availability_zone = local.azs[count.index]
  cidr_block = cidrsubnet("10.0.0.0/16", 4, count.index + 1)         # /20 slices
}
resource "aws_db_subnet_group" "db" { name = "db"  subnet_ids = aws_subnet.data[*].id }

Security groups chain the tiers: the internet reaches only the load balancer, the load balancer reaches the application, and the application reaches the database. For resilience, route each private subnet to the NAT Gateway in its own AZ, so an AZ failure does not remove outbound access for the others and cross-AZ NAT charges are avoided. For development environments you may use a single NAT to save money.

Benefits and trade-offs

This layout gives security by segmentation and high availability by AZ spread. The trade-offs are more subnets to manage, NAT Gateway costs per AZ, and cross-AZ data charges between tiers. Define the whole layout as infrastructure as code.

5. Subnets and Availability Zones

A subnet is created in one specific Availability Zone and stays there. This is why high availability is something you design: you create matching subnets in several AZs, and services such as Application Load Balancers, Auto Scaling groups and RDS Multi-AZ use subnets in different AZs to spread their resources. These services need subnets in at least two AZs.

AZ names such as ap-south-1a are mapped to physical zones per account. If two accounts must use the same physical zone, compare AZ IDs such as aps1-az1. Traffic between subnets in different AZs is charged per GB and adds a little latency, so for very chatty components prefer the same AZ when resilience allows, and use one NAT Gateway per AZ.

aws ec2 describe-availability-zones --region ap-south-1 --query "AvailabilityZones[].[ZoneName,ZoneId]" --output table
aws elbv2 create-load-balancer --name web --subnets subnet-a subnet-b subnet-c --security-groups sg-123      # spread across AZs

Shared subnets

With AWS Resource Access Manager a central network account can share subnets with other accounts in the organisation. The other accounts launch their resources into the shared subnet, while the owner manages the VPC, route tables and CIDR. This reduces the number of VPCs and NAT Gateways, but participants cannot change the subnet, and cost and responsibility need clear rules.

6. Subnets for Common AWS Services

Different services have different subnet needs, and getting them wrong is a frequent source of incidents.

ServiceSubnet needs
Application Load BalancerSubnets in at least two AZs with free addresses; public for internet-facing, private for internal
NAT GatewayMust be in a public subnet with an Elastic IP; one per AZ
RDS / AuroraA DB subnet group with subnets in at least two AZs, usually isolated; do not make it publicly accessible
Lambda in a VPCPrivate subnets in several AZs plus a security group; needs NAT or endpoints to reach the internet or AWS APIs
ECS / EKSPrivate subnets; with the default VPC CNI each pod uses one VPC IP, so subnets must be large
Interface endpointsOne ENI per chosen subnet, usually one per AZ, with a security group allowing 443
aws rds create-db-subnet-group --db-subnet-group-name prod-db --db-subnet-group-description prod --subnet-ids subnet-data-a subnet-data-b subnet-data-c
aws lambda update-function-configuration --function-name orders --vpc-config SubnetIds=subnet-app-a,subnet-app-b,SecurityGroupIds=sg-123
aws eks create-cluster --name prod --role-arn arn:aws:iam::123:role/eks --resources-vpc-config subnetIds=subnet-app-a,subnet-app-b,subnet-app-c

IP exhaustion on EKS

A cluster using the default VPC CNI gives every pod an IP address from the subnet, so a few hundred pods can exhaust a /24. Avoid it with larger subnets (/19 or /20), a secondary VPC CIDR with custom networking for pods, or prefix delegation that assigns blocks of addresses to nodes.

7. Troubleshooting, Best Practices & Security

When something in a subnet cannot connect, work through a fixed checklist. First security groups on both ends (a timeout usually means a silent drop), then network ACLs (stateless, so check both directions and ephemeral ports), then route tables (correct association, no blackhole routes to deleted gateways), then gateways (IGW attached, NAT in a public subnet with an Elastic IP and the right route), and finally IP addresses and the application (public IP, DNS, and whether the app listens on 0.0.0.0 and not only on localhost). A refused connection means nothing is listening, while a timeout means something dropped the packets.

aws ec2 describe-route-tables --filters Name=association.subnet-id,Values=subnet-123 --query "RouteTables[].Routes"
aws ec2 describe-network-acls --filters Name=association.subnet-id,Values=subnet-123
aws ec2 create-network-insights-path --source i-0aaa --destination i-0bbb --protocol tcp --destination-port 443
aws ec2 create-flow-logs --resource-type Subnet --resource-ids subnet-123 --traffic-type ALL --log-destination-type cloud-watch-logs --log-group-name subnet-flow

Best practices

Keep workloads in private subnets and expose only load balancers. Put databases in isolated subnets. Use two or three AZs and the same layout in each. Size subnets for interfaces, not servers, and leave spare ranges. Keep the main route table private and associate route tables explicitly. Use security groups as the main control and NACLs as an extra layer. Enable Flow Logs on sensitive subnets. Use VPC endpoints to keep AWS traffic private and reduce NAT cost. Tag subnets with their tier (and with Kubernetes tags where needed) and manage everything as code.

8. Interview Q&A: Subnets

Q1. What is a subnet?

Short answer: A range of IP addresses within a VPC, placed in a single Availability Zone.

It lets you segment the network and apply different routing and firewall rules.

Q2. Can a subnet span multiple AZs?

Short answer: No, each subnet exists in exactly one Availability Zone.

Create one per AZ for high availability.

Q3. What is the difference between a public and a private subnet?

Short answer: A public subnet has a route to an Internet Gateway, while a private subnet does not.

Private subnets reach the internet through a NAT Gateway if needed.

Q4. What makes a subnet public?

Short answer: A route table entry 0.0.0.0/0 pointing to an Internet Gateway.

Resources also need public IPs and permissive security rules.

Q5. What is an isolated subnet?

Short answer: A private subnet with no route to the internet, not even through NAT.

It suits databases, with AWS services reached through VPC endpoints.

Q6. How many IP addresses does AWS reserve in a subnet?

Short answer: Five: network, VPC router, DNS, future use and broadcast.

A /24 therefore has 251 usable addresses.

Q7. What are the smallest and largest subnet sizes?

Short answer: /28 (16 addresses) is the smallest, and the largest is the size of the VPC, up to /16.

Subnets must fit inside the VPC CIDR.

Q8. Can you change a subnet's CIDR?

Short answer: No, you must create a new subnet and migrate resources.

You can add secondary CIDR blocks to the VPC for more space.

Q9. What happens when a subnet runs out of IP addresses?

Short answer: New resources cannot launch in it.

Plan sizes, count network interfaces and add subnets from a secondary CIDR if needed.

Q10. How many usable IPs in 10.0.1.0/26?

Short answer: 59, since a /26 has 64 addresses and five are reserved.

Always subtract five.

Q11. Where do you place the NAT Gateway?

Short answer: In a public subnet, with an Elastic IP.

Private subnets route 0.0.0.0/0 to it; use one per AZ.

Q12. Where do you place databases?

Short answer: In private or isolated subnets, in a DB subnet group spanning at least two AZs.

Never make them publicly accessible.

Q13. What is a DB subnet group?

Short answer: A collection of subnets in at least two AZs that RDS can use.

It enables Multi-AZ deployments and failover.

Q14. How do load balancers choose subnets?

Short answer: You select subnets in at least two AZs; internet-facing use public subnets, internal ones use private.

They need free IP addresses for their nodes.

Q15. How does a Lambda function in a VPC reach the internet?

Short answer: Through a NAT Gateway in a public subnet, since the Lambda runs in private subnets; or VPC endpoints for AWS services.

Placing Lambda in a public subnet does not give it internet access.

Q16. Why do EKS clusters exhaust subnet IPs?

Short answer: With the default VPC CNI each pod gets a VPC IP address from the subnet.

Use larger subnets, custom networking with a secondary CIDR or prefix delegation.

Q17. What is the main route table?

Short answer: The route table used by subnets that have no explicit association.

Keep it private so new subnets are not accidentally public.

Q18. How do security groups and NACLs apply to a subnet?

Short answer: Security groups apply to network interfaces, and the NACL applies to the whole subnet.

Traffic must pass both; NACLs are stateless.

Q19. What is cross-AZ traffic and does it cost?

Short answer: Traffic between subnets in different AZs, charged per GB in each direction.

Design to minimise it for chatty services while keeping resilience.

Q20. How do you share subnets between accounts?

Short answer: Use AWS Resource Access Manager from the VPC owner account.

Participants launch resources in the shared subnets but cannot modify them.

Q21. What are AZ IDs and why do they matter?

Short answer: Stable identifiers of physical zones, unlike AZ names which are mapped per account.

Use them to place subnets in the same physical zone across accounts.

Q22. An instance in a public subnet cannot be reached from the internet. What do you check?

Short answer: IGW and route, public IP, security group, NACL both directions, OS firewall and that the app listens on 0.0.0.0.

Use Reachability Analyzer and Flow Logs to locate the block.

Q23. Design the subnets for a three-tier app in three AZs.

Short answer: Nine subnets: public for ALB and NAT, private for apps and isolated for databases per AZ, with NAT per AZ and security-group chaining.

Size the app tier largest and keep spare CIDR space.
