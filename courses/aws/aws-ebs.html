1. What is EBS?

Amazon Elastic Block Store (EBS) provides durable block storage volumes for EC2. A volume behaves like a raw disk that you attach to an instance, format with a file system and mount. Unlike instance store, an EBS volume is network-attached, persistent and independent of the instance: it survives a stop and can be detached and attached elsewhere.

Each volume lives in one Availability Zone and is automatically replicated within that AZ for durability. You choose the volume type, size, IOPS and throughput, and you can resize and retune on the fly with Elastic Volumes. Backups are taken as snapshots.

Features and benefits

EBS gives persistent storage, consistent low latency, encryption with KMS, incremental snapshots, live resizing and a range of SSD and HDD types for different cost and performance needs.

Problems and limits

A volume is tied to one AZ and (except Multi-Attach) one instance, you pay for provisioned size even when empty, performance is capped by both the volume and the instance type, restored volumes lazy-load at first, and volumes cannot be shrunk. Unattached volumes keep costing money.

VOL=$(aws ec2 create-volume --availability-zone us-east-1a --size 100 --volume-type gp3 --iops 4000 --throughput 250 --encrypted --query VolumeId --output text)
aws ec2 attach-volume --volume-id $VOL --instance-id i-123 --device /dev/sdf
sudo mkfs -t xfs /dev/nvme1n1 && sudo mkdir /data && sudo mount /dev/nvme1n1 /data
echo 'UUID=$(blkid -s UUID -o value /dev/nvme1n1) /data xfs defaults,nofail 0 2' | sudo tee -a /etc/fstab

2. Volume Types: Choosing Correctly

SSD volumes suit random IO and boot disks. gp3 is the default: a baseline of 3,000 IOPS and 125 MiB/s that you can raise independently of size, at a lower price than the older gp2, which ties IOPS to size (3 per GB) and uses burst credits. io2 and io2 Block Express offer provisioned IOPS and higher durability for critical databases. HDD volumes suit sequential, throughput-heavy workloads: st1 for frequently accessed big data and sc1 for cold data. HDD types cannot be boot volumes.

resource "aws_ebs_volume" "data" {
  availability_zone = "us-east-1a"
  size              = 200
  type              = "gp3"
  iops              = 6000
  throughput        = 400
  encrypted         = true
  kms_key_id        = aws_kms_key.ebs.arn
}
resource "aws_volume_attachment" "data" { device_name = "/dev/sdf" volume_id = aws_ebs_volume.data.id instance_id = aws_instance.app.id }

Remember the instance ceiling: a fast volume cannot exceed the EBS bandwidth and IOPS limits of the instance it is attached to.

3. Snapshots, Backup and Restore

A snapshot is a point-in-time backup stored in AWS-managed, S3-backed storage. The first is a full copy and later ones are incremental, storing only changed blocks, and you can delete older ones safely because needed blocks are kept. Snapshots can create new volumes (even in another AZ), build AMIs, be copied across Regions and shared with accounts. Automate them with Amazon Data Lifecycle Manager or AWS Backup.

A volume restored from a snapshot is usable at once but loads blocks lazily from S3, so first reads are slower. Fast Snapshot Restore (extra cost) or reading all blocks first removes this. For consistent database backups, quiesce or freeze the file system or use application-aware tooling, because snapshots are crash-consistent by default. Recycle Bin can protect against accidental deletion.

aws ec2 create-snapshot --volume-id vol-123 --description "nightly" --tag-specifications 'ResourceType=snapshot,Tags=[{Key=Backup,Value=daily}]'
aws ec2 copy-snapshot --source-region us-east-1 --source-snapshot-id snap-123 --region eu-west-1 --encrypted --kms-key-id alias/ebs-dr
aws dlm create-lifecycle-policy --execution-role-arn arn:aws:iam::123456789012:role/dlm --description daily --state ENABLED --policy-details file://policy.json
aws ec2 create-volume --snapshot-id snap-123 --availability-zone us-east-1b --volume-type gp3

4. Encryption, Attachment and Elastic Volumes

EBS encrypts data at rest, snapshots and data in transit between instance and volume using AWS KMS keys, with negligible performance impact. Turn on EBS encryption by default in each Region so every new volume is encrypted, and use a customer-managed key when you need control or cross-account sharing. A volume is tied to one AZ; to move it, snapshot and restore elsewhere. Multi-Attach lets io1/io2 volumes attach to several Nitro instances in one AZ for cluster-aware applications. Elastic Volumes let you change size, type, IOPS and throughput live, then extend the file system; there is roughly a six-hour wait between modifications and volumes cannot shrink.

aws ec2 enable-ebs-encryption-by-default --region us-east-1
aws ec2 modify-volume --volume-id vol-123 --size 300 --volume-type gp3 --iops 6000
sudo growpart /dev/nvme0n1 1 && sudo xfs_growfs -d /          # ext4: sudo resize2fs /dev/nvme0n1p1
aws ec2 describe-volumes-modifications --volume-ids vol-123
To encrypt an existing unencrypted volume, snapshot it, copy the snapshot with encryption on, and create a new volume from it.

5. EBS vs Instance Store, EFS, S3 and FSx

Choose by access pattern. EBS is durable block storage for one instance, ideal for boot disks and databases. Instance store is faster local storage that vanishes on stop or failure, ideal for caches and scratch. EFS is a shared, elastic NFS file system across instances and AZs for Linux. S3 is object storage for backups, media and data lakes. FSx provides managed Windows (SMB), Lustre, NetApp ONTAP and OpenZFS file systems.

6. Performance Tuning & Troubleshooting

For slow disks, check in order: has the volume hit its IOPS or throughput limit, has the instance hit its EBS bandwidth cap, is a restored volume still initialising, and what do the CloudWatch metrics show? VolumeQueueLength rising means the volume cannot keep up, and a gp2 burst balance near zero means throttling.

ScenarioAction
Database latency spikesMove to gp3 with more IOPS or io2; check queue length
Restored volume slow at firstFast Snapshot Restore or pre-read blocks
Disk fullElastic Volumes then growpart and resize file system
Cost too highDelete unattached volumes and old snapshots; migrate gp2 to gp3
Need DR copyCopy snapshots cross-Region with DLM
Stripe for more throughputRAID 0 across volumes (no redundancy) or just raise gp3/io2 limits

sudo fio --name=test --filename=/dev/nvme1n1 --rw=randread --bs=4k --iodepth=32 --runtime=30 --time_based
aws cloudwatch get-metric-statistics --namespace AWS/EBS --metric-name VolumeQueueLength --dimensions Name=VolumeId,Value=vol-123 --start-time 2026-01-01T00:00:00Z --end-time 2026-01-01T01:00:00Z --period 60 --statistics Average
aws ec2 describe-volumes --filters Name=status,Values=available --query "Volumes[].[VolumeId,Size]"   # unattached, costing money

7. Interview Q&A: EBS

Q1. What is EBS?

Short answer: Durable, network-attached block storage for EC2 instances.

A volume lives in one AZ.

Q2. EBS versus instance store?

Short answer: EBS persists independently of the instance; instance store is local, faster and ephemeral.

Use instance store for caches.

Q3. Can an EBS volume attach across AZs?

Short answer: No, it is tied to one AZ; use a snapshot to create a volume elsewhere.

Use EFS for multi-AZ shared storage.

Q4. What volume types exist?

Short answer: gp3, gp2, io2, io1 (SSD) and st1, sc1 (HDD).

Only SSD types can be boot volumes.

Q5. gp3 versus gp2?

Short answer: gp3 provides a baseline of 3,000 IOPS and 125 MiB/s with independent provisioning at lower cost; gp2 ties IOPS to size.

Migrate gp2 to gp3.

Q6. When use io2?

Short answer: For critical, latency-sensitive databases needing high provisioned IOPS and durability.

Costs more.

Q7. What is a snapshot?

Short answer: An incremental point-in-time backup of a volume stored durably by AWS.

Deleting older snapshots keeps needed blocks.

Q8. Why are snapshots incremental?

Short answer: Only blocks changed since the last snapshot are stored, saving cost and time.

Each snapshot is still independently restorable.

Q9. How do you move a volume to another AZ?

Short answer: Create a snapshot and create a new volume from it in the target AZ.

Or copy to another Region.

Q10. How do you encrypt an existing volume?

Short answer: Snapshot it, copy the snapshot with encryption enabled, then create a volume from the copy.

Or enable default encryption for new volumes.

Q11. What does EBS encryption cover?

Short answer: Data at rest, snapshots, and data moving between instance and volume.

Uses KMS keys.

Q12. Can you resize a volume live?

Short answer: Yes, with Elastic Volumes you can increase size and change type or performance, then extend the file system.

You cannot shrink.

Q13. What is Multi-Attach?

Short answer: Attaching an io1 or io2 volume to multiple Nitro instances in the same AZ.

The application must handle concurrent writes.

Q14. Why is a restored volume slow initially?

Short answer: Blocks load lazily from S3 on first access.

Use Fast Snapshot Restore or pre-warm.

Q15. What is Fast Snapshot Restore?

Short answer: A feature that fully initialises volumes created from a snapshot in chosen AZs.

It is billed per AZ-hour.

Q16. What happens to EBS on instance termination?

Short answer: Root volumes are deleted by default (DeleteOnTermination) and additional volumes persist by default.

Change the flags as needed.

Q17. How do you automate backups?

Short answer: With Amazon Data Lifecycle Manager or AWS Backup policies targeting tags.

Include retention and cross-Region copy.

Q18. What limits EBS performance besides the volume?

Short answer: The instance type's EBS bandwidth and IOPS caps.

Pick an appropriate instance.

Q19. EBS versus EFS?

Short answer: EBS is block storage for one instance in one AZ; EFS is shared NFS across instances and AZs.

EFS suits shared content.

Q20. How do you reduce EBS cost?

Short answer: Delete unattached volumes and old snapshots, use gp3, right-size, and use lifecycle policies and archive tier for snapshots.

Review regularly.

Q21. How do you get a consistent database snapshot?

Short answer: Quiesce or freeze the file system or use application-aware backups, because default snapshots are crash-consistent.

Test restores.
