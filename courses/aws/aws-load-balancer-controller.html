1. What is the AWS Load Balancer Controller?

The AWS Load Balancer Controller is a Kubernetes controller that provisions AWS Elastic Load Balancers for your cluster. When you create an Ingress, it builds an Application Load Balancer; when you create a Service of type LoadBalancer with the right class, it builds a Network Load Balancer. It also keeps the load balancer's target groups in sync with your pods as they scale and roll.

It runs as a Deployment in your cluster, watches Kubernetes resources, and calls the AWS ELB and EC2 APIs using an IAM role for its service account. In IP target mode the load balancer sends traffic straight to pod IPs, which works because the VPC CNI gives pods VPC addresses. It replaces the older in-tree cloud provider load balancer code.

Features and benefits

It gives you native ALB features (host and path routing, WAF, OIDC auth, redirects), NLB support, direct-to-pod routing for lower latency, IngressGroups that share one ALB across many Ingresses to save cost, TargetGroupBinding for externally managed load balancers, and pod readiness gates for safe rollouts.

Problems and limits

Setup depends on correct IAM permissions and subnet tags, and failures often look like an Ingress with no address. Annotations are numerous and easy to mistype, each Ingress by default makes its own ALB (cost) unless grouped, IP mode needs VPC-routable pod IPs, and rollouts can drop requests without readiness gates and graceful draining. Gateway API support is evolving.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
  namespace: apps
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP":80},{"HTTPS":443}]'
    alb.ingress.kubernetes.io/ssl-redirect: "443"
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:us-east-1:123456789012:certificate/abc
    alb.ingress.kubernetes.io/healthcheck-path: /health
spec:
  ingressClassName: alb
  rules:
    - host: app.example.com
      http:
        paths:
          - { path: /api, pathType: Prefix, backend: { service: { name: api, port: { number: 80 } } } }
          - { path: /,    pathType: Prefix, backend: { service: { name: web, port: { number: 80 } } } }

2. Ingress, Service, IngressGroup and TargetGroupBinding

An Ingress with ingressClassName: alb becomes an ALB: each rule becomes a listener rule, each backend Service a target group. A Service of type LoadBalancer with loadBalancerClass: service.k8s.aws/nlb becomes an NLB. An IngressGroup (annotation group.name) lets many Ingresses, even from different namespaces, share one ALB, with group.order controlling rule priority, which is the main cost-saving feature. A TargetGroupBinding registers a Service's pods into an existing target group, ideal when Terraform owns the load balancer and Kubernetes only manages targets.

apiVersion: v1
kind: Service
metadata:
  name: game
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-nlb-target-type: ip
    service.beta.kubernetes.io/aws-load-balancer-scheme: internet-facing
spec:
  type: LoadBalancer
  loadBalancerClass: service.k8s.aws/nlb
  selector: { app: game }
  ports: [ { name: udp, port: 7777, protocol: UDP, targetPort: 7777 } ]
---
apiVersion: elbv2.k8s.aws/v1beta1
kind: TargetGroupBinding
metadata: { name: api-tgb, namespace: apps }
spec:
  serviceRef: { name: api, port: 80 }
  targetGroupARN: arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/api/abc123
  targetType: ip

3. Annotations: Subnets, TLS, Health Checks, WAF

Behaviour is configured with annotations. Scheme and subnets: choose internet-facing or internal; the controller finds subnets by tag kubernetes.io/role/elb (public) or kubernetes.io/role/internal-elb (private) unless you list them. TLS: set the ACM certificate ARN, an SSL policy and an ssl-redirect from HTTP to HTTPS. Health checks: set path, port, interval and success codes to match your readiness probe. Protection: attach WAFv2 with an ACL ARN, enable Shield, or add OIDC or Cognito authentication.

    alb.ingress.kubernetes.io/success-codes: "200-299"

4. Installing, Safe Rollouts and Troubleshooting

Install in three steps. Create the IAM policy from the project, create an IAM role for the controller's service account (IRSA or Pod Identity), then install the Helm chart with your cluster name. Tag your subnets for discovery. For zero-downtime rollouts, enable pod readiness gates by labelling the namespace, so new pods are not Ready until the load balancer reports them healthy, and add a preStop sleep plus a suitable termination grace period so old pods keep serving until they are deregistered.

curl -o iam_policy.json https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/main/docs/install/iam_policy.json
aws iam create-policy --policy-name AWSLoadBalancerControllerIAMPolicy --policy-document file://iam_policy.json
helm repo add eks https://aws.github.io/eks-charts && helm repo update
helm install aws-load-balancer-controller eks/aws-load-balancer-controller -n kube-system \
  --set clusterName=main --set serviceAccount.create=false --set serviceAccount.name=aws-load-balancer-controller
kubectl label namespace apps elbv2.k8s.aws/pod-readiness-gate-inject=enabled
kubectl -n kube-system logs deploy/aws-load-balancer-controller --tail=50

5. Interview Q&A: AWS Load Balancer Controller

Q1. What is the AWS Load Balancer Controller?

Short answer: A Kubernetes controller that provisions ALBs for Ingress and NLBs for Services and keeps their target groups in sync with pods.

It replaces the in-tree implementation.

Q2. How does it get permission to create load balancers?

Short answer: Through an IAM role for its service account using IRSA or Pod Identity, with the project's IAM policy attached.

Missing permissions are a top failure cause.

Q3. Ingress versus Service for load balancers?

Short answer: An Ingress creates an ALB for HTTP/HTTPS routing; a Service of type LoadBalancer with the NLB class creates an NLB for layer 4.

Choose by protocol.

Q4. What is IP target mode?

Short answer: The load balancer registers pod IPs directly, so traffic goes straight to pods without a node hop.

Requires VPC-routable pod IPs.

Q5. IP versus instance target mode?

Short answer: IP mode targets pods; instance mode targets node ports and relies on kube-proxy to reach pods.

IP mode is preferred.

Q6. How does it choose subnets?

Short answer: By tags kubernetes.io/role/elb for public and kubernetes.io/role/internal-elb for private subnets, or an explicit subnets annotation.

Missing tags break creation.

Q7. How do you enable HTTPS?

Short answer: Add the ACM certificate-arn annotation, listen on 443 and add ssl-redirect for HTTP.

Choose an SSL policy.

Q8. What is an IngressGroup?

Short answer: A set of Ingresses sharing one ALB via the group.name annotation, with group.order setting rule priority.

It saves cost.

Q9. What is TargetGroupBinding?

Short answer: A custom resource that registers a Service's pods into an existing target group.

Useful when Terraform owns the load balancer.

Q10. How do you attach WAF?

Short answer: Use the wafv2-acl-arn annotation on the Ingress.

You can also enable Shield.

Q11. What are pod readiness gates?

Short answer: Conditions that keep a pod not-Ready until the load balancer reports it healthy.

They prevent dropped traffic during rollouts.

Q12. How do you avoid 5XX during deployments?

Short answer: Use readiness gates, a preStop sleep, adequate terminationGracePeriodSeconds and matching deregistration delay.

Test with load.

Q13. Why does an Ingress have no address?

Short answer: The controller cannot create the ALB: usually IAM permissions, subnet tags or invalid annotations.

Check Ingress events and controller logs.

Q14. How do you configure health checks?

Short answer: With healthcheck annotations for path, port, interval and success codes, aligned with the readiness probe.

Open the security group to the ALB.

Q15. How do you make an internal load balancer?

Short answer: Set scheme to internal and tag private subnets with kubernetes.io/role/internal-elb.

Used for east-west or private traffic.

Q16. How do you get a static IP with an NLB?

Short answer: Use an NLB Service with Elastic IP allocation annotations or put Global Accelerator in front.

ALB IPs are not static.

Q17. How do you install the controller?

Short answer: Create the IAM policy and service account role, install the eks/aws-load-balancer-controller Helm chart with the cluster name, and tag subnets.

Use a recent chart version.

Q18. Can it work with Fargate pods?

Short answer: Yes, but only in IP target mode because Fargate has no node ports to target.

Pods need VPC IPs.

Q19. How do you reduce load balancer cost?

Short answer: Share ALBs with IngressGroups and delete unused Ingresses.

Each ALB has an hourly charge.

Q20. What does the controller tag on resources?

Short answer: It tags load balancers and target groups it owns with cluster and ingress identifiers.

Do not edit them by hand.
