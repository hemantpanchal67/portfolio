1. What is a Security Group?

A security group is a virtual, stateful firewall attached to a network interface (ENI). It controls which traffic may reach a resource, such as an EC2 instance, load balancer, RDS database or Lambda in a VPC, and which traffic it may send. Security groups are the first and most important layer of network security in AWS, and almost every architecture uses them.

Three properties define them. They are allow-only: you list what is permitted and everything else is denied, with no deny rules. They are stateful: when a request is allowed in, the reply is automatically allowed out, and vice versa. And they work at the resource level, so two instances in the same subnet can have completely different rules.

Features and benefits

Rules can reference other security groups, so you describe relationships ("the app may talk to the database") instead of IP addresses. Changes take effect immediately, multiple groups can be attached to one interface, and the service is free.

Problems and limits

You cannot write deny rules, so blocking one bad IP needs a NACL or firewall. Rules are limited in number, groups belong to a single VPC, and overly broad rules such as 0.0.0.0/0 on SSH or databases are one of the most common causes of AWS breaches. Because they are allow-only and cumulative, a permissive group attached by accident silently opens access.

SG=$(aws ec2 create-security-group --group-name web --description "web tier" --vpc-id vpc-123 --query GroupId --output text)
aws ec2 authorize-security-group-ingress --group-id $SG --protocol tcp --port 443 --cidr 0.0.0.0/0
aws ec2 describe-security-groups --group-ids $SG
aws ec2 revoke-security-group-ingress --group-id $SG --protocol tcp --port 443 --cidr 0.0.0.0/0

2. Rules and Sources: CIDR, Security Groups, Prefix Lists

Each rule has a protocol, a port range and a source (inbound) or destination (outbound). The source can be a CIDR block, a security group, or a prefix list. Use CIDRs for the internet or fixed external addresses. Inside your VPC, prefer security-group references, because membership follows the instances automatically as they scale or change IP. A group may also reference itself so cluster members can talk to each other.

resource "aws_security_group" "db" {
  name   = "db"
  vpc_id = aws_vpc.main.id
  ingress { from_port = 5432 to_port = 5432 protocol = "tcp" security_groups = [aws_security_group.app.id] }
  egress  { from_port = 0 to_port = 0 protocol = "-1" cidr_blocks = ["0.0.0.0/0"] }
}
{ "IpPermissions": [ { "IpProtocol": "tcp", "FromPort": 443, "ToPort": 443,
    "IpRanges": [ { "CidrIp": "203.0.113.0/24", "Description": "Office" } ],
    "UserIdGroupPairs": [ { "GroupId": "sg-0abc" } ] } ] }
Always add a description to every rule. Months later, "Office VPN" explains itself while an unlabelled 203.0.113.0/24 does not.

Prefix lists let you name a set of CIDRs and reuse it, and AWS publishes managed lists such as those for S3 or CloudFront. A rule matching a group source only matches traffic that arrives from a member's private IP, so it works for in-VPC traffic and peering but not for traffic that crossed a NAT or came via a public address.

3. Designing Tiers and Least Privilege

A well-designed set of groups mirrors the architecture. The load balancer group allows 443 from the internet. The app group allows the application port only from the load balancer group. The database group allows the database port only from the app group. Because each rule names a group instead of an IP range, the design survives auto scaling and redeployments, and the internet can never reach the app or database directly.

resource "aws_security_group" "alb" { name = "alb" vpc_id = aws_vpc.main.id
  ingress { from_port = 443 to_port = 443 protocol = "tcp" cidr_blocks = ["0.0.0.0/0"] } }
resource "aws_security_group" "app" { name = "app" vpc_id = aws_vpc.main.id
  ingress { from_port = 8080 to_port = 8080 protocol = "tcp" security_groups = [aws_security_group.alb.id] } }
resource "aws_security_group" "db"  { name = "db"  vpc_id = aws_vpc.main.id
  ingress { from_port = 5432 to_port = 5432 protocol = "tcp" security_groups = [aws_security_group.app.id] } }

Least-privilege habits

Open only the ports needed, avoid 0.0.0.0/0 except on public load balancers, restrict outbound on sensitive tiers, remove all rules from the default group, and manage groups with infrastructure as code and code review. For administration, use Systems Manager Session Manager or EC2 Instance Connect Endpoint instead of opening SSH or RDP, and use AWS Config rules or Security Hub to alert on 0.0.0.0/0 on sensitive ports.

aws ec2 describe-security-groups --filters Name=ip-permission.from-port,Values=22 Name=ip-permission.cidr,Values=0.0.0.0/0 --query "SecurityGroups[].GroupId"
aws configservice put-config-rule --config-rule file://restricted-ssh.json

4. Limits, Default Group & Scope

Security groups have quotas: by default 60 inbound and 60 outbound rules per group, and 5 groups per network interface (both adjustable within limits), so consolidate with prefix lists and group references. A group belongs to one VPC and cannot be reused elsewhere; use infrastructure as code to create equivalents. Every VPC has a default security group that allows traffic between its members and all outbound, and it cannot be deleted, so strip its rules and use named groups instead. Finally, groups apply to network interfaces, not subnets, which is the key difference from network ACLs. Check current quota values in the AWS documentation.

5. Troubleshooting & Scenarios

A timeout almost always means something dropped the packet silently, usually a missing security group rule, a NACL or a route. A connection refused means the packet reached the host but nothing was listening. Check the inbound rule (port, protocol, source), then the NACL and routes on the whole path, then the app and OS firewall, and finally whether a group-reference source really matches the private IP of the client.

6. Interview Q&A: Security Groups

Q1. What is a security group?

Short answer: A stateful, allow-only virtual firewall attached to network interfaces that controls inbound and outbound traffic.

It is the first layer of VPC security.

Q2. What does stateful mean?

Short answer: Return traffic for an allowed connection is permitted automatically.

You do not need return rules, unlike NACLs.

Q3. Can you create deny rules?

Short answer: No, security groups only allow; everything not allowed is denied.

Use NACLs or firewalls for explicit denies.

Q4. What are the default rules of a new group?

Short answer: No inbound traffic is allowed and all outbound traffic is allowed.

Add explicit rules.

Q5. Security group versus NACL?

Short answer: Security groups are stateful, allow-only and apply to interfaces; NACLs are stateless, support deny and apply to subnets.

Use both for defence in depth.

Q6. How are multiple rules evaluated?

Short answer: All rules are evaluated together and traffic is allowed if any rule matches.

There is no ordering.

Q7. What can be a rule source?

Short answer: A CIDR block, another security group, or a prefix list.

A group can also reference itself.

Q8. Why reference a security group instead of a CIDR?

Short answer: Membership updates automatically as instances scale, so no IP lists to maintain.

It expresses relationships between tiers.

Q9. How do you secure a three-tier app?

Short answer: Load balancer allows 443 from the internet, app allows its port from the load balancer group, database allows its port from the app group.

Servers stay private.

Q10. How many security groups can an interface have?

Short answer: Five by default, adjustable, and rules from all of them combine.

Check quotas.

Q11. Do security groups apply to subnets?

Short answer: No, they apply to network interfaces.

Different instances in a subnet can have different groups.

Q12. What is the default security group?

Short answer: A built-in group in each VPC that allows traffic between its members and all outbound.

Remove its rules and avoid using it.

Q13. Can a security group span VPCs?

Short answer: No, it belongs to a single VPC, though peered VPCs in a Region can reference each other's groups.

Create per VPC with IaC.

Q14. How do you avoid opening SSH?

Short answer: Use Systems Manager Session Manager or EC2 Instance Connect Endpoint.

If SSH is needed, limit to a /32.

Q15. Why restrict outbound rules?

Short answer: To limit data exfiltration and lateral movement from compromised hosts.

Allow only required destinations.

Q16. A rule is removed but a connection continues. Why?

Short answer: Because connection tracking keeps existing flows, and some flows are untracked in certain cases.

New connections follow the new rules.

Q17. What is connection tracking?

Short answer: The mechanism by which the group remembers allowed flows to permit replies.

Can be affected by rules allowing all traffic, which make flows untracked.

Q18. How do you find overly open groups?

Short answer: Use AWS Config managed rules, Security Hub or describe-security-groups filters for 0.0.0.0/0 on sensitive ports.

Automate remediation.

Q19. How do you troubleshoot a timeout?

Short answer: Check security group rules, NACLs, routes and then the app, using Reachability Analyzer and flow logs.

Timeouts mean silent drops.

Q20. What is a prefix list?

Short answer: A named, reusable set of CIDRs used in security groups and route tables.

Update once and it applies everywhere.
