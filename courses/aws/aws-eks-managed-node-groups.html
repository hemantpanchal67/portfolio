1. What are EKS Managed Node Groups?

An EKS managed node group automates the provisioning and lifecycle of the EC2 worker nodes in your cluster. Behind the scenes EKS creates an Auto Scaling group in your account, launches nodes from an EKS-optimised AMI (Amazon Linux, Bottlerocket or Windows), registers them with the cluster, and handles graceful rolling updates and terminations. You choose instance types, capacity type and size limits; EKS does the rest.

Compared with self-managed nodes, where you build the Auto Scaling group, bootstrap script and update process yourself, managed node groups remove most of that toil. Compared with Fargate, you still own EC2 instances, so you keep control of instance types, GPUs, DaemonSets and host-level tooling.

Features and benefits

You get one-command node creation, automatic cordon and drain during updates, Spot and On-Demand capacity types, ARM and GPU support, labels and taints, launch template customisation, health reporting, and no extra charge beyond the EC2 and EBS resources.

Problems and limits

You are still responsible for node patching cadence (updating to new AMIs), choosing instance sizes that bin-pack well, handling IP exhaustion, and keeping node groups in version skew with the control plane. Each node group is one architecture and AMI type, a single multi-AZ group cannot always place nodes where an EBS volume lives, and strict PodDisruptionBudgets can stall updates. For fully hands-off nodes, consider EKS Auto Mode or Fargate.

aws eks create-nodegroup --cluster-name main --nodegroup-name general --subnets subnet-a subnet-b subnet-c \
  --node-role arn:aws:iam::123456789012:role/eksNodeRole --scaling-config minSize=2,maxSize=10,desiredSize=3 \
  --instance-types m6i.large m6a.large m5.large --capacity-type ON_DEMAND --ami-type AL2023_x86_64_STANDARD \
  --labels workload=general --update-config maxUnavailablePercentage=33
aws eks describe-nodegroup --cluster-name main --nodegroup-name general --query "nodegroup.[status,health.issues]"
kubectl get nodes -L eks.amazonaws.com/nodegroup,eks.amazonaws.com/capacityType

2. Capacity: On-Demand, Spot, Graviton, GPU and Launch Templates

A node group has one capacity type: ON_DEMAND for stable baselines or SPOT for savings. For Spot, list several instance types of similar size so EKS can find capacity, and run interruption-tolerant pods there; EKS handles draining on interruption notices. A group uses one AMI type, so create separate groups for Graviton (ARM) and x86, and a tainted GPU group for ML pods. A launch template lets you set a custom AMI, user data, volumes, tags, security groups and require IMDSv2 with a hop limit suited to containers.

resource "aws_eks_node_group" "spot" {
  cluster_name = aws_eks_cluster.main.name  node_group_name = "spot-arm"  node_role_arn = aws_iam_role.node.arn
  subnet_ids = aws_subnet.private[*].id
  capacity_type = "SPOT"  ami_type = "AL2023_ARM_64_STANDARD"
  instance_types = ["m7g.large", "m6g.large", "c7g.large", "r7g.large"]
  scaling_config { min_size = 0  max_size = 20  desired_size = 2 }
  update_config  { max_unavailable_percentage = 33 }
  labels = { lifecycle = "spot", arch = "arm64" }
  taint  { key = "lifecycle"  value = "spot"  effect = "NO_SCHEDULE" }
  launch_template { id = aws_launch_template.nodes.id  version = aws_launch_template.nodes.latest_version }
}
resource "aws_launch_template" "nodes" {
  name_prefix = "eks-nodes-"
  metadata_options { http_tokens = "required"  http_put_response_hop_limit = 2 }
  block_device_mappings { device_name = "/dev/xvda"  ebs { volume_size = 50  volume_type = "gp3"  encrypted = true } }
}
spec:
  tolerations: [ { key: lifecycle, operator: Equal, value: spot, effect: NoSchedule } ]
  nodeSelector: { kubernetes.io/arch: arm64 }

3. Updates, Draining and Patching

Updating a node group, whether to a new AMI release, a new launch template version or a new Kubernetes version, is a rolling replacement: EKS launches new nodes, cordons and drains old ones while respecting PodDisruptionBudgets, then terminates them. The maxUnavailable setting (count or percent) controls how fast. Upgrade the control plane first, then the node groups, keeping within the supported version skew. Patch regularly by moving to the latest AMI release, ideally automated and tested in lower environments; never patch nodes in place.

aws eks update-nodegroup-version --cluster-name main --nodegroup-name general --release-version 1.31.2-20250101
aws eks update-nodegroup-config --cluster-name main --nodegroup-name general --update-config maxUnavailablePercentage=25
aws eks describe-update --name main --nodegroup-name general --update-id $UPDATE_ID
kubectl get pdb -A
kubectl drain ip-10-0-1-23.ec2.internal --ignore-daemonsets --delete-emptydir-data
A PodDisruptionBudget with minAvailable equal to the replica count, or a single-replica Deployment with a PDB, can never be drained. Keep at least one allowed disruption.

4. Scaling, Placement and Troubleshooting

The Cluster Autoscaler resizes existing node groups when pods are pending, within min and max, discovering groups by tags. Karpenter instead provisions right-sized nodes directly and consolidates them, usually faster and cheaper; it typically runs on a small managed node group so it can start before it creates its own capacity. Use labels, taints and tolerations to dedicate groups to system, Spot or GPU workloads. For stateful pods using EBS, which are tied to an AZ, a node group per AZ lets the autoscaler add a node in the right zone.

Troubleshooting

Start with the node group health issues, then the node role mapping or access entry, routes to the API endpoint and ECR, security groups, quotas and subnet IPs.

5. Interview Q&A: Managed Node Groups

Q1. What is an EKS managed node group?

Short answer: An EKS-managed Auto Scaling group of EC2 worker nodes whose provisioning, registration and updates EKS automates.

Nodes run in your account.

Q2. Managed versus self-managed nodes?

Short answer: Managed groups automate AMIs, joining, draining and updates; self-managed nodes give full control but you build and operate everything.

Prefer managed unless you need custom control.

Q3. Managed node groups versus Fargate?

Short answer: Managed groups give EC2 control (instance types, GPUs, DaemonSets); Fargate removes nodes entirely but with restrictions.

Many clusters use both.

Q4. What does a node group cost?

Short answer: Nothing beyond the EC2 instances, EBS volumes and related resources.

The cluster itself has an hourly fee.

Q5. Which AMIs are supported?

Short answer: EKS-optimised Amazon Linux, Bottlerocket and Windows AMIs, or custom ones via launch templates.

One AMI type per group.

Q6. What IAM permissions does the node role need?

Short answer: AmazonEKSWorkerNodePolicy, AmazonEC2ContainerRegistryReadOnly and CNI permissions (preferably via IRSA/Pod Identity).

Pods should use their own roles.

Q7. On-Demand versus Spot node groups?

Short answer: On-Demand is stable; Spot is cheaper but interruptible, so use several instance types and tolerant workloads.

Separate groups for each.

Q8. Can one node group mix architectures?

Short answer: No, each group has one AMI type and architecture; use separate groups for ARM and x86.

Use node selectors.

Q9. How do node group updates work?

Short answer: Rolling: new nodes launch, old ones are cordoned and drained respecting PDBs, then terminated, within maxUnavailable.

Control plane is upgraded first.

Q10. Why would an update hang?

Short answer: A PodDisruptionBudget or non-evictable pod blocks draining, causing PodEvictionFailure.

Relax the PDB or add replicas.

Q11. How do you keep nodes patched?

Short answer: Regularly roll to the latest AMI release version, automated and tested in lower environments.

Never patch in place.

Q12. What is version skew?

Short answer: The allowed difference between control plane and node versions; upgrade nodes soon after the control plane.

Check the current policy.

Q13. Cluster Autoscaler versus Karpenter?

Short answer: Cluster Autoscaler resizes defined node groups; Karpenter provisions right-sized nodes directly and consolidates.

Karpenter runs on a small managed group.

Q14. How do you dedicate nodes to workloads?

Short answer: Labels and taints on the node group with nodeSelector and tolerations in pods.

Typical for GPU and Spot.

Q15. Why a node group per AZ?

Short answer: So the autoscaler can add capacity in the AZ where a pod's EBS volume exists.

Karpenter handles this automatically.

Q16. What does maxUnavailable do?

Short answer: It sets how many nodes can be updated at once, as a count or percentage.

Balance speed against capacity.

Q17. A node group will not create. What do you check?

Short answer: Node health issues, node role and access entry, routes to the API endpoint and ECR, subnets, security groups and quotas.

Read describe-nodegroup.

Q18. Why are pods stuck in ContainerCreating?

Short answer: The VPC CNI may be out of IPs because of subnet or ENI limits.

Use prefix delegation or larger subnets.

Q19. How do you secure nodes?

Short answer: Require IMDSv2, minimal node role, private subnets, encrypted volumes, patched AMIs and restricted SSH (use SSM).

Use Bottlerocket for a smaller surface.

Q20. When would you pick EKS Auto Mode instead?

Short answer: When you want AWS to manage node provisioning, scaling and patching with less configuration.

Check features and cost.
