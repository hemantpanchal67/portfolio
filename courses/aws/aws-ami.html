1. What is an AMI?

An Amazon Machine Image (AMI) is the template used to launch EC2 instances. It packages the operating system, installed software and configuration, plus launch permissions and a block device mapping that describes which volumes to attach. Every instance starts from an AMI, and you can build your own so that new servers are identical and ready in minutes.

Most AMIs are EBS-backed: the root volume is stored as an EBS snapshot, so instances can stop and start and keep their disks. Older instance-store-backed AMIs load from S3 and lose data on stop, and are rarely used now. An AMI is Regional: it has a distinct ID in each Region and must be copied to use elsewhere.

Features and benefits

AMIs provide repeatability (every instance identical), speed (software pre-installed), scaling (Auto Scaling launches from them), portability across accounts and Regions by copy and share, and a base for immutable infrastructure and disaster recovery.

Problems and limits

AMIs age: unpatched images spread vulnerabilities, sprawl costs money because each stores snapshots, secrets baked in leak when shared, ID differences per Region break hard-coded scripts, architecture must match the instance type, and encrypted AMIs complicate sharing because of key policies.

aws ec2 describe-images --owners self --query "Images[].[ImageId,Name,CreationDate]" --output table
aws ssm get-parameter --name /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 --query Parameter.Value --output text
aws ec2 run-instances --image-id resolve:ssm:/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 --instance-type t3.micro

2. Creating AMIs: Manual, Pipelines, Snapshots and Import

The simplest way is create-image from a configured instance, which snapshots its volumes (and reboots the instance by default for consistency). For repeatable builds, use EC2 Image Builder or HashiCorp Packer: they start from a base, apply components such as patches, agents and hardening, test the result and distribute it to Regions and accounts on a schedule. You can also register an AMI from a snapshot, and import on-premises VM images with VM Import/Export or AWS Application Migration Service.

aws ec2 create-image --instance-id i-123 --name "web-2026-05-01" --description "web golden" --no-reboot
aws ec2 register-image --name from-snap --architecture x86_64 --root-device-name /dev/xvda --virtualization-type hvm --ena-support \
  --block-device-mappings DeviceName=/dev/xvda,Ebs={SnapshotId=snap-123,VolumeType=gp3}
aws ec2 deregister-image --image-id ami-123 && aws ec2 delete-snapshot --snapshot-id snap-123
source "amazon-ebs" "web" {
  region = "us-east-1"  instance_type = "t3.small"  ssh_username = "ec2-user"
  ami_name = "web-{{timestamp}}"
  source_ami_filter { filters = { name = "al2023-ami-*-x86_64" } owners = ["amazon"] most_recent = true }
}
build { sources = ["source.amazon-ebs.web"]  provisioner "shell" { script = "harden.sh" } }
Deregistering an AMI does not delete its snapshots; delete them too or you keep paying.

3. Golden AMIs, Hardening and Lifecycle

A golden AMI is a standard, hardened, tested base image that teams launch from, rebuilt on a schedule so patches flow out. Never hard-code AMI IDs; use SSM Parameter Store (public parameters for the latest Amazon Linux, your own for golden images) so launches resolve the current ID at run time. Tag AMIs with version, owner and build, set deprecation dates and automate cleanup. Never bake secrets, keys or credentials into an image; clear logs and shell history, scan with Amazon Inspector, and supply configuration at launch through IAM roles, Secrets Manager and user data.

aws ssm put-parameter --name /golden/web/latest --type String --value ami-0abc123 --overwrite
aws ec2 enable-image-deprecation --image-id ami-0abc123 --deprecate-at 2026-12-31T00:00:00Z
aws ec2 create-tags --resources ami-0abc123 --tags Key=Version,Value=2026.05 Key=Owner,Value=platform

4. Copying, Sharing and Encryption

An AMI is Regional, so copy it to each Region where you need it; each copy gets a new AMI ID. You can share an AMI privately by adding account IDs or an AWS Organization to its launch permissions, or make it public (rarely wise). If its snapshots are encrypted, the key matters: the AWS-managed EBS key cannot be shared, so use a customer-managed KMS key whose key policy allows the target account, and the recipient usually copies the AMI into their account to own it. You can encrypt an unencrypted AMI by copying it with encryption on. Be careful with marketplace and community AMIs: verify the publisher and scan them before use.

aws ec2 copy-image --source-image-id ami-123 --source-region us-east-1 --region eu-west-1 --name web-eu --encrypted --kms-key-id alias/ami-eu
aws ec2 modify-image-attribute --image-id ami-123 --launch-permission "Add=[{UserId=111122223333}]"
aws ec2 modify-image-attribute --image-id ami-123 --launch-permission "Add=[{OrganizationArn=arn:aws:organizations::123456789012:organization/o-abc}]"

5. Deploying with AMIs: Launch Templates, Refresh and DR

In production, AMIs drive immutable deployments: build a new AMI, create a new launch template version that points to it, and run an instance refresh on the Auto Scaling group, which replaces instances in rolling batches while keeping a minimum healthy percentage. Decide what to bake into the image (slow, stable dependencies) versus what to pass through user data (per-environment settings): baking gives faster scale-out and less drift. For disaster recovery, copy AMIs to a second Region and keep launch templates ready there.

aws ec2 create-launch-template-version --launch-template-id lt-123 --source-version 1 --launch-template-data '{"ImageId":"ami-0new"}'
aws autoscaling update-auto-scaling-group --auto-scaling-group-name web --launch-template LaunchTemplateId=lt-123,Version='$Latest'
aws autoscaling start-instance-refresh --auto-scaling-group-name web --preferences '{"MinHealthyPercentage":90,"InstanceWarmup":120}'

6. Interview Q&A: AMI

Q1. What is an AMI?

Short answer: A template that contains the OS, software and configuration needed to launch EC2 instances.

It includes a root snapshot, launch permissions and a block device mapping.

Q2. Is an AMI Regional or global?

Short answer: Regional; to use it elsewhere you copy it, producing a new AMI ID.

Automate with Image Builder.

Q3. EBS-backed versus instance-store-backed AMI?

Short answer: EBS-backed AMIs use snapshots, can stop and start and persist; instance-store-backed AMIs load from S3 and lose data on stop.

EBS-backed is standard.

Q4. How do you create an AMI?

Short answer: From an instance with create-image, with an automated pipeline such as EC2 Image Builder or Packer, from a snapshot, or by importing a VM.

Pipelines are best.

Q5. What is a golden AMI?

Short answer: A hardened, tested and patched standard image rebuilt regularly and used as the base for launches.

It supports immutable infrastructure.

Q6. What does create-image do to the instance?

Short answer: It snapshots the volumes and by default reboots the instance for file system consistency.

no-reboot skips it at a consistency risk.

Q7. How do you share an AMI?

Short answer: Add account IDs or an Organization to its launch permissions, and share the KMS key if the snapshots are encrypted.

Recipients can copy it.

Q8. Can an AMI encrypted with the default key be shared?

Short answer: No, the AWS-managed EBS key cannot be shared; copy it using a customer-managed key.

Update the key policy.

Q9. How do you encrypt an unencrypted AMI?

Short answer: Copy it with encryption enabled to create a new encrypted AMI.

Update launch templates to use the new ID.

Q10. Why not hard-code AMI IDs?

Short answer: IDs differ per Region and change with each build; use SSM parameters or resolve:ssm references instead.

It keeps templates current.

Q11. What happens to snapshots when you deregister an AMI?

Short answer: They remain and keep costing money until deleted.

Delete them explicitly.

Q12. What must never be baked into an AMI?

Short answer: Secrets, private keys, credentials and personal data.

Inject at launch via roles and Secrets Manager.

Q13. How do you roll out a new AMI to an ASG?

Short answer: Create a new launch template version and start an instance refresh.

Set min healthy percentage.

Q14. Bake an AMI or use user data?

Short answer: Bake slow, stable dependencies for fast boots and less drift; use user data for per-environment configuration.

Combine both.

Q15. What is EC2 Image Builder?

Short answer: A managed service to build, test, patch and distribute AMIs and container images through pipelines.

It is an alternative to Packer.

Q16. Why might an AMI not launch on an instance type?

Short answer: Architecture mismatch (arm64 versus x86_64), unsupported virtualisation or boot mode, or missing ENA support.

Build per architecture.

Q17. How do AMIs help disaster recovery?

Short answer: Copies in a second Region plus launch templates allow quick replacement of servers.

Pair with replicated data.

Q18. What is AMI deprecation?

Short answer: A way to mark an AMI as obsolete at a date so it stops appearing in default searches.

Helps manage sprawl.

Q19. Are public community AMIs safe?

Short answer: Not necessarily; they may contain malware or misconfigurations, so prefer verified publishers and scan them.

Prefer your own builds.

Q20. How do you find the latest Amazon Linux AMI?

Short answer: Read the public SSM parameter for it or use resolve:ssm in the launch request.

No manual lookup needed.
