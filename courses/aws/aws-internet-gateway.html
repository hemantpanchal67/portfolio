1. What is an Internet Gateway?

An Internet Gateway (IGW) is a managed AWS component that connects a VPC to the internet. It is horizontally scaled, redundant and highly available by design, so you never size it, patch it or worry about its bandwidth, and there is no charge for the gateway itself. It does two jobs: it provides a target in route tables for internet-bound traffic, and it performs network address translation (NAT) for resources that have public IPv4 addresses.

Without an Internet Gateway, a VPC is private: nothing inside can talk to the public internet and nothing outside can reach it. Attaching an IGW is the first step to creating public subnets. Each VPC can have one IGW, and each IGW attaches to one VPC.

Features and benefits

The IGW needs no management, scales automatically, supports IPv4 and IPv6, costs nothing itself and works with every AWS compute service that has a public address. It is the simplest way to expose a service to the internet.

Problems and limits

The IGW does no filtering, so security comes only from security groups, network ACLs, WAF and Shield. It cannot give private instances outbound access (use a NAT Gateway), it only translates addresses that exist, and public IPv4 addresses cost money. Careless route tables or broad security groups make resources exposed by accident. Finally, because an IGW belongs to one VPC, large designs with many VPCs need one each.

IGW=$(aws ec2 create-internet-gateway --query InternetGateway.InternetGatewayId --output text)
aws ec2 attach-internet-gateway --internet-gateway-id $IGW --vpc-id vpc-123
aws ec2 create-route --route-table-id rtb-public --destination-cidr-block 0.0.0.0/0 --gateway-id $IGW
aws ec2 create-route --route-table-id rtb-public --destination-ipv6-cidr-block ::/0 --gateway-id $IGW
aws ec2 describe-internet-gateways --filters Name=attachment.vpc-id,Values=vpc-123

2. Making a Subnet Public: The Four Requirements

For a resource to reach the internet through an IGW, four things must all be true. First, the IGW must be attached to the VPC. Second, the subnet route table must have a route for 0.0.0.0/0 (and ::/0 for IPv6) to the IGW. Third, the resource must have a public address: an auto-assigned public IPv4, an Elastic IP, or an IPv6 address. Fourth, security groups and network ACLs must allow the traffic.

resource "aws_internet_gateway" "igw" { vpc_id = aws_vpc.main.id }
resource "aws_route_table" "public"  { vpc_id = aws_vpc.main.id  route { cidr_block = "0.0.0.0/0" gateway_id = aws_internet_gateway.igw.id } }
resource "aws_subnet" "public_a" { vpc_id = aws_vpc.main.id  cidr_block = "10.0.1.0/24"  map_public_ip_on_launch = true }
resource "aws_route_table_association" "a" { subnet_id = aws_subnet.public_a.id  route_table_id = aws_route_table.public.id }
resource "aws_security_group" "web" { vpc_id = aws_vpc.main.id
  ingress { from_port = 443 to_port = 443 protocol = "tcp" cidr_blocks = ["0.0.0.0/0"] } }

Elastic IPs and public IPv4

An auto-assigned public IPv4 is released when the instance stops, while an Elastic IP is a static address you keep until you release it. AWS charges for every public IPv4 address, so avoid them where a load balancer or IPv6 will do. Remember that the OS inside the instance only sees its private IP, and learns its public IP from the instance metadata service.

TOKEN=$(curl -sX PUT http://169.254.169.254/latest/api/token -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
curl -sH "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/public-ipv4
aws ec2 allocate-address --domain vpc && aws ec2 associate-address --instance-id i-123 --allocation-id eipalloc-123
Detaching an IGW fails while any resource in the VPC still uses a public IP mapped through it. Release or disassociate those addresses first.

3. IPv4, IPv6, Egress-only Gateway & Cost

For IPv4 the IGW performs static one-to-one NAT: inbound it swaps the public address for the private one, and outbound the reverse. For IPv6 there is no translation, because every IPv6 address is globally unique and routable, so the IGW simply routes it. That also means an IPv6 instance in a public subnet is reachable from the internet if security groups allow it. To give private IPv6 resources outbound-only access, use an egress-only Internet Gateway, which is stateful and blocks connections started from the internet.

aws ec2 create-egress-only-internet-gateway --vpc-id vpc-123
aws ec2 create-route --route-table-id rtb-private --destination-ipv6-cidr-block ::/0 --egress-only-internet-gateway-id eigw-123
aws ec2 associate-vpc-cidr-block --vpc-id vpc-123 --amazon-provided-ipv6-cidr-block

The IGW has no hourly fee, and inbound data is free, but outbound data transfer and public IPv4 addresses are charged. Moving workloads to IPv6 and putting CloudFront in front of content reduces both.

4. IGW vs NAT Gateway vs Egress-only vs VPC Endpoints

These four components are often confused. An Internet Gateway gives two-way access to resources that have public addresses. A NAT Gateway gives outbound-only access to private IPv4 resources and sits in a public subnet that routes to the IGW. An egress-only Internet Gateway does the same for IPv6. VPC endpoints give private access to AWS services without using the internet at all.

ComponentDirectionTypical useCost
Internet GatewayInbound and outboundPublic subnets, load balancersFree
NAT GatewayOutbound only (IPv4)Updates and APIs from private subnetsHourly + per GB
Egress-only IGWOutbound only (IPv6)Private IPv6 workloadsFree
Gateway endpointPrivate to S3 and DynamoDBAvoid NAT for AWS trafficFree
Interface endpointPrivate to many AWS servicesSecrets Manager, ECR, SSMHourly + per GB

A useful rule: choose the narrowest path that works. If the destination is an AWS service, use an endpoint; if a private resource needs the public internet outbound, use NAT; only resources that must be reachable from the internet get public addresses behind an IGW.

5. Securing Internet Access & Troubleshooting

Because the IGW filters nothing, security is built around it. Expose only load balancers in public subnets and keep servers private. Use Systems Manager Session Manager instead of public SSH. Attach AWS WAF and Shield to the load balancer or CloudFront. Keep security groups narrow, and use VPC Block Public Access, a newer guardrail that can block internet traffic through IGWs for chosen VPCs or subnets, to prevent accidents (check the documentation for current options).

6. Interview Q&A: Internet Gateway

Q1. What is an Internet Gateway?

Short answer: A managed, highly available VPC component that connects the VPC to the internet and provides a route target and NAT for public IPv4 addresses.

It has no charge and no bandwidth limit.

Q2. Is the IGW a single point of failure?

Short answer: No, it is redundant and horizontally scaled by AWS across the Region.

You do not manage its availability.

Q3. How many IGWs can a VPC have?

Short answer: One, and an IGW attaches to one VPC only.

Create separate gateways for separate VPCs.

Q4. What is needed for an instance to be reachable from the internet?

Short answer: An attached IGW, a route to it, a public address, and security group and NACL rules that allow the traffic.

Also the application must listen on the right address.

Q5. What NAT does the IGW perform?

Short answer: Static one-to-one NAT between an instance's private IPv4 and its public IPv4 or Elastic IP.

For IPv6 no translation occurs.

Q6. How does an instance know its public IP?

Short answer: Through the instance metadata service, since the OS only sees the private address.

Query 169.254.169.254 with IMDSv2.

Q7. Elastic IP versus auto-assigned public IP?

Short answer: An auto-assigned address is released when the instance stops, while an Elastic IP is static and stays until released.

Both incur charges as public IPv4 addresses.

Q8. IGW versus NAT Gateway?

Short answer: An IGW is two-way for public addresses, while a NAT Gateway is outbound-only for private IPv4 resources.

A NAT Gateway itself sits in a public subnet routed to the IGW.

Q9. Does the IGW filter traffic?

Short answer: No, filtering is done by security groups, NACLs, WAF and Shield.

The IGW only routes and translates.

Q10. What is an egress-only Internet Gateway?

Short answer: A stateful gateway for outbound-only IPv6 traffic that blocks connections started from the internet.

It is the IPv6 counterpart of NAT.

Q11. Why is a subnet with an IGW route but instances without public IPs not working?

Short answer: The IGW translates only public addresses, so instances need a public IPv4, Elastic IP or IPv6 address.

Otherwise use NAT for outbound.

Q12. What does the IGW cost?

Short answer: Nothing for the gateway; you pay for public IPv4 addresses and outbound data transfer.

Inbound data is free.

Q13. Why can an IGW not be detached?

Short answer: Because resources in the VPC still use public IPs mapped through it.

Release or disassociate those addresses first.

Q14. How do you make a subnet public?

Short answer: Associate it with a route table that routes 0.0.0.0/0 to the IGW and give resources public addresses.

Use a custom route table, not the main one.

Q15. How do you reduce public IPv4 usage?

Short answer: Put resources behind load balancers, use IPv6, VPC endpoints and Session Manager.

Public IPv4 addresses are charged hourly.

Q16. How do you reach S3 without the internet?

Short answer: Use a gateway VPC endpoint.

It needs no IGW or NAT.

Q17. Is IPv6 in a public subnet automatically safe?

Short answer: No, IPv6 addresses are directly routable, so access is controlled only by security groups and NACLs.

Use an egress-only gateway for private IPv6.

Q18. How do you secure internet-facing workloads?

Short answer: Expose only load balancers, keep servers private, use WAF and Shield, narrow security groups and Session Manager instead of SSH.

Add VPC Block Public Access as a guardrail.

Q19. What is an edge association or ingress routing?

Short answer: Associating a route table with an IGW to steer inbound traffic through an inspection appliance.

It is an advanced security pattern.

Q20. How do you find which subnets are public?

Short answer: Look for route tables with a route to an IGW and list their associated subnets.

Use describe-route-tables with a gateway filter.

Q21. A newly attached IGW does nothing. Why?

Short answer: Attachment does not create routes; you must add a route to the IGW in the route table.

Also ensure public IPs exist.
