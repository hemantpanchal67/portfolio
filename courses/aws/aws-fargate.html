1. What is AWS Fargate?

AWS Fargate is a serverless compute engine for containers. You package your app as a container image, tell ECS or EKS how much CPU and memory it needs, and Fargate finds capacity, starts it, connects it to your VPC and runs it. There are no EC2 instances to choose, patch, scale or secure; you pay only for the resources your task or pod requests while it runs.

Each task or pod runs in its own isolated micro-VM with its own kernel, so workloads do not share a host. It receives its own elastic network interface, a private IP and a security group in your subnet, and its own IAM role. Fargate is not a separate orchestrator: it is a compute option for ECS and EKS.

Features and benefits

Benefits include no server management, strong isolation, right-sized resources per workload, per-second billing, quick scaling without capacity planning, and integration with VPC, IAM, CloudWatch and load balancers.

Problems and limits

Fargate has no host access (no privileged containers, DaemonSets or host paths), slower start than warm instances, fixed CPU and memory combinations, ephemeral storage that needs EFS or similar for persistence, and a higher price per unit than well-packed EC2 at steady, high utilisation. GPU and some specialised workloads still need EC2.

aws ecs run-task --cluster main --launch-type FARGATE --task-definition web:12 \
  --network-configuration "awsvpcConfiguration={subnets=[subnet-a,subnet-b],securityGroups=[sg-123],assignPublicIp=DISABLED}"
aws ecs describe-tasks --cluster main --tasks $TASK --query "tasks[].[lastStatus,cpu,memory,platformVersion]"

2. Fargate on ECS and EKS, Spot and Graviton

On ECS, Fargate is a launch type or capacity provider: write a task definition in awsvpc mode with Fargate compatibility, pick CPU and memory from the allowed combinations, and run it as a service or one-off task. On EKS, a Fargate profile selects pods by namespace and labels; matching pods are scheduled onto Fargate, one pod per micro-VM, with no node group needed. Fargate Spot offers discounted spare capacity for ECS tasks with a two-minute SIGTERM notice, and Graviton (ARM64) tasks cost less when your images are multi-architecture.

resource "aws_ecs_service" "api" {
  name = "api"  cluster = aws_ecs_cluster.main.id  task_definition = aws_ecs_task_definition.api.arn  desired_count = 4
  capacity_provider_strategy { capacity_provider = "FARGATE"      base = 2  weight = 1 }
  capacity_provider_strategy { capacity_provider = "FARGATE_SPOT"           weight = 3 }
  network_configuration { subnets = aws_subnet.private[*].id  security_groups = [aws_security_group.api.id] }
}
resource "aws_eks_fargate_profile" "apps" {
  cluster_name = aws_eks_cluster.main.name  fargate_profile_name = "apps"  pod_execution_role_arn = aws_iam_role.fargate.arn
  subnet_ids = aws_subnet.private[*].id
  selector { namespace = "apps" labels = { compute = "fargate" } }
}

3. Limits, Storage, Start-up Time and Cost

Know the constraints before choosing Fargate. There is no privileged mode, host networking, DaemonSets or hostPath, so host-level agents must become sidecars or managed features. Tasks start slower because a micro-VM is provisioned and the image pulled; small images, SOCI lazy loading and scaling earlier reduce the pain. Ephemeral storage is 20 GiB by default (configurable higher) and is lost when the task stops, so use EFS or managed volumes, or external services like S3 and databases, for persistence. On cost, you pay for requested size, so right-size; Compute Savings Plans and Spot help, but at large, steady, densely packed scale, EC2 can still be cheaper.

4. Security, Networking and Troubleshooting

Security on Fargate is shared: AWS patches the hosts and runtime, while you patch your container images, so scan them with ECR and redeploy. Give each workload its own role (ECS task role, or IRSA / EKS Pod Identity for pods), run tasks in private subnets with narrow security groups, add VPC endpoints for ECR, S3, CloudWatch Logs and Secrets Manager, and inject secrets at start. Ephemeral storage is encrypted by default.

5. Interview Q&A: Fargate

Q1. What is Fargate?

Short answer: A serverless compute engine for containers that runs ECS tasks and EKS pods without you managing servers.

You pay for requested vCPU and memory.

Q2. Fargate versus EC2 launch type?

Short answer: Fargate removes host management and bills per task size; EC2 gives control over instances, GPUs and packing but you manage the hosts.

Mix them with capacity providers.

Q3. How is Fargate isolated?

Short answer: Each task or pod runs in its own micro-VM with a dedicated kernel and its own ENI.

No shared host between workloads.

Q4. How is Fargate billed?

Short answer: Per second for requested vCPU, memory and extra storage, with a one-minute minimum.

Spot and Savings Plans reduce cost.

Q5. How does Fargate work with EKS?

Short answer: A Fargate profile matches namespaces and labels so those pods run on Fargate nodes, one pod per node.

No managed node group is needed.

Q6. What network mode is used?

Short answer: awsvpc: each task gets its own ENI, private IP and security group.

Plan subnet IP capacity.

Q7. What are Fargate limitations?

Short answer: No privileged containers, host networking, DaemonSets or hostPath, ephemeral storage, and slower start than warm instances.

Some workloads need EC2.

Q8. How do you persist data?

Short answer: Use EFS, supported managed volumes, or external stores like S3 and databases.

Task storage is ephemeral.

Q9. What is Fargate Spot?

Short answer: Discounted spare capacity for ECS tasks with a two-minute SIGTERM interruption notice.

Use for fault-tolerant work.

Q10. Can you use GPUs on Fargate?

Short answer: Not generally; GPU workloads typically use EC2 capacity.

Check current support.

Q11. How do you cut Fargate costs?

Short answer: Right-size tasks, use Fargate Spot, Compute Savings Plans, Graviton and scale in when idle.

Compare with EC2 at scale.

Q12. How do you speed up task start?

Short answer: Use small images, SOCI lazy-loading, multi-stage builds and scale earlier.

Image pull dominates start time.

Q13. How do workloads get AWS permissions?

Short answer: ECS uses task roles; EKS pods use IRSA or Pod Identity.

There is no shared node role.

Q14. Who patches what?

Short answer: AWS patches hosts and runtime; you patch the content of your container images.

Scan with ECR and redeploy.

Q15. How do private tasks pull images?

Short answer: Via VPC endpoints for ECR and S3 or a NAT Gateway, plus execution-role permissions.

Check routes first.

Q16. How do you debug a running Fargate container?

Short answer: Use ECS Exec (SSM) or kubectl exec, plus CloudWatch logs.

There is no SSH to the host.

Q17. Why is a task stuck in PROVISIONING?

Short answer: Often the subnet has no free IPs, ENI limits are hit or capacity is lacking.

Add subnets.

Q18. How do you size a Fargate task?

Short answer: Choose a valid CPU and memory combination based on measured usage with headroom, then adjust.

Billing follows the requested size.

Q19. Fargate versus Lambda?

Short answer: Fargate runs long-lived or containerised workloads with any runtime; Lambda is event-driven, short-running functions.

Choose by execution model.

Q20. When would you not choose Fargate?

Short answer: When you need privileged access, GPUs, host agents or the lowest cost at large steady scale.

Use EC2 nodes then.
