1. What is a Network Load Balancer?

A Network Load Balancer (NLB) distributes TCP, UDP and TLS traffic at layer 4. It is engineered for millions of requests per second, ultra-low latency and sudden traffic spikes, and gives you one static IP per Availability Zone (or your own Elastic IPs). Because it does not read the application payload, it is fast and works with any protocol, not just HTTP.

The model is simple: a listener accepts connections on a port and protocol and forwards them to a target group of instances, IP addresses or even an ALB. The NLB picks a target by flow hashing (protocol, addresses and ports) and keeps a connection on the same target for its lifetime.

Features and benefits

You get extreme performance, static and Elastic IPs, client IP preservation, TLS termination, PrivateLink support, zonal isolation and support for long-lived connections such as WebSockets over TCP, databases and game sessions.

Problems and limits

There is no content-based routing (no host or path rules), cross-zone balancing is off by default and can cause uneven load, health-check and security-group misconfiguration is a frequent cause of "unhealthy" targets, and client IP handling differs between instance and IP targets. For HTTP applications that need routing, WAF or authentication, an ALB is usually the better choice.

aws elbv2 create-load-balancer --name edge --type network --subnet-mappings SubnetId=subnet-a,AllocationId=eipalloc-1 SubnetId=subnet-b,AllocationId=eipalloc-2
aws elbv2 create-target-group --name game --protocol UDP --port 7777 --vpc-id vpc-123 --target-type instance --health-check-protocol TCP --health-check-port 8080
aws elbv2 create-listener --load-balancer-arn $NLB --protocol UDP --port 7777 --default-actions Type=forward,TargetGroupArn=$TG

2. Static IPs, Client IP, TLS and PrivateLink

Static IPs: each AZ node has a fixed IP, and you can bind your own Elastic IPs so partners can allow-list you; internal NLBs can use chosen private IPs. Client IP preservation: for instance targets the original client address reaches the application, whereas for IP targets you may see the NLB's address unless you enable preservation or use Proxy Protocol v2. TLS listeners terminate TLS with ACM certificates and SNI, or you can use a TCP listener for passthrough. An NLB is also the required front of a PrivateLink endpoint service.

resource "aws_lb" "edge" {
  name = "edge"  load_balancer_type = "network"
  dynamic "subnet_mapping" { for_each = aws_subnet.public  content { subnet_id = subnet_mapping.value.id  allocation_id = aws_eip.nlb[subnet_mapping.key].id } }
  enable_cross_zone_load_balancing = true
}
resource "aws_lb_listener" "tls" {
  load_balancer_arn = aws_lb.edge.arn  port = 443  protocol = "TLS"
  certificate_arn = aws_acm_certificate.cert.arn  ssl_policy = "ELBSecurityPolicy-TLS13-1-2-2021-06"
  default_action { type = "forward" target_group_arn = aws_lb_target_group.app.arn }
}
resource "aws_vpc_endpoint_service" "svc" { acceptance_required = true  network_load_balancer_arns = [aws_lb.edge.arn] }

3. NLB vs ALB vs GWLB and Common Scenarios

Choose by protocol and need. An ALB works at layer 7 with host and path routing, WAF and authentication. An NLB works at layer 4 with static IPs, UDP, extreme scale and PrivateLink. A Gateway Load Balancer works at layer 3 to steer traffic through security appliances. You can combine them: an NLB with an ALB target gives static IPs plus HTTP routing, or use AWS Global Accelerator for anycast static IPs in front of ALBs.

4. Operations, Cross-Zone and Troubleshooting

Cross-zone load balancing is off by default on an NLB: each AZ node sends only to targets in its own AZ, so unequal target counts per AZ cause uneven load. Enable it for even spread, accepting cross-AZ data charges. Health checks use TCP, HTTP or HTTPS, and the target security group and NACL must allow the check traffic. With client IP preservation targets see client addresses, so allow those sources, otherwise allow the NLB. Deregistration delay lets long-lived connections drain before reset.

5. Interview Q&A: Network Load Balancer

Q1. What is an NLB?

Short answer: A layer 4 load balancer for TCP, UDP and TLS that offers extreme performance, low latency and static IPs.

It does not inspect HTTP content.

Q2. NLB versus ALB?

Short answer: NLB is layer 4 with static IPs and high throughput; ALB is layer 7 with content-based routing, WAF and authentication.

Choose by protocol and features.

Q3. Does an NLB have static IPs?

Short answer: Yes, one per AZ, and you can assign your own Elastic IPs.

This helps partner allow-lists.

Q4. How does an NLB choose a target?

Short answer: Flow hashing on protocol, addresses and ports, keeping a connection on one target.

It is not per-request round robin.

Q5. What protocols does it support?

Short answer: TCP, UDP, TCP_UDP and TLS.

Not HTTP routing features.

Q6. What is client IP preservation?

Short answer: Targets see the original client IP; for instance targets this is default, for IP targets it is configurable or via Proxy Protocol.

Affects security group rules.

Q7. What is Proxy Protocol v2?

Short answer: A header that carries the original connection information to the target.

The application must parse it.

Q8. Can an NLB terminate TLS?

Short answer: Yes, with a TLS listener and ACM certificates, or use TCP for passthrough.

SNI is supported.

Q9. What is cross-zone load balancing on NLB?

Short answer: Spreading traffic across targets in all AZs, off by default and with cross-AZ data charges when on.

Enable it if targets are unequal per AZ.

Q10. How do you give an HTTP API a static IP?

Short answer: Put an NLB with an ALB target in front of the ALB, or use Global Accelerator.

Each adds a hop or cost.

Q11. Can an NLB front an ALB?

Short answer: Yes, using the ALB target type.

Gives static IPs plus layer 7 routing.

Q12. How does PrivateLink relate to NLB?

Short answer: An endpoint service is backed by an NLB (or GWLB), and consumers connect through interface endpoints.

It is one-way and avoids CIDR conflicts.

Q13. What are NLB target types?

Short answer: Instance, IP and ALB.

IP targets include on-premises over VPN or Direct Connect.

Q14. Why are my targets unhealthy?

Short answer: Security groups or NACLs block health checks, the port or protocol is wrong, or the app is not listening.

Check target-health reasons.

Q15. What is the hairpin issue?

Short answer: With client IP preservation, a target connecting to the NLB can be routed back to itself and fail.

Use IP targets or a different design.

Q16. Does an NLB support security groups?

Short answer: Newer NLBs can have security groups; older ones do not and targets see client IPs.

Check current support.

Q17. How do long-lived connections behave on deregistration?

Short answer: They continue until the deregistration delay ends, then reset unless connection termination is enabled earlier.

Tune for your protocol.

Q18. When would you pick a Gateway Load Balancer?

Short answer: To insert third-party security appliances transparently into traffic flows.

It works at layer 3 with GENEVE.

Q19. How does an NLB scale?

Short answer: Automatically, handling millions of requests per second and sudden spikes without pre-warming.

Monitor with CloudWatch.

Q20. Where is the NLB deployed?

Short answer: In subnets across AZs you choose, one node per AZ with its own IP.

Use at least two AZs.
