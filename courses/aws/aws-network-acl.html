1. What is a Network ACL?

A network access control list (NACL) is an optional, stateless firewall at the subnet boundary. It inspects every packet entering or leaving a subnet and decides, based on a numbered list of rules, whether to allow or deny it. Where a security group protects a single network interface, a NACL protects everything in the subnet at once, which makes it a good second layer of defence and a handy place for subnet-wide rules.

Its defining properties are that it is stateless (return traffic needs explicit rules), that rules are numbered and evaluated in order with the first match winning, and that it supports both allow and deny actions. Each subnet is associated with exactly one NACL, while one NACL can serve many subnets.

Features and benefits

NACLs let you explicitly deny traffic such as a malicious IP, add a subnet-wide guardrail that protects you from security-group mistakes, and segment subnets from each other. They are free and apply instantly.

Problems and limits

Statelessness makes them easy to misconfigure, particularly forgetting ephemeral ports for return traffic. They only understand IPs, ports and protocols, not domains or application content, have a limited number of rules, and apply only to traffic that crosses the subnet boundary, not between instances in the same subnet. For these reasons most teams keep the default allow-all NACL and rely on security groups, adding NACLs only for specific needs.

NACL=$(aws ec2 create-network-acl --vpc-id vpc-123 --query NetworkAcl.NetworkAclId --output text)
aws ec2 create-network-acl-entry --network-acl-id $NACL --ingress --rule-number 100 --protocol tcp --port-range From=443,To=443 --cidr-block 0.0.0.0/0 --rule-action allow
aws ec2 create-network-acl-entry --network-acl-id $NACL --egress  --rule-number 100 --protocol tcp --port-range From=1024,To=65535 --cidr-block 0.0.0.0/0 --rule-action allow
aws ec2 replace-network-acl-association --association-id aclassoc-123 --network-acl-id $NACL

2. How a Packet Flows: NACL and Security Group Together

For a request into an instance, the packet is first checked by the subnet NACL inbound rules and then by the security group on the interface; both must allow it. The reply leaves through the security group, which allows it automatically because it is stateful, and then must pass the NACL outbound rules, which have no memory of the request and need a matching rule, typically for the ephemeral port range. Traffic between two subnets crosses both subnets' NACLs in each direction.

A client picks a random ephemeral port as source. Linux commonly uses 32768–60999, Windows 49152–65535, and NAT Gateways and many load balancers use 1024–65535. Allowing 1024–65535 for return traffic covers all of them.

3. Rules, Defaults and Per-Tier Design

Every VPC has a default NACL that allows all traffic in both directions, and new subnets use it automatically. A custom NACL starts by denying everything, so you must add rules for both directions. Rule numbers range from 1 to 32766, and a good habit is to number in steps of 10 or 100 so you can insert rules later. The final rule, shown as *, denies anything unmatched and cannot be changed. Changing a subnet's association takes effect immediately, so test first.

resource "aws_network_acl" "data" {
  vpc_id     = aws_vpc.main.id
  subnet_ids = [for s in aws_subnet.data : s.id]

  ingress { rule_no = 100  action = "allow"  protocol = "tcp"  from_port = 5432  to_port = 5432  cidr_block = "10.0.10.0/22" }   # app subnets
  egress  { rule_no = 100  action = "allow"  protocol = "tcp"  from_port = 1024  to_port = 65535 cidr_block = "10.0.10.0/22" }   # replies
  ingress { rule_no = 50   action = "deny"   protocol = "-1"   from_port = 0     to_port = 0     cidr_block = "198.51.100.0/24" }  # blocked range
}

A common design is a NACL per tier: public subnets allow web ports and replies, app subnets allow the app port from the public CIDRs, and data subnets allow the database port only from the app CIDRs. Keep it simple and documented; complex NACLs are hard to debug.

4. When to Use NACLs (and When Not To)

Use a NACL when you need what security groups cannot give. First, explicit denies, such as blocking an abusive address range. Second, a subnet-wide guardrail that overrides mistakes, for example denying database ports from the internet on every data subnet. Third, segmentation between subnets or environments. Fourth, compliance requirements that call for a second, independent control.

Do not expect them to handle everything. For domain filtering, intrusion prevention or large block lists, use AWS Network Firewall or AWS WAF. For routine allow rules between tiers, security groups are simpler and safer because they are stateful. A pragmatic rule is: security groups for normal access, NACLs for explicit denies and guardrails.

aws ec2 create-network-acl-entry --network-acl-id acl-123 --ingress --rule-number 10 --protocol -1 --cidr-block 198.51.100.0/24 --rule-action deny
aws ec2 describe-network-acls --filters Name=association.subnet-id,Values=subnet-123

5. Troubleshooting & Real Scenarios

When a connection fails and security groups look right, suspect the NACL. The most common cause is missing ephemeral port rules, so the request arrives but the reply is dropped. Next check rule order, because a lower-numbered deny can mask a later allow. Remember that traffic between subnets is evaluated by both subnets' NACLs, and confirm with VPC Flow Logs and Reachability Analyzer, which can name the exact blocking component.

6. Interview Q&A: Network ACL

Q1. What is a network ACL?

Short answer: A stateless, numbered-rule firewall applied at the subnet boundary that can allow or deny traffic.

Each subnet has exactly one NACL.

Q2. What does stateless mean?

Short answer: The NACL does not track connections, so return traffic must be allowed by explicit rules.

Security groups are stateful.

Q3. NACL versus security group?

Short answer: NACLs are stateless, subnet-level and support deny; security groups are stateful, interface-level and allow-only.

Use both.

Q4. How are NACL rules evaluated?

Short answer: In ascending rule-number order, and the first matching rule applies.

The final * rule denies all.

Q5. What is the default NACL behaviour?

Short answer: The default NACL allows all inbound and outbound traffic.

A custom NACL denies all until rules are added.

Q6. How many NACLs can a subnet have?

Short answer: Exactly one, but one NACL can be associated with many subnets.

Swapping is immediate.

Q7. What are ephemeral ports?

Short answer: Random high ports clients use as the source of a connection, which become destination ports of replies.

Allow 1024-65535 in NACLs for return traffic.

Q8. Which is evaluated first inbound?

Short answer: The NACL is evaluated before the security group on inbound traffic.

Outbound it is the security group first, then the NACL.

Q9. Do NACLs filter traffic within a subnet?

Short answer: No, only traffic crossing the subnet boundary.

Use security groups within a subnet.

Q10. How do you block an IP address?

Short answer: Add a DENY rule with a low number to the NACL.

Security groups cannot deny.

Q11. Why use rule numbers in steps of 10 or 100?

Short answer: So you can insert new rules between existing ones without renumbering.

Rule order decides the outcome.

Q12. What is the maximum number of NACL rules?

Short answer: A default quota (20 per direction, adjustable up to a limit) applies, so keep rules few.

Check current quotas.

Q13. Traffic between two subnets: how many NACL checks?

Short answer: Four per round trip: the source subnet outbound and destination subnet inbound, then the reverse for the reply.

Both subnets need rules.

Q14. A web request works but the page does not load. Why?

Short answer: The outbound ephemeral port rule is missing, so replies are dropped.

Allow 1024-65535 outbound.

Q15. How do you diagnose NACL issues?

Short answer: Use VPC Flow Logs for REJECT records and Reachability Analyzer to identify the blocking component.

Review rule order.

Q16. When would you use NACLs?

Short answer: For explicit denies, subnet-wide guardrails, segmentation and compliance backstops.

Otherwise stick to security groups.

Q17. What are alternatives to NACLs for deeper filtering?

Short answer: AWS Network Firewall, AWS WAF and Gateway Load Balancer appliances.

They inspect domains and content.

Q18. Is it safe to swap a subnet's NACL?

Short answer: It takes effect immediately and can break live traffic.

Test and have a rollback.

Q19. Can NACLs filter by domain name?

Short answer: No, only IP ranges, ports and protocols.

Use Network Firewall for domains.

Q20. How do NACLs handle IPv6?

Short answer: Rules for IPv6 use separate IPv6 CIDR entries; IPv4 rules do not cover IPv6.

Add both families when needed.
