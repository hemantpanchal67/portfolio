1. What is an Application Load Balancer?

An Application Load Balancer (ALB) distributes incoming HTTP, HTTPS and gRPC traffic across multiple targets such as EC2 instances, containers, IP addresses and Lambda functions. It works at layer 7, so it can look inside the request and route by host, path, header, query string or method, which makes it the standard front door for web applications and microservices.

An ALB has a DNS name and places a network interface in each subnet you choose (at least two AZs), so it is highly available and scales automatically. Its building blocks are listeners (port and protocol), rules (conditions and actions), and target groups (the backends with health checks).

Features and benefits

You get content-based routing, TLS termination with ACM, WAF integration, built-in authentication, HTTP/2 and WebSockets, weighted routing for canaries, container support through dynamic port mapping, and deep integration with Auto Scaling and ECS.

Problems and limits

An ALB is regional and not static-IP (its IPs change; use Global Accelerator or an NLB in front if you need fixed addresses). It is layer 7 only, so it does not handle arbitrary TCP/UDP. It costs per hour plus capacity units, has idle timeouts that cause 502/504 surprises, and misconfigured health checks take healthy targets out of service.

aws elbv2 create-load-balancer --name web --type application --subnets subnet-a subnet-b --security-groups sg-alb
aws elbv2 create-target-group --name web-tg --protocol HTTP --port 8080 --vpc-id vpc-123 --health-check-path /health --target-type instance
aws elbv2 create-listener --load-balancer-arn $ALB --protocol HTTPS --port 443 --certificates CertificateArn=$CERT --default-actions Type=forward,TargetGroupArn=$TG

2. Listener Rules and Routing

Listener rules are evaluated in priority order, lowest number first, and the first match wins; the default rule catches the rest. Conditions include host header, path pattern, HTTP header, query string, method and source IP. Actions include forward (optionally to several weighted target groups), redirect, fixed response and authenticate. This lets one ALB serve many services, saving cost and simplifying DNS.

resource "aws_lb_listener_rule" "api" {
  listener_arn = aws_lb_listener.https.arn  priority = 10
  action    { type = "forward" target_group_arn = aws_lb_target_group.api.arn }
  condition { path_pattern { values = ["/api/*"] } }
  condition { host_header  { values = ["app.example.com"] } }
}
resource "aws_lb_listener" "http" {
  load_balancer_arn = aws_lb.web.arn  port = 80  protocol = "HTTP"
  default_action { type = "redirect" redirect { port = "443" protocol = "HTTPS" status_code = "HTTP_301" } }
}
resource "aws_lb_listener_rule" "canary" {
  listener_arn = aws_lb_listener.https.arn  priority = 20
  action { type = "forward" forward {
    target_group { arn = aws_lb_target_group.blue.arn  weight = 95 }
    target_group { arn = aws_lb_target_group.green.arn weight = 5 } } }
  condition { path_pattern { values = ["/*"] } }
}

3. Target Groups, Health Checks and Containers

A target group holds the backends and their health check. Target types are instance (by ID), IP (any private IP, including on-premises over VPN and ECS or EKS tasks) and Lambda. The ALB sends a health request, for example GET /health expecting 200, and routes only to healthy targets. For containers, dynamic port mapping or per-task IPs let many tasks share an instance. Algorithms are round robin (default) or least outstanding requests, and slow start eases a new target in.

aws elbv2 modify-target-group --target-group-arn $TG --health-check-path /health --health-check-interval-seconds 15 --healthy-threshold-count 2 --unhealthy-threshold-count 3 --matcher HttpCode=200-299
aws elbv2 modify-target-group-attributes --target-group-arn $TG --attributes Key=load_balancing.algorithm.type,Value=least_outstanding_requests Key=deregistration_delay.timeout_seconds,Value=30
aws elbv2 describe-target-health --target-group-arn $TG
Target typeUse
instanceEC2 and Auto Scaling groups
ipECS awsvpc tasks, EKS pods, on-premises servers

Make the health endpoint cheap and meaningful: check critical dependencies lightly, but never let a shared dependency outage mark every target unhealthy at once.

4. TLS, WAF, Authentication and Security Groups

The ALB terminates TLS using certificates from AWS Certificate Manager; SNI lets one listener hold many certificates, and a security policy sets the minimum TLS version and ciphers. Attach AWS WAF for managed rules and rate limits, and use Shield for DDoS. The ALB can authenticate users with OIDC or Cognito before forwarding and passes verified claims to the backend. Chain security groups: the ALB allows 443 from the internet, targets allow the app port only from the ALB group. For end-to-end encryption, use HTTPS to the targets too.

aws elbv2 modify-listener --listener-arn $L --ssl-policy ELBSecurityPolicy-TLS13-1-2-2021-06
aws elbv2 add-listener-certificates --listener-arn $L --certificates CertificateArn=$CERT2
aws wafv2 associate-web-acl --web-acl-arn $WAF --resource-arn $ALB
aws elbv2 modify-load-balancer-attributes --load-balancer-arn $ALB --attributes Key=routing.http.drop_invalid_header_fields.enabled,Value=true Key=access_logs.s3.enabled,Value=true Key=access_logs.s3.bucket,Value=my-alb-logs

5. Operations, Troubleshooting & Scenarios

Key operational knobs are stickiness (cookie affinity, better avoided by externalising sessions), deregistration delay (time to finish in-flight requests, default 300 seconds), access logs and metrics, and the idle timeout (default 60 seconds). A 502 usually means the target sent an invalid response or closed a keep-alive connection early, 503 means no healthy targets, and 504 means the target did not answer in time. Set target keep-alive higher than the ALB idle timeout.

6. Interview Q&A: Application Load Balancer

Q1. What is an ALB?

Short answer: A layer 7 load balancer that routes HTTP, HTTPS and gRPC traffic to targets using content-based rules.

It is regional and scales automatically.

Q2. What are listeners, rules and target groups?

Short answer: A listener checks a port and protocol, rules map conditions to actions, and target groups hold backends with health checks.

Rules run in priority order.

Q3. What can an ALB route on?

Short answer: Host, path, HTTP headers, query strings, methods and source IP.

Actions are forward, redirect, fixed response and authenticate.

Q4. What target types exist?

Short answer: Instance, IP and Lambda.

IP targets cover ECS tasks, EKS pods and on-premises.

Q5. ALB versus NLB?

Short answer: ALB is layer 7 with content routing; NLB is layer 4 with extreme performance, static IPs and TCP/UDP/TLS support.

Choose by protocol and needs.

Q6. Does an ALB have a static IP?

Short answer: No, its IPs can change; use the DNS name, or put Global Accelerator or an NLB in front for static IPs.

Never hard-code ALB IPs.

Q7. How do you redirect HTTP to HTTPS?

Short answer: Listener on port 80 with a redirect action to port 443.

Use 301.

Q8. How do you host multiple domains on one ALB?

Short answer: Host-based rules and SNI certificates on one HTTPS listener.

ACM can supply certificates.

Q9. What is SNI?

Short answer: Server Name Indication lets a listener present different certificates based on the requested hostname.

Supports many certificates per listener.

Q10. How do you do blue/green with an ALB?

Short answer: Weighted target groups on a rule, shifting weights gradually, often automated by CodeDeploy.

Keep rollback ready.

Q11. What is deregistration delay?

Short answer: Time for a deregistering target to finish in-flight requests, default 300 seconds.

Tune it for short requests.

Q12. What is session stickiness?

Short answer: Cookie-based affinity that sends a client to the same target for a duration.

Prefer stateless apps.

Q13. What causes 502, 503 and 504?

Short answer: 502 is a bad or closed response from a target, 503 means no healthy targets, 504 means the target timed out.

Check logs and health.

Q14. What is the idle timeout?

Short answer: The time a connection may be idle before the ALB closes it, 60 seconds by default.

Set target keep-alive above it.

Q15. How do you protect an ALB from attacks?

Short answer: Attach AWS WAF, use Shield, TLS policies, and restrict targets to the ALB security group.

Rate limit with WAF.

Q16. Can an ALB authenticate users?

Short answer: Yes, with OIDC or Cognito actions that handle login and pass claims to targets.

Backends should verify the headers.

Q17. How does an ALB work with ECS?

Short answer: ECS registers tasks as targets, using dynamic ports on EC2 or task IPs with awsvpc and Fargate.

Health checks drive task replacement.

Q18. What load-balancing algorithms are available?

Short answer: Round robin (default), least outstanding requests, and weighted random with anomaly mitigation.

Least outstanding suits uneven request times.

Q19. How do you see what happened to requests?

Short answer: Enable access logs to S3 and use CloudWatch metrics and Athena.

Logs include target response codes.

Q20. Internal versus internet-facing ALB?

Short answer: Internet-facing has public IPs in public subnets; internal has private IPs only for in-VPC or hybrid traffic.

Use internal between tiers.

Q21. What happens when all targets are unhealthy?

Short answer: The ALB can fail open and send traffic to all targets, otherwise returns 503 in some cases.

Fix health checks quickly.
