1. What is AWS IAM?

AWS Identity and Access Management (IAM) is the service that controls who can do what on which AWS resources. Every request to AWS is checked by IAM in two steps: authentication, proving who you are, and authorization, deciding whether that identity is allowed to perform the action. IAM is a global service, free to use, and it is the foundation of AWS security.

Without IAM, every person and application would share one all-powerful login. With IAM you create separate identities and give each only the permissions it needs, which is the principle of least privilege.

Features

IAM offers users, groups and roles, fine-grained JSON policies with conditions, multi-factor authentication, temporary credentials through the Security Token Service, federation with external identity providers, permissions boundaries, integration with AWS Organizations SCPs, and audit tools such as credential reports, Access Analyzer and CloudTrail.

Benefits and problems

The benefits are security (least privilege), accountability (every call is attributed), flexibility (conditions on time, IP, tags, MFA) and no extra cost. The problems are complexity, because policy evaluation has many layers, over-permissioning (people attach AdministratorAccess to save time), credential leaks from long-lived access keys, and sprawl of users and roles across many accounts. The rest of this course shows how to avoid them.

aws sts get-caller-identity                              # who am I?
aws iam list-users
aws iam create-user --user-name asha
aws iam attach-user-policy --user-name asha --policy-arn arn:aws:iam::aws:policy/ReadOnlyAccess

2. Users, Groups, Roles & the Root User

The root user is the identity created when the account is opened. It has unrestricted access that no policy can limit, so you enable MFA, delete its access keys and use it only for the few tasks that need it. An IAM user is a long-lived identity with a name and credentials. A group collects users so you can attach policies once. A role is an identity with permissions but no long-term credentials: a trusted entity assumes it and receives temporary credentials.

IdentityCredentialsBest used for
Root userE-mail, password, MFARare account-level tasks only
IAM userPassword and/or access keysLegacy or break-glass cases
GroupNone (just a container)Sharing policies between users
RoleTemporary, from STSApplications, services, cross-account, federated people

Today the guidance is: people use IAM Identity Center (federation), workloads use roles (EC2 instance profiles, Lambda execution roles, ECS task roles, EKS IRSA), and long-lived access keys are avoided.

aws iam create-group --group-name developers
aws iam add-user-to-group --user-name asha --group-name developers
aws iam attach-group-policy --group-name developers --policy-arn arn:aws:iam::aws:policy/PowerUserAccess

aws iam create-role --role-name app-role --assume-role-policy-document file://trust.json
aws iam create-instance-profile --instance-profile-name app-profile
aws iam add-role-to-instance-profile --instance-profile-name app-profile --role-name app-role
import boto3
s3 = boto3.client("s3")        # on EC2/Lambda this uses the role automatically: no keys in code
print(boto3.client("sts").get_caller_identity()["Arn"])

3. IAM Policies: Structure & Examples

A policy is a JSON document with one or more statements. Each statement has an Effect (Allow or Deny), the Action (such as s3:GetObject), the Resource (identified by an ARN) and optionally a Condition. Resource-based policies also have a Principal, saying who the statement applies to.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadReports",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": ["arn:aws:s3:::acme-reports", "arn:aws:s3:::acme-reports/*"],
      "Condition": { "Bool": { "aws:MultiFactorAuthPresent": "true" },
                     "IpAddress": { "aws:SourceIp": "203.0.113.0/24" } }
    },
    { "Effect": "Deny", "Action": "s3:DeleteObject", "Resource": "arn:aws:s3:::acme-reports/*" }
  ]
}

Policies can be AWS managed (maintained by AWS, such as ReadOnlyAccess), customer managed (yours, reusable) or inline (embedded in one identity). Prefer customer managed policies. Use wildcards carefully: "Action": "*", "Resource": "*" is full administrator access. Use NotAction and NotResource only when you fully understand them.

Useful condition keys

KeyUse
aws:MultiFactorAuthPresentRequire MFA
aws:SourceIp, aws:SourceVpceLimit by network
aws:RequestedRegionRestrict Regions
aws:PrincipalTag / aws:ResourceTagAttribute-based access
aws:PrincipalOrgIDAllow only your organisation
aws:SecureTransportRequire HTTPS
s3:prefixLimit S3 folders

4. Types of Policies

IAM has several kinds of policies that work together. Identity-based policies are attached to users, groups and roles and grant permissions. Resource-based policies are attached to resources such as S3 buckets and KMS keys and name a principal. Permissions boundaries set the maximum an identity can have. Service control policies from AWS Organizations set the maximum for whole accounts. Session policies narrow a single role session. ACLs are a legacy mechanism.

TypeGrants permissions?Attached toTypical use
Identity-basedYesUser, group, roleEveryday permissions
Resource-basedYesBucket, queue, key, role (trust)Cross-account access
Permissions boundaryNo, only limitsUser or roleSafe delegated administration
SCPNo, only limitsAccount or OUOrganisation-wide guardrails
Session policyNo, only limitsA sessionScoped access per user
{ "Version": "2012-10-17", "Statement": [{
    "Effect": "Allow", "Principal": { "AWS": "arn:aws:iam::222222222222:role/analytics" },
    "Action": "s3:GetObject", "Resource": "arn:aws:s3:::acme-data/*" }] }

The example is an S3 bucket policy, a resource-based policy that lets a role from another account read objects. The analytics role also needs its own identity policy allowing s3:GetObject, because for cross-account access both sides must allow.

5. How AWS Evaluates Permissions

Understanding the evaluation logic is the key to solving "Access Denied" problems and a favourite interview topic. The rules are simple to state: the default is deny; an explicit deny always wins; and, for an allow, every applicable guardrail (SCP, permissions boundary, session policy) must allow, and an identity-based or resource-based policy must grant the action.

Walk through it in order. First AWS checks for any explicit Deny in any policy. Next, if the account belongs to an organisation, an SCP must allow the action. Then a permissions boundary and session policy, if present, must allow it. Finally an identity-based or resource-based policy must allow it. For same-account access either policy type is enough, but for cross-account access both the resource policy and the identity policy must allow.

ScenarioResult
No policy mentions the actionImplicit deny
Identity policy allows, SCP does not allowDenied
Identity policy allows, bucket policy explicitly deniesDenied (explicit deny wins)
Identity policy allows, boundary does not include the actionDenied
Same account, only the bucket policy allows the roleAllowed

Debugging AccessDenied

aws iam simulate-principal-policy --policy-source-arn arn:aws:iam::123:role/app --action-names dynamodb:PutItem --resource-arns arn:aws:dynamodb:ap-south-1:123:table/orders
aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=PutItem --max-results 5
aws accessanalyzer validate-policy --policy-document file://policy.json --policy-type IDENTITY_POLICY

Read the error message first: newer messages say which type of policy caused the denial. Then check SCPs, boundaries, resource policies, KMS key policies and VPC endpoint policies.

6. Roles, STS & Cross-Account Access

A role has two policies. The trust policy lists who may assume the role, and the permission policies list what the role can do. To use a role, a principal calls sts:AssumeRole on the AWS Security Token Service (STS), which checks the trust policy and returns temporary credentials: an access key, a secret key and a session token, valid from 15 minutes to 12 hours. While the session lasts, the caller has only the role's permissions.

{ "Version": "2012-10-17", "Statement": [{            // trust policy: let account 111122223333 assume this role, with MFA
    "Effect": "Allow", "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
    "Action": "sts:AssumeRole",
    "Condition": { "Bool": { "aws:MultiFactorAuthPresent": "true" } } }] }
aws sts assume-role --role-arn arn:aws:iam::444455556666:role/audit --role-session-name asha-audit
aws configure set role_arn arn:aws:iam::444455556666:role/audit --profile audit      # profile that assumes it
aws s3 ls --profile audit
import boto3
creds = boto3.client("sts").assume_role(RoleArn="arn:aws:iam::444455556666:role/audit", RoleSessionName="job")["Credentials"]
s3 = boto3.client("s3", aws_access_key_id=creds["AccessKeyId"], aws_secret_access_key=creds["SecretAccessKey"], aws_session_token=creds["SessionToken"])

Service roles and common patterns

AWS services use roles too. An EC2 instance profile gives code on an instance temporary credentials, a Lambda execution role lets a function call other services, an ECS task role does the same per container, and service-linked roles are predefined roles that services use on your behalf. For cross-account access, the target account creates a role that trusts the source account. For third parties, add an external ID to prevent the confused deputy problem. GitHub Actions can assume a role through OIDC federation, so no access keys are stored in the repository.

7. Federation & IAM Identity Center

Creating an IAM user for every employee in every account does not scale and leaves long-lived passwords. Federation lets people sign in with the identity they already have at work, such as Microsoft Entra ID, Okta or Google Workspace, and receive temporary AWS access. The protocols are SAML 2.0 and OpenID Connect. The managed service for this is IAM Identity Center, which works with AWS Organizations.

An administrator connects the company identity provider and automatic provisioning with SCIM. Then they create permission sets, which are templates of policies, and assign a group to an account with a permission set. In that account Identity Center creates a role, and when a user signs in to the access portal and picks the account, they land in that role with temporary credentials. Leavers are removed centrally and lose access immediately.

aws configure sso                         # creates a profile, opens the browser to sign in
aws sso login --profile dev-admin
aws s3 ls --profile dev-admin             # uses temporary credentials, no access keys on disk
// GitHub Actions: trust policy for OIDC federation (no access keys in the repo)
{ "Effect": "Allow", "Principal": { "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": { "StringLike": { "token.actions.githubusercontent.com:sub": "repo:acme/shop:ref:refs/heads/main" } } }

Benefits and problems

Benefits are single sign-on, central MFA, central joiner-mover-leaver handling and no long-lived credentials. Problems are the need for AWS Organizations, an extra service to administer, and the need to design permission sets thoughtfully so they do not become too broad.

8. Best Practices, Auditing & Common Problems

Good IAM is mostly habits. Protect the root user with MFA and no access keys. Require MFA for people, preferring phishing-resistant passkeys or hardware keys. Apply least privilege: start narrow, and use IAM Access Analyzer to generate policies from real usage. Use roles instead of access keys. Rotate and remove unused credentials using the credential report. Turn on CloudTrail for every Region and account. Use tags for attribute-based access. Separate environments into different accounts.

Manage IAM as code (CloudFormation, CDK or Terraform) and review policy changes in pull requests, so access is versioned and auditable.

9. Interview Q&A: IAM

Q1. What is IAM?

Short answer: IAM is the AWS service that manages identities and their permissions, deciding who can do what on which resources.

It performs authentication and authorization for every API call. It is global and free.

Q2. Difference between a user, group and role?

Short answer: A user is a long-lived identity, a group is a set of users sharing policies and a role is an identity with temporary credentials assumed by a trusted entity.

Roles are preferred for workloads and federated people because they have no permanent keys.

Q3. Why not use the root user?

Short answer: It has unrestricted access that cannot be limited by policies, so any compromise is total.

Enable MFA, delete its keys and use it only for tasks that require it.

Q4. What is a policy and what are its elements?

Short answer: A JSON document made of statements with Effect, Action, Resource, optional Condition and, in resource policies, Principal.

The Version is 2012-10-17. Use Sid to label statements.

Q5. Managed versus inline policies?

Short answer: Managed policies are standalone and reusable (AWS managed or customer managed), while inline policies are embedded in a single identity.

Prefer customer managed for reuse and version history.

Q6. Identity-based versus resource-based policies?

Short answer: Identity-based policies attach to users, groups and roles, and resource-based policies attach to resources and name a principal.

Resource policies enable cross-account access directly.

Q7. What is a permissions boundary?

Short answer: A managed policy that sets the maximum permissions an identity can have.

Effective permissions are the intersection of the identity policy and the boundary. It is used for safe delegation.

Q8. What is an SCP and does it grant permissions?

Short answer: A Service Control Policy in AWS Organizations sets the maximum permissions for accounts, and it never grants permissions.

Identities still need IAM policies. SCPs apply to the root user of member accounts too.

Q9. Explain the policy evaluation logic.

Short answer: Default deny, explicit deny wins, and for an allow the guardrails (SCP, boundary, session) must allow and an identity or resource policy must grant.

Cross-account access needs both sides to allow; same-account needs either.

Q10. Which wins, allow or deny?

Short answer: An explicit deny always wins over any allow.

Absent any allow, the default is an implicit deny.

Q11. How does a role work?

Short answer: A trusted principal calls STS AssumeRole, STS checks the trust policy and returns temporary credentials for the role's permissions.

Credentials last 15 minutes to 12 hours.

Q12. Trust policy versus permission policy?

Short answer: The trust policy says who can assume the role, and the permission policy says what the role can do.

A role needs both to be useful.

Q13. How do you give an EC2 instance access to S3?

Short answer: Create a role with S3 permissions, attach it through an instance profile and let the SDK use the instance credentials.

No access keys are stored on the machine.

Q14. How do you set up cross-account access?

Short answer: In the target account create a role that trusts the source account, then allow sts:AssumeRole to the principals in the source account.

Add MFA or external ID conditions where needed.

Q15. What is the confused deputy problem?

Short answer: A third party that has access to your account could be tricked into acting for someone else; an external ID prevents it.

The role trust policy requires the external ID that only you and the third party know.

Q16. What is IAM Identity Center?

Short answer: The service for workforce single sign-on across AWS accounts and applications with permission sets.

It connects to an IdP, provisions users with SCIM and gives temporary credentials.

Q17. SAML versus OIDC federation?

Short answer: SAML is an XML-based standard used mostly for enterprise SSO, while OIDC is JSON/OAuth-based and common for web and CI systems.

Both give temporary AWS credentials through STS.

Q18. How do you avoid access keys in CI/CD?

Short answer: Use OIDC federation so the pipeline assumes a role with short-lived credentials.

Restrict the trust policy to the specific repository and branch.

Q19. What is MFA and how do you enforce it?

Short answer: A second factor beyond the password; enforce it with the aws:MultiFactorAuthPresent condition.

Prefer FIDO2 keys or passkeys for phishing resistance.

Q20. How do you apply least privilege in practice?

Short answer: Start with minimal permissions, review last-accessed information and generate policies from CloudTrail with Access Analyzer.

Replace wildcards and remove unused permissions.

Q21. What is ABAC?

Short answer: Attribute-based access control grants access when tags on the principal match tags on the resource.

It scales better than listing each resource in policies.

Q22. What does IAM Access Analyzer do?

Short answer: It finds resources shared externally, identifies unused access and validates policies.

It helps remove unintended access.

Q23. How do you audit IAM activity?

Short answer: With CloudTrail logs, the credential report, last-accessed data and Access Analyzer findings.

Send logs to a separate, protected account.

Q24. An application gets AccessDenied. How do you troubleshoot?

Short answer: Read the error, identify the principal and action, check identity, resource, boundary and SCP policies and use the policy simulator and CloudTrail.

Also check KMS key policies and VPC endpoint policies.
