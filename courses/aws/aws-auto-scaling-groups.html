1. What is an Auto Scaling Group?

An Auto Scaling group (ASG) manages a fleet of EC2 instances as one unit. It launches instances from a launch template, keeps the number between a minimum and a maximum, replaces unhealthy ones and adds or removes capacity as demand changes. The result is an application that heals itself and pays for only what it needs.

Three numbers define the group: minimum (the floor), maximum (the ceiling) and desired (what it tries to maintain right now). Scaling policies move desired between min and max. The group spreads instances across the subnets and Availability Zones you choose, and usually attaches to a load balancer target group so traffic reaches new instances automatically.

Features and benefits

You get high availability across AZs, self-healing through health checks, elasticity through policies, cost control via mixed On-Demand and Spot, and safe updates with instance refresh. The service itself is free; you pay for the instances and related resources.

Problems and limits

Scaling takes minutes, so sudden spikes can outrun it. Wrong thresholds cause flapping. Stateful or slow-booting applications are hard to scale, quotas and capacity can block launches, and unhealthy-instance loops can burn money. Applications must be stateless or keep state outside the instance for ASG to work well.

aws autoscaling create-auto-scaling-group --auto-scaling-group-name web --min-size 2 --max-size 10 --desired-capacity 2 \
  --launch-template LaunchTemplateId=lt-123,Version='$Latest' --vpc-zone-identifier "subnet-a,subnet-b" \
  --target-group-arns arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/web/abc \
  --health-check-type ELB --health-check-grace-period 120
aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names web

2. Scaling Policies

Target tracking is the recommended policy: you pick a metric and a target, for example average CPU at 50% or ALB requests per target, and the group creates the alarms and adjusts capacity like a thermostat. Step scaling applies different adjustments depending on how far an alarm breaches. Simple scaling applies one adjustment then waits for a cooldown. Scheduled scaling changes capacity at known times, and predictive scaling uses machine learning on past load to scale ahead of recurring patterns.

resource "aws_autoscaling_policy" "cpu" {
  name = "cpu-50"  autoscaling_group_name = aws_autoscaling_group.web.name  policy_type = "TargetTrackingScaling"
  target_tracking_configuration { target_value = 50  predefined_metric_specification { predefined_metric_type = "ASGAverageCPUUtilization" } }
}
resource "aws_autoscaling_schedule" "morning" {
  scheduled_action_name = "morning"  autoscaling_group_name = aws_autoscaling_group.web.name
  min_size = 4  max_size = 20  desired_capacity = 6  recurrence = "0 7 * * MON-FRI"
}

3. Lifecycle, Hooks, Instance Refresh & Warm Pools

Every instance passes through states: Pending, InService, Terminating and Terminated. Lifecycle hooks pause an instance in Pending:Wait or Terminating:Wait so you can install agents, register with systems or drain work, then continue. An instance warm-up stops new instances from counting in metrics until they are ready, which prevents over-scaling. Instance refresh replaces instances in rolling batches when you change the template or AMI, honouring a minimum healthy percentage. Warm pools keep pre-initialised stopped or hibernated instances ready so scale-out is fast for slow-booting applications.

aws autoscaling put-lifecycle-hook --auto-scaling-group-name web --lifecycle-hook-name drain --lifecycle-transition autoscaling:EC2_INSTANCE_TERMINATING --heartbeat-timeout 300
aws autoscaling complete-lifecycle-action --auto-scaling-group-name web --lifecycle-hook-name drain --lifecycle-action-result CONTINUE --instance-id i-123
aws autoscaling start-instance-refresh --auto-scaling-group-name web --preferences '{"MinHealthyPercentage":90,"InstanceWarmup":120,"AutoRollback":true}'
aws autoscaling put-warm-pool --auto-scaling-group-name web --pool-state Stopped --min-size 2

4. Mixed Instances, Spot, Multi-AZ and Termination

A mixed instances policy lets one group use several instance types and purchase options: an On-Demand base for stability plus Spot for savings, with the price-capacity-optimized allocation strategy choosing the deepest pools. List many types so Spot capacity is easy to find. The group balances across AZs, replaces capacity in healthy zones during an outage, and rebalances afterwards. Scale-in protection shields busy instances, and a termination policy decides who goes first (by default it balances AZs, then removes the oldest launch template or instance).

resource "aws_autoscaling_group" "web" {
  name = "web"  min_size = 2  max_size = 20  vpc_zone_identifier = aws_subnet.private[*].id
  health_check_type = "ELB"  health_check_grace_period = 120  capacity_rebalance = true
  mixed_instances_policy {
    instances_distribution { on_demand_base_capacity = 2  on_demand_percentage_above_base_capacity = 25  spot_allocation_strategy = "price-capacity-optimized" }
    launch_template {
      launch_template_specification { launch_template_id = aws_launch_template.web.id  version = "$Latest" }
      override { instance_type = "m7g.large" } override { instance_type = "m6g.large" } override { instance_type = "c7g.large" } override { instance_type = "m6i.large" }
    }
  }
}
Spot interruptions arrive with a two-minute notice. Enable capacity rebalancing so the group launches a replacement as soon as AWS signals elevated risk.

5. Patterns, Scenarios & Troubleshooting

If scaling misbehaves, start with the scaling activity history, which tells you why instances failed to launch or were terminated. Common causes are flapping from tight thresholds, launch failures from capacity, quotas, subnet IP exhaustion or role problems, a replace loop where instances fail health checks before the app is ready, and runaway cost from an oversized maximum.

6. Interview Q&A: Auto Scaling Groups

Q1. What is an Auto Scaling group?

Short answer: A managed group of EC2 instances that maintains capacity, replaces unhealthy instances and scales between a minimum and maximum.

It launches from a launch template.

Q2. What are min, desired and max?

Short answer: Minimum is the floor, maximum the ceiling and desired the number currently targeted.

Policies adjust desired within the bounds.

Q3. Launch template versus launch configuration?

Short answer: Launch templates are versioned and support newer features; launch configurations are legacy.

Use templates.

Q4. What scaling policy types exist?

Short answer: Target tracking, step, simple, scheduled and predictive scaling.

Target tracking is recommended.

Q5. How does target tracking work?

Short answer: You choose a metric and target and the group creates alarms and adjusts capacity to hold it.

Scale-out is aggressive, scale-in conservative.

Q6. Which metric for a web app behind an ALB?

Short answer: ALBRequestCountPerTarget, often better than CPU for web workloads.

It reflects actual load.

Q7. How do you scale queue workers?

Short answer: Scale on backlog per instance, computed from queue depth divided by running instances.

Use a custom metric.

Q8. What is a health check grace period?

Short answer: Time after launch during which health check failures are ignored while the instance boots.

Set to boot time.

Q9. EC2 versus ELB health checks?

Short answer: EC2 checks hardware and OS status; ELB checks the application through the load balancer.

Use ELB for web apps.

Q10. What are lifecycle hooks?

Short answer: Pauses in Pending:Wait or Terminating:Wait for custom actions before an instance enters service or terminates.

Complete the action to continue.

Q11. What is instance refresh?

Short answer: A rolling replacement of instances to apply a new template or AMI with a minimum healthy percentage.

Supports auto rollback.

Q12. What is a warm pool?

Short answer: Pre-initialised stopped or hibernated instances kept ready for faster scale-out.

Stopped ones cost only storage.

Q13. How do you use Spot with ASG?

Short answer: A mixed instances policy with an On-Demand base, many types, price-capacity-optimized and capacity rebalancing.

Handle interruptions.

Q14. How does ASG handle an AZ failure?

Short answer: It launches replacements in the remaining AZs and rebalances when the AZ recovers.

Use at least two AZs.

Q15. Which instance is terminated on scale-in?

Short answer: By default the group balances AZs then removes instances with the oldest launch template or launch time.

Customisable termination policy.

Q16. What is scale-in protection?

Short answer: A setting that prevents specific instances from being terminated by scale-in.

It does not block health replacement.

Q17. What is flapping?

Short answer: Repeated scale-out and scale-in because thresholds are too close or warm-up too short.

Use target tracking and proper warm-up.

Q18. Instances keep terminating after launch. Why?

Short answer: They fail health checks before the app is ready, due to a short grace period or broken user data.

Check boot logs.

Q19. How do you deploy a new AMI without downtime?

Short answer: Update the launch template and run an instance refresh with a high minimum healthy percentage.

Add rollback alarms.

Q20. Can ASG make a single instance self-healing?

Short answer: Yes, set min, max and desired to one so a failed instance is replaced automatically.

Re-attach an Elastic IP or ENI in a hook.

Q21. Is Auto Scaling free?

Short answer: Yes, you pay only for the EC2 instances and related resources it creates.

CloudWatch alarms and detailed monitoring may cost.
