🗺️Start Introduction: the journey from 1 user to millions

Hinglish samajh: Is chapter ki kahani simple hai. Har bada website pehle din ek hi computer par chalta tha. Jaise jaise users badhte gaye, site slow hoti gayi ya crash hone lagi. Tab ek ek karke naye blocks joode gaye: alag database, load balancer, replication, cache, CDN, stateless web tier, multiple data centers, message queue aur sharding. Interview mein bhi yahi bolna hai: "Main chhote setup se shuru karunga aur har problem ke hisaab se ek naya block jodunga." Yaad rakhein, har naya block ek problem solve karta hai par ek nayi problem bhi laa sakta hai.

Almost every big website you use today, such as a shopping app, a video app or a chat app, started very small. On the first day it ran on one computer and had a handful of users. Over time more people arrived, and the owners had to change the design again and again so that the site stayed fast and did not crash.

This chapter tells that story step by step. We begin with the simplest setup, where everything lives on one server. Then, each time the site "hurts" (it becomes slow, it crashes, or it cannot store more data), we add one new building block that fixes that exact pain. By the end you will know why each block exists and when to use it, which is exactly what interviewers want to hear.

Scaling is not one big decision. It is many small, careful steps. Each step solves one problem but may bring a new one, so a good architect always asks two questions: "What problem am I solving?" and "What new problem am I creating?"

✨ Features

  • It builds the design one problem at a time, so you can reuse the same reasoning in any interview.
  • Every building block is introduced only when a real pain appears.
  • The same blocks (load balancer, cache, queue, shard) appear in almost every system design question.

Interview questions and answers

Where do you start when asked to design a system for millions of users?
Start small and say it out loud: "I will begin with a single server and evolve the design as load grows." Then add one block at a time (database split, load balancer, replication, cache, CDN, stateless web tier, multiple data centers, queue, sharding) and explain the problem each one solves. Do not draw the final picture on minute one.
Why not build the final big architecture from day one?
It costs a lot, takes longer to build, and is harder to run. Early on you do not know your real traffic pattern, so you could scale the wrong part. Start simple, measure, then scale the part that actually hurts.
What is the one rule behind every step?
Remove single points of failure and let every layer scale on its own. If a part can stop the whole system when it breaks, or if it cannot grow without growing everything else, it needs to be fixed.

🖥️Step 1 Single server setup

Hinglish samajh: Shuruaat mein sab kuch ek hi server par chalta hai: website, database aur cache. User domain name type karta hai, browser DNS se IP address maangta hai, phir us IP par HTTP request bhejta hai, aur server HTML ya JSON wapas deta hai. Mobile app mostly JSON use karti hai kyunki wo halka hota hai. Fayda ye hai ki setup sasta aur aasan hai. Nuksan ye hai ki agar server band hua to poori site band, aur database aur web ek hi CPU share karte hain, isliye ek hissa akela bada nahi kiya ja sakta.

On day one, the simplest thing you can do is run everything on one server: the web application, the database and the cache. Think of a small shop where one person is the owner, the cashier and the storekeeper. It works well when only a few customers come in.

Here is what happens when someone opens your website. First, the user types a domain name such as api.mysite.com. A browser cannot connect to a name, it needs an IP address, so it asks a DNS (Domain Name System) service to translate the name into an IP address. DNS is usually a paid service run by a third party, not something you host yourself.

Once the browser has the IP address, it sends an HTTP request to your web server. The server does its work and sends back either an HTML page (for a website) or a JSON message (for a mobile app or an API). The user sees the result.

Two kinds of clients talk to your server. A web application uses a server-side language such as Java or Python for the business logic and data storage, and a client-side language such as HTML and JavaScript to show things on screen. A mobile application talks to the web server using HTTP, and the data travels in JSON because it is light and easy to read.

How it works, step by step

  1. The user types api.mysite.com in the browser or the app calls this address.
  2. The browser asks DNS for the IP address of that name. DNS replies with the address (for example 203.0.113.10).
  3. The browser sends an HTTP request directly to that IP address.
  4. The web server runs the code, reads or writes data, and returns an HTML page or a JSON response.
  5. The browser draws the page, or the mobile app shows the data.

✨ Features

  • One machine to buy, install, secure and monitor.
  • No network delay between the app and the database, because they are on the same box.
  • Very quick to build and perfect for a prototype or a new product.

✅ Benefits

  • Cheapest option at the start.
  • Easy to debug because everything is in one place.
  • No complex deployment or networking.

⚠️ Problems

  • Single point of failure: if the server dies, the whole site is down.
  • Shared resources: a heavy database query can slow down the web pages because they fight for the same CPU and memory.
  • Cannot scale one part alone: to give the database more power you must upgrade the whole machine.

Interview questions and answers

What happens when you type a URL in the browser?
The browser asks DNS to translate the domain into an IP address, opens a connection to that IP, sends an HTTP request, the web server processes it (reading the database if needed) and returns HTML or JSON, and the browser shows it.
Why do mobile apps use JSON?
JSON is small, easy to read and supported in every language, so it keeps the data transfer light and fast on slow mobile networks.
Is a single server setup always bad?
No. It is a fine starting point for a small product. It becomes a problem only when traffic grows or when downtime becomes costly.
Who runs DNS and what happens if it is down?
It is mostly a third-party service. If DNS is down, new users cannot find your site even though your server is healthy, which is why many companies use more than one DNS provider.

🗄️Step 2 Database separation (web tier and data tier)

Hinglish samajh: Jab users badhte hain, sabse pehla kadam database ko alag server par rakhna hai. Ab web tier aur data tier alag hain, isliye dono ko apni zarurat ke hisaab se bada kiya ja sakta hai. Database do tarah ke hote hain: relational (MySQL, PostgreSQL) jisme tables aur joins hote hain, aur non-relational yaani NoSQL (DynamoDB, Cassandra, MongoDB, Redis). Jab tak saaf wajah na ho, relational se shuru karein. NoSQL tab lein jab bahut kam latency chahiye, data unstructured ho, sirf JSON jaisa data store karna ho, ya bahut zyada data ho.

When users start to grow, one server is not enough. The first, most natural fix is to give the database its own server. Now we have two groups of machines: the web tier, which handles traffic and runs the application, and the data tier, which only stores and returns data.

The big advantage is independence. If the website becomes slow because many people are browsing, you can add power to the web tier without touching the database. If the database is the slow part, you can improve only the database. Before the split, you could not do either without paying for both.

Next you must choose what kind of database to use. A relational database (SQL) such as MySQL, PostgreSQL or Oracle stores data in tables with rows and columns, and it can join tables together. It is very mature and has been trusted for over forty years, so it is the default choice for most businesses.

A non-relational database (NoSQL) such as DynamoDB, Cassandra, MongoDB, Redis or Neo4j does not use tables and joins in the usual way. NoSQL has four main families: key-value stores, graph databases, column stores and document stores. In general, joins are not supported in NoSQL.

So how do you choose? Start with relational unless you have a clear reason not to. Pick NoSQL when your application needs super-low latency, when your data is unstructured or has no relational shape, when you only need to serialize and deserialize data such as JSON, XML or YAML, or when you need to store a massive amount of data.

✨ Features

  • Two tiers, each with its own hardware and tuning.
  • Relational databases give tables, joins and strong consistency.
  • NoSQL databases give flexible shapes and easy horizontal growth.

✅ Benefits

  • Web and data tiers scale independently.
  • The database is no longer slowed down by web processing.
  • You can protect the database better, for example by keeping it in a private network.

⚠️ Problems

  • Every request now has a network hop to the database, so latency grows a little.
  • Still a single database: if it fails, the site fails.
  • Choosing the wrong database type early can be painful to change later.

Interview questions and answers

Why separate the database from the web server?
So each tier can scale on its own and one cannot starve the other of CPU or memory. It also lets you secure the database in a private network.
SQL or NoSQL, how do you decide?
Default to SQL. Choose NoSQL for very low latency, unstructured data, data that is just serialized (JSON), or a huge volume. You can also use both in one system.
Cross question: Does NoSQL mean no schema or no consistency?
Not exactly. Many NoSQL stores let you skip a fixed schema, and some offer weaker consistency by default, but it depends on the product and its settings. Always check the specific database.
What is the next risk after separating the database?
The database is now a single point of failure. That is why replication comes later in the chapter.

📈Step 3 Vertical scaling vs horizontal scaling

Hinglish samajh: Server par load zyada ho to do raste hain. Vertical scaling matlab ek hi server ko bada karna, jaise zyada CPU aur RAM lagana. Ye aasan hai par iski limit hoti hai aur ek server kharab hua to sab band. Horizontal scaling matlab zyada servers jodna. Isme limit nahi hoti aur ek server fail hone par baaki chalte rehte hain. Bade systems ke liye horizontal scaling behtar hai, par uske liye load balancer chahiye.

When a server is too busy, you have exactly two ways to give it more power. The first is vertical scaling, also called "scale up". You keep one server but make it bigger by adding more CPU, more memory or faster disks. It is like replacing your small car with a bigger truck.

Vertical scaling is simple, and for a low-traffic system it is a great choice. But it has two hard limits. First, there is a ceiling: you cannot add unlimited CPU and RAM to one machine. Second, a single bigger machine is still one machine, so if it breaks everything stops. It has no failover and no redundancy.

The second way is horizontal scaling, also called "scale out". Instead of making one server bigger, you add more servers to a pool. It is like adding more trucks to your fleet. If one truck breaks down, the others keep delivering.

Horizontal scaling is the right fit for large systems because there is no real upper limit and one failure does not stop everything. The price is complexity: you now need a way to decide which server handles which request, and that job belongs to a load balancer, which is our next topic.

Scale up vs scale out

PointVertical (scale up)Horizontal (scale out)
What you doMake one server biggerAdd more servers
LimitHardware ceilingPractically none
FailureSingle point of failureOthers keep working
ComplexityLowHigher (needs load balancer)

✨ Features

  • Vertical: bigger machine, no code change.
  • Horizontal: more machines, needs a load balancer.
  • Real systems usually do both: strong enough machines, and many of them.

✅ Benefits

  • Vertical is simple and needs no change in the application.
  • Horizontal has almost no upper limit.
  • Horizontal gives redundancy: one failure does not stop the service.

⚠️ Problems

  • Vertical has a hardware ceiling and its price rises steeply for the biggest machines.
  • Vertical has no failover. One machine, one risk.
  • Horizontal needs a load balancer and, often, stateless application design.

Interview questions and answers

When would you still choose vertical scaling?
When traffic is low, when the app is hard to run on many machines, or as a quick short-term fix. It is also common for databases at first, because splitting a database is hard.
Why is horizontal scaling preferred for big systems?
It has no hard ceiling and a failed machine does not take the service down. You also pay for many cheaper machines instead of one very expensive one.
Cross question: What must change in the app to scale out?
The web servers should be stateless, so any server can handle any request. Session data has to live outside the server. That is covered in the stateless web tier section.
What is auto scaling?
It is horizontal scaling done automatically: servers are added when load is high and removed when load is low, based on rules such as CPU use.

⚖️Step 4 Load balancer

Hinglish samajh: Jab web servers ek se zyada ho jate hain to load balancer chahiye. User sirf load balancer ke public IP se judta hai, aur load balancer request ko kisi healthy server tak bhejta hai. Servers private IP par hote hain, isliye internet unhe seedha nahi dekh sakta, jo security ke liye achha hai. Agar Server 1 band ho jaye to sara traffic Server 2 par chala jata hai. Traffic badhe to naya server jod do. Dhyan rahe: load balancer khud single point of failure ban sakta hai, isliye do ya zyada rakhte hain.

Once you have more than one web server, a new question appears: when a user arrives, which server should answer? If users connect directly to servers, one server may get all the traffic while another sits idle. And if a server goes down, users who were sent to it see an error.

A load balancer solves this. Think of the person at a restaurant door who looks at all the tables and sends each new group to a table that has space. Users connect to the load balancer's public IP address. The load balancer then forwards each request to one of the web servers, spreading the load evenly.

For better security, the servers behind the load balancer use private IP addresses. A private IP can only be reached between servers inside the same network, so the internet cannot call the web servers directly. Only the load balancer is exposed to the public.

This gives two big wins. First, redundancy: if Server 1 goes offline, the load balancer sends all traffic to Server 2, and the site stays up. Second, scalability: if traffic grows quickly, you just add more servers to the pool and the load balancer starts using them. The web tier is now healthy, but the data tier is still one database, which we will fix next.

How it works, step by step

  1. The user connects to the public IP address of the load balancer, not to a web server.
  2. The load balancer picks a healthy server using a rule such as round robin (take turns) or least connections.
  3. It forwards the request to the chosen server using that server's private IP address.
  4. The server replies, and the answer goes back to the user through the load balancer.
  5. If a server stops responding, the load balancer stops sending it traffic until it is healthy again.

✨ Features

  • Spreads traffic across servers using algorithms like round robin, least connections or IP hash.
  • Runs health checks so broken servers get no traffic.
  • Keeps servers on private IPs, which improves security.

✅ Benefits

  • No single web server failure can bring the site down.
  • Add or remove servers without telling the users.
  • Better response time because work is shared.

⚠️ Problems

  • The load balancer itself can become a single point of failure, so production setups run two or more of them.
  • It adds a small network hop and a cost.
  • Requests from the same user may land on different servers, so the app must be stateless (see the stateless section).

Interview questions and answers

What does a load balancer do?
It receives all incoming requests and distributes them across several servers so that no single server is overloaded, and it removes unhealthy servers from rotation.
Which balancing methods do you know?
Round robin (take turns), least connections (send to the least busy), IP hash (same client goes to the same server) and weighted variants for stronger servers.
Cross question: Is the load balancer a single point of failure?
It can be. To avoid that, run at least two load balancers (active-passive or active-active) or use a managed cloud load balancer that is already redundant.
Why private IPs for web servers?
Private addresses cannot be reached from the internet. Only the load balancer is public, so there is a smaller attack surface.
Layer 4 vs layer 7 load balancing?
Layer 4 routes using IP and port and is very fast. Layer 7 understands HTTP and can route by URL, header or cookie, which is more flexible.

🧬Step 5 Database replication

Hinglish samajh: Database replication matlab data ki copies alag servers par rakhna. Master sirf write leta hai (insert, update, delete) aur slaves sirf read karte hain. Zyadatar apps mein read zyada hote hain, isliye slaves ki sankhya zyada hoti hai. Isse speed badhti hai aur data safe rehta hai. Agar slave band ho jaye to read baaki slaves ya master par chale jate hain. Agar master band ho jaye to ek slave ko master bana diya jata hai. Dhyan rahe ki slave kabhi kabhi thoda peeche hota hai (replication lag), isliye naye master mein kuch data recover karna pad sakta hai.

Now the web tier has many servers, but there is still only one database. If it fails, all your data is unavailable. If it is busy, everything is slow. The fix is database replication: keeping copies of the same data on more than one database server.

The most common design is called master and slave (many teams now say primary and replica). The master database is the only one that accepts writes. Every insert, update and delete must go to the master. The slave databases receive a copy of the data from the master and serve only reads, such as SELECT queries.

Why this split? Most applications read far more than they write. A common ratio is many reads for each write. So it makes sense to have one master and several slaves. Reads run in parallel on different slaves, so queries become faster. Your data is also safer, because if one database is destroyed in a disaster, the others still hold copies, and you can even place them in different locations.

Failures are handled in a clear way. If there is only one slave and it goes offline, reads temporarily go to the master, and a new slave is created later. If there are many slaves and one goes offline, reads go to the healthy slaves and a replacement is created. If the master goes offline, one slave is promoted to be the new master and a new slave is added.

Promotion is not trivial. In a real system the slave you promote might be a little behind, because replication takes a moment. So its data may be missing the last few changes, and these have to be recovered with recovery scripts. Some teams use extra patterns such as multi-master or circular replication, but those are more complex.

How it works, step by step

  1. A write request (such as "save this order") is sent to the master. The master saves it.
  2. The master sends the change to each slave. This copy step is called replication.
  3. A read request (such as "show my orders") is sent to one of the slaves. The load is shared among them.
  4. If a slave dies, the other slaves keep answering and a new one is created.
  5. If the master dies, a slave is promoted to master and the system continues.

✨ Features

  • One master for writes, many slaves for reads.
  • Replication can be asynchronous (fast, may lag) or synchronous (safer, slower).
  • Slaves can live in different locations.

✅ Benefits

  • Better performance: reads run in parallel across many slaves.
  • Reliability: data is copied, so a disaster in one place does not destroy everything.
  • High availability: the site stays online if one database is offline.

⚠️ Problems

  • Replication lag: a slave may show old data for a short time right after a write.
  • Promotion risk: a promoted slave may miss the latest writes.
  • Write bottleneck: there is still one master, so heavy writes are not solved yet (that needs sharding).

Interview questions and answers

What is database replication and why use it?
It is keeping copies of the same data on several servers. We use it to get faster reads, better availability and protection against data loss.
What happens if the master goes down?
A slave is promoted to master, the application is pointed to it, and a new slave is added. Some recent writes may need to be recovered if the slave was behind.
Cross question: What is replication lag and how do you handle it?
It is the short delay before a slave receives a change. For data that must be fresh (for example a user's own profile just after saving), read from the master. For other data, a small delay is acceptable.
Does replication help with heavy writes?
No. All writes still go to the master. To scale writes you need sharding (split the data) or a different design.
Synchronous vs asynchronous replication?
Synchronous waits for the slave to confirm, which is safer but slower. Asynchronous does not wait, which is faster but may lose the last writes if the master fails.

⚡Step 6 Cache

Hinglish samajh: Cache ek tez, temporary storage hai jo memory mein data rakhta hai. Web server pehle cache dekhta hai. Agar data mil gaya (cache hit) to turant wapas, nahi mila (cache miss) to database se padhta hai, cache mein rakhta hai aur phir user ko deta hai. Isse database par load kam hota hai aur response tez hota hai. Dhyan rakhein: cache un data ke liye achha hai jo zyada padhe jate hain aur kam badalte hain. TTL lagayein, cache aur database ko sync rakhein, ek se zyada cache server rakhein, aur jab cache full ho to LRU jaisi policy se purane items hatayein.

A cache is a small, very fast temporary storage that keeps the results of expensive work so that the next request can reuse them. In our system, the cache holds data that was recently read from the database, in memory. Memory is far faster than a database that reads from disk, and it also takes work off the database.

Why is this needed? Every time a page loads, it may call the database several times. If a thousand people ask for the same popular product page, the database repeats the same work a thousand times. With a cache, the first request goes to the database and the result is stored. The next 999 requests are answered from memory in a fraction of the time.

The most common pattern is called read-through or cache-aside. After receiving a request, the web server first checks the cache. If the data is there (a cache hit), it returns it immediately. If it is not there (a cache miss), it queries the database, stores the result in the cache, and then returns it to the client.

Caching is powerful but needs some care. Think about five things. Use case: cache data that is read often but changed rarely, because cached data lives in memory and memory is limited. Expiration: give cached items a time to live (TTL); too short and the database is hit often, too long and the data becomes stale. Consistency: the database and the cache can go out of sync, because updating both is not done in one transaction, especially across regions.

Mitigating failures: one cache server is a single point of failure, so use several cache servers, ideally in different data centers, and leave extra memory as a buffer. Eviction policy: when the cache is full, something must be removed to make room. The most popular rule is LRU (least recently used), which removes the item that was used the longest time ago. Others are LFU (least frequently used) and FIFO (first in, first out).

How it works, step by step

  1. A request arrives at the web server asking for some data, for example a product.
  2. The web server looks in the cache. If found (hit), it returns the data straight away.
  3. If not found (miss), the web server reads the database.
  4. The web server stores the result in the cache with a TTL and returns it to the user.
  5. When the data changes, the cached copy is deleted or updated so users do not see old data.

✨ Features

  • Cache-aside, write-through and write-back are common patterns.
  • TTL (time to live) removes old items automatically.
  • Eviction policies like LRU free memory when the cache is full.

✅ Benefits

  • Much faster responses (memory instead of disk).
  • Less load on the database, so it can serve more users.
  • Cheap way to handle traffic spikes on popular content.

⚠️ Problems

  • Stale data: the cache may hold an old value after the database changes.
  • Cache stampede: when a popular item expires, many requests hit the database at the same moment.
  • Extra moving part: another server to run, monitor and keep available.

Interview questions and answers

What is a cache and when should you use it?
A cache is fast temporary storage, usually in memory. Use it when data is read often and changed rarely, for example product details, user profiles or configuration.
How do you keep the cache and database consistent?
Delete or update the cache entry whenever the database changes, and use a sensible TTL as a safety net. Perfect consistency is hard, so decide how much staleness the business can accept.
What is LRU?
Least Recently Used. When the cache is full, it removes the item that has not been used for the longest time, on the idea that it is least likely to be needed again.
Cross question: What is a cache stampede and how do you avoid it?
When a hot key expires, many requests miss at once and flood the database. Avoid it with staggered (randomized) TTLs, a lock so only one request refills the key, or by refreshing popular keys before they expire.
Where should the cache live?
On its own servers (for example Redis), not inside the web servers, so all web servers share it. Use several cache nodes to avoid a single point of failure.

🌍Step 7 Content Delivery Network (CDN)

Hinglish samajh: CDN duniya bhar mein phaile servers ka network hai jo images, CSS, JavaScript jaisi static files ki copy rakhta hai. User ko file sabse paas wale CDN server se milti hai, isliye page jaldi load hota hai aur aapke main server par load kam hota hai. Pehli baar file CDN ke paas nahi hoti, to wo origin se leta hai, TTL ke saath store karta hai, aur aage ke users ko seedha deta hai. Dhyan rakhein: cost, sahi expiry time, CDN band hone par fallback, aur file badalne par invalidate ya URL mein version lagana.

A CDN is a network of servers spread across the world that keeps copies of your static content: images, videos, CSS and JavaScript files. When a user asks for such a file, it is delivered by the CDN server closest to them instead of travelling all the way to your main server.

Distance matters. A user in Mumbai fetching an image from a server in Virginia must wait for the data to cross oceans, and the delay is longer the farther away they are. If the same image is served from a CDN server in Mumbai, it arrives much sooner. Your own web servers are also relieved from serving heavy files.

Here is the flow. User A asks for image.png using a CDN URL. If the CDN server does not have the file yet (a cache miss), it asks your origin server (or storage such as S3), receives the file, stores it with a TTL (set by the Cache-Control header), and returns it to User A. When User B asks for the same image, the CDN returns it straight from its cache until the TTL ends.

There are several things to plan for. Cost: CDNs are run by third parties and charge for data transfer in and out, so keep only content that is used often. Cache expiry: the time should be neither too long (stale files) nor too short (frequent trips to the origin). CDN fallback: if the CDN has an outage, clients should be able to request the file from the origin. Invalidating files: if you update a file before it expires, either use the vendor's invalidate API or add a version to the URL, such as image.png?v=2.

How it works, step by step

  1. User A requests https://cdn.mysite.com/logo.png. DNS sends the request to the nearest CDN server.
  2. The CDN server has no copy, so it asks the origin for the file.
  3. The origin returns the file with a Cache-Control: max-age header.
  4. The CDN stores the file and returns it to User A.
  5. User B asks for the same file. The CDN returns it from its own storage until the TTL ends.

Interview questions and answers

What is a CDN and what content should go on it?
A geographically distributed network that caches content near users. Put static, often-requested files on it: images, videos, CSS, JavaScript and downloads.
How do you update a file that is already cached on the CDN?
Call the vendor's invalidation API, or give the file a new version in its URL so it becomes a new cache entry.
Cross question: How is a CDN different from a cache like Redis?
A CDN sits close to users across the world and serves static files over HTTP. Redis sits inside your data center and stores application data for your servers. Different place, different purpose.
What if the CDN goes down?
Build a fallback so the page can load the file from the origin. Monitor the CDN and consider a second provider for critical sites.

🪶Step 8 Stateless web tier

Hinglish samajh: Web tier ko aasani se scale karne ke liye usse state (user ka session, cart wagairah) bahar nikalna padta hai. Stateful design mein user ka data ek server par hota hai, isliye usi server par request jaana zaroori hota hai. Stateless design mein session Redis, Memcached ya NoSQL jaise shared store mein rakha jata hai, to koi bhi server kisi bhi user ko handle kar sakta hai. Isse auto scaling aasan ho jati hai, server jodna ya hatana safe hota hai, aur ek server band hone par bhi koi user logout nahi hota.

To scale the web tier horizontally, we have to move something out of it: the state. State means information about the user that the server remembers between requests, such as who is logged in or what is in the shopping cart.

In a stateful architecture, the server remembers the user's data from one request to the next. Imagine User A's session is stored on Server 1. Every request from User A must go to Server 1. If it goes to Server 2, that server has never heard of User A and treats them as logged out. To avoid this, some load balancers use "sticky sessions", but that adds overhead and makes adding or removing servers harder.

In a stateless architecture, servers keep no user data. Session data is kept in a shared store outside the web tier, for example a relational database, Redis, Memcached or NoSQL. Any web server can read it when a request arrives. So User A's first request can go to Server 1, the next to Server 3, and everything still works.

The result is a web tier that is simple, robust and easy to scale. You can add servers when traffic rises and remove them when it falls, which is called auto scaling. The cloud can do this for you, adding machines when CPU use is high. A NoSQL store is a popular choice for shared session data because it scales easily.

How it works, step by step

  1. User A logs in. The server creates a session and writes it to the shared store.
  2. The next request from User A reaches any server, for example Server 3.
  3. Server 3 reads User A's session from the shared store using a session id from the cookie.
  4. Server 3 answers. Nothing was remembered inside the server.
  5. If traffic rises, auto scaling adds more servers. They work at once because they need no local data.

  • Session data lives in Redis, Memcached or NoSQL.

  • Simple horizontal scaling and auto scaling.
  • Better availability: if a server dies, no user loses their session.
  • Easier deployments and rolling updates.

  • The shared store is a new dependency and must itself be highly available.
  • Reading the session adds a small network call to each request.
  • Needs careful design, for example avoiding large data in the session.

Interview questions and answers

What is the difference between stateful and stateless servers?
A stateful server remembers client data between requests, so the same client must return to the same server. A stateless server remembers nothing; the state is kept in shared storage so any server can answer any request.
Why is stateless needed for auto scaling?
Because new servers can start and old ones can be removed at any moment without anyone losing data. If sessions were inside the servers, removing one would log users out.
Cross question: What about JWT tokens, are they stateless too?
Yes. A signed token carries the user info inside it, so the server needs no session store. The trade-off is that revoking a token before it expires is harder.
Are sticky sessions a good idea?
They work, but they weaken load balancing and make failures and scaling harder. Prefer a shared session store.

🏢Step 9 Multiple data centers

Hinglish samajh: Jab users puri duniya mein hon to ek data center kaafi nahi hota. Do data center rakhne se speed bhi badhti hai aur ek poora data center band hone par bhi service chalti rehti hai. GeoDNS user ki location dekhkar sabse paas wale data center ka IP deta hai. Agar ek data center fail ho jaye to saara traffic doosre par chala jata hai (failover). Mushkilein: traffic ko sahi jagah bhejna, data ko dono jagah sync rakhna, aur automated deployment se sab jagah ek jaisa code chalana.

As the product becomes international, one data center is no longer enough. Two reasons stand out. The first is speed: users far from the data center have slower responses. The second is availability: if a whole data center loses power, floods or fails, the product must stay online.

The usual approach is to run two or more data centers. In normal operation, users are sent to the closest one with geoDNS (geo-routed DNS). GeoDNS returns a different IP address depending on where the user is. For example, a user in the US east may be sent to the US-East data center and a user in Asia to the Asia data center, so traffic is split between them (for example 60% and 40%).

If one data center has a major outage, all the traffic is redirected to the healthy data center. This is called failover. Both data centers need to be capable of handling the full load, or at least the critical part of it.

Several technical problems must be solved. Traffic redirection: you need good tools such as geoDNS to direct users properly. Data synchronization: users in different regions may use different local databases or caches; when failover happens, traffic might go to a data center where the data does not exist. A common strategy is to replicate data across data centers. Test and deployment: with multiple data centers, it is essential to test the application at different locations, and to use automated deployment tools so all data centers run the same version.

How it works, step by step

  1. A user types the domain name. GeoDNS looks at where the user is.
  2. GeoDNS returns the IP of the nearest healthy data center.
  3. The user is served by that data center, which has its own full stack.
  4. Data is continuously replicated between data centers.
  5. If one data center fails, GeoDNS stops returning its IP and all users go to the other one (failover).

  • Each data center has a full stack of web, cache and data.

Interview questions and answers

Why would you run more than one data center?
For lower latency to users around the world, and for disaster recovery: the product keeps running if one site goes down.
What is geoDNS?
A DNS feature that returns different IP addresses based on where the request comes from, so users are directed to the nearest data center.
Cross question: How do you keep data consistent between data centers?
Replicate data between them. Writes may be accepted in one primary region or in several regions; both choices have trade-offs in speed and conflicts, so decide based on the product's needs.
How do you deploy safely to many data centers?
Use automated pipelines that roll out the same build to all data centers step by step, with tests and the ability to roll back.

📬Step 10 Message queue

Hinglish samajh: Message queue ek durable buffer hai jo producer aur consumer ko ek doosre se alag (decouple) karta hai. Producer message queue mein daal deta hai aur wait nahi karta; consumer baad mein message uthakar kaam karta hai. Jaise photo upload: web server turant "upload ho gaya" bol deta hai, aur workers background mein photo process karte hain. Queue lambi ho to workers badha do, khali ho to kam kar do. Dhyan rakhein: message do baar process ho sakta hai, isliye kaam idempotent banayein, aur retry ya dead-letter queue ka plan rakhein.

To scale further, we need to decouple the parts of the system, which means making them independent so that each can grow and fail without breaking the others. A message queue is the key tool for this.

A message queue is a durable component that stores messages until they are processed. It supports asynchronous communication, which means the sender does not wait for the receiver. The sender, called a producer or publisher, creates a message and puts it in the queue. A receiver, called a consumer or subscriber, connects to the queue and performs the work described by the message.

A simple example is photo processing. When a user uploads a photo, the app needs to crop, sharpen and blur it, which takes time. Without a queue, the user would wait while the web server does all this. With a queue, the web server just puts a "process this photo" message in the queue and immediately tells the user that the upload is done. Photo workers pick up the messages and process the photos in the background.

The producer and the consumer can be scaled independently. If the queue gets long, you add more workers. If the queue is nearly empty, you can remove workers to save money. And if the consumers are temporarily down, the producer can still publish messages, which wait safely in the queue until consumers return.

How it works, step by step

  1. The user uploads a photo. The web server saves the file and publishes a message to the queue.
  2. The web server immediately replies "upload received". The user is not kept waiting.
  3. A photo worker takes the message from the queue and processes the photo.
  4. When done, the worker acknowledges the message, and it is removed from the queue.
  5. If the queue grows too long, add more workers. If it is empty, remove some.

Interview questions and answers

What problem does a message queue solve?
It decouples the producer from the consumer and lets slow work run in the background, so users get quick replies and spikes do not overwhelm the system.
What if a worker crashes while handling a message?
The message is not acknowledged, so the queue gives it to another worker after a timeout. This means a message might be processed twice, so make handlers idempotent.
Cross question: What does idempotent mean here?
Doing the same work twice gives the same result as doing it once. For example, "set status to done" is idempotent, but "add 100 to balance" is not unless you guard it with a unique id.
Queue vs direct API call?
Use a direct call when the caller needs the answer now. Use a queue when the work can happen later or may take long.

📊Step 11 Logging, metrics and automation

Hinglish samajh: Jab system bada ho jata hai to har server ka log haath se dekhna mumkin nahi. Logging se errors ka record rehta hai, metrics se system ki sehat dikhti hai (host level, tier level aur business metrics jaise daily active users). Automation (CI/CD) se build, test aur deploy apne aap hota hai, jisse galtiyan kam hoti hain. Logs aur metrics se dekhte hain, automation se action lete hain. Alert aise banayein jo kaam ke hon, warna log unhe ignore karne lagte hain.

When a small site runs on one server, you can log in and read the log file. When the system grows into dozens of servers, it becomes impossible to do this manually. You need tools that collect information and help you act on it quickly.

Logging means recording errors and events. Logs tell you what went wrong and when. At scale you should collect logs from every server into one central place, where they can be searched easily. Metrics are numbers measured over time that show how healthy the system is and how the business is doing. There are three levels: host-level metrics (CPU, memory, disk I/O), aggregated-level metrics (for example the performance of the whole database tier or cache tier), and key business metrics (daily active users, retention, revenue).

Automation is the third part. When systems are big and complex, we need tools to reduce human error and save time. Continuous integration means every code change is built and tested automatically, so problems are found early. Automating build, test, deploy and scaling makes development faster and safer.

Together, these three give you eyes and hands: logs and metrics let you see, and automation lets you act. Without them, a large system is like driving a car with no dashboard and no steering assist. Set alerts too, so that you hear about problems before your users do.

🧩Step 12 Database scaling: vertical scaling and sharding

Hinglish samajh: Data bahut badhne par database scale karna sabse mushkil hota hai. Vertical scaling matlab ek database ko bada karna, jiski limit aur kharcha dono hote hain. Horizontal scaling ko sharding kehte hain: bade database ko chhote hisson (shards) mein baant dete hain. Har shard ka schema same hota hai par data alag. Sharding key sabse zaroori hai, jaise user_id, aur wo data ko barabar baantni chahiye. Dikkatein: resharding mushkil hai (consistent hashing se aasan hota hai), celebrity problem (ek shard par zyada load), aur shards ke beech joins mushkil hain, isliye data ko de-normalize karte hain.

As data keeps growing, the database tier becomes the hardest part to scale. There are two options, just like for the web tier. Vertical scaling means adding more power (CPU, RAM, disk) to a single database server. Some big databases run on very strong machines with hundreds of gigabytes of RAM. It is simple, but it has a hard limit, it is expensive, and it keeps a single point of failure.

Horizontal scaling of a database is called sharding. Sharding splits a huge database into smaller, easier-to-manage pieces called shards. Every shard has the same schema (the same tables and columns) but holds different data. For example, with a user table and a rule of user_id % 4, user 0, 4, 8 live in shard 0, users 1, 5, 9 live in shard 1, and so on. Each shard can have its own master and slaves.

The most important decision is the sharding key (also called a partition key). It is the column used to decide which shard holds a row, like user_id. A good key spreads data evenly. A poor key puts too much data on one shard, and that shard becomes a hot spot.

Sharding is powerful but brings real problems. Resharding: when one shard fills up, or the data is uneven, you need to move data and change the rule; a technique called consistent hashing makes this much easier. Celebrity (hotspot) problem: if one shard holds very popular users (like a celebrity with millions of followers), it can be overloaded; you may give such users their own shard or split them further. Joins and de-normalization: after sharding it is hard to join tables across shards; a common workaround is to de-normalize the data so queries can be answered from a single table.

How it works, step by step

  1. Choose a sharding key that spreads data evenly, for example user_id.
  2. Apply a rule or hash to the key to find the shard, for example user_id % 4.
  3. Send reads and writes for that user to that shard only.
  4. Watch shard sizes and load. When a shard is full or hot, reshard or rebalance.
  5. Avoid cross-shard joins by de-normalizing data or doing joins in the application.

Interview questions and answers

What is sharding?
Splitting a large database into smaller parts (shards) that share the same schema but hold different data, so the load and data volume are spread over many servers.
How do you choose a good sharding key?
It should spread data and traffic evenly, be present in most queries, and not change often. A high-cardinality key like user_id is usually better than a country code.
Cross question: What is the celebrity problem?
When a few keys (for example very popular users) get a huge share of reads or writes, their shard is overloaded. Fix it by giving them dedicated shards, splitting their data, or caching heavily.
How do you do joins after sharding?
Avoid cross-shard joins. De-normalize so the needed data sits together, or fetch from each shard and join in the application.
What is consistent hashing and why use it?
A way to map keys to servers on a ring so that adding or removing a server moves only a small part of the keys. It makes resharding far less painful than plain modulo.

🏁Step 13 Conclusion and the final architecture

Hinglish samajh: Ab sab kuch jod lete hain. User ki request GeoDNS se sahi data center tak jaati hai, static files CDN se aati hain, baaki requests load balancer ke through stateless web servers tak jaati hain. Web servers cache aur session store use karte hain, writes master par aur reads slaves par bhejte hain, aur dheere kaam queue ke zariye workers ko dete hain. Data bada ho to sharding hoti hai. Logs, metrics aur automation poore system par nazar rakhte hain. Yaad rakhein: web tier stateless rakho, har tier mein redundancy do, cache aur CDN use karo, multiple data centers rakho, database shard karo, aur har cheez ko monitor aur automate karo.

Let us put all the pieces together. A user's request first finds the right data center through geoDNS. Static files come from the CDN. Dynamic requests pass through a load balancer to a group of stateless web servers. The web servers read hot data from the cache, keep sessions in a shared store, send reads to database slaves, and send writes to the master. Slow tasks are handed to a message queue and processed by workers. The data tier is sharded when it grows too large. Logging, metrics and automation watch over everything.

You can learn the whole chapter in five rules. Keep the web tier stateless. Build redundancy at every tier so nothing is a single point of failure. Cache as much data as you can and use a CDN for static files. Support multiple data centers. Host static assets in a CDN and scale the data tier by sharding. And finally, split tiers into individual services, monitor the system, and automate what you can.

Remember that scaling is a continuous process. You will always find new bottlenecks, and each fix will bring new challenges. The skill is knowing the pain, picking the smallest solution that fixes it, and understanding the trade-offs. That is what makes a strong answer in a system design interview.

How it works, step by step

  1. Keep the web tier stateless.
  2. Build redundancy at every tier.
  3. Cache data as much as you can.
  4. Support multiple data centers.
  5. Host static assets in a CDN.
  6. Scale the data tier by sharding.
  7. Split tiers into individual services.
  8. Monitor your system and use automation tools.

✨ Features

  • Each block exists because of a specific pain.
  • No single point of failure is left.
  • Every tier scales on its own.

Interview questions and answers

Walk me through the architecture for a system that must serve millions of users.
Start with DNS and CDN, then a load balancer in front of stateless web servers. Add a cache and a shared session store. Use a master with read replicas for the database and shard it when it gets too large. Add a message queue and workers for slow jobs, deploy in multiple data centers, and finish with logging, metrics and automation.
Where is the next bottleneck after each step?
Single server: no redundancy. Database split: single database. Replication: master writes. Cache: consistency. CDN: invalidation. Multi-DC: data sync. Queue: duplicates. Sharding: joins and hotspots.
Cross question: What would you build first for a new product with 1000 users?
A single or two-tier setup with a managed database and backups. Add a load balancer and a second web server for availability, then add cache and a CDN only when metrics show the need.
How do you decide what to scale?
Measure. Look at metrics for CPU, memory, query time, cache hit rate and queue length, find the real bottleneck, and fix that part first.
