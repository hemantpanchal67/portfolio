AWS Lambda ☁️ λ

Complete handwritten-style notes · Basics → Triggers → Security → Monitoring → Interview

1. Introduction to AWS Lambda

AWS Lambda is Amazon's way of letting you run code without ever thinking about the machine it runs on. Normally, to run a program you must rent a server, install an operating system, keep it patched, decide how big it should be and pay for it around the clock. With Lambda you simply package your code as a function, tell AWS when it should run, and AWS does the rest. Think of it like a taxi instead of owning a car: you pay only for the ride, and you never worry about fuel, parking or servicing. Lambda was launched in 2014 and became the foundation of the whole serverless movement on AWS.

  • AWS Lambda = serverless, event-driven compute service (launched 2014)
  • You upload code (a function); AWS runs it when an event occurs
  • No server provisioning, no OS patching, no capacity planning
  • Supports Python, Node.js, Java, .NET, Ruby, Go (custom runtime), container images
  • Billing: only for requests + execution time — idle = ₹0 / $0

2. What is Serverless Computing?

Serverless computing is a cloud model where the provider takes full responsibility for servers, while you only deal with your application logic. The name is slightly misleading: servers definitely exist, you just never see, patch, scale or pay for them while they sit idle. The big shift is in how you are billed and how you scale: instead of renting capacity in advance and hoping you guessed right, capacity appears the moment an event arrives and disappears when the work is done. This makes serverless ideal for unpredictable or spiky workloads where traffic might be zero at night and thousands of requests per second during a sale.

  • Servers still exist! But AWS manages them, not you
  • You focus on code & business logic only
  • Key traits: no server management · auto-scaling · pay-per-use · built-in high availability
  • Other serverless services: S3, DynamoDB, API Gateway, SQS, SNS, Fargate, Step Functions

3. Features of AWS Lambda

Lambda's features can be grouped into three ideas. First, it runs by itself: automatic scaling, built-in high availability across multiple Availability Zones and pay-per-millisecond billing mean you never provision anything. Second, it connects to everything: over 200 AWS services can trigger it, and you can write functions in many languages or even ship a full container image up to 10 GB. Third, it helps you manage change: layers share common libraries, versions and aliases let you release safely and roll back, and features such as environment variables, VPC access, X-Ray tracing and SnapStart handle configuration, networking, debugging and speed.

  • Auto scaling (0 → 1000s)
  • Event-driven triggers (200+ services)
  • Multiple languages / runtimes
  • Pay-per-ms billing
  • Built-in fault tolerance (multi-AZ)
  • Layers (shared libraries)
  • Versions & Aliases
  • Container image support (10 GB)
  • Function URL (built-in HTTPS)
  • VPC, env variables, X-Ray, SnapStart

4. Benefits

The most visible benefit is cost: since you pay only while your code is actually running, a small internal tool that runs a few thousand times a month may cost nothing at all thanks to the free tier. The second benefit is scalability without effort: if one user or ten thousand users show up at once, Lambda simply creates more copies of your function to serve them. The third is speed of delivery, because developers skip server setup and go straight to writing business logic. Finally, operations become lighter: AWS patches the OS and runtime, replaces unhealthy hardware and spreads your function over multiple data centres, so your team spends time on features rather than maintenance.

5. Real-World Use Cases

In practice Lambda shines wherever work is triggered by something happening. A very common pattern is a serverless web API: a mobile app calls API Gateway, which invokes Lambda, which reads or writes DynamoDB. Another is file processing: when someone uploads a photo to S3, Lambda automatically creates thumbnails or scans the file. Lambda also handles real-time data such as clickstreams or IoT readings coming through Kinesis, scheduled jobs like a nightly report or cleanup (replacing cron servers), and automation such as stopping untagged EC2 instances or sending Slack alerts. The common thread is short, event-driven, independent pieces of work.

  • Serverless REST APIs (API Gateway + Lambda + DynamoDB)
  • Image/video processing on S3 upload (thumbnails)
  • Real-time stream processing (Kinesis, DynamoDB Streams)
  • Scheduled jobs / cron (EventBridge)
  • Chatbots & Alexa skills
  • ETL / data transformation
  • Notifications & email (SNS / SES)
  • Infra automation, security remediation, log processing

6. Event-Driven Architecture (EDA)

In a traditional design, component A directly calls component B and waits for it. In an event-driven design, A just announces that something happened (an event, such as "order placed" or "file uploaded") and anyone interested reacts to it. There are three roles: the producer that emits the event, the router (like EventBridge, SNS or SQS) that carries it, and the consumer that reacts, which is usually a Lambda function. Because producer and consumer do not know about each other, you can add, change or scale one without touching the other. Lambda fits this model perfectly because it sits idle at zero cost until an event wakes it up.

  • System reacts to events (state changes) instead of being called directly
  • Three parts: Event Producer → Event Router/Bus → Event Consumer
  • Loosely coupled, scalable, asynchronous
  • Lambda = typical consumer; S3 / API GW / SNS = producers

7. Execution Flow

The execution flow describes what happens from the moment an event occurs until you get a result. An event reaches the Lambda service, which first looks for an already-prepared (warm) execution environment for your function. If none is free it builds a new one: it downloads your code, starts the language runtime and runs any code outside the handler. Only then is your handler called with the event data. When the handler returns, the response goes back to the caller (or is discarded for async events), logs are shipped to CloudWatch, and the environment is paused so the next request can reuse it. Understanding this flow explains why the first request is slower than later ones.

  1. Event arrives (HTTP request, file upload, message…)
  2. Lambda service checks for a warm environment, else creates a new one
  3. Runtime starts, code loaded (cold start)
  4. Handler runs with event + context
  5. Result returned / logs sent to CloudWatch; environment frozen for reuse

8. Request Life Cycle (3 phases)

Every execution environment goes through three phases. Init happens once when the environment is created: Lambda downloads the code, starts the runtime and executes your static/global code, such as imports and creating database or SDK clients. Invoke is the phase that repeats: Lambda calls your handler with an event, and this can run many times in the same environment as long as it stays warm. Shutdown occurs when the environment has been idle for a while (or is being replaced) and Lambda terminates the runtime. The dotted arrow in the picture shows the key optimisation idea: warm requests skip Init completely, so put expensive one-time setup outside the handler.

  • Init phase is billed too (for most runtimes), max 10 s
  • Between invokes the env is frozen; /tmp and global vars persist while warm

9. Runtime Environment

The runtime environment is the sandbox your code actually runs in. Each one is a lightweight, isolated Firecracker microVM on Amazon Linux, so your function cannot see or interfere with other customers' functions. Inside it live the language runtime (for example Python 3.12), your code, any layers and optional extensions. You control memory (128 MB to 10 GB, with CPU and network power growing proportionally), the timeout (up to 15 minutes) and temporary disk in /tmp. An environment handles only one request at a time; if ten requests arrive together, Lambda starts ten environments. And because environments are disposable, treat your function as stateless and keep important data in S3 or a database.

  • Isolated sandbox (Firecracker microVM) on Amazon Linux
  • Contains: runtime (Python 3.12 etc.), your code, layers, extensions
  • Resources: memory 128 MB–10 GB (CPU ∝ memory), /tmp 512 MB–10 GB, timeout ≤ 15 min
  • Env vars available: AWS_REGION, AWS_LAMBDA_FUNCTION_NAME, credentials of execution role…
  • Stateless: one request per environment at a time — never rely on local state

10. Handler Function

The handler is the single function Lambda calls whenever an event arrives; it is the doorway into your code. You tell Lambda where it is using the format file.function, such as lambda_function.lambda_handler. Lambda passes two arguments: event, a JSON-like object containing the actual input (an HTTP request body from API Gateway, the bucket and key from S3, or the messages from SQS), and context, an object with information about the invocation, such as the request ID, function name and how many milliseconds remain before timeout. Whatever you return becomes the response for synchronous callers, while for asynchronous ones it is simply ignored. The structure of event depends entirely on which service triggered the function, so always print it once and inspect it.

  • Entry point AWS calls. Config format: filename.function → lambda_function.lambda_handler
  • event – JSON input (data from trigger) · context – runtime info (aws_request_id, get_remaining_time_in_millis(), memory limit)
  • Return value → response (sync) or ignored (async)
def lambda_handler(event, context):
    # business logic here
    return {"statusCode": 200, "body": "ok"}

11. Invocation Types

How a function is called changes how errors, retries and responses behave. In synchronous invocation the caller sends a request and waits for the answer, as with an API call from a browser; if it fails, the caller sees the error and must decide whether to retry. In asynchronous invocation the caller hands the event to Lambda, immediately receives an acknowledgement and moves on; Lambda queues the event internally and retries failures twice by itself, after which the event can go to a dead-letter queue. In poll-based invocation Lambda does the reaching out: an event source mapping continuously polls a queue or stream (SQS, Kinesis, DynamoDB Streams), collects records into a batch and invokes your function with that batch. Choosing the right model is a key design decision.

TypeHow it worksExamplesErrors / retries
SynchronousCaller waits for responseAPI Gateway, ALB, Function URL, CLI RequestResponseCaller must retry
AsynchronousLambda queues event, returns 202 immediatelyS3, SNS, EventBridge, Event invokeAuto retry 2× (configurable 0-2); DLQ / Destinations

Create Your Own Lambda

Steps to create a Lambda function

Creating a function through the console takes only a few minutes. Open the Lambda service and choose Create function, then pick Author from scratch so you start with an empty function. Give it a meaningful name, choose the runtime, and decide the permissions: by default AWS creates a basic execution role that lets the function write logs. After you press create you land in a code editor with a starter handler. Edit the code, press Deploy to save it, then create a test event and press Test to run it and see the output. Later you add triggers, environment variables and tighter permissions as the function matures.

  1. Sign in to AWS Console → search Lambda → Create function
  2. Choose Author from scratch (or blueprint / container image)
  3. Enter function name, e.g. HelloLambda
  4. Select runtime and architecture (x86_64 / arm64)
  5. Set permissions → create/choose execution role
  6. Click Create function → write code in editor
  7. Deploy → create Test event → Test → view logs

Runtime selection

The runtime is the language environment that executes your code, and picking it is mostly about your team's skills and the workload's needs. Python and Node.js start quickly and have huge ecosystems, making them the usual choice for APIs, glue code and automation. Java and .NET are powerful but start more slowly because of larger runtimes, which is why SnapStart exists. Go and Rust compile to fast native binaries and use a custom or OS-only runtime. You also choose an architecture: arm64 (Graviton) is typically cheaper and faster for the same work, while x86_64 is safer if your dependencies are compiled only for Intel. Always select a currently supported version, because AWS eventually deprecates old ones.

  • Pick by team skill + performance need: Python / Node.js (fast cold start, great for scripts/APIs), Java / .NET (heavier; use SnapStart), Go / Rust (custom runtime, very fast)
  • Architecture: arm64 (Graviton) ≈ 20% cheaper & faster; x86_64 for compatibility
  • Use a supported (non-deprecated) runtime version, e.g. Python 3.12

Function configuration

Besides code, a function's behaviour is shaped by its configuration. Memory is the main dial: more memory also gives more CPU, so a memory-hungry or CPU-heavy job may finish faster and sometimes even cost less. Timeout stops runaway executions; the default is only 3 seconds, so many beginners hit a timeout error until they raise it. The execution role defines what AWS resources the function may touch, while environment variables hold settings such as table names without changing code. Optional settings include a VPC (to reach private databases), concurrency limits, layers and destinations or a DLQ for failures. Change one setting at a time and watch the effect in the logs.

Deploy and Test

Deploy and test form the daily development loop. Deploy publishes your edited code to the working copy of the function (called $LATEST); in the console you must click it, otherwise your changes are not live. For bigger projects you package a zip or container image and deploy it with the CLI, SAM, CDK, Terraform or a CI/CD pipeline. Testing means creating a JSON test event that imitates real input and running it; the console then shows the returned value, the log output and a summary line with duration, billed duration and memory used. Read that summary after each test: it tells you immediately if memory or timeout is set badly.

  • Deploy = saves & publishes code to $LATEST (console editor). For zip/container: upload via console, CLI, SAM, CDK, Terraform
  • Test = create a JSON test event → run → see Execution result, Log output, billed duration, memory used
  • CLI test: aws lambda invoke --function-name HelloLambda out.json

Sample Python Lambda Code

The sample below is a complete, minimal function. It imports json and sets up a logger at module level, so that work is done only once per environment. The handler reads an optional name from the incoming event (using a default so it never crashes on missing data), logs the whole event for debugging, and returns a dictionary with statusCode, headers and body. That exact shape is what API Gateway expects when Lambda is used as a web API. Note that the body must be a string, so we call json.dumps. We also return the request ID from the context object, which is very useful when tracing a specific call in the logs.

import json
import logging

logger = logging.getLogger()
logger.setLevel(logging.INFO)

def lambda_handler(event, context):
    logger.info("Event: %s", json.dumps(event))
    name = event.get("name", "World")

    return {
        "statusCode": 200,
        "headers": {"Content-Type": "application/json"},
        "body": json.dumps({
            "message": f"Hello, {name}!",
            "request_id": context.aws_request_id
        })
    }

A. Lambda Triggers

1. API Gateway

API Gateway is the front door that turns HTTP requests into Lambda invocations. A client (browser or mobile app) calls a URL such as /orders; API Gateway checks authentication, throttles abusive traffic, optionally caches the answer and then calls your function synchronously, packaging the method, headers, path and body into the event. Your function must reply with a statusCode, headers and string body, which API Gateway converts back into an HTTP response. It comes in REST, HTTP (cheaper, simpler) and WebSocket flavours. Remember its 29-second maximum integration timeout, so long jobs should be done asynchronously.

  • Exposes Lambda as REST / HTTP / WebSocket API. Synchronous
  • Use: web/mobile backends, microservices. Supports auth (Cognito, IAM, JWT), throttling, caching
  • Needs Lambda proxy response: {statusCode, headers, body}

2. Amazon S3

S3 can notify Lambda whenever something happens to an object, such as ObjectCreated when a file is uploaded or ObjectRemoved when one is deleted. This is an asynchronous trigger: S3 hands over the event and does not wait. The event contains the bucket name and object key, and your function then downloads the file with the SDK and does the work, such as resizing an image, parsing a CSV into a database or scanning for malware. A classic beginner mistake is writing the output back into the same bucket and prefix that triggers the function, which creates an endless loop and a huge bill; use a separate bucket or prefix filter.

  • Events: ObjectCreated, ObjectRemoved… Asynchronous
  • Use: image resize, virus scan, CSV → DB. Avoid writing back to same bucket/prefix (infinite loop!)

3. DynamoDB Streams

A DynamoDB stream is an ordered log of every change (insert, modify, remove) made to a table for 24 hours. Lambda polls that stream through an event source mapping and delivers the changes in batches, keeping order per item. This lets you react to data changes without touching the application that writes them: send a welcome email when a user item is inserted, keep a search index or aggregate table up to date, or record an audit trail. Each record can include the old and new image of the item. If your function keeps failing on a batch, the stream can get stuck, so configure retries, batch bisecting and an on-failure destination.

  • Captures item changes (INSERT / MODIFY / REMOVE) in order. Poll-based
  • Use: audit trails, replication, aggregates, triggers on data change

4. Amazon EventBridge

EventBridge is a serverless event bus: events from AWS services, your own applications or SaaS partners flow into it, and rules match the events by pattern and send them to targets such as Lambda. For example, a rule can say "when an EC2 instance changes state to stopped, invoke this function". It also supports schedules using cron or rate expressions, which makes it the modern way to run a function every hour or every morning. Invocation is asynchronous, and you can add retry policies and a DLQ. Its big strength is decoupling: producers just publish, and new consumers can be added later without any change to them.

  • Serverless event bus: rules match events (AWS services, SaaS, custom apps) → target Lambda. Async
  • Also scheduled cron / rate rules and EventBridge Scheduler

5. Amazon SNS

SNS (Simple Notification Service) uses the publish/subscribe model. A publisher sends one message to a topic, and SNS pushes a copy to every subscriber: Lambda functions, SQS queues, email addresses, HTTP endpoints or mobile devices. When Lambda is the subscriber, SNS invokes it asynchronously. This fan-out pattern is perfect when one event must trigger several independent actions, for example "order placed" notifying billing, inventory and email functions at the same time. If you also need buffering and controlled processing speed, put an SQS queue between SNS and Lambda.

  • Pub/Sub topic → fan-out to many subscribers (Lambda, SQS, email). Async
  • Use: notifications, alerts, broadcasting one event to many functions

6. Amazon SQS

SQS is a managed message queue that holds work until something processes it. With Lambda, you create an event source mapping and Lambda polls the queue for you, reading messages in batches and invoking the function. If the function succeeds, the messages are deleted; if it fails, they become visible again after the visibility timeout and are retried, eventually moving to a dead-letter queue after a set number of attempts. SQS therefore acts as a shock absorber that protects downstream systems like databases from traffic spikes. Set the queue's visibility timeout to at least six times your function timeout, and use partial batch responses so one bad message does not force the whole batch to be retried.

  • Message queue; Lambda polls and processes in batches (up to 10,000 w/ batching window for standard)
  • Use: decouple & buffer traffic. Set visibility timeout ≥ 6× function timeout, add DLQ, use partial batch response

7. CloudWatch Events → EventBridge

CloudWatch Events was the older service for scheduled and event-based rules. AWS evolved it into EventBridge, which uses the same underlying API but adds custom event buses, SaaS integrations, schema registry and better filtering, so in current documentation you will see EventBridge everywhere. In interviews it is fine to say "CloudWatch Events, now Amazon EventBridge". Typical uses remain the same: run a function on a schedule such as cron(0 9 * * ? *) for 9 AM daily, react to an EC2 state change, or respond to a CloudTrail API call or CloudWatch alarm. Existing rules continue to work and appear inside EventBridge.

  • CloudWatch Events was renamed/replaced by EventBridge (same API, more features)
  • Use: cron jobs (cron(0 9 * * ? *)), react to EC2 state change, CloudTrail events, alarms

AWS Lambda – Security 🔐

1. IAM Roles & Permissions

Security in Lambda answers two separate questions: who is allowed to run my function, and what is my function allowed to do. Both are handled through AWS Identity and Access Management (IAM), using roles and policies written in JSON. Everything is denied by default, so you must explicitly allow each action. Keeping these two questions apart is the key to understanding the rest of this section: one is controlled by a resource-based policy on the function, the other by the function's execution role.

  • Lambda security has 2 sides: who can invoke / manage the function and what the function can access
  • Both controlled by IAM (roles + policies)

2. Execution Role

The execution role is the identity your function uses when it talks to other AWS services. When the function starts, Lambda assumes this role on its behalf and hands the code short-lived credentials, which the AWS SDK picks up automatically, so no access keys are ever stored in code. The role has a trust policy that says "the Lambda service may assume me" and one or more permission policies that list the allowed actions. At minimum it needs permission to write logs to CloudWatch (AWSLambdaBasicExecutionRole); beyond that you add exactly what the function needs, such as reading one DynamoDB table. The most common error you will see is AccessDeniedException, which almost always means the execution role is missing a permission.

  • IAM role the function assumes at runtime (trust policy: lambda.amazonaws.com)
  • Gives temporary credentials via env variables → used by SDK calls (S3, DynamoDB…)
  • Minimum needed: AWSLambdaBasicExecutionRole (write logs to CloudWatch)
  • Add AWSLambdaVPCAccessExecutionRole for VPC, AWSXRayDaemonWriteAccess for tracing
Trust policy:
{ "Effect":"Allow",
  "Principal":{"Service":"lambda.amazonaws.com"},
  "Action":"sts:AssumeRole" }

3. IAM Policies

A policy is a JSON document made of statements, and each statement has an Effect (Allow or Deny), the Actions covered, the Resources they apply to and optional Conditions. AWS managed policies are ready-made and convenient for common cases but are often broader than necessary. Customer managed policies are ones you author and reuse across roles, with version history. Inline policies live inside a single role and disappear with it. The evaluation rule is simple but important: an explicit Deny always wins, otherwise an explicit Allow is required, and anything else is denied implicitly.

  • AWS managed – prebuilt by AWS (e.g. AWSLambdaBasicExecutionRole)
  • Customer managed – your own reusable, versioned policies
  • Inline – embedded in one role only (tight 1:1 coupling)
  • Identity-based policies attach to roles/users: “this identity can do X on Y”
{ "Effect":"Allow",
  "Action":["dynamodb:GetItem","dynamodb:PutItem"],
  "Resource":"arn:aws:dynamodb:ap-south-1:123456789012:table/Orders" }

4. Resource-Based Policies

While the execution role controls outbound access, a resource-based policy controls inbound access: it is attached to the Lambda function itself and lists which principals may invoke it. When you add an S3 trigger in the console, AWS quietly adds a statement to this policy allowing s3.amazonaws.com to call lambda:InvokeFunction for that bucket. It is also how you let another AWS account call your function. Always add a condition such as AWS:SourceArn so that only your specific bucket or topic can invoke it, and not any bucket belonging to someone else (preventing the "confused deputy" problem).

  • Attached to the Lambda function itself – says who may invoke it
  • Used to allow S3, SNS, API Gateway, EventBridge or another account to call the function
  • Add with console trigger or aws lambda add-permission
{ "Effect":"Allow",
  "Principal":{"Service":"s3.amazonaws.com"},
  "Action":"lambda:InvokeFunction",
  "Condition":{"ArnLike":{"AWS:SourceArn":"arn:aws:s3:::my-bucket"}} }

5. Least Privilege Principle

Least privilege means giving an identity exactly the permissions required to do its job and nothing extra. Imagine a hotel keycard that opens only your room instead of a master key: if the card is lost, damage is limited. For Lambda, that means a separate role per function, listing specific actions (for example dynamodb:PutItem rather than dynamodb:*) and specific resource ARNs rather than "*". If a function is ever compromised through a vulnerable library or malicious input, tight permissions limit what an attacker can reach. A good workflow is to start with very little, run the function, read the AccessDenied errors and add only what is truly needed.

  • Give only the permissions needed, nothing more
  • One role per function · specific actions (no "*") · specific resource ARNs · add Conditions
  • Review with IAM Access Analyzer; start narrow & widen if needed

6. Security Tips

Beyond IAM there are several habits that keep Lambda safe. Never put passwords or API keys in code or plain environment variables; fetch them from Secrets Manager or Parameter Store and encrypt with KMS. Treat every event as untrusted input and validate it, since API calls or queue messages can contain anything. Attach a function to a VPC only when it must reach private resources, and use VPC endpoints so traffic to AWS services stays on the AWS network. Turn on CloudTrail to audit who changed or invoked functions, keep libraries up to date, and protect public endpoints with authorizers, throttling and AWS WAF.

  • Never hardcode secrets → use Secrets Manager / SSM Parameter Store; encrypt env vars with KMS
  • Separate role per function; use aws:SourceArn/SourceAccount conditions (avoid confused deputy)
  • Put functions in a VPC only if needed (private resources); use VPC endpoints
  • Enable CloudTrail for API audit; sign & validate code with Code Signing
  • Keep dependencies & runtime updated (scan for CVEs); validate all input events
  • Protect API Gateway endpoints (authorizers, WAF, throttling); Function URL with AWS_IAM auth

7. Permission Flow Diagram

Read the diagram left to right. When an event source (for example S3 or API Gateway) tries to invoke the function, AWS first checks the function's resource-based policy to see whether that caller is allowed. If yes, the function runs and assumes its execution role, receiving temporary credentials from STS. Whenever the code then calls another service, such as reading from S3 or writing to DynamoDB, IAM checks whether the role's identity policies allow that exact action on that exact resource. If a check fails, or an explicit deny is present, the call returns AccessDenied. So two independent gates exist: one to get in, and one to reach out.

IAM Roles and Permissions

1. IAM Role for Lambda

An IAM role is an identity without a password or permanent keys; it is meant to be assumed temporarily by a trusted entity. For Lambda, the role has two parts. The trust policy says which entity may assume it, which here is the Lambda service. The permissions policy says what that entity can do once it has assumed the role. When you create a function in the console, AWS can generate a role for you automatically with log permissions; for production you normally create the role yourself, attach only the policies needed and reference its ARN when creating the function.

  • Role = identity with no password/keys; assumed temporarily by a trusted entity
  • For Lambda: Trust policy (who can assume = Lambda service) + Permissions policy (what it can do)
  • Console auto-creates a basic role when you create a function – then add permissions
  • CLI: aws iam create-role → attach-role-policy → use ARN in create-function --role

2. IAM Policy Types

Different policy types exist because permissions are needed at different levels. Identity-based policies (AWS managed, customer managed and inline) are attached to roles or users and say what they can do. Resource-based policies are attached to a resource and say who can use it. Permissions boundaries set a ceiling on what a role could ever be granted, which is useful when developers are allowed to create their own roles. Service control policies in AWS Organizations are guardrails at account level, for example to block usage of certain regions. The effective permission is the combination of all of these, and a deny anywhere overrides allows elsewhere.

AWS Lambda – Monitoring & Logging 📊

1. Overview

Once a function is deployed, you need to know whether it is healthy, fast and cheap. Lambda integrates automatically with CloudWatch for logs and metrics, and optionally with X-Ray for traces. Logs tell you what happened inside a particular execution, metrics tell you how the function behaves in aggregate (how many errors, how long runs take), and traces show where time is spent across multiple services. Used together with alarms, they let you detect problems before users complain and find the cause quickly.

  • Lambda automatically sends logs, metrics to CloudWatch; traces to X-Ray (if enabled)
  • 3 pillars: Logs (what happened) · Metrics (how much) · Traces (where/why slow)

2. Amazon CloudWatch Logs

Anything your function writes to standard output, such as print or a logger call, is captured and sent to a CloudWatch log group named /aws/lambda/<function-name>. Each execution environment writes to its own log stream. Lambda also adds three special lines: START, END and a REPORT line showing duration, billed duration, memory size, memory used and init duration, which is the first place to look when tuning. By default logs are kept forever and you pay for storage, so set a retention period. Emit logs as structured JSON and use Logs Insights to search and aggregate them with a SQL-like query language.

  • Log group /aws/lambda/<function-name> → log streams per environment
  • print() / logger output goes here. Special lines: START, END, REPORT (duration, billed duration, memory used, init duration)
  • Logs Insights to query; set retention (default never expires → cost!); use structured JSON logs; metric filters for alarms
fields @timestamp, @message
| filter @message like /ERROR/
| sort @timestamp desc | limit 20

3. CloudWatch Metrics

Lambda publishes metrics without any setup. Invocations counts how often the function ran, Errors counts failed runs, Duration shows how long runs take (watch the p95/p99 rather than only the average), and Throttles counts requests rejected because concurrency limits were reached. ConcurrentExecutions shows how many copies are running at once, and IteratorAge shows how far behind a stream consumer is. The real power comes from alarms: for example, trigger an SNS notification when Errors exceed a threshold in five minutes, or when Throttles are greater than zero.

MetricMeaning
InvocationsNumber of times function ran
ErrorsInvocations that failed (exception/timeout)
DurationExecution time (avg / p95 / p99 / max)
ThrottlesRejected due to concurrency limit
ConcurrentExecutionsParallel runs now
IteratorAgeLag for stream sources (Kinesis/DDB)
DeadLetterErrors / AsyncEventAgeFailed async deliveries
  • Create Alarms on Errors, Throttles, Duration → notify via SNS

4. AWS X-Ray

Logs show events inside one function, but modern applications span many services. X-Ray adds distributed tracing: when you enable active tracing, each request gets a trace ID that follows it from API Gateway through Lambda to DynamoDB or other downstream calls. The console draws a service map and a timeline of segments, so you can see, for instance, that the function itself takes 20 ms but the call to an external API takes 900 ms. Add the X-Ray SDK to automatically trace boto3 and HTTP calls, and ensure the execution role has permission to send trace data.

  • Distributed tracing: enable Active tracing (needs xray permission)
  • Shows service map, segments & subsegments (Init, Invocation, downstream calls) → find bottleneck
  • Use aws_xray_sdk to trace boto3/HTTP calls

5. Error Tracking

Errors in Lambda come in several flavours, and each needs a different fix. Unhandled exceptions are bugs in code; timeouts mean the function ran longer than allowed; out-of-memory errors mean the memory setting is too low; throttling means concurrency limits were hit; and permission errors point to IAM. How the error surfaces depends on the invocation type: a sync caller receives it directly, async events are retried and then sent to a DLQ or destination, and poll-based sources retry the batch. Track them using the Errors metric with alarms, search logs for the stack trace, and always configure a place for failed events to land so nothing is lost silently.

  • Types: handled errors (your try/except) · unhandled exceptions · timeouts · out-of-memory · throttling · permission (AccessDenied)
  • Track with: Errors metric + alarms, Logs Insights, X-Ray, DLQ / on-failure destination, CloudWatch Lambda Insights
  • Sync: error returned to caller · Async: retried then DLQ · Poll: retried until success / record expires

6. Debugging Best Practices

Good debugging starts before something fails. Log the incoming event and the request ID, using structured JSON and never writing secrets or personal data. When a failure happens, read the REPORT line first: was the duration equal to the timeout, or was memory used equal to the memory limit? For AccessDenied errors, check the execution role before touching code. You can reproduce issues on your laptop with sam local invoke and a saved test event, and use X-Ray to find slow calls. Use versions and aliases so a bad release can be rolled back instantly, and pass a correlation ID between services so one request can be followed end to end.

  • Log the event and aws_request_id (use structured JSON logs; mask secrets/PII)
  • Reproduce locally with SAM CLI (sam local invoke) and saved test events
  • Check REPORT line: timeout? memory maxed? Check IAM errors first for AccessDenied
  • Use X-Ray to find slow downstream calls; use correlation IDs across services
  • Use versions/aliases to roll back quickly; set correct log level via env var

7. Monitoring Architecture Diagram

This diagram shows how the pieces connect. The Lambda function sits in the middle and automatically emits three streams of information: logs to CloudWatch Logs, metrics to CloudWatch Metrics and, if enabled, traces to X-Ray. Metrics feed alarms, which send notifications through SNS to email, Slack or a paging tool. 8. Performance Factors

Lambda performance depends on a handful of settings and behaviours. Cold starts add delay to the first request in a new environment, so reduce package size and initialisation work, or remove them with Provisioned Concurrency or SnapStart. Memory also controls CPU, so increasing it often shortens duration and can lower total cost; use the AWS Lambda Power Tuning tool to find the sweet spot. Timeout should be just above the worst-case runtime and below any caller's timeout. Reserved concurrency guarantees and caps the number of parallel runs for one function, protecting both the function and downstream systems, while provisioned concurrency keeps pre-warmed environments ready for steady low latency at an extra price.

FactorExplanation & tip
Cold StartDelay creating new environment + init code. Reduce: smaller package, lighter deps, arm64, init clients outside handler, SnapStart, Provisioned Concurrency, avoid heavy VPC setups (now improved w/ Hyperplane ENI)
Memory Allocation128 MB–10 GB; CPU & network scale with memory. More memory can reduce duration and cost → test with AWS Lambda Power Tuning
Timeout1 s–15 min (default 3 s). Set just above expected max duration; must be < caller timeout (API GW 29 s) and SQS visibility timeout < …
Reserved ConcurrencyGuarantees & caps concurrency for a function (free). Protects downstream DB and ensures capacity; 0 = disable function
Provisioned ConcurrencyPre-initialised warm environments → no cold start for predictable latency. Costs extra even when idle; use with aliases / autoscaling
Account default concurrency = 1000/region (can request increase). Burst scaling: +1000 envs per 10 s per function.

9. Cost Optimization Tips

Lambda cost is requests multiplied by duration multiplied by memory, so every optimisation attacks one of these. Reduce duration by reusing connections, caching data in globals or /tmp and running independent calls in parallel. Tune memory to the cheapest point (more memory is sometimes cheaper because the run is shorter). Reduce requests by batching records from SQS or Kinesis and by using event filtering so unneeded events never invoke the function. Choose arm64 for roughly 20% savings, set log retention so CloudWatch does not become your biggest cost, use provisioned concurrency only where latency demands it, and guard against recursive loops with reserved concurrency and budgets.

  • Right-size memory with Power Tuning · use arm64 (Graviton) (~20% cheaper)
  • Reduce duration: reuse connections, cache in /tmp / globals, avoid unnecessary waits
  • Batch records (SQS/Kinesis batch size) to cut invocations
  • Filter events at source (event filtering) so Lambda isn't invoked for unwanted events
  • Set CloudWatch log retention & log level · avoid Provisioned Concurrency unless needed
  • Use Compute Savings Plans · avoid recursive loops · set timeouts and reserved concurrency as guard rails

10. AWS Lambda Pricing

Pricing has two main components. You pay a small fee per million requests, and you pay for duration measured in GB-seconds: the memory configured, in gigabytes, multiplied by the execution time in seconds (billed per millisecond). A generous monthly free tier of one million requests and 400,000 GB-seconds means many small workloads are effectively free. Extras include provisioned concurrency, extra ephemeral storage and data transfer. The worked example below shows that a function with 512 MB running 200 ms a million times uses just 100,000 GB-seconds, which fits entirely inside the free tier.

  • Requests: ~$0.20 per 1M requests
  • Duration: per ms × memory (GB-seconds), x86 ≈ $0.0000166667 per GB-s; arm64 cheaper
  • Free tier (every month): 1M requests + 400,000 GB-seconds
  • Extra: Provisioned Concurrency, ephemeral storage > 512 MB, data transfer, SnapStart restore (Java)
Cost = (requests × price/req) + (GB × seconds × price/GB-s)
Ex: 512 MB (0.5 GB), 200 ms, 1M calls
 = 0.5 × 0.2 × 1,000,000 = 100,000 GB-s → free-tier covered!

(Prices approximate – check the AWS pricing page for your region.)

11. Performance Optimization Flow Chart

Use the flow chart as a troubleshooting routine whenever a function is slow or expensive. First look at the REPORT line and X-Ray to identify where time goes. If the Init duration is high, you have a cold-start problem; if the main duration is long, the code or its downstream calls are slow; if you see timeouts or out-of-memory, the resources are wrong. Apply the matching fix, then check whether throttling or an overloaded database is the real bottleneck, in which case use reserved concurrency, an SQS buffer or RDS Proxy. Finally re-test, compare latency and cost, and repeat; optimisation is a loop, not a one-off.

12. Best Practices & Key Concepts

This section collects the habits that separate a demo function from a production one. Security means least privilege and no hardcoded secrets. Reliability means handling errors on purpose, retrying safely and making sure that processing the same event twice does no harm. Performance means smart memory settings and reusing connections. Operations means logging, alarms and safe deployments with versions and aliases. Read the lists below as a checklist before releasing any function.

Security best practices

Security is built in layers: give each function a tightly scoped role, keep secrets out of code and encrypt configuration, validate every event and keep dependencies patched. No single measure is enough, but together they make an attack hard and limit its impact.

  • Least-privilege role per function · secrets in Secrets Manager · KMS-encrypted env vars
  • Validate input, patch dependencies, enable CloudTrail, VPC only when needed

Error handling

Decide for each failure whether it is something the caller should know about (return a clear 4xx/5xx), something Lambda should retry (raise the exception) or something to park for later (send to a DLQ). Swallowing exceptions with a bare try/except makes Lambda believe the run succeeded, so the event is lost.

  • Use try/except; log with context; raise for real failures so Lambda can retry/DLQ
  • Return proper status codes for API (4xx client, 5xx server); don’t swallow exceptions
  • Configure DLQ / on-failure destination; for SQS use batchItemFailures (partial batch response)

Retry mechanism

Each invocation type retries differently, and knowing which is crucial. Because retries and duplicates are normal (delivery is at-least-once), write functions so that running them twice with the same event has the same result, for example by using a unique ID and conditional writes.

InvocationRetry behaviour
SyncNo auto retry – caller (client / API GW) must retry
Async2 retries (1 min, then 2 min wait); max event age 6 h; then DLQ/destination
SQSMessage reappears after visibility timeout; after maxReceiveCount → DLQ
Kinesis / DDB StreamsRetries the batch until success or data expires (blocks shard!) → configure max retry, bisect, on-failure dest
Make functions idempotent – retries / duplicates WILL happen (at-least-once delivery).

Common Mistakes ❌

Most real-world Lambda problems come from a short list of avoidable mistakes. Scan this list and compare with your own functions; fixing even two or three of them usually removes most cost surprises and outages.

  • Admin / * permissions on the role
  • Timeout too low (3 s default) or memory too low
  • Creating SDK clients / DB connections inside the handler each time
  • Recursive trigger loop (S3 → Lambda → same bucket) → huge bill
  • Hardcoded secrets · storing state in /tmp or globals
  • Opening too many DB connections (use RDS Proxy) · no log retention · ignoring DLQ
  • Huge deployment packages · using $LATEST in production (use versions + aliases)
  • Long-running (>15 min) work in Lambda → use Step Functions / Fargate / Batch

13. Top AWS Lambda Interview Questions & Answers

Q1. What is AWS Lambda? A serverless, event-driven compute service that runs code in response to events and auto-manages the infrastructure; billed per request & duration.
Q2. What is a cold start? How to reduce it? Extra latency when a new execution environment is created (download code + start runtime + init). Reduce with Provisioned Concurrency, SnapStart, smaller packages, lighter runtimes (Python/Node), arm64, avoiding heavy init.
Q3. Max timeout, memory, package size? 15 min; 128 MB–10,240 MB; 50 MB zipped / 250 MB unzipped (10 GB container image).
Q4. Sync vs async vs poll-based invocation? Sync: caller waits (API GW). Async: queued, 202 returned, 2 retries (S3, SNS). Poll-based: Lambda polls SQS/Kinesis/DDB Streams in batches.
Q5. Execution role vs resource-based policy? Execution role = what Lambda can access. Resource-based = who can invoke Lambda.
Q6. Reserved vs Provisioned concurrency? Reserved = guaranteed + capped capacity, no cost. Provisioned = pre-warmed environments to avoid cold starts, extra cost.
Q7. How does Lambda scale? Creates a new environment per concurrent request (burst then +1000 per 10 s) up to the account/function concurrency limit; excess is throttled (429).
Q8. Is Lambda stateless? How to persist data? Yes. Use S3, DynamoDB, RDS, ElastiCache, EFS. /tmp is only temporary cache.
Q9. How to connect Lambda to a VPC resource / internet? Configure VPC subnets + security group; for internet access put it in a private subnet with NAT Gateway; use VPC endpoints for AWS services.
Q10. What are Layers? Zip archives with shared libraries/code/data attached to functions (max 5 layers, total ≤ 250 MB unzipped).
Q11. Versions and aliases? Version = immutable snapshot; alias = named pointer (prod/dev) that can shift traffic weights between versions (canary).
Q12. How to handle failures? try/except, retries, DLQ (SQS/SNS), on-failure destinations, idempotency, alarms.
Q13. How are you billed? Requests + GB-seconds (memory × duration, 1-ms granularity), plus extras like provisioned concurrency.
Q14. When NOT to use Lambda? Long-running (>15 min) jobs, steady high-throughput workloads (cheaper on containers/EC2), special hardware/GPU, ultra-low latency needs.
Q15. How to give Lambda access to a DB without hardcoding credentials? Secrets Manager/SSM + IAM role; IAM database auth; RDS Proxy for connection pooling.
Q16. Lambda vs EC2? Lambda: event-driven, no servers, auto scale, short tasks. EC2: full control, long-running, custom OS, pay while running.

15. Lambda Lifecycle Summary

The big picture ties everything together. You create the function, configure its role, memory and timeout, and connect a trigger. When the first event arrives, an environment is initialised and the handler is invoked; later events reuse the warm environment until it is idle and is shut down. Throughout, logs, metrics and traces flow to CloudWatch and X-Ray, and you use them to optimise cost and speed. Then you repeat: update the code, publish a new version, shift the alias and watch the metrics.

  • Create → Configure (role, memory, timeout) → Trigger → Init → Invoke → (Freeze/Reuse or Shutdown) → Monitor via logs/metrics/traces → Optimize

16. Important AWS Services Used with Lambda

Lambda rarely works alone; it is the glue between other services. API Gateway, S3, SNS, SQS, EventBridge, Kinesis and DynamoDB Streams start it; DynamoDB, S3, RDS and SES are what it often works with; Step Functions orchestrates multiple functions into workflows; IAM, KMS and Secrets Manager secure it; CloudWatch, X-Ray and CloudTrail observe it; and CloudFormation, SAM and CDK deploy it. Knowing which service plays which role lets you design a complete serverless architecture from only a few building blocks.

  • API Gateway – HTTP APIs
  • S3 – object storage events
  • DynamoDB – NoSQL + Streams
  • SQS / SNS – queue & pub-sub
  • EventBridge – event bus / schedule
  • Kinesis – streaming data
  • Step Functions – orchestration
  • IAM / KMS / Secrets Manager – security
  • CloudWatch / X-Ray / CloudTrail – observability
  • RDS Proxy / VPC – DB connectivity
  • Cognito – auth · SES – email
  • CloudFormation / SAM / CDK – deploy
