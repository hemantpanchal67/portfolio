1. What is .NET Core?

.NET is a free, open-source, cross-platform development platform from Microsoft for building almost any kind of application, such as websites, web APIs, cloud services, desktop programs, mobile apps, games and command line tools. The name .NET Core was first used for the rewritten, cross-platform version that appeared in 2016. Since .NET 5 the word "Core" has been dropped and it is simply called .NET, but many people, books and job descriptions still say ".NET Core", which is why this course uses both names for modern .NET.

A .NET application is made of three things that work together. The first is a language, most commonly C#, in which you write your code. The second is a runtime, called the Common Language Runtime or CLR, which compiles your program to machine code while it runs, manages memory with a garbage collector and takes care of threads and exceptions. The third is a large set of libraries, known as the Base Class Library, which already contain things like collections, file handling, networking, JSON, cryptography and HTTP so you do not have to write them yourself. On top of these sit frameworks such as ASP.NET Core for web applications and Entity Framework Core for databases.

Because everything compiles to a common intermediate format, the same application can run on Windows, Linux and macOS, and on processors such as x64 and ARM64. This is the reason .NET is now a very common choice for services that run inside Docker containers and Kubernetes clusters in the cloud.

The smallest .NET program

// Program.cs  (top-level statements, no Main method needed since C# 9)
Console.WriteLine("Hello from .NET!");
dotnet new console -n Hello      # create a project
cd Hello
dotnet run                       # compile and run

The smallest web API

var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapGet("/", () => "Hello, web!");
app.MapGet("/greet/{name}", (string name) => new { message = $"Hello, {name}" });   // returned as JSON

app.Run();

With only these few lines you already have a fast web server (Kestrel), routing, dependency injection, configuration and logging, because the WebApplication builder sets all of them up with sensible defaults.

2. History, Versions & Support Policy

To understand the names you will meet in interviews, it helps to know the story. In 2002 Microsoft released the .NET Framework, which only ran on Windows and was installed as part of the operating system. It powered classic ASP.NET, Windows Forms and WPF applications for many years. In 2016 Microsoft released .NET Core 1.0, a complete rewrite that was open source, modular, much faster and able to run on Linux and macOS. Alongside them lived .NET Standard, a specification that let library authors target many platforms with one build, and Mono/Xamarin for mobile.

This created confusion, so in 2020 Microsoft merged everything into a single platform called .NET 5 and skipped the number 4 to avoid being mistaken for the older Framework. Since then a new version arrives every November. Versions with an even number, such as .NET 6, 8 and 10, are Long-Term Support (LTS) releases that get patches for about three years, while the odd numbered versions are Standard-Term Support (STS) releases with a shorter support window (the exact length has been changed by Microsoft, so check the official support policy page before you plan an upgrade).

3. Key Features

Modern .NET has a long list of features, but they fall into a few easy groups. Knowing these groups lets you answer the common interview question "Why is .NET Core better than .NET Framework?" with a clear and structured answer.

First, the platform is cross-platform and open source. The runtime, the libraries, the compiler (Roslyn) and ASP.NET Core are developed in the open on GitHub, and you can build and run on Windows, Linux and macOS, including inside lightweight Docker images. Second, it is high performance. ASP.NET Core with the Kestrel server consistently ranks near the top of independent web framework benchmarks, because of asynchronous I/O, a tiered JIT compiler, Span<T> for allocation free code and constant optimization work in every release.

Third, it is modular and lightweight. You add only the packages you need through NuGet, instead of carrying the whole framework. Fourth, it has built-in dependency injection, configuration, logging and options, so even a small project starts with good architecture habits. Fifth, it provides a unified programming model, where MVC controllers, minimal APIs, Razor Pages, Blazor, SignalR and gRPC share the same pipeline, hosting and security system.

Sixth, it supports side-by-side versioning, meaning different applications on one machine can run different .NET versions without conflict, and an app can even bundle its own runtime (self-contained deployment). Seventh, it is cloud and container ready, with first class support for Docker, Kubernetes, health checks, OpenTelemetry and .NET Aspire. Finally, the tooling is excellent: the dotnet command line, Visual Studio, VS Code, JetBrains Rider, hot reload and a very rich debugger.

4. Benefits

Why do companies choose .NET? The first benefit is developer productivity. C# is a modern, expressive language with excellent tooling, so teams write less code and find mistakes early. IntelliSense, refactoring, the debugger and hot reload make everyday work fast, and the strong type system acts like a safety net during large refactorings.

The second benefit is performance and cost savings. Because the runtime is fast and memory efficient, the same traffic can often be served with fewer servers than with many other stacks, and this directly lowers cloud bills. The third is scalability: asynchronous programming, a stateless web layer and good support for caching and messaging let applications scale out horizontally.

The fourth is security and reliability. Microsoft publishes regular security patches, ASP.NET Core ships with protections such as anti-forgery tokens, the Data Protection API and HTTPS defaults, and the type system and garbage collector remove whole classes of memory bugs. The fifth is a mature ecosystem: hundreds of thousands of NuGet packages, strong libraries for every common task, long-term support releases for enterprises and a very large community.

The sixth benefit is versatility with one skill set. A developer who knows C# can build a web API, a background worker, a desktop app, a mobile app with .NET MAUI, a game with Unity or a machine-learning feature with ML.NET. Finally, there is enterprise and cloud integration: first-class support for Azure, but also for AWS and Google Cloud, plus excellent interoperability with SQL Server, Active Directory and Microsoft 365.

5. Problems, Limitations & How to Handle Them

No technology is perfect, and a good engineer can explain the weak points honestly. The most common complaint is breaking changes between versions. Moving from .NET Framework to modern .NET, or even from one major version to another, can need code changes because some APIs, such as System.Web, WCF server, Web Forms and AppDomains, are not available or work differently. The remedy is to upgrade regularly in small steps, use the Upgrade Assistant and analyzers, and cover the code with tests before upgrading.

A second problem is the learning curve and size of the ecosystem. A beginner meets many terms at once: SDK, runtime, middleware, dependency injection, async and EF Core. The remedy is to learn in a sensible order and build small projects. A third issue is cold start and memory use in serverless and container settings. The JIT compiler needs time to warm up, which can be noticeable in short-lived functions. ReadyToRun, tiered compilation and Native AOT help, but AOT places limits on reflection and some libraries.

Fourth, there are async pitfalls. Blocking on tasks with .Result or .Wait() can starve the thread pool and produce slow or hanging services, and forgetting to await a task silently hides errors. Fifth, EF Core can be misused: N+1 queries, loading entire tables and leaving change tracking on for read-only queries all hurt performance. Sixth, some libraries and tools remain Windows centric, for example parts of WPF, WinForms and certain COM based or GDI+ APIs, so cross-platform code must be checked with the platform compatibility analyzer.

Seventh is ecosystem churn and licensing changes: popular third-party libraries sometimes change their license or go commercial (this has happened with several well known .NET packages), so teams should review dependencies and have alternatives. Eighth, the garbage collector can cause pauses if the code allocates heavily or keeps large caches, which is solved by measuring, pooling buffers and tuning GC settings. Finally, there is a perception that .NET is only for Windows or only for enterprises, which is no longer true but still influences hiring in some regions.

8. How .NET Works: Compilation, CLR, JIT & AOT

When you press run, several things happen. First the Roslyn compiler reads your C# files and produces an assembly, a .dll file that contains Intermediate Language (IL) and metadata. IL is not machine code, it is a CPU-independent set of instructions, which is why the same file can run on Intel, AMD and ARM processors. Second, the Common Language Runtime (CLR) starts, its loader reads the assembly and its dependencies, and the JIT (Just-In-Time) compiler translates each method from IL into machine code the first time the method is called.

Modern .NET uses tiered compilation. A method is first compiled quickly with little optimization (tier 0) so that the application starts fast. If the method turns out to be called often, the runtime recompiles it with heavy optimization (tier 1), and with dynamic PGO it can even use measured run-time information, such as which type is most common at a call site, to generate better code. The result is that applications are fast at startup and become faster as they warm up.

For scenarios where startup time matters, there are two ahead-of-time options. ReadyToRun precompiles the IL into native code but keeps the JIT for tiering and dynamic code. Native AOT compiles everything into one self-contained native executable without a JIT, which starts in milliseconds and uses little memory, but it requires code that is friendly to trimming, meaning it avoids unrestricted reflection and runtime code generation. Source generators, for example for JSON serialization, make popular libraries AOT-friendly.

10. C# Essentials for Interviews

C# is a statically typed, object-oriented language that also supports functional ideas. Almost every .NET interview begins with the language itself, so this lesson explains the ideas you must be comfortable with and shows each in a short example.

Types. C# has value types (int, double, bool, struct, enum) that hold their data directly, and reference types (class, interface, delegate, array, string) that hold a reference to an object on the heap. Assigning a value type copies the data, assigning a reference type copies the reference. Boxing happens when a value type is converted to object, which allocates on the heap and should be avoided in hot code. Strings are immutable, so use StringBuilder for many concatenations.

Object-oriented ideas. Encapsulation hides data behind properties and methods, inheritance lets a class reuse another, polymorphism lets a base reference call derived behaviour through virtual and override, and abstraction exposes only what is needed through abstract classes and interfaces. An interface defines a contract with no state, while an abstract class can hold shared code and state. Since C# 8, interfaces may also have default method bodies.

Modern features. Records give immutable, value-equal data types. Pattern matching with switch expressions makes branching concise. Nullable reference types make the compiler warn when a value could be null. LINQ lets you query collections declaratively. Generics create type-safe reusable code, with constraints such as where T : class, new(). Extension methods add methods to existing types. Delegates, events and lambdas pass behaviour around. Tuples and deconstruction return several values.

11. Memory Management & Garbage Collection

In .NET you do not free memory by hand. The garbage collector (GC) finds objects that nothing can reach any more and reclaims their memory. Local variables of value types and the references themselves live on the stack, which is fast and automatically cleaned when a method returns, while objects live on the managed heap. Allocating on the heap is very cheap, because the runtime only moves a pointer, but the cost comes later when the GC has to clean up.

The heap is split into generations because most objects die young. New objects start in Generation 0. When Gen 0 fills up, a quick collection removes the dead ones, and the survivors are promoted to Generation 1 and later to Generation 2, which holds long-lived data like caches and singletons. A full collection of Gen 2 is expensive, so good .NET code avoids creating lots of long-lived garbage. Objects of 85,000 bytes or more go to the Large Object Heap (LOH), which is collected only with Gen 2 and is not compacted by default, so repeatedly allocating big arrays is a classic performance problem.

The GC only knows about memory. Resources such as files, sockets and database connections are unmanaged resources, and objects that hold them implement IDisposable. Calling Dispose, preferably through a using statement, releases them immediately instead of waiting for the GC. A finalizer is a last-resort safety net that runs non-deterministically, so it should be avoided unless you directly own native handles, and then you should use SafeHandle.

Server applications normally use server GC with concurrent (background) collection to give high throughput with short pauses. Memory leaks can still happen in managed code when objects stay reachable by mistake, for example through static collections that grow forever, event handlers that are never unsubscribed, or caches without an expiry.

// IDisposable with using: connection returned to the pool deterministically
await using var conn = new SqlConnection(cs);
await conn.OpenAsync();

// The full dispose pattern (only when you own unmanaged resources)
public sealed class NativeBuffer : IDisposable
{
    private IntPtr _ptr = Marshal.AllocHGlobal(1024);
    private bool _disposed;
    public void Dispose() { if (_disposed) return; Marshal.FreeHGlobal(_ptr); _disposed = true; GC.SuppressFinalize(this); }
    ~NativeBuffer() => Dispose();
}

12. Async / Await, Tasks & Threading

Web servers spend most of their time waiting for databases, files and other services. In synchronous code a thread would sit blocked during that wait, so a server with 100 threads could serve only 100 slow requests at a time. Asynchronous code with async and await releases the thread while the operation is in progress and picks the work up again when it finishes, so a small number of threads can serve thousands of requests. Importantly, async does not make a single request faster, it makes the server scale better.

When the compiler sees an async method, it rewrites it into a state machine. At each await on an incomplete task, the method saves its state, registers the rest of the method as a continuation and returns an incomplete Task to its caller. When the awaited operation completes, the continuation is scheduled on a thread pool thread and the method continues where it left off. Exceptions are captured in the task and rethrown at the await, so normal try/catch works.

A few rules help avoid bugs. Use async all the way from the controller down to the database call, and never block with .Result or .Wait(). Avoid async void except for event handlers. Accept a CancellationToken and pass it along so work stops when the client disconnects. Use Task.WhenAll to run independent operations concurrently, and use Task.Run only for CPU-bound work, not for I/O. In ASP.NET Core there is no synchronization context, so ConfigureAwait(false) is optional in application code but still good practice in reusable libraries.

public async Task<OrderSummary> GetSummaryAsync(int id, CancellationToken ct)
{
    // start both calls first, so they run at the same time
    var orderTask    = _db.Orders.AsNoTracking().FirstAsync(o => o.Id == id, ct);
    var customerTask = _http.GetFromJsonAsync<CustomerDto>($"customers/by-order/{id}", ct);

    await Task.WhenAll(orderTask, customerTask);                     // total time = slowest call, not the sum
    return new OrderSummary(orderTask.Result, customerTask.Result!); // Result is safe: tasks are already complete
}

13. Dependency Injection & Service Lifetimes

Dependency Injection (DI) is a way of giving a class the things it needs, instead of letting the class create them itself. A class declares what it needs through its constructor, usually as interfaces, and a container provides matching objects. This makes code loosely coupled, easy to test with fake implementations, and easy to change by editing one registration. ASP.NET Core has a built-in container, so every controller, middleware and background service can use DI without extra libraries.

Every registration has a lifetime. A singleton is created once and shared by the whole application, so it must be thread-safe. A scoped service is created once per scope, which in a web app means once per HTTP request, and is the right choice for DbContext. A transient service is created every time it is requested. The golden rule is that a service may only depend on services with the same or a longer lifetime. If a singleton holds a scoped service you get a captive dependency, where the scoped object lives far too long, and the framework can detect this when scope validation is on in development.

public interface IClock { DateTime UtcNow { get; } }

15. Hosting, Program.cs & Kestrel

An ASP.NET Core application is really a console application that starts a host. The host is an object that owns the application's resources: the dependency injection container, configuration, logging, hosted background services and the web server. Since .NET 6 the minimal hosting model puts everything into one short Program.cs file with top-level statements, where WebApplication.CreateBuilder sets up good defaults and builder.Build() creates the app.

The program has two clear phases. In the service registration phase you add services to builder.Services, and in the pipeline configuration phase you add middleware and map endpoints on the built app. After app.Run() the application listens for requests until it is stopped. On shutdown, the host signals cancellation to background services and waits for in-flight requests to finish, which is called graceful shutdown and is very important in Kubernetes.

Kestrel is the web server that listens on the network. It is cross-platform, supports HTTP/1.1, HTTP/2 and HTTP/3, uses asynchronous I/O and is fast enough to be used directly on the internet, although it is normally placed behind a reverse proxy or load balancer for TLS, caching and protection. On Windows you can also host inside IIS (in-process is fastest), and HTTP.sys is an alternative server for Windows-only scenarios.

The environment, read from the ASPNETCORE_ENVIRONMENT variable, is usually Development, Staging or Production. It selects which appsettings file is loaded and turns development helpers on or off, such as the detailed error page and Swagger.

16. The Middleware Pipeline

Middleware are small pieces of code that form a chain. Each piece receives the HttpContext and a next delegate. It can do work before calling next, which is on the way in, then call next to pass control to the following middleware, and do more work after it returns, which is on the way out. A middleware can also decide not to call next at all, which is called short-circuiting, for example when static files answer a request or when authentication fails with 401.

Order matters because the registration order is the execution order. Exception handling goes first, so it can catch errors from everything after it. HTTPS redirection and static files come early, because they are cheap and can finish the request. Routing selects the endpoint, then CORS, authentication and authorization act on it, and finally the endpoint runs. If you place UseAuthorization before UseAuthentication, nobody can ever be authorized because nobody has been identified yet.

There are three ways to build the pipeline: app.Use adds middleware that can call next, app.Run adds a terminal middleware that ends the pipeline, and app.Map branches the pipeline for a path. You can write middleware as an inline lambda, as a class with an InvokeAsync method, or as a class implementing IMiddleware. Services with scoped lifetime must be taken as parameters of InvokeAsync and not in the constructor, because the middleware instance is created only once.

// 1) inline middleware: measure how long each request takes
app.Use(async (context, next) =>
{
    var sw = Stopwatch.StartNew();
    await next(context);                                    // everything after this runs on the way out
    app.Logger.LogInformation("{Method} {Path} -> {Status} in {Ms} ms",
        context.Request.Method, context.Request.Path, context.Response.StatusCode, sw.ElapsedMilliseconds);
});

// 2) class-based middleware: correlation id
public class CorrelationIdMiddleware(RequestDelegate next)
{
    private const string Header = "X-Correlation-Id";

    public async Task InvokeAsync(HttpContext ctx, ILogger<CorrelationIdMiddleware> log)     // scoped services go here
    {

        using (log.BeginScope(new Dictionary<string, object> { ["CorrelationId"] = id }))
            await next(ctx);
    }
}

17. Routing, Minimal APIs & Controllers

ASP.NET Core offers two main styles for building APIs. Minimal APIs map a URL and an HTTP method directly to a small function, which gives very little ceremony and is great for microservices and small services. Controllers are classes decorated with attributes, which provide structure, filters and conventions that suit large APIs with many endpoints. Both use the same endpoint routing system, run on the same pipeline, and can live side by side in one project.

Routing works in two steps. UseRouting inspects the URL and HTTP method and selects an endpoint; the selected endpoint carries metadata such as [Authorize] that later middleware can read; and the endpoint middleware finally runs it. Route templates can contain parameters and constraints, for example /orders/{id:int} or /files/{**path}.

18. Model Binding, Validation, Filters & API Design

Model binding converts parts of the HTTP request into method parameters. By default simple types are read from the route or query string, and complex types are read from the JSON body. You can be explicit with [FromRoute], [FromQuery], [FromHeader], [FromBody], [FromForm] and [FromServices]. Never bind directly to your database entities, because attackers can then set fields they should not, which is called over-posting. Use separate DTO (data transfer object) classes for input and output.

Validation checks that the data is acceptable. Simple rules use DataAnnotations attributes, and richer rules use FluentValidation. With [ApiController], an invalid model automatically produces a 400 response in the standard ProblemDetails format (RFC 7807), so clients always get a predictable error shape.

Filters are hooks that run around controller actions and minimal API endpoints. There are authorization filters, resource filters, action filters, exception filters and result filters, and they run in that order. Use them for concerns that need to know about the action, such as validation, caching headers or auditing, while middleware is better for concerns that apply to every request.

19. Authentication & Authorization (JWT, Identity, Policies)

Authentication answers "who are you?" and authorization answers "what may you do?". In ASP.NET Core both are handled by middleware and are configured through authentication schemes such as cookies (for server-rendered sites), JWT bearer tokens (for APIs) and OpenID Connect (for single sign-on with an identity provider). The result of authentication is a ClaimsPrincipal in HttpContext.User, which holds claims, which are statements about the user such as name, email, role or scope.

Modern systems avoid storing passwords in each API. The client signs in at an identity provider (Microsoft Entra ID, Auth0, Keycloak, Duende IdentityServer and similar) using OAuth 2.0 / OpenID Connect, preferably the Authorization Code flow with PKCE for browser and mobile apps. The provider returns a short-lived JWT access token. The client sends it in the Authorization: Bearer header, and the API validates its signature, issuer, audience and expiry without calling the provider each time. A longer-lived refresh token is used to obtain new access tokens quietly.

For authorization, policy-based rules are the most flexible way. A policy is a named set of requirements, for example "the user must have the scope orders.write and be over 18". You can also do resource-based checks in code, for example to verify that an order belongs to the current user, which prevents a common vulnerability called insecure direct object reference (IDOR).

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)

20. Entity Framework Core & Data Access

Entity Framework Core is an object-relational mapper (ORM). You describe your tables as C# classes called entities, work with them through a DbContext, and write queries using LINQ. EF Core translates the LINQ to SQL, executes it, and turns the rows back into objects. It also tracks the changes you make to those objects and, when you call SaveChanges, creates the necessary INSERT, UPDATE and DELETE statements inside a single transaction. This pattern is called the unit of work.

Entities can be configured with attributes or, preferably, with the Fluent API inside OnModelCreating. Migrations record each change to the model as a code file, so the database schema can be created and upgraded in a controlled way. Relationships (one-to-many, many-to-many, one-to-one) are described with navigation properties. Loading related data can be done with Include (eager), explicit loading, or lazy loading, which is convenient but is a common cause of the N+1 query problem.

21. Caching, Compression, Rate Limiting & Health Checks

ASP.NET Core ships with several features that improve speed and resilience without extra libraries. Caching avoids repeating expensive work. IMemoryCache stores objects in the memory of one server, which is the fastest but not shared between instances. IDistributedCache with Redis is shared by all instances. HybridCache (new in .NET 9) combines an in-memory first level with a distributed second level and protects against cache stampedes. Output caching stores whole responses and response caching follows HTTP cache headers.

23. Error Handling & Observability

Failures will happen, so a good application handles them in a consistent and safe way. The recommended approach for APIs is a global exception handler that logs the exception once, hides internal details from users and returns a standard ProblemDetails JSON response with an appropriate status code. Expected problems, such as "order not found" or "validation failed", should be handled locally and returned as normal results, instead of being thrown as exceptions, because exceptions are slow and make control flow hard to follow. The Result pattern is a popular way to model such expected failures.

builder.Services.AddProblemDetails();
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();
app.UseExceptionHandler();

public class GlobalExceptionHandler(ILogger<GlobalExceptionHandler> log) : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(HttpContext ctx, Exception ex, CancellationToken ct)
    {
        log.LogError(ex, "Unhandled exception for {Path}", ctx.Request.Path);
        var (status, title) = ex switch
        {
            NotFoundException        => (404, "Resource not found"),
            ValidationException      => (400, "Validation failed"),
            OperationCanceledException => (499, "Client closed request"),
            _                        => (500, "An unexpected error occurred")
        };
        ctx.Response.StatusCode = status;
        await ctx.Response.WriteAsJsonAsync(new ProblemDetails { Status = status, Title = title, Instance = ctx.Request.Path }, ct);
        return true;
    }
}

// Result pattern for expected failures
public readonly record struct Result<T>(T? Value, string? Error) { public bool Ok => Error is null; }

24. Testing: Unit, Integration & Test Doubles

Automated tests let you change code with confidence. The test pyramid says to have many fast unit tests for business logic, fewer integration tests that check several parts together with a real database or HTTP pipeline, and only a few slow end-to-end tests through the UI. The common frameworks are xUnit (the default choice for .NET), NUnit and MSTest. Use Moq, NSubstitute or FakeItEasy to create test doubles: a stub returns fixed data, a mock checks that a call happened, and a fake is a simple working replacement such as an in-memory repository.

25. Performance Tuning

The first rule of performance work is measure before you optimize. Use profilers and tools such as BenchmarkDotNet for micro-benchmarks, dotnet-counters and dotnet-trace for live systems, and Application Insights or OpenTelemetry for production. Most real slowness comes from the database and network, not from C# code, so check queries, indexes, round trips and payload sizes first.

Within the application, the biggest wins are usually: using async I/O properly so threads are not blocked, adding caching for repeated work, fixing N+1 queries and using projections and AsNoTracking, reusing connections with HttpClientFactory, paginating large lists and enabling response compression. In hot code paths, reduce allocations, because every allocation will eventually cost GC time. Use Span<T> and Memory<T> for slicing without copying, ArrayPool<T> for buffers, StringBuilder or interpolated string handlers instead of repeated concatenation, structs and ValueTask where measurements show a benefit, and source-generated serializers and logging to avoid reflection.

26. Security Best Practices

Security must be designed in from the start. ASP.NET Core provides good defaults, but you still have to use them correctly. Start with the OWASP Top 10 list of common web risks and think in layers, which is called defence in depth.

Injection attacks, such as SQL injection, are prevented by always using parameterized queries, which LINQ and FromSqlInterpolated do for you. Cross-site scripting (XSS) is prevented because Razor and Blazor encode output by default, so never write raw HTML from user input and consider a Content Security Policy header. Cross-site request forgery (CSRF) affects cookie based sites and is prevented with anti-forgery tokens; token based APIs are less exposed. Broken access control is prevented by checking authorization on the server for every request, including ownership of the resource. Sensitive data must be protected in transit with HTTPS and HSTS and at rest with encryption, and secrets such as keys and connection strings belong in Key Vault or a secret manager, never in source control.

// HTTPS + HSTS + security headers
app.UseHsts(); app.UseHttpsRedirection();
app.Use(async (ctx, next) =>
{
    ctx.Response.Headers["X-Content-Type-Options"] = "nosniff";
    ctx.Response.Headers["X-Frame-Options"] = "DENY";
    ctx.Response.Headers["Content-Security-Policy"] = "default-src 'self'";
    ctx.Response.Headers["Referrer-Policy"] = "no-referrer";
    await next();
});

27. Clean Architecture & Project Structure

As an application grows, the biggest risk is that business rules get tangled with web, database and framework code. Clean Architecture (also known as onion or hexagonal architecture) solves this by arranging the code in concentric layers with one strict rule: source code dependencies point only inward. The innermost Domain layer knows nothing about anything else. The Application layer uses the domain and defines interfaces for things it needs from the outside world. The outer Infrastructure and Presentation layers depend on the application, and they implement or call those interfaces.

The practical benefit is that the business logic can be tested without a database or a web server, and technologies can be replaced with little effort: moving from SQL Server to PostgreSQL only touches the infrastructure project. This works because of the Dependency Inversion Principle: the application declares IOrderRepository, the infrastructure implements it, and the DI container connects the two in the composition root, which is Program.cs.

├─ Shop.Domain            (no references)             Order, Money, OrderPlaced event
├─ Shop.Application       → Domain                    PlaceOrderHandler, IOrderRepository, validators
├─ Shop.Infrastructure    → Application               ShopDb (EF Core), OrderRepository, EmailSender
└─ Shop.Api               → Application, Infrastructure   endpoints, DI wiring, auth

    {
        if (Status != OrderStatus.Draft) throw new DomainException("Only draft orders can be changed.");
        if (qty <= 0) throw new DomainException("Quantity must be positive.");
        _lines.Add(new OrderLine(sku, qty, price));
    }

}

Domain-Driven Design (DDD) adds vocabulary for modelling the business: entities have identity, value objects are compared by value, an aggregate is a cluster of objects changed as one unit through its aggregate root, and bounded contexts mark the borders where a word such as "customer" has one meaning. Vertical slice architecture is an alternative that organizes code by feature, putting the endpoint, handler, validator and data access for one use case together, which reduces jumping between layers. 28. SOLID, Design Patterns & CQRS

Design principles and patterns give teams a shared language. The SOLID principles are the foundation. The Single Responsibility Principle says a class should have only one reason to change, so a controller should not also send emails and calculate prices. The Open/Closed Principle says code should be open for extension but closed for modification, which you achieve by adding new implementations of an interface instead of editing a big if chain. The Liskov Substitution Principle says a derived class must be usable wherever its base class is expected without surprising behaviour. The Interface Segregation Principle prefers several small interfaces to one large one. The Dependency Inversion Principle says high-level code should depend on abstractions, which dependency injection implements.

Several patterns appear constantly in .NET code. The Repository and Unit of Work patterns hide data access, although EF Core's DbContext already implements both, so a generic repository on top of it often adds little value. The Factory pattern creates objects without exposing the construction logic. The Strategy pattern swaps algorithms at run time, such as different payment gateways or discount rules. The Decorator pattern adds behaviour by wrapping an object, for example caching or logging around a repository. The Observer pattern is built into the language as events and, at a larger scale, as publish-subscribe messaging. The Mediator pattern sends requests to handlers without the sender knowing the handler, popularised by the MediatR library. The Options and Builder patterns configure objects fluently.

// Strategy + DI: pick an implementation without if/else chains (Open/Closed)
public interface IDiscountRule { bool AppliesTo(Order o); decimal Apply(Order o); }
public class BulkDiscount : IDiscountRule { /* ... */ public bool AppliesTo(Order o) => o.Lines.Sum(l => l.Qty) > 10; public decimal Apply(Order o) => o.Total * 0.9m; }
public class FestivalDiscount : IDiscountRule { /* ... */ public bool AppliesTo(Order o) => DateTime.Today.Month == 10; public decimal Apply(Order o) => o.Total * 0.85m; }

public class PricingService(IEnumerable<IDiscountRule> rules)        // the container injects all registered rules
{
    public decimal Price(Order o) => rules.Where(r => r.AppliesTo(o)).Select(r => r.Apply(o)).DefaultIfEmpty(o.Total).Min();
}

29. Microservices with .NET

In a microservices architecture, a system is split into small services, each owning one business capability and its own data, deployed independently. The goals are independent releases, independent scaling and team autonomy. The costs are real: network calls can fail, data is spread across services, debugging needs distributed tracing, and operations become much more complex. A modular monolith is often the better starting point, and you extract services only when there is a clear need.

Clients usually talk to an API gateway, built with YARP, Ocelot or a cloud gateway, which routes requests, validates tokens and applies rate limits. Services call each other synchronously with HttpClient or gRPC when an immediate answer is needed, and asynchronously through a message broker such as Azure Service Bus, RabbitMQ or Kafka when loose coupling is better. Each service has its own database, so there are no shared tables and no cross-service joins; data needed elsewhere is requested through APIs or copied through events.

Because a business operation may now span several services, you cannot use a single database transaction. The saga pattern splits it into local transactions with compensating actions, and the outbox pattern makes sure the event is published reliably by saving it in the same transaction as the business data. Resilience is added with Polly: timeouts, retries with exponential backoff and jitter, circuit breakers and bulkheads. .NET Aspire helps to run, connect and observe all services locally and in the cloud.

30. Deployment, Docker, Kubernetes & CI/CD

A .NET application can be deployed in several ways. Framework-dependent deployment ships only your code and uses the runtime installed on the server, which keeps the package small. Self-contained deployment bundles the runtime so the target machine needs nothing installed. Single-file and Native AOT options produce one executable. Today most teams package the app in a Docker container and run it on Kubernetes, Azure Container Apps, Azure App Service, AWS ECS or similar platforms, because a container behaves the same on a laptop, in testing and in production.

A CI/CD pipeline automates the path from commit to production. Continuous Integration builds the code and runs the tests on every push, and Continuous Delivery or Deployment publishes a versioned image and releases it. Quality gates such as analyzers, code coverage and vulnerability scans stop bad changes early, and release strategies such as rolling, blue-green and canary lower the risk of the release itself. Configuration comes from environment variables and secret stores, never from files baked into the image.

31. Best Practices & Anti-patterns

Experienced .NET developers share a set of habits. They keep controllers and endpoints thin and put business rules into services and domain objects. They use async all the way and pass CancellationTokens. They register services with the correct lifetime and turn on scope validation in development. They use the options pattern with validation at startup, keep secrets out of source control, and write structured logs with correlation ids. They return DTOs rather than entities, validate all input, use ProblemDetails for errors and paginate lists.

For data access they use AsNoTracking and projections for reads, avoid N+1 queries, add the right indexes, keep DbContext short-lived and never share it across threads. They enable nullable reference types and treat warnings as errors, run analyzers, write automated tests, and publish with health checks, OpenTelemetry and graceful shutdown. They keep the SDK and dependencies up to date, because security fixes arrive through updates.

32. Interview Q&A: .NET & C# Fundamentals

Q1. What is the difference between .NET Framework, .NET Core and .NET 5+?

Short answer: .NET Framework is the old Windows-only platform, .NET Core is the cross-platform rewrite, and .NET 5 and later is the unified successor of both that is now simply called .NET.

The .NET Framework ships with Windows, is closed in large parts and is in maintenance mode. .NET Core was introduced in 2016 as an open-source, modular and much faster platform that also runs on Linux and macOS. In 2020 Microsoft dropped the word Core and the number 4, so .NET 5 became the single future platform, with a new major version every November. New projects should target the latest LTS version.

💡 Interview tip: Mention that .NET Standard was only a bridge for library authors and is not needed for new libraries, which can target a modern net version directly.

Q2. Explain CLR, CTS, CLS, JIT and IL.

Short answer: The CLR is the runtime that executes .NET code, the CTS defines the common types, the CLS is a set of rules for language interoperability, IL is the intermediate code produced by the compiler and the JIT converts IL to machine code at run time.

When you compile C#, Roslyn creates an assembly with IL and metadata. At run time the CLR loads the assembly, and the JIT compiler turns each method into native code the first time it is called. The Common Type System guarantees that an int means the same thing in C#, F# and VB, and the Common Language Specification lists the features every language should support to interoperate. Tiered compilation first generates quick code and later re-optimizes hot methods.

Q3. What is the difference between value types and reference types? What is boxing?

Short answer: Value types hold their data directly and are copied on assignment, reference types hold a reference to an object on the heap and assignment copies the reference.

Structs, enums and primitives like int are value types, while classes, interfaces, delegates, arrays and strings are reference types. Value type locals usually live on the stack, but a value type inside a class lives inside that object on the heap. Boxing is the conversion of a value type to object or an interface, which allocates a heap object and copies the value; unboxing copies it back. Boxing in hot loops creates garbage, which is why generic collections like List<int> are preferred to the old non-generic ArrayList.

Q4. Why are strings immutable in C#, and when should you use StringBuilder?

Short answer: A string cannot be changed after creation, which makes it thread-safe and safe to use as a dictionary key, and it allows the runtime to intern and share it.

Every concatenation creates a new string, so building a large text in a loop with += copies the data again and again and creates garbage. StringBuilder keeps a mutable buffer and is the right tool for many appends. For a few concatenations the compiler optimizes, and string interpolation is perfectly fine.

Q5. What is the difference between an interface and an abstract class?

Short answer: An interface defines a contract without state, while an abstract class can hold state and shared implementation and supports only single inheritance.

A class can implement many interfaces but inherit from only one class. Use an interface to describe a capability that unrelated types can have, such as IDisposable or IComparable, and use an abstract class when related classes share code and fields. Since C# 8 interfaces can contain default method implementations, which blurs the difference slightly but still does not allow instance state.

Q6. What are the differences between struct and class, and when would you pick a struct?

Short answer: A struct is a value type that is copied by value, a class is a reference type that lives on the heap; choose a struct for small, immutable, short-lived data.

Microsoft guidance says a struct should be small (around 16 bytes), logically represent a single value and preferably be immutable. Large structs are expensive to copy, and mutable structs cause confusing bugs because you modify a copy. A readonly struct or a record struct is a good fit for things like coordinates, money and ids.

Q7. Explain const, readonly and static readonly.

Short answer: const is a compile-time constant baked into the calling code, readonly is assigned once at run time in a declaration or constructor, and static readonly is a run-time constant shared by the type.

Because const values are copied into every assembly that uses them, changing a public const requires recompiling all dependents, which is a versioning trap. A static readonly field is evaluated once when the type is initialized and does not have this problem.

Q8. What are delegates, events, Func and Action?

Short answer: A delegate is a type-safe reference to a method, an event is a restricted delegate that only the owner can raise, and Func and Action are built-in generic delegate types.

Action represents a method that returns nothing, Func returns a value, and Predicate returns bool. Lambdas create delegates inline and are the base of LINQ. Events follow the observer pattern: subscribers add handlers with += and the owner invokes them, but outside code cannot invoke or replace the whole list. Always unsubscribe long-lived publisher events to avoid memory leaks.

Q9. What is LINQ, and what is deferred execution?

Short answer: LINQ is a set of query operators for collections and data sources, and deferred execution means that a query does not run when it is defined but when it is enumerated.

Methods like Where and Select only build a pipeline, while ToList, Count, First or a foreach loop execute it. This allows composing queries and, with IQueryable, translating them into SQL. A common bug is enumerating the same deferred query several times, which runs it several times, so call ToList when you need a snapshot.

var query = numbers.Where(n => n > 5);     // nothing runs yet
numbers.Add(10);
var list = query.ToList();                  // runs now and includes 10

Q10. What is the difference between IEnumerable, ICollection, IList and IQueryable?

Short answer: IEnumerable only supports iteration, ICollection adds Count and modification, IList adds index access, and IQueryable represents a query that a provider translates, for example to SQL.

Return the narrowest type that serves the caller, such as IEnumerable or IReadOnlyList for read-only results. IQueryable should not usually leave the data layer, because callers may add expressions that the provider cannot translate.

Q11. Explain generics and constraints. Why are they better than object?

Short answer: Generics let you write type-safe reusable code with a type parameter, and constraints restrict which types may be used.

Unlike object-based code, generics avoid boxing and casts, give compile-time type checks and run faster. In .NET generics are reified, so the runtime knows the real type argument, which differs from Java type erasure. Constraints such as where T : class, new() or where T : IComparable<T> let you call members of the type parameter.

Q12. What are nullable reference types, and why enable them?

Short answer: It is a compiler feature that treats reference types as non-nullable by default and warns when a possibly null value is dereferenced.

Enabling <Nullable>enable</Nullable> finds many potential NullReferenceExceptions at compile time. You mark a type as nullable with ?, as in string?, and use null checks, the null-conditional operator ?. and null-coalescing ?? to handle it. It does not change run-time behaviour, it only adds static analysis.

Q13. What are records and when should you use them?

Short answer: Records are reference types, or value types for record struct, with built-in value equality, immutability by default through init properties, a readable ToString and non-destructive copying with the with expression.

They are ideal for DTOs, messages, events and value objects. Two records with the same values are equal, unlike classes that compare references. Use ordinary classes for entities that have identity and change over time.

Q14. What is the difference between == and Equals(), and how do you override equality?

Short answer: == is an operator that compares references for classes unless overloaded and values for value types, while Equals is a virtual method that can be overridden to define logical equality.

If you override Equals you must also override GetHashCode so that equal objects have equal hash codes, otherwise dictionaries and hash sets will behave incorrectly. Records generate both for you. Strings overload == to compare content.

Q15. What are extension methods and how do they work?

Short answer: They are static methods in a static class whose first parameter uses the this keyword, so they can be called as if they were instance methods of that type.

They are resolved at compile time, they cannot access private members and they do not change the original type. LINQ itself is built from extension methods on IEnumerable.

Q16. How do exceptions work, and what are best practices?

Short answer: An exception unwinds the call stack until a matching catch block is found; use try/catch for exceptional situations, finally or using for cleanup, and never swallow exceptions silently.

Catch specific exceptions, use throw; to rethrow so the stack trace is preserved (not throw ex;), and add filters with when. Do not use exceptions for normal control flow, since throwing is slow, and create custom exceptions only when callers can act on them. In async code the exception is stored in the task and is rethrown at the await.

Q17. What is the difference between Task and Thread, and between Task.Run and async/await?

Short answer: A Thread is an operating system thread, a Task is a higher-level abstraction of work that usually runs on the thread pool, and async/await is the language support for waiting on tasks without blocking a thread.

Task.Run queues CPU-bound work to the thread pool, while await is used with I/O-bound operations where no thread is needed during the wait. Using Task.Run to wrap an I/O call on a web server only wastes a thread.

Q18. What is the garbage collector and how do generations work?

Short answer: The GC automatically reclaims memory of unreachable objects, and generations (0, 1, 2 plus the large object heap) make it efficient because most objects die young.

New objects are in Gen 0. When it fills up, the GC marks reachable objects, frees the rest and promotes survivors to Gen 1 and eventually Gen 2. A Gen 2 collection examines the whole heap and is the most expensive. The LOH holds objects of 85,000 bytes or more. Background GC performs part of the Gen 2 work concurrently so request threads pause less.

Q19. What is IDisposable, and what is the dispose pattern?

Short answer: IDisposable lets an object release unmanaged resources deterministically, and the using statement guarantees Dispose is called.

Because the GC only frees memory, files, sockets and connections must be released explicitly. Implement the full dispose pattern, with a protected Dispose(bool) and GC.SuppressFinalize, only when you directly own unmanaged resources; otherwise implement Dispose simply by disposing your disposable fields. IAsyncDisposable and await using exist for asynchronous cleanup.

Q20. What are Span and Memory?

Short answer: Span is a stack-only struct that represents a contiguous region of memory without copying, and Memory is the heap-friendly version that can be stored in fields and used across awaits.

They let you slice arrays, strings and native memory without allocating, which is valuable in parsers and high-throughput code. A Span cannot be a field of a class or be used in an async method across an await, because it is a ref struct.

Q21. What are attributes and reflection?

Short answer: Attributes attach metadata to code elements and reflection reads metadata and invokes members at run time.

Frameworks use them heavily, for example [HttpGet], [Authorize] and [Required]. Reflection is flexible but slower and not trimming or AOT friendly, which is why source generators are replacing it in modern libraries.

Q22. What is the difference between abstract, virtual, override, sealed and new?

Short answer: virtual allows a method to be overridden, abstract requires derived classes to implement it, override replaces a base implementation, sealed prevents further overriding or inheritance and new hides a base member instead of overriding it.

With override the call is resolved by the real object type, which is polymorphism, while with new the call depends on the variable type, which is usually a source of bugs and should be avoided.

Q23. What are the new features in recent C# versions that you use?

Short answer: Useful features include records, top-level statements, pattern matching enhancements, primary constructors, collection expressions, required members, raw string literals and file-scoped namespaces.

For example, C# 12 added primary constructors for classes and collection expressions like int[] a = [1, 2, 3];, and C# 11 added required members and raw string literals. Mention only the ones you really use, and confirm the details of the latest version in the official documentation.

33. Interview Q&A: ASP.NET Core

Q1. What is ASP.NET Core and how is it different from classic ASP.NET?

Short answer: ASP.NET Core is the modern, cross-platform, high-performance and modular web framework for .NET, which replaced the Windows-only System.Web based ASP.NET.

It has a lightweight middleware pipeline, built-in dependency injection, unified MVC and Web API, minimal APIs, Kestrel as a fast web server, configuration through providers, and it can be self-hosted or run in containers. Classic ASP.NET depended on IIS and System.Web, which made it heavy and Windows only.

Q2. Explain the request pipeline and middleware. Why does order matter?

Short answer: The pipeline is a chain of middleware, each of which can act before and after the next one, and the order of registration is the order of execution.

For example exception handling must be first to catch errors of later components, static files are early to avoid unnecessary work, and authentication must come before authorization because a user must be identified before permissions can be checked. A middleware may short-circuit the pipeline by not calling next. You can write your own with app.Use or a class with InvokeAsync.

Q3. What is the difference between Use, Run and Map?

Short answer: Use adds middleware that may call the next component, Run adds a terminal component that ends the pipeline, and Map branches the pipeline based on the request path.

MapWhen branches on any condition. The branched pipeline is separate, so middleware registered after the Map call does not run for requests handled inside the branch unless it is also added there.

Q4. What is Kestrel and why do we need a reverse proxy?

Short answer: Kestrel is the cross-platform web server built into ASP.NET Core, and a reverse proxy in front of it adds TLS handling, load balancing, caching and protection.

Kestrel is secure enough to face the internet, but proxies like NGINX, IIS, YARP or cloud gateways provide extra features. When using a proxy you must enable forwarded headers so the app sees the original client IP and scheme.

Q5. Explain dependency injection and the three lifetimes.

Short answer: DI supplies a class with its dependencies from outside; singleton is one instance for the app, scoped is one per request and transient is a new instance on every request for it.

Choose scoped for DbContext and per-request state, singleton for stateless or thread-safe shared services such as caches, and transient for lightweight stateless helpers. A longer-lived service must never depend on a shorter-lived one, otherwise you create a captive dependency. Enable ValidateScopes in development to catch this.

Q6. What is a captive dependency?

Short answer: It is a longer-lived service, such as a singleton, that holds a reference to a shorter-lived service, such as a scoped DbContext, keeping it alive for the lifetime of the singleton.

This causes stale data, memory growth and thread-safety bugs. The fix is to change the lifetime, inject a factory such as IDbContextFactory, or create a scope with IServiceScopeFactory inside the singleton for each unit of work.

Q7. Minimal APIs versus controllers: how do you choose?

Short answer: Minimal APIs are lighter and perfect for small services, while controllers provide more built-in structure and filters for large APIs; performance is almost the same.

Minimal APIs support route groups, endpoint filters, typed results and are AOT friendly. Controllers give attribute routing, automatic model validation with ApiController, content negotiation and a rich filter pipeline. Both can coexist in one project.

Q8. How does model binding and validation work?

Short answer: The framework reads values from the route, query, headers, form and body into parameters, and validation runs DataAnnotations or other validators on the bound model.

With [ApiController], an invalid model automatically returns a 400 ProblemDetails response. In minimal APIs validation is not automatic before .NET 10, so many teams add FluentValidation or an endpoint filter. Always bind to DTOs, never to entities, to prevent over-posting.

Q9. What are filters in ASP.NET Core?

Short answer: Filters run code before or after specific stages of the MVC action pipeline: authorization, resource, action, exception and result filters.

They are used for concerns that need access to action context, such as validation, auditing, caching headers or consistent error mapping. They differ from middleware, which runs for every request and knows nothing about controllers or actions.

Q10. How do you handle errors globally in a Web API?

Short answer: Register a global exception handler, such as UseExceptionHandler with IExceptionHandler, that logs the error and returns a ProblemDetails response.

Expected problems should be returned as normal results with proper status codes, and unexpected ones are caught by the global handler. Never return stack traces to clients in production, and include a trace id so support can find the log entry.

Q11. How do you implement authentication and authorization using JWT?

Short answer: Configure AddJwtBearer with the authority and audience, add UseAuthentication and UseAuthorization, and protect endpoints with [Authorize] or RequireAuthorization using policies.

The middleware validates the signature, issuer, audience and expiry, and builds the ClaimsPrincipal. Use short-lived access tokens and refresh tokens, and get tokens from a proper identity provider using the authorization code flow with PKCE rather than issuing them yourself, when possible.

Q12. What is the difference between authentication and authorization, and between 401 and 403?

Short answer: Authentication identifies the caller, authorization decides what they may do; 401 means not authenticated and 403 means authenticated but not allowed.

A missing or invalid token should give 401 with a WWW-Authenticate header, while a valid user lacking the required role or claim gets 403.

Q13. What is CORS and how do you configure it?

Short answer: CORS is a browser mechanism that controls whether a web page from one origin may call an API on another origin, and the API allows origins through AddCors and UseCors.

It does not protect the API from non-browser clients. Specify exact origins, methods and headers, avoid AllowAnyOrigin with credentials, and place UseCors after UseRouting and before authentication.

Q14. How do you configure and read settings, and what is the options pattern?

Short answer: Settings come from layered configuration providers, and the options pattern binds sections to typed classes that are injected through IOptions, IOptionsSnapshot or IOptionsMonitor.

Add validation with ValidateDataAnnotations and ValidateOnStart so that wrong configuration stops the app immediately. Use user secrets locally and Key Vault in production.

Q15. What is IHttpClientFactory and why use it?

Short answer: It manages HttpClient instances and their handlers, pooling connections and refreshing DNS, which avoids socket exhaustion and stale DNS problems.

It also lets you configure named or typed clients and attach Polly resilience handlers for retries, timeouts and circuit breakers in one place.

Q16. How does ASP.NET Core support real-time features?

Short answer: Through SignalR, which uses WebSockets with fallbacks to push messages from the server to connected clients.

You define hubs, clients connect and join groups, and for multiple servers you add a backplane such as Redis or use Azure SignalR Service.

Q17. What are health checks and how are they used with Kubernetes?

Short answer: Health checks are endpoints that report whether the app and its dependencies are healthy, and Kubernetes probes use them to restart or route traffic.

A liveness probe tells whether the process is stuck and should be restarted, while a readiness probe tells whether it can accept traffic now. Keep liveness light and put dependency checks into readiness.

Q18. What is the difference between IOptions, IOptionsSnapshot and IOptionsMonitor?

Short answer: IOptions is a singleton read once, IOptionsSnapshot is scoped and re-reads per request, and IOptionsMonitor is a singleton that notifies about changes.

Use IOptionsMonitor in singletons that need live configuration changes, and IOptionsSnapshot only in scoped services.

Q19. What changed in minimal hosting and how does WebApplicationFactory work with it?

Short answer: Since .NET 6 Startup and Program are merged into one Program.cs using WebApplication, and tests access the entry point through a public partial Program class.

WebApplicationFactory<Program> starts the app in memory so integration tests can issue real HTTP calls and replace services through ConfigureTestServices.

34. Interview Q&A: EF Core, Async & Performance

Q1. What is Entity Framework Core and what is the DbContext?

Short answer: EF Core is an ORM that maps C# classes to database tables, and DbContext is the session that tracks entities and saves changes as a unit of work.

DbContext exposes DbSet properties for querying, keeps a change tracker, and SaveChanges writes all pending inserts, updates and deletes in one transaction. It is not thread-safe and should be scoped to a request.

Q2. Code-first versus database-first?

Short answer: Code-first starts from C# classes and creates the database through migrations, and database-first generates classes from an existing database with scaffolding.

Code-first is the common choice for new projects because the model is the source of truth and schema changes are versioned in code. Database-first suits legacy databases, and you can re-scaffold when the schema changes.

Q3. What are migrations, and how do you apply them safely in production?

Short answer: Migrations are code files describing incremental schema changes, and for production you generate an idempotent SQL script or bundle and run it as a deployment step.

Avoid calling Migrate at startup in multi-instance deployments because instances can race and need elevated rights. For zero-downtime releases use expand-and-contract: add new columns first, deploy code that works with both, then remove old columns later.

Q4. What is the N+1 query problem and how do you solve it?

Short answer: It happens when one query loads a list and then one extra query per item loads related data, producing many round trips; solve it with Include, projections or explicit batching.

Lazy loading hides the problem and makes it easy to introduce, so many teams disable it. Use the logging of EF Core or a profiler to count queries during development, and use AsSplitQuery when a large Include creates a cartesian explosion.

Q5. Tracking versus no-tracking queries?

Short answer: Tracking queries keep entities in the change tracker so changes can be saved, while AsNoTracking skips that overhead for read-only data.

Use AsNoTracking for lists, reports and APIs that only read, which is faster and uses less memory. You can set it as the default on the context for read-heavy services.

Q6. IEnumerable versus IQueryable in EF Core?

Short answer: IQueryable builds an expression tree that EF translates and runs in the database, while IEnumerable executes in memory after the data is loaded.

Calling ToList or AsEnumerable early means later Where clauses filter in memory after loading the entire table, which is a typical performance bug.

Q7. How do you handle concurrency conflicts?

Short answer: Use optimistic concurrency with a row version or concurrency token, catch DbUpdateConcurrencyException, and then reload, merge or ask the user.

EF adds the token to the WHERE clause of UPDATE and DELETE statements, and if no rows are affected it knows that someone else changed the data. Pessimistic locking is possible with database locks but reduces scalability.

Q8. How do transactions work in EF Core?

Short answer: SaveChanges is atomic by default, and for multiple steps you use Database.BeginTransactionAsync or TransactionScope.

Execution strategies that retry on transient failures need the whole transaction inside strategy.ExecuteAsync. Keep transactions short to avoid blocking other users.

Q9. When would you use Dapper or raw SQL instead of EF Core?

Short answer: Use Dapper or raw SQL for performance-critical reads, complex reports and stored procedures, and EF Core for productivity with change tracking and migrations.

They are not exclusive: many systems use EF Core for writes and Dapper or FromSql for specific read models.

Q10. How do you prevent SQL injection?

Short answer: Always use parameterized queries, which LINQ and FromSqlInterpolated do automatically.

Never concatenate user input into SQL strings, including FromSqlRaw. Also limit the database permissions of the application account.

Q11. Explain async and await and why it matters in web applications.

Short answer: Async and await release the thread while waiting for I/O, which lets a server handle many more concurrent requests with the same threads.

The compiler turns the method into a state machine, and the continuation runs on a thread pool thread when the operation completes. It improves scalability but not the latency of a single request.

Q12. What is thread pool starvation and how do you avoid it?

Short answer: It happens when all thread pool threads are blocked, so queued work waits although the CPU is idle, and it is avoided by never blocking on async code.

Typical causes are calling .Result or .Wait in request code, synchronous I/O and long running work on pool threads. Use async all the way, move long jobs to background services and monitor thread pool queue length with dotnet-counters.

Q13. Why avoid async void?

Short answer: Exceptions in async void cannot be caught by the caller and can crash the process, and the caller cannot await the completion.

Use async Task instead. async void is acceptable only for event handlers.

Q14. Task.WhenAll versus awaiting sequentially?

Short answer: Task.WhenAll runs independent operations concurrently, so the total time is the slowest one instead of the sum.

Start all tasks first, then await them together. Be careful with a shared DbContext, which cannot run two queries at once.

Q15. What is ConfigureAwait(false)?

Short answer: It tells the awaiter not to resume on the captured synchronization context, which avoids deadlocks and overhead in libraries.

ASP.NET Core has no synchronization context, so it is not required in application code, but UI apps and library authors still use it.

Q16. How do you cache data in ASP.NET Core and avoid stale data and stampedes?

Short answer: Use IMemoryCache or distributed cache with sensible expiry, invalidate on updates and use single-flight or HybridCache to prevent stampedes.

Add jitter to expiry times, cache only data that is safe to be slightly old, and watch memory usage. Output caching with tags makes bulk invalidation easy.

Q17. How would you find and fix a memory leak in a .NET service?

Short answer: Observe memory growth with dotnet-counters, capture a dump or GC dump, and find which objects are retained and who references them.

Common causes are static collections, unsubscribed event handlers, captured closures, unbounded caches, undisposed HttpClient or timers, and large object heap fragmentation. After the fix, verify with a load test that memory stays flat.

Q18. How do you improve the performance of an API endpoint that is slow?

Short answer: Measure first, then look at database queries, network calls, serialization and allocations, in that order.

Typical fixes are adding indexes, removing N+1 queries, projecting only needed columns, caching, parallelizing independent calls, paging, compression and reducing allocations in hot code. Use traces to see where the time goes and BenchmarkDotNet to verify micro-optimizations.

Q19. What is Native AOT and what are its limits?

Short answer: Native AOT compiles an app ahead of time to a self-contained native executable with fast startup and low memory use, but it restricts reflection and dynamic code generation.

It suits serverless functions, containers and CLI tools. Libraries must be trimming and AOT compatible, and ASP.NET Core supports it for minimal APIs with source-generated serialization.

35. Interview Q&A: Architecture, Security & Cloud

Q1. What is Clean Architecture and what are its benefits?

Short answer: Clean Architecture arranges code in layers where dependencies point inward to the domain, so business rules do not depend on frameworks, databases or UI.

Benefits are testability without infrastructure, replaceable technologies and a clear place for each kind of code. The cost is more projects and mapping code, so it fits long-lived, complex applications better than tiny CRUD services.

Q2. Explain SOLID with an example from .NET.

Short answer: SOLID is five principles: single responsibility, open/closed, Liskov substitution, interface segregation and dependency inversion.

For example, instead of an if chain for payment methods in a service, define IPaymentGateway and register several implementations; adding a new gateway needs no change to the existing code, which is open/closed, and the service depends on an abstraction supplied by DI, which is dependency inversion.

Q3. What is CQRS and when should you use it?

Short answer: CQRS separates commands that change state from queries that read it, so each can use its own model and be scaled independently.

It is useful when read and write needs differ greatly, for instance complex write rules but very fast flexible reads. It adds complexity and often eventual consistency, so avoid it for simple CRUD.

Q4. What is the repository pattern and do you need it with EF Core?

Short answer: A repository hides data access behind an interface, but EF Core already implements repository and unit of work, so a generic repository on top often adds nothing.

A specific repository or query object per aggregate is still useful when you want to isolate infrastructure from the application layer and make unit tests simpler.

Q5. Monolith or microservices?

Short answer: Start with a modular monolith and move to microservices when team size, independent scaling or release independence justifies the added distributed-system complexity.

Microservices bring network failures, data consistency challenges and operations cost. Split along business boundaries (bounded contexts), give every service its own database and communicate mostly through events.

Q6. How do you handle distributed transactions in microservices?

Short answer: Avoid them by design, and where needed use the saga pattern with compensating actions plus the outbox pattern for reliable messaging.

Two-phase commit is blocking and rarely used across services. In .NET, MassTransit state machines, NServiceBus sagas or Durable Functions help orchestrate sagas.

Q7. What is the outbox pattern?

Short answer: It stores outgoing messages in the same database transaction as the business change, and a background process publishes them afterwards.

This solves the dual-write problem where the database commit succeeds but publishing fails. Because delivery is at least once, consumers must be idempotent.

Q8. How do you make an API idempotent?

Short answer: Accept an idempotency key, store the result of the first processing and return the same result for repeats, or design operations with natural keys and conditional updates.

PUT and DELETE are idempotent by definition, POST is not, so payments and order creation need keys or unique constraints.

Q9. Explain resilience patterns and Polly.

Short answer: Resilience patterns are timeouts, retries with backoff and jitter, circuit breakers, bulkheads and fallbacks, which Polly implements for .NET.

Retry only idempotent operations, put retries at one layer to avoid retry storms, and use AddStandardResilienceHandler on HttpClient for sensible defaults.

Q10. How do you secure an ASP.NET Core API?

Short answer: Use HTTPS, token-based authentication through a trusted identity provider, policy-based authorization with ownership checks, validation, rate limiting, secure secrets and up-to-date dependencies.

Also use CORS with specific origins, security headers, DTOs against over-posting, parameterized queries, logging without secrets, and regular vulnerability scans.

Q11. What is the OWASP Top 10 and which items matter most for .NET APIs?

Short answer: It is a list of the most critical web application security risks, such as broken access control, injection, cryptographic failures and vulnerable components.

For APIs the most frequent problem is broken access control, for example not checking that a resource belongs to the caller, followed by misconfiguration and unsafe dependencies.

Q12. How do you store passwords?

Short answer: Never store plain text or fast hashes; use a slow, salted hashing algorithm such as PBKDF2, bcrypt or Argon2, ideally through ASP.NET Core Identity or by delegating login to an identity provider.

Add rate limiting, lockout and multi-factor authentication to resist brute force attacks.

Q13. What is OAuth 2.0 versus OpenID Connect, and which flow for which client?

Short answer: OAuth 2.0 delegates authorization to access resources, OpenID Connect adds authentication with an ID token; use authorization code with PKCE for browser and mobile apps and client credentials for service-to-service calls.

The implicit and password flows are discouraged because they expose tokens or credentials.

Q14. How do you deploy a .NET app to Kubernetes?

Short answer: Build a multi-stage Docker image, push it to a registry and deploy it with a Deployment, Service and Ingress with probes, resource limits and configuration from ConfigMaps and Secrets.

Use rolling updates, a horizontal pod autoscaler, graceful shutdown and OpenTelemetry for visibility. Run database migrations as a separate controlled step.

Q15. What is .NET Aspire?

Short answer: .NET Aspire is an opinionated stack for building observable, cloud-ready distributed applications, with an app host that describes services and resources in C# and a dashboard for logs, metrics and traces.

It simplifies local orchestration and service discovery and generates deployment manifests for platforms such as Azure Container Apps and Kubernetes.

Q16. How do you version an API without breaking clients?

Short answer: Add fields rather than change them, version in the URL or a header when breaking changes are needed, and support old versions for a published period.

The Asp.Versioning package helps, and consumer-driven contract tests catch accidental breaking changes.

Q17. How do you design for high availability and scalability in .NET?

Short answer: Keep the web tier stateless, scale horizontally behind a load balancer, use caching and asynchronous processing, replicate data and add health checks, retries and circuit breakers.

Store sessions in a distributed cache, use multiple availability zones, and design for graceful degradation so one failing dependency does not take the whole system down.

Q18. What is gRPC and when would you use it instead of REST?

Short answer: gRPC is a binary RPC framework over HTTP/2 using Protobuf, with strong typing and streaming, best for internal service-to-service calls.

REST remains better for public APIs and browser clients because it is simple, cacheable and human-readable.

Q19. How do you monitor a .NET application in production?

Short answer: Use OpenTelemetry for traces, metrics and logs, health checks, dashboards and alerts based on SLOs, and diagnostic tools such as dotnet-counters and dotnet-dump for deep investigation.

Alert on user-visible symptoms such as error rate and latency percentiles, and always include correlation ids in logs.

36. Interview Q&A: Scenarios & Coding Questions

Q1. Your API suddenly became slow under load, but CPU usage is low. What do you check?

Short answer: Low CPU with high latency usually means threads are waiting, so I check thread pool starvation, slow dependencies and connection pool exhaustion.

First I look at dashboards for the affected endpoints and at traces to see which call takes the time. With dotnet-counters I check thread pool queue length and thread count. I search for blocking calls like .Result, synchronous I/O and locks. I also check database waits and connection pool limits. The fix is usually to make the code async all the way, add timeouts and reduce slow dependency calls.

Q2. The service memory grows until the container is killed. How do you investigate?

Short answer: I confirm the growth with metrics, take memory dumps or GC dumps at different times and compare which object types grow and what holds them.

I use dotnet-gcdump or dotnet-dump and analyze retention paths. Typical findings are static dictionaries used as caches without limits, event handlers never removed, HttpClient created per request, or large buffers on the LOH. I fix the cause, set bounds and expiry on caches, and verify with a soak test. I also check whether the container memory limit is lower than the GC expects.

Q4. How would you design an endpoint that safely handles payment retries?

Short answer: Require an Idempotency-Key header, store the key with the result atomically, and return the stored result for repeated requests.

app.MapPost("/payments", async (HttpContext ctx, PaymentRequest req, PaymentsDb db, IPaymentGateway gw, CancellationToken ct) =>
{
    var key = ctx.Request.Headers["Idempotency-Key"].ToString();
    if (string.IsNullOrWhiteSpace(key)) return Results.BadRequest("Idempotency-Key header is required.");

    var existing = await db.Payments.AsNoTracking().FirstOrDefaultAsync(p => p.IdempotencyKey == key, ct);
    if (existing is not null) return Results.Ok(existing.ToResponse());              // replay

    var payment = new Payment { IdempotencyKey = key, Amount = req.Amount, Status = "Pending" };
    db.Payments.Add(payment);
    try { await db.SaveChangesAsync(ct); }                                           // unique index on IdempotencyKey guards races
    catch (DbUpdateException) { return Results.Conflict("Request is already being processed."); }

    var result = await gw.ChargeAsync(req, key, ct);                                 // pass the key to the gateway too
    payment.Status = result.Success ? "Paid" : "Failed";
    await db.SaveChangesAsync(ct);
    return Results.Ok(payment.ToResponse());
});

Q5. Write a thread-safe, async-friendly in-memory cache with single-flight loading.

Short answer: Store a Lazy> per key in a ConcurrentDictionary so only one caller loads the value while others await the same task.

public class SingleFlightCache<TKey, TValue> where TKey : notnull
{
    private readonly ConcurrentDictionary<TKey, Lazy<Task<TValue>>> _items = new();

    public async Task<TValue> GetOrLoadAsync(TKey key, Func<TKey, Task<TValue>> loader)
    {
        var lazy = _items.GetOrAdd(key, k => new Lazy<Task<TValue>>(() => loader(k)));   // one loader per key
        try { return await lazy.Value; }
        catch { _items.TryRemove(key, out _); throw; }                                   // do not cache failures
    }
}

Q6. Implement a simple retry with exponential backoff and jitter, without a library.

Short answer: Loop up to a maximum, catch transient exceptions only, wait base delay times two to the power of the attempt plus a random jitter, and rethrow after the last attempt.

public static async Task<T> RetryAsync<T>(Func<CancellationToken, Task<T>> action, int maxAttempts = 4, CancellationToken ct = default)
{
    for (var attempt = 1; ; attempt++)
    {
        try { return await action(ct); }
        catch (HttpRequestException) when (attempt < maxAttempts)
        {
            var delay = TimeSpan.FromMilliseconds(200 * Math.Pow(2, attempt - 1) + Random.Shared.Next(0, 100));
            await Task.Delay(delay, ct);
        }
    }
}

In real applications prefer Microsoft.Extensions.Resilience or Polly, which add circuit breakers and metrics.

Q7. Write a middleware that rejects requests without an API key.

Short answer: Create a middleware class that reads the header, compares it with the configured value using a constant-time comparison, and returns 401 when it does not match.

public class ApiKeyMiddleware(RequestDelegate next, IOptions<ApiKeyOptions> options)
{
    public async Task InvokeAsync(HttpContext ctx)
    {
        if (ctx.Request.Path.StartsWithSegments("/health")) { await next(ctx); return; }

        var supplied = Encoding.UTF8.GetBytes(ctx.Request.Headers["X-Api-Key"].ToString());
        var expected = Encoding.UTF8.GetBytes(options.Value.Key);
        if (!CryptographicOperations.FixedTimeEquals(supplied, expected))               // avoids timing attacks
        {
            ctx.Response.StatusCode = StatusCodes.Status401Unauthorized;
            await ctx.Response.WriteAsJsonAsync(new ProblemDetails { Status = 401, Title = "Invalid API key" });
            return;
        }
        await next(ctx);
    }
}

Q9. A background worker must process messages exactly once. Is that possible?

Short answer: True exactly-once delivery is not possible in distributed systems, but you can achieve exactly-once effects with at-least-once delivery and idempotent processing.

Give every message a unique id, record processed ids in the same transaction as the business change (the inbox pattern), and ignore duplicates. Use the outbox pattern on the producer side so the message is published only if the data change committed.

Q10. How would you migrate a large .NET Framework application to modern .NET?

Short answer: Do it gradually: assess with the Upgrade Assistant and portability analyzer, move shared libraries to netstandard or net, then migrate applications piece by piece, using the strangler pattern for web apps.

Add tests before changing anything, replace unsupported technologies such as WCF server, Web Forms and System.Web with alternatives (CoreWCF, Blazor or Razor, ASP.NET Core), update dependencies, and run the old and new systems side by side behind a proxy such as YARP until the old one can be retired.

Q11. A deployment caused errors in production. What is your approach?

Short answer: Stabilize first by rolling back or turning off the feature flag, then investigate with logs and traces, and finally fix the cause and improve the process.

A blameless post-mortem asks why tests, canary releases or alerts did not catch it, and the team adds a test, an alert or a deployment guard so the same failure cannot silently repeat.

Q12. How would you design a rate-limited public API for many tenants?

Short answer: Identify tenants through API keys or tokens, apply per-tenant token bucket limits at the gateway and in the app, return 429 with Retry-After and expose usage metrics.

Store counters in Redis when limits must be shared across instances, and use different limits per plan. Provide clear documentation, because well-behaved clients should back off with jitter.
