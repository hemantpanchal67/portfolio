🐳 Docker basics and the Azure container services

Hinglish samajh: Docker application aur uski saari zarooratein ek image mein pack karta hai; image chalane par container banta hai jo har jagah ek jaisa chalta hai. Azure mein "Docker service" ek hi nahi hai, balki kai services containers chalati hain: ACR (images store), ACI (quick single container), Container Apps (serverless), App Service for Containers (web apps) aur AKS (full Kubernetes).

Docker packages an application together with everything it needs (runtime, libraries, settings) into an image. Running an image gives a container, which behaves the same on a laptop, a test server and in the cloud. Containers are lighter than virtual machines because they share the host operating system kernel instead of each carrying a full OS. You describe the image in a Dockerfile, build it with docker build, and store it in a registry.

There is no single product called "Azure Docker service". Azure offers several services that store and run Docker containers, and choosing between them is the real interview question. Azure Container Registry (ACR) stores your images privately. Azure Container Instances (ACI) runs a container quickly without any servers. Azure Container Apps runs containers serverlessly with autoscaling to zero and microservice features. Azure App Service (Web App for Containers) hosts a containerized web app or API. Azure Kubernetes Service (AKS) runs containers at scale with full Kubernetes control. You can also run Docker on a plain Azure VM.

Azure container services run standard OCI-compatible images, so an image built with Docker works on all of them. (AKS itself uses containerd as the runtime, but images are the same.)

✨ Features

  • Docker: image, container, Dockerfile, registry.
  • Azure services: ACR, ACI, Container Apps, App Service, AKS and VMs.
  • Images follow the OCI standard, so they run on all of them.

✅ Benefits

  • The same image runs everywhere: laptop, test and production.
  • Lighter and faster to start than VMs.
  • Easy to version, roll back and scale.

⚠️ Problems

  • Containers are temporary, so data needs volumes or managed services.
  • Many services to choose from can confuse.
  • Security needs care: image scanning, no root, no secrets in images.

🔗 Azure container services overview

Interview questions and answers

What is Docker and why use containers?
Docker packages an app and its dependencies into an image that runs the same everywhere. Containers are light, start fast and make deployment consistent.
Which Azure services run Docker containers?
Azure Container Instances, Azure Container Apps, App Service for Containers, AKS and VMs, with Azure Container Registry to store the images.
Cross question: What is the difference between a VM and a container?
A VM includes a full guest operating system on virtualized hardware. A container shares the host OS kernel and packages only the app and its libraries, so it is smaller and starts faster, with less isolation.
Cross question: Does Docker run inside AKS?
AKS nodes use containerd as the runtime. You still build Docker images, because they are OCI-compatible, but Docker itself is not the runtime on the nodes.

📦 Azure Container Registry (ACR)

Hinglish samajh: Azure Container Registry aapke Docker images ka private managed registry hai (myregistry.azurecr.io). Workflow: build, tag, login, push, aur services pull karti hain. ACR Tasks cloud mein image build kar deta hai. SKUs: Basic, Standard aur Premium (geo-replication aur Private Link). Security ke liye managed identity (AcrPull) use karein, admin account nahi, aur latest tag se bachein.

Azure Container Registry is a private, managed registry for your container images (and Helm charts and other OCI artifacts), based on the open-source Docker registry. Instead of storing images on Docker Hub where they are public or rate limited, you keep them in ACR, close to the services that run them, with Azure security and access control. Its address is myregistry.azurecr.io.

The workflow: build the image, tag it with the registry name (myregistry.azurecr.io/shop:1.0), log in (az acr login), push it, and let your services pull it. You can even build in the cloud with ACR Tasks (az acr build), which builds images without a local Docker, and can rebuild automatically when the base image or the code changes.

There are three SKUs (tiers). Basic is for learning and low usage. Standard is for most production uses with more storage and throughput. Premium adds geo-replication (one registry with copies in several regions for fast, resilient pulls), private endpoints / Private Link, higher throughput, content trust and customer-managed keys. Security: use Microsoft Entra ID and managed identities (role AcrPull to pull, AcrPush to push) rather than the admin account (a single shared username and password, to be disabled in production). Attach ACR to AKS so the cluster pulls images through its managed identity. Enable Defender for Containers to scan images for vulnerabilities, and use tags and digests carefully (prefer immutable version tags over latest).

  • Using the latest tag makes deployments unpredictable.
  • Old images pile up and cost storage unless cleaned by retention or purge tasks.

Interview questions and answers

What is Azure Container Registry?
A private, managed registry in Azure for Docker and OCI images and Helm charts, with Entra ID access control, tasks to build images, and optional geo-replication.
How does AKS pull images from ACR securely?
Attach ACR to the cluster so its managed identity gets the AcrPull role. No usernames or passwords are stored.
Cross question: Which ACR tier for a global production system?
Premium, for geo-replication (copies near each region), Private Link, higher throughput and customer-managed keys.
Cross question: Why avoid the latest tag?
It is mutable, so you cannot tell which version runs and rollbacks are unclear. Use immutable version tags (or digests) and deploy specific versions.
Cross question: How do you build images without Docker on your machine?
Use ACR Tasks: az acr build uploads the source and builds the image in Azure, and tasks can rebuild automatically on code or base image changes.

🚀 Azure Container Instances (ACI)

Hinglish samajh: ACI mein container seconds mein chalta hai, bina server ya cluster ke, aur CPU aur memory ka per-second bill aata hai. Container group mein kai containers ek IP, storage aur lifecycle share karte hain (pod jaisa), sidecar ke liye bhi. Restart policy Always, OnFailure ya Never hoti hai. ACI chhote jobs, tests aur burst ke liye hai; autoscaling aur rolling updates ke liye Container Apps ya AKS chuniye.

Azure Container Instances is the simplest way to run a container in Azure: you give it an image, CPU and memory, and Azure starts it in seconds with no servers, VMs or cluster to manage. You are billed per second for the CPU and memory your container group uses, so it is cheap for short tasks. It supports Linux and Windows containers, public IP addresses with DNS names, VNet integration, mounting Azure Files volumes and environment variables and secrets.

The main unit is a container group: one or more containers that run on the same host and share the same lifecycle, network (one IP address) and storage volumes. This is like a pod in Kubernetes. It lets you run a main app with a sidecar container (for logging or a proxy). A restart policy decides what happens when a container stops: Always, OnFailure or Never (use Never or OnFailure for one-off jobs).

ACI is good for simple apps, short-lived jobs, build agents, tests, quick demos, and burst capacity (for example AKS virtual nodes use ACI to add pods fast). It is not an orchestrator: there is no built-in autoscaling, rolling updates, load balancing between many instances, service discovery or advanced scheduling. For microservices or production scaling, use Container Apps or AKS.

✨ Features

  • Run containers in seconds with no servers to manage.
  • Per-second billing for CPU and memory.
  • Container groups share network, storage and lifecycle (like a pod).

✅ Benefits

  • Very fast and simple to start.
  • Cost-effective for short-lived and bursty work.
  • Supports Linux, Windows, VNet and Azure Files.

  • No built-in autoscaling, rolling updates or load balancing across instances.
  • Not suited to complex microservices.
  • Always-on workloads can cost more than other options.

Interview questions and answers

What is Azure Container Instances?
A serverless way to run containers in Azure quickly, with no VMs or cluster to manage, billed per second for the CPU and memory used.
What is a container group?
A set of containers scheduled on the same host that share one IP address, network, storage volumes and lifecycle, similar to a Kubernetes pod. It allows sidecar patterns.
Cross question: When would you use ACI and when not?
Use ACI for simple apps, short jobs, build agents, tests and burst capacity. Do not use it when you need autoscaling, rolling updates, service discovery or many cooperating microservices; use Container Apps or AKS.
Cross question: How do you run a job that should stop when finished?
Set the restart policy to Never or OnFailure. The container group stops after the process exits, and you stop paying for compute.

🌱 Azure Container Apps and App Service for Containers

Hinglish samajh: Container Apps Kubernetes par bana serverless container platform hai jo Kubernetes ko chhupa deta hai: autoscaling (zero tak), revisions aur traffic splitting, Dapr aur jobs. App Service for Containers ek containerized web app ko App Service ke features (slots, custom domain) ke saath always-on chalata hai. Microservices aur event-driven kaam ke liye Container Apps, simple web app ke liye App Service, aur full control ke liye AKS.

Azure Container Apps is a serverless platform for running containers, built on top of Kubernetes (with KEDA for event-driven scaling, Dapr for microservice building blocks and Envoy for ingress) but without exposing Kubernetes to you. You deploy a container image and Azure handles the cluster. Key features: autoscaling including scale to zero (rules based on HTTP traffic, queue length, CPU and more), revisions (every change creates a new immutable version, which allows traffic splitting for blue-green and canary releases), built-in HTTPS ingress, managed identity and secrets, jobs (scheduled or on-demand tasks that run to completion), and a shared environment where apps in one environment can reach each other privately. Plans: a Consumption plan (pay for what you use) and Dedicated workload profiles (reserved, special sizes and GPUs).

Azure App Service for Containers (Web App for Containers) runs one containerized web app or API on the App Service platform. You get the familiar App Service features: custom domains and TLS, deployment slots for safe swaps, autoscale rules, built-in authentication, VNet integration and easy CI/CD. It is always on and billed by the App Service plan you choose. It is a good fit for a containerized web application that you want managed like any other App Service app.

Choosing between them: pick App Service for Containers for a simple, always-on web app with slots and the App Service ecosystem. Pick Container Apps for microservices, event-driven or background workers, APIs that should scale to zero, and apps that benefit from revisions and Dapr, with less Kubernetes knowledge. Pick AKS when you need full Kubernetes (custom controllers, service mesh choices, deep networking control).

  • App Service plans cost money even when idle.
  • Container Apps hides Kubernetes, so some advanced Kubernetes features are not available.

Interview questions and answers

What is Azure Container Apps?
A serverless container platform built on Kubernetes (KEDA, Dapr, Envoy) that hides the cluster. It autoscales including to zero, supports revisions with traffic splitting, jobs, and private networking.
Container Apps vs AKS?
Container Apps is simpler and serverless with no Kubernetes management. AKS gives full Kubernetes control (custom resources, service meshes, node-level control) but needs more skills and operations.
Cross question: Container Apps vs App Service for Containers?
App Service suits a single always-on web app using slots and the App Service features. Container Apps suits microservices and event-driven workloads that benefit from scale to zero, revisions and Dapr.
Cross question: How do you do a canary release in Container Apps?
Use multiple revision mode, deploy the new revision, and split traffic, for example 90 percent to the old and 10 percent to the new, then increase the share as it proves stable.
Cross question: How would you scale a worker that processes a Service Bus queue?
Add a KEDA-based scale rule for Service Bus queue length so replicas follow the backlog, scaling to zero when the queue is empty.

🎯 Choosing the right service and interview cheat sheet

Hinglish samajh: Chunav: sirf images rakhne ke liye ACR; ek container ya chhote job ke liye ACI; simple web app ke liye App Service for Containers; microservices aur workers ke liye Container Apps; full Kubernetes control ke liye AKS. Dockerfile best practices: chhoti base image, multi-stage build, non-root user, image mein secrets nahi, pinned version tags, health check aur stateless containers.

Use a simple decision path. Do you only need to store images? Use ACR. A single container or short job with no orchestration? Use ACI. A simple always-on web app in a container? Use App Service for Containers. Microservices, APIs and workers that should autoscale (even to zero) without Kubernetes work? Use Container Apps. A large platform needing full Kubernetes features and control? Use AKS. Need to control the host or run special software? Use a VM with Docker.

Common best practices for Dockerfiles and containers: use a small base image (slim or alpine variants), use multi-stage builds to keep build tools out of the final image, run as a non-root user, never put secrets in the image (use Key Vault and managed identity), pin version tags, add a .dockerignore file, define health checks, write logs to stdout and keep containers stateless (data in volumes or managed services). Scan images in ACR with Defender.

Monitoring and cost: send logs and metrics to Azure Monitor and Log Analytics (Container Insights for AKS). Set CPU and memory limits, use autoscaling, and clean up old images with ACR retention policies. Use managed identities everywhere to avoid credentials.

Interview questions and answers

How do you choose between ACI, Container Apps, App Service and AKS?
ACI for single containers and jobs; App Service for simple always-on web apps; Container Apps for microservices and event-driven workloads with autoscale to zero; AKS when you need full Kubernetes control. ACR stores images for all of them.
What are Dockerfile best practices?
Small base image, multi-stage builds, non-root user, no secrets in the image, pinned version tags, a .dockerignore file, health checks, and stateless containers that log to stdout.
Cross question: What is a multi-stage build and why use it?
A Dockerfile with several stages: an early stage with the SDK builds the app and a final stage copies only the output onto a small runtime image. The result is smaller, faster to ship and has fewer vulnerabilities.
Cross question: How would you deploy a containerized API with zero downtime?
Push a new tagged image to ACR, deploy it as a new revision or slot, run health checks, shift traffic gradually or swap the slot, and roll back by returning traffic to the old revision.
Cross question: Where should a container keep its data?
Not inside the container, because it is temporary. Use mounted volumes (Azure Files), managed databases or Blob Storage so data survives restarts and scaling.
