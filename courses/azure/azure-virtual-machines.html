💻 What Azure VMs are and what you manage

Hinglish samajh: Azure VM ek cloud computer hai jo aap control karte hain (IaaS). Azure hardware aur virtualization sambhalta hai; OS, patching, software aur security aapki zimmedari hai. VM ke hisse: VM, OS aur data disks, NIC, VNet aur subnet, optional public IP aur NSG firewall. Jab OS-level control ya legacy software chahiye tab VM chuniye, warna PaaS aasan hota hai.

Azure Virtual Machines give you a computer in the cloud that you control: you choose the operating system (Windows or Linux), the size, the disks and the network, and then install and run any software. This is IaaS (Infrastructure as a Service). Azure runs the physical hardware, the network and the virtualization layer, and you manage everything from the operating system upwards: OS patching, software, security settings and backups.

The responsibility split is a classic interview point. In IaaS (VMs) you manage the OS and above. In PaaS (App Service, Azure SQL, Functions) Azure manages the OS and runtime and you manage your app and data. In SaaS (Microsoft 365) you only use the software. Choose VMs when you need full control, legacy or custom software, specific OS settings, or a lift-and-shift migration of existing servers. If PaaS can do the job, it is usually cheaper to run and easier to maintain.

A VM is not a single object. It is made of several resources: the VM itself (compute), one or more disks, a network interface (NIC) attached to a virtual network (VNet) and subnet, optionally a public IP address, and a Network Security Group (NSG) that acts as a firewall. All are created inside a resource group in a chosen region.

  • IaaS: you choose OS, size, disks and network, and manage the OS and above.
  • A VM includes compute, disks, NIC, VNet, optional public IP and NSG.

✅ Benefits

  • Good for lift-and-shift of existing servers.
  • Wide choice of sizes, including GPU and memory-heavy ones.

⚠️ Problems

  • You must patch, secure and back up the OS yourself.
  • Costs run while the VM is allocated, even if idle.
  • More management work than PaaS services.

Interview questions and answers

What is an Azure VM and what do you manage?
A cloud computer under your control (IaaS). Azure manages the physical hardware and virtualization; you manage the operating system, patches, software, security settings and backups.
IaaS vs PaaS vs SaaS?
IaaS (VMs): you manage OS and up. PaaS (App Service, Azure SQL): Azure manages OS and runtime, you manage app and data. SaaS: you only use the software.
Cross question: When would you choose a VM instead of App Service?
When you need OS-level control, custom or legacy software that cannot run on PaaS, special drivers, or a lift-and-shift migration. Otherwise PaaS is easier and often cheaper to operate.
What resources make up a VM?
The VM, OS and data disks, a NIC in a VNet and subnet, an optional public IP, and an NSG, all inside a resource group.

📏 VM sizes, images and disks

Hinglish samajh: VM sizes series mein bante hain: B (burstable, sasta), D (general purpose), E (memory), F (compute), L (storage), N (GPU) aur M (bahut badi memory). Disks: Standard HDD, Standard SSD, Premium SSD, Premium SSD v2 aur Ultra. Temporary disk ka data VM badalne par chala jaata hai, isliye usme zaroori data na rakhein.

VM sizes are grouped in series (families) by purpose. B-series are burstable and cheap, for light workloads that sometimes need more CPU. D-series are general purpose (balanced CPU and memory) for most apps and databases. E-series are memory optimized for in-memory databases and caches. F-series are compute optimized (more CPU per memory). L-series are storage optimized for fast local disks. N-series have GPUs for AI and graphics. M-series are very large memory machines. Pick the family by workload, then the size by vCPU and memory, and resize later if needed (it usually needs a restart).

A VM starts from an image (Windows Server, Ubuntu, Red Hat, or your own custom image from the Azure Compute Gallery). It has an OS disk and optional data disks. Managed disks come in types: Standard HDD (cheapest, backups and rarely used data), Standard SSD (web servers and light workloads), Premium SSD (production and databases), Premium SSD v2 (tune size, IOPS and throughput separately) and Ultra Disk (highest performance and lowest latency for demanding databases). Disks are replicated: LRS or ZRS options keep copies for durability.

Every VM also has a temporary disk (local, fast) on many sizes. Data on the temporary disk is lost if the VM moves to another host or is redeployed, so use it only for swap, temp files and caches, never for important data. Use managed disks (Azure handles storage accounts for you) rather than unmanaged disks. Encrypt disks (Azure Disk Encryption or encryption at host, with platform or customer-managed keys).

  • Storing important data on the temporary disk loses it.
  • Oversized VMs and disks waste money; undersized ones hurt performance.

Interview questions and answers

How do you choose a VM size?
Pick the family by workload (D general, E memory, F compute, N GPU, L storage, B burstable), then size by vCPU and memory, measure usage, and resize or use Reserved Instances once the need is stable.
What disk types does Azure offer?
Standard HDD, Standard SSD, Premium SSD, Premium SSD v2 and Ultra Disk, increasing in performance and cost. Databases in production normally use Premium SSD or better.
Cross question: What is the temporary disk?
A local disk on the host for temporary data. Its data is lost when the VM is moved or redeployed, so never store important data there.
Cross question: A burstable VM becomes slow after some hours. Why?
B-series VMs earn CPU credits while idle and spend them when busy. When credits run out the CPU is throttled to its baseline, so move the workload to a D-series or larger size.

🛡️ Networking and security for VMs

Hinglish samajh: VM VNet aur subnet mein rehta hai; traffic NSG ke allow aur deny rules se control hota hai (kam priority number pehle). RDP ya SSH ko internet par khula na rakhein; Azure Bastion ya JIT access use karein. App traffic ke liye Load Balancer ya Application Gateway (WAF ke saath). Managed identity, patching, disk encryption aur monitoring bhi zaroori hain.

A VM lives in a virtual network (VNet), a private network in Azure that you divide into subnets. Each VM has a private IP; a public IP is optional and often unnecessary. Traffic is filtered by a Network Security Group (NSG), a list of allow and deny rules by source, destination, port and protocol, attached to a subnet or a NIC. Rules have priorities, and the lowest number is processed first. By default inbound traffic from the internet is denied.

Do not open RDP (3389) or SSH (22) to the whole internet. Use Azure Bastion, which lets you connect to a VM through the browser over TLS without a public IP on the VM. Or use just-in-time (JIT) VM access from Microsoft Defender for Cloud, which opens the management port only for a short time for approved requests. For traffic to the application, put VMs behind a load balancer (layer 4) or Application Gateway (layer 7, with WAF) rather than exposing each VM.

More security points: use a managed identity so the VM can call Azure services (Key Vault, Storage) without passwords; keep the OS patched (Update Manager); encrypt disks; install endpoint protection (Defender for Servers); and send logs to Azure Monitor and Log Analytics. Connect VNets with peering, and connect to on-premises with a VPN Gateway or ExpressRoute. Use Azure Firewall for central network filtering.

Interview questions and answers

How do you secure a VM in Azure?
Put it in a VNet with NSG rules, avoid public IPs, use Bastion or JIT for admin access, use a managed identity instead of passwords, patch with Update Manager, encrypt disks and enable Defender and monitoring.
What is an NSG?
A Network Security Group is a set of allow and deny rules for inbound and outbound traffic, matched by priority (lowest number first), attached to a subnet or a NIC.
Cross question: How do you let admins connect without exposing RDP or SSH?
Use Azure Bastion (browser-based, no public IP on the VM) or JIT VM access that opens the port temporarily after approval.
Cross question: Load Balancer or Application Gateway?
Load Balancer works at layer 4 (TCP, UDP). Application Gateway works at layer 7 (HTTP), with URL routing, TLS termination and an optional Web Application Firewall.

🔁 Availability, scale sets and backup

Hinglish samajh: Availability: single VM (Premium SSD) ka SLA 99.9%, Availability Set (fault aur update domains, ek data center mein) 99.95%, aur Availability Zones (alag data centers) 99.99%. VM Scale Set same VMs ko apne aap scale out aur in karta hai. Backup data ke khone ya kharab hone se bachata hai, Site Recovery region ke disaster ke liye hai. VM ko deallocate karne par hi compute billing ruki hoti hai.

A single VM can fail (hardware, host maintenance), so Azure gives ways to stay available, with SLAs that grow as you spread VMs wider. A single VM with Premium SSD or Ultra disks has a 99.9% SLA. An Availability Set spreads two or more VMs across fault domains (separate racks with their own power and network) and update domains (groups that are rebooted one at a time during maintenance) inside one data center, for a 99.95% SLA. Availability Zones spread VMs across physically separate data centers in a region, for a 99.99% SLA. Always run at least two VMs behind a load balancer for any real availability.

Virtual Machine Scale Sets (VMSS) manage a group of identical VMs that scale out and in automatically based on rules (for example CPU above 70%) or a schedule, and can be spread across zones. They suit stateless web and application tiers. Flexible orchestration is the recommended mode. To scale a stateful service you need extra design (shared state outside the VM).

For recovery, remember the difference: Azure Backup protects against data loss and corruption by taking backups (restore points) of VMs and disks. Azure Site Recovery protects against a disaster by replicating VMs to another region so you can fail over. Also know that deallocating a VM (stopping it from the portal or CLI so that it is "Stopped (deallocated)") stops compute billing, while merely shutting down the OS from inside leaves the VM allocated and still billed. Disks keep costing money either way.

Interview questions and answers

Explain Availability Sets and Availability Zones.
An Availability Set spreads VMs across fault domains and update domains in one data center (99.95% SLA). Availability Zones spread VMs across separate data centers in a region (99.99% SLA).
What is a VM Scale Set?
A group of identical VMs managed together that scale out and in automatically by rules or schedule, often behind a load balancer, and can span availability zones.
Cross question: Backup vs Site Recovery?
Backup creates restore points for recovering lost or corrupted data. Site Recovery replicates VMs to another region and lets you fail over during a regional disaster.
Cross question: Does stopping a VM stop billing?
Only if it is deallocated (Stopped, deallocated), which releases compute. Shutting down from inside the OS keeps it allocated and billed. Disk and IP costs continue.
Cross question: Maintenance reboots are planned. How do you avoid downtime?
Run at least two VMs in an availability set or across zones behind a load balancer, so only part of them restart at a time.

🎯 Cost, comparison and interview cheat sheet

Hinglish samajh: VM ka kharcha: compute (per second jab tak allocated), disks, network data out, IPs aur licenses. Bachat: Reservations (1 ya 3 saal), Savings Plan, Spot VMs (sasta par evict ho sakta hai), Hybrid Benefit, right-sizing, auto-shutdown aur deallocate. Chunav: full control ke liye VM, web apps ke liye App Service, event code ke liye Functions, containers ke liye ACI, Container Apps ya AKS.

How VM cost works: you pay for compute (per second while the VM is allocated), disks, network data leaving Azure, public IPs and extra services such as backup, plus licenses for Windows and SQL Server unless you use the Azure Hybrid Benefit with your own licenses. The main saving options are: Pay-as-you-go (flexible, most expensive), Reservations (commit to a VM size for 1 or 3 years for a large discount), Savings Plans for compute (commit to an hourly spend across services), Spot VMs (very cheap spare capacity that Azure can evict with short notice, good for batch, test and stateless jobs), and Dev/Test pricing.

Other cost habits: right-size using Azure Advisor recommendations, auto-shutdown dev machines, deallocate unused VMs, delete orphaned disks and IPs, use autoscale, and use the right disk type. Use tags and Cost Management budgets and alerts to see who spends what.

Choosing a compute service: Use VMs for full control or legacy software. VM Scale Sets for scalable stateless VM fleets. App Service for web apps without server management. Azure Functions for event-driven code. Containers (ACI, Container Apps, AKS) for container workloads. Azure Batch for large parallel jobs. Azure Virtual Desktop for desktops.

Interview questions and answers

How do you reduce Azure VM costs?
Right-size using Advisor, use Reservations or Savings Plans for steady workloads, Spot VMs for interruptible jobs, Hybrid Benefit for licenses, auto-shutdown for dev machines, deallocate unused VMs, delete orphaned disks and IPs, and use autoscale.
What is a Spot VM?
A VM that uses Azure's spare capacity at a big discount but can be evicted when Azure needs the capacity. Use it for batch, test and fault-tolerant stateless jobs.
Cross question: Reservation or Savings Plan?
A reservation gives the biggest discount for a specific VM size and region for 1 or 3 years. A savings plan commits to an hourly spend and is more flexible across sizes and regions, with a slightly smaller discount.
Cross question: A client wants to migrate an old application server to Azure with minimal changes. What do you suggest?
Lift-and-shift to a VM with the same OS, sized by measured usage, with a disk type that matches its I/O, in a VNet behind a load balancer. Later consider modernizing to PaaS or containers.
Cross question: How do you make a VM-based app highly available?
Run at least two VMs across Availability Zones behind a load balancer, use a scale set for autoscale, keep state outside the VMs, and back up with Azure Backup and Site Recovery for DR.
