🚌 What Azure Service Bus is and when to use it

Hinglish samajh: Azure Service Bus ek managed enterprise message broker hai. Sender message broker mein daalta hai aur receiver baad mein use leta hai; dono ko ek saath online hone ki zaroorat nahi. Isse system reliable aur scalable banta hai: receiver down ho to message safe rehta hai, aur traffic badhe to broker use sambhal leta hai. Orders aur payments jaise zaroori messages ke liye ise chunte hain.

Azure Service Bus is a fully managed enterprise message broker. A message broker sits between applications: one application (the sender or producer) puts a message in the broker, and another application (the receiver or consumer) takes it out later. The two do not need to be online at the same time and do not need to know about each other. This is called decoupling.

Why is this useful? It makes systems more reliable and scalable. If the receiver is down or slow, messages wait safely in the broker instead of being lost. If traffic suddenly rises, the broker absorbs the spike (load leveling) and receivers process at their own speed. You can also add more receivers to share the work (competing consumers).

Service Bus is chosen for business-critical messages that must not be lost, such as orders, payments and workflow commands. It offers features such as ordering, duplicate detection, transactions and dead-lettering. It speaks the AMQP protocol (and also HTTPS), and it has SDKs for .NET, Java, Python and JavaScript.

✨ Features

  • Fully managed enterprise message broker.
  • Queues for one receiver, topics for many receivers.
  • Ordering, duplicate detection, transactions and dead-lettering.

✅ Benefits

  • Sender and receiver are decoupled in time and in code.
  • Absorbs traffic spikes (load leveling).
  • Messages survive receiver failures.

⚠️ Problems

  • Messaging is asynchronous, so there is no instant reply.
  • Receivers must handle duplicates and failures.
  • Throughput and cost depend on the chosen tier.

Interview questions and answers

What is Azure Service Bus?
A managed enterprise message broker. Applications send messages to queues or topics, and other applications receive them later, so they are decoupled.
Why use a message broker?
To decouple services, absorb traffic spikes, keep messages safe if a receiver is down, and scale receivers independently.
Cross question: Give an example of a good Service Bus use.
An order service sends "order placed" messages; payment, inventory and email services each process them reliably, even if one of them is down for a while.
Cross question: What does decoupling in time mean?
The receiver does not have to be running when the message is sent. The message waits in the broker until the receiver is ready.

📬 Queues, topics and subscriptions

Hinglish samajh: Sab kuch namespace ke andar hota hai. Queue point-to-point hai: har message sirf ek receiver ko jaata hai (FIFO). Topic publish-subscribe hai: ek baar publish karne par har subscription ko apni copy milti hai, aur subscription par filter rules bhi lag sakte hain. Ek kaam ek worker ko dena ho to queue, aur ek event par kai systems ko react karna ho to topic chuniye.

Everything lives inside a namespace, which is a container with its own address (like mycompany.servicebus.windows.net) and its own access rules. Inside a namespace you create queues and topics.

A queue is point-to-point: many senders can send to it, but each message is delivered to one receiver only. If several receivers listen to the same queue, they compete and share the work. Messages are normally delivered in first-in, first-out (FIFO) order. Use a queue to hand a task to one worker, such as "process this order".

A topic is publish-subscribe: a sender publishes a message once to the topic, and every subscription gets its own copy. Each subscription is like a private queue for one application, and it can have filter rules so that it only receives the messages it cares about (for example only orders with country = "IN"). Use a topic when many different systems must react to the same event, such as billing, shipping and analytics all reacting to "order placed".

✨ Features

  • Namespace contains queues and topics.
  • Queue: one receiver per message (FIFO, competing consumers).
  • Topic: each subscription gets a copy and can filter.

⚠️ Problems

  • Choosing a queue when many systems need the event forces extra copying code.
  • Subscriptions without good filters receive messages they do not need.
  • A very slow subscription builds a backlog and can hit size limits.

Interview questions and answers

What is the difference between a queue and a topic?
A queue delivers each message to one receiver. A topic delivers a copy of each message to every subscription, and each subscription can filter what it receives.
What is a subscription?
A virtual queue attached to a topic. It receives copies of the topic's messages that match its filter rules and is read by one application.
Cross question: Two instances of the same service read from one queue. What happens?
They are competing consumers: each message goes to only one of them, so the work is shared.
Cross question: Two different services must react to the same event. Queue or topic?
A topic with one subscription per service, so each service gets its own copy and processes it independently.

🔒 Receiving messages safely: peek-lock and settlement

Hinglish samajh: Service Bus mein sabse zaroori baat message ko safely receive karna hai. Peek-lock mode (default) mein message receiver ko diya jaata hai aur kuch der ke liye lock ho jaata hai (default 30 second). Kaam hone par receiver Complete karta hai (message delete), Abandon karta hai (dobara try), ya Dead-letter karta hai. Lock expire ho ya receiver crash ho to message dobara aata hai, isliye receiver idempotent hona chahiye. Max delivery count (default 10) ke baad message dead-letter queue mein chala jaata hai.

The most important idea in Service Bus is how a message is received safely. There are two receive modes. In receive and delete, the broker removes the message the moment it is delivered. This is fast but risky: if the receiver crashes while processing, the message is lost (at-most-once). In peek-lock (the default and recommended mode), the broker gives the message to the receiver and locks it for a time (the lock duration, 30 seconds by default, up to 5 minutes). The message stays in the queue but is invisible to other receivers.

After processing, the receiver must settle the message by telling the broker what happened. Complete: success, so the message is deleted. Abandon: release the lock so the message becomes available again (a retry). Dead-letter: move it to the dead-letter queue because it can never succeed. Defer: set it aside to be fetched later by its sequence number. If the receiver crashes or the lock expires, the message becomes visible again and is delivered again. Each delivery increases the delivery count; when it passes the max delivery count (10 by default), the broker moves the message to the dead-letter queue (DLQ) automatically.

Because a message can be delivered more than once (at-least-once delivery), receivers must be idempotent: processing the same message twice must not cause harm (for example, check whether the order was already handled by its ID). The dead-letter queue is a special sub-queue for each queue or subscription that holds messages that could not be processed, so you can inspect, fix and resend them. Messages also expire after their time-to-live (TTL), and can be moved to the DLQ on expiry if you enable it.

✨ Features

  • Peek-lock locks a message while it is processed.
  • Complete, abandon, dead-letter and defer settle the message.
  • Max delivery count (default 10) sends repeat failures to the DLQ.

⚠️ Problems

  • If processing is longer than the lock duration, the message is delivered again.
  • Without idempotent receivers, duplicates cause double processing.
  • Nobody watching the DLQ means failed messages are silently ignored.

Interview questions and answers

Explain peek-lock.
The broker delivers the message and locks it for a period. The receiver processes it and then completes it (deleted), abandons it (retry) or dead-letters it. If the lock expires or the receiver crashes, the message becomes available again.
What is the dead-letter queue?
A sub-queue that holds messages that cannot be delivered or processed, for example after exceeding the max delivery count or when a receiver dead-letters them. You inspect and resend them.
Cross question: A message was processed twice. Why, and how do you prevent damage?
Service Bus guarantees at-least-once delivery, and a lock may expire or a crash may happen before completing. Make the receiver idempotent, for example by tracking processed message IDs, and consider duplicate detection on the sender side.
Cross question: Processing takes longer than the lock duration. What do you do?
Increase the lock duration (up to 5 minutes), renew the lock while working (the SDK processor can auto-renew), or split the work into smaller steps.
Cross question: When would you use receive and delete?
When losing an occasional message is acceptable and speed matters more, such as non-critical telemetry. Not for orders or payments.

🧰 Important features: sessions, duplicates, scheduling and filters

Hinglish samajh: Sessions se ek hi SessionId ke messages ek receiver ko order mein milte hain, jabki alag sessions parallel chalte hain. Duplicate detection MessageId se ek time window (default 10 minute) mein dobara aaye message ko hata deta hai. Scheduled messages baad ke samay par dikhte hain. Topic ke subscriptions par SQL ya correlation filter lagakar har subscriber ko sirf zaroori messages mil sakte hain.

Sessions give you ordered, grouped processing. You set a SessionId on messages (for example the customer ID). All messages with the same session ID are delivered to one receiver at a time, in order. This is how you get strict FIFO per group while still processing different groups in parallel. The queue must be created with sessions enabled.

Duplicate detection lets the broker drop a message if another message with the same MessageId arrived within a time window (10 minutes by default, configurable). This protects against a sender that retries after a timeout and accidentally sends twice. Scheduled messages are sent now but become visible only at a time you choose (for example a reminder in 24 hours). Time-to-live (TTL) makes messages expire if not processed in time. Auto-forwarding chains a queue or subscription to another queue. Transactions let you group several operations, such as complete one message and send another, so they succeed or fail together.

On topics, subscription rules decide which messages each subscription gets. A SQL filter uses a condition on message properties (for example country = 'IN' AND amount > 1000). A correlation filter matches exact property values and is faster. A boolean filter is always true or false. Filters let one topic serve many subscribers without each of them reading everything.

✨ Features

  • Sessions give FIFO per session ID with parallel groups.
  • Duplicate detection uses MessageId in a time window.
  • Scheduled messages, TTL, transactions, auto-forwarding and filters.

⚠️ Problems

  • Sessions limit parallelism to one receiver per session.
  • Duplicate detection only works within its time window and needs a stable MessageId.
  • Complex SQL filters on many subscriptions can slow publishing.

Interview questions and answers

How do you guarantee ordering in Service Bus?
Use sessions. Messages with the same SessionId are delivered in order to a single receiver, while different sessions are processed in parallel.
What is duplicate detection?
The broker drops a message if one with the same MessageId was already received within the detection window (default 10 minutes), protecting against sender retries.
Cross question: How do you send a reminder 24 hours from now?
Use a scheduled message with a scheduled enqueue time. It is accepted now and becomes visible to receivers at that time. You can also cancel it before it appears.
Cross question: How does a subscription receive only some messages?
It has a rule with a filter: a SQL filter (condition on properties), a correlation filter (exact property match, faster) or a boolean filter.
Cross question: Does Service Bus guarantee ordering without sessions?
Queues are generally FIFO, but with several competing receivers and retries the processing order can differ. Use sessions when order truly matters.

🎯 Tiers, security, comparison and interview cheat sheet

Hinglish samajh: Tiers: Basic mein sirf queues, Standard mein topics aur advanced features, Premium mein dedicated resources, VNet/Private Link aur 100 MB tak ke messages. Security ke liye Entra ID aur managed identity behtar hain, connection string nahi. Chunav: zaroori commands ke liye Service Bus, "kuch hua" ki notification ke liye Event Grid, bahut bade streaming ke liye Event Hubs, aur simple sasti queue ke liye Storage Queues.

Tiers. Basic has queues only (no topics), with small messages and basic features. Standard adds topics and subscriptions, transactions, sessions and duplicate detection, and is shared infrastructure billed per operation. Premium gives dedicated resources (messaging units) with predictable performance, VNet integration and Private Link, larger messages (up to 100 MB; Standard is 256 KB) and geo-disaster recovery. Choose Premium for production workloads that need isolation, steady latency or large messages.

Security. Prefer Microsoft Entra ID with managed identities and Azure roles such as Azure Service Bus Data Sender and Data Receiver, instead of connection strings. Shared Access Signatures (SAS) keys still exist but are harder to rotate and control. Use Private endpoints and firewall rules to keep traffic private. Data is encrypted at rest and in transit.

Choosing a messaging service. This is a favorite interview topic. Service Bus is for reliable business messages and commands that need guaranteed delivery, ordering, transactions and dead-lettering. Event Grid is for lightweight notifications of "something happened" (events) that are pushed to handlers. Event Hubs is for very high-volume streaming of events and telemetry (millions per second) that consumers read like a log. Storage Queues are simple, cheap queues for very large volumes when you do not need advanced features.

  • Basic (queues), Standard (topics and features), Premium (dedicated, private, 100 MB).
  • Entra ID with managed identities is preferred over SAS keys.
  • Choose between Service Bus, Event Grid, Event Hubs and Storage Queues by message type.

⚠️ Problems

  • Using connection strings with full rights in code is a security risk.
  • Standard tier shares resources, so latency can vary under load.
  • Picking Service Bus for high-volume telemetry is costly; Event Hubs fits better.

Interview questions and answers

Service Bus vs Event Grid vs Event Hubs?
Service Bus is a reliable broker for commands with ordering, transactions and dead-lettering. Event Grid pushes lightweight event notifications to handlers. Event Hubs ingests very high-volume event streams that consumers read like a log.
Which tier would you choose for production?
Premium when you need dedicated capacity, predictable latency, VNet or Private Link, large messages (up to 100 MB) or geo-disaster recovery. Standard for general workloads that do not need isolation.
Cross question: How do you secure access without keys?
Use managed identities with Entra ID and role assignments such as Data Sender and Data Receiver, plus private endpoints and firewall rules.
Cross question: Service Bus or Storage Queue?
Storage Queue is simpler and cheaper for very large, basic queues. Choose Service Bus when you need topics, sessions, ordering, duplicate detection, dead-lettering or transactions.
Cross question: How would you handle a poison message?
After the max delivery count it moves to the dead-letter queue. Alert on DLQ depth, inspect the message and its dead-letter reason, fix the cause, and resubmit if appropriate.
