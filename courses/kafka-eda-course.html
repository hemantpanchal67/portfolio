1. What is Apache Kafka?

Apache Kafka is an open-source distributed event streaming platform. It lets applications publish, store and process streams of events (records) in real time, reliably and at very large scale. Kafka was created at LinkedIn (2010), open-sourced in 2011 and became a top-level Apache project in 2012. It is written in Java and Scala and named after the author Franz Kafka.

  • Publish and subscribe to streams of events (like a messaging system).
  • Store events durably and in order for as long as you want (like a distributed commit log).
  • Process events as they occur or later (stream processing).
  • Runs as a cluster of servers called brokers; data is split into partitions and replicated.
  • Handles millions of events per second with low latency.

The idea in one picture

 Producers                 Kafka cluster                    Consumers
 (publish events)   --->   topic "orders"  (stored log)  --->  (subscribe & read)
 order-service             [0][1][2][3][4][5] ...              billing, analytics,
 sensors, apps             partitioned + replicated            email, search index
Analogy: Kafka is like a newspaper archive. Publishers keep adding new editions (events) in order; many readers read at their own speed and can come back to older editions.

2. What is Event-Driven Architecture (EDA)?

In an event-driven architecture services do not call each other directly. When something important happens (an event: OrderPlaced, PaymentFailed), the service that owns it publishes an event, and any interested services react. Kafka is the most common event backbone that carries these events.

Request / response (REST)Event-driven (Kafka)
CouplingCaller must know and wait for the calleeProducer does not know the consumers
AvailabilityFailure of one service can cascadeServices fail and recover independently; events wait in Kafka
ScalingScale whole call chain togetherScale each consumer group on its own
Adding featuresChange the callerAdd a new subscriber; no producer change
Data flowPull: ask when neededPush: react when something happens
HistoryNone unless you store itReplayable log of everything that happened

Event-carried state transferEvent contains the data consumers needCustomerUpdated {id, name, address}

5. Problems, Limitations & When NOT to Use Kafka

Kafka is powerful but has costs. Knowing them is a standard interview topic.

ProblemWhyMitigation
Operational complexityDistributed system: brokers, partitions, replication, tuningManaged Kafka (MSK, Confluent Cloud), KRaft, automation, Strimzi
Eventual consistencyAsynchronous flows; data is not instantly the same everywhereDesign for it: idempotency, sagas, clear ownership
Ordering is per partition onlyNo global order across partitionsChoose keys carefully; one partition if strict order is needed
Duplicates / at-least-onceRetries and rebalances re-deliverIdempotent consumers, transactions
Partition count is hard to changeCan increase but not decrease; changes key mappingPlan capacity early; over-partition moderately
RebalancesConsumer group pauses while partitions are reassignedCooperative assignor, static membership, tune timeouts
Debugging distributed flowsEvent chains are harder to traceCorrelation ids, tracing, schema registry, good observability
Not a database or request/reply toolNo ad-hoc queries, per-message priority or delayUse a database or a different broker for those
Small-message / low-volume overkillCluster overhead for tiny workloadsUse SQS/RabbitMQ or a simple queue
Schema evolutionBreaking changes break consumersSchema Registry with compatibility rules

Avoid Kafka when…

  • You only need a simple task queue with a few messages per second.
  • You need complex routing, per-message TTL, priorities or request/reply (RabbitMQ fits better).
  • You need strong cross-service ACID transactions rather than eventual consistency.
  • The team cannot operate (or pay for) a distributed system.

7. Events, Records & Messages

An event records that something happened. In Kafka it is stored as a record (also called a message). Every record has a key (optional), a value, a timestamp, optional headers, and, once stored, a partition and an offset.

PartPurpose
KeyDecides the partition; used for ordering and compaction (e.g. orderId)
ValueThe payload: JSON, Avro, Protobuf, bytes
TimestampEvent time or log-append time
HeadersMetadata such as trace id, event type, schema version
Partition / offsetAssigned by Kafka; the record's address

Example record (JSON value)

key:   "order-1001"
value: {
  "eventId": "e7c5f1b0-9a1e-4c1c-8a55-2d6c5b3d1f10",
  "type": "OrderCreated",
  "occurredAt": "2025-03-14T10:15:30Z",
  "orderId": "order-1001",
  "customerId": "cust-42",
  "items": [{ "sku": "BOOK-7", "qty": 2 }],
  "total": 59.90
}
headers: { "traceId": "abc123", "schemaVersion": "1" }
  • Kafka stores only bytes; serialisation is your choice.
  • Default maximum record size is about 1 MB (max.message.bytes); store large files elsewhere and send a reference.
  • Always include a unique eventId to make consumers idempotent.

8. Topics, Partitions & Offsets

A topic is a named stream of events. It is split into partitions, each an ordered, append-only log. Every record in a partition has an offset. Click the parts of the diagram.

ConceptMeaningRemember
TopicNamed category of eventsMany producers and consumers
PartitionOrdered log; unit of parallelism and storageOrder only inside a partition
OffsetPosition of a record in a partitionUnique per partition, never reused
KeyChooses the partition: murmur2(key) % partitionsSame key = same partition
Replication factorCopies of each partitionUsually 3

Create and describe a topic

kafka-topics.sh --bootstrap-server localhost:9092 --create --topic orders \
  --partitions 3 --replication-factor 3 --config retention.ms=604800000

kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders
# Topic: orders  PartitionCount: 3  ReplicationFactor: 3
#   Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
  • You can increase partitions later, but never decrease them, and increasing changes key-to-partition mapping.
  • More partitions = more parallelism, but more open files, memory and longer recovery.
  • Pick the key so related events (same customer or order) stay in order.

9. Brokers, Cluster & KRaft (vs ZooKeeper)

A broker is a Kafka server. A cluster is several brokers working together. Each partition has a leader on one broker and followers on others. A controller manages metadata and leader election.

ZooKeeper mode (old)KRaft mode (current)
Metadata stored inExternal ZooKeeper ensembleInternal Raft log (__cluster_metadata)
Extra systems to runZooKeeper clusterNone
Controller failoverSlower (reload from ZooKeeper)Fast (standby controllers already up to date)
ScalabilityLimited partition countsMillions of partitions possible
StatusRemoved in Kafka 4.0Only mode from Kafka 4.0

Minimal KRaft broker configuration

process.roles=broker,controller          # small cluster: one node does both
node.id=1
controller.quorum.voters=1@broker1:9093,2@broker2:9093,3@broker3:9093
listeners=PLAINTEXT://:9092,CONTROLLER://:9093
advertised.listeners=PLAINTEXT://broker1:9092
controller.listener.names=CONTROLLER
log.dirs=/var/lib/kafka/data
  • Production: dedicated controllers (3) and separate brokers.
  • Clients connect to any bootstrap server and then discover all brokers.
  • Spread brokers across availability zones and use broker.rack.

Partitioning rules

11. Consumers & Consumer Groups

A consumer pulls records in a poll loop. Consumers with the same group.id form a consumer group and share the partitions: each partition goes to exactly one consumer in the group. Watch the diagram: a new consumer joins and a rebalance moves a partition.

  • Scale out: add consumers (up to the number of partitions).
  • Failover: if a consumer dies its partitions move to others.
  • Pub/sub: different groups each get all records.
  • Offsets: each group stores its own progress in __consumer_offsets.
  • Lag = log end offset − committed offset; the key health metric.

12. Replication, ISR & High Watermark

Each partition is copied to several brokers. One copy is the leader; the others are followers that fetch from the leader. Followers that are fully caught up form the ISR (in-sync replicas). Click the diagram.

TermMeaning
Replication factor (RF)Number of copies (leader + followers)
ISRReplicas caught up within replica.lag.time.max.ms
High watermarkLast offset replicated to all ISR; consumers read only up to it
min.insync.replicasMinimum ISR size for acks=all writes
Preferred leaderFirst replica in the list; leadership rebalanced back to it
Unclean leader electionOut-of-sync replica becomes leader: availability over safety (off by default)

Durable configuration recipe

# topic / broker
replication.factor=3
min.insync.replicas=2
unclean.leader.election.enable=false
# producer
acks=all
enable.idempotence=true
With RF=3 and min.insync.replicas=2 you can lose one broker and keep both availability and durability.

13. Retention, Log Compaction & Tiered Storage

Kafka does not delete a record because it was read. Data is removed by retention rules or kept as the latest value per key by compaction.

PolicySettingBehaviour
Time retentionretention.ms (default 7 days)Delete segments older than the limit
Size retentionretention.bytesDelete oldest segments beyond the size
Compactioncleanup.policy=compactKeep at least the latest record per key; null value = tombstone deletes the key
Bothcleanup.policy=compact,deleteCompact and also expire
Tiered storageremote.storage.enable=trueMove old segments to object storage (S3) and keep recent data local

Compacted topic example

offset: 0   1   2   3   4   5
key:    A   B   A   C   B   A      (before compaction)
value:  v1  v1  v2  v1  v2  v3

after compaction -> latest per key:
        C:v1   B:v2   A:v3
  • Use compaction for changelogs, reference data and state (KTables, __consumer_offsets).
  • Compaction is eventual: older duplicates may still be readable for a while.

14. Life of a Message (End to End)

Follow one record from the producer to a consumer. Watch the highlighted step.

  1. Producer serialises, partitions, batches and compresses the record, then sends it to the partition leader.
  2. The leader appends it to its log and assigns an offset.
  3. Followers fetch it from the leader; the high watermark advances when all ISR members have it.
  4. The leader acknowledges the producer (acks=all).
  5. A consumer in a group polls from its last committed offset up to the high watermark.
  6. After processing, the consumer commits the offset; the record stays in the log until retention expires.

17. Producer & Consumer Code (.NET / C#)

For .NET use the Confluent.Kafka NuGet package (a .NET wrapper around the high-performance librdkafka C library). Install it with dotnet add package Confluent.Kafka. It supports .NET 6/8+ and works in console apps, worker services and ASP.NET Core.

Reliable producer

using Confluent.Kafka;

var config = new ProducerConfig
{
    BootstrapServers = "localhost:9092",
    Acks = Acks.All,                 // wait for all in-sync replicas
    EnableIdempotence = true,        // no duplicates on retry
    CompressionType = CompressionType.Lz4,
    LingerMs = 10                    // wait a little to build bigger batches
};

using var producer = new ProducerBuilder<string, string>(config).Build();

// awaitable: returns partition + offset when the broker acknowledges
var result = await producer.ProduceAsync("orders",
    new Message<string, string> { Key = "order-1001", Value = "{\"orderId\":\"order-1001\",\"total\":59.9}" });
Console.WriteLine($"partition={result.Partition.Value} offset={result.Offset.Value}");

// high-throughput style: fire and handle the result in a callback
producer.Produce("orders", new Message<string, string> { Key = "order-1002", Value = "{}" },
    report => { if (report.Error.IsError) Console.Error.WriteLine(report.Error.Reason); });

producer.Flush(TimeSpan.FromSeconds(10));   // wait for outstanding messages before exit

Consumer with manual commit (at-least-once)

using Confluent.Kafka;

var config = new ConsumerConfig
{
    BootstrapServers = "localhost:9092",
    GroupId = "billing",
    AutoOffsetReset = AutoOffsetReset.Earliest,
    EnableAutoCommit = false,                                   // we commit after processing
    PartitionAssignmentStrategy = PartitionAssignmentStrategy.CooperativeSticky
};

using var cts = new CancellationTokenSource();
Console.CancelKeyPress += (_, e) => { e.Cancel = true; cts.Cancel(); };

using var consumer = new ConsumerBuilder<string, string>(config).Build();
consumer.Subscribe("orders");
try
{
    while (true)
    {
        var cr = consumer.Consume(cts.Token);       // blocks until a record arrives
        Process(cr.Message.Key, cr.Message.Value);  // must be idempotent
        consumer.Commit(cr);                        // commit AFTER processing
    }
}
catch (OperationCanceledException) { }
finally { consumer.Close(); }                       // leave the group cleanly (commits, triggers rebalance)
  • ProduceAsync returns a Task; await it for confirmation, or use Produce with a delivery handler for maximum throughput.
  • Use typed serializers (ProducerBuilder<string, OrderCreated>().SetValueSerializer(...)), for example System.Text.Json or Avro/Protobuf with the Schema Registry client.
  • Create one producer per application and reuse it (thread-safe); creating one per request is slow.

Node.js (kafkajs)

const { Kafka } = require("kafkajs");
const kafka = new Kafka({ clientId: "shop", brokers: ["localhost:9092"] });

async function run() {
  const producer = kafka.producer({ idempotent: true });
  await producer.connect();
  await producer.send({ topic: "orders", acks: -1,
    messages: [{ key: "order-1001", value: JSON.stringify({ total: 59.9 }) }] });

  const consumer = kafka.consumer({ groupId: "billing" });
  await consumer.connect();
  await consumer.subscribe({ topic: "orders", fromBeginning: true });
  await consumer.run({
    autoCommit: false,
    eachMessage: async ({ topic, partition, message }) => {
      console.log(message.key.toString(), message.value.toString());
      await consumer.commitOffsets([{ topic, partition, offset: (Number(message.offset) + 1).toString() }]);
    },
  });
}

19. ASP.NET Core & Worker Services with Kafka

In a real .NET application register Kafka clients with dependency injection: a singleton IProducer for publishing (for example from a minimal API) and a BackgroundService that runs the consumer loop.

appsettings.json

{
  "Kafka": { "BootstrapServers": "localhost:9092", "GroupId": "billing", "Topic": "orders" }
}

Program.cs (web API that publishes + worker that consumes)

using Confluent.Kafka;
using Microsoft.Extensions.Options;
using System.Text.Json;

var builder = WebApplication.CreateBuilder(args);
builder.Services.Configure<KafkaOptions>(builder.Configuration.GetSection("Kafka"));

// one shared, thread-safe producer
builder.Services.AddSingleton<IProducer<string, string>>(sp =>
{
    var o = sp.GetRequiredService<IOptions<KafkaOptions>>().Value;
    return new ProducerBuilder<string, string>(new ProducerConfig
    {
        BootstrapServers = o.BootstrapServers, Acks = Acks.All, EnableIdempotence = true
    }).Build();
});
builder.Services.AddScoped<IBillingService, BillingService>();
builder.Services.AddHostedService<OrderConsumer>();

var app = builder.Build();

app.MapPost("/orders", async (OrderRequest req, IProducer<string, string> producer, IOptions<KafkaOptions> opt) =>
{
    var evt = new OrderCreated(Guid.NewGuid(), req.OrderId, req.CustomerId, req.Total);
    var result = await producer.ProduceAsync(opt.Value.Topic,
        new Message<string, string> { Key = req.OrderId, Value = JsonSerializer.Serialize(evt) });
    return Results.Accepted($"/orders/{req.OrderId}", new { result.Partition.Value, Offset = result.Offset.Value });
});
app.Run();

public record KafkaOptions { public string BootstrapServers { get; init; } = ""; public string GroupId { get; init; } = ""; public string Topic { get; init; } = ""; }
public record OrderRequest(string OrderId, string CustomerId, decimal Total);
public record OrderCreated(Guid EventId, string OrderId, string CustomerId, decimal Total);

OrderConsumer.cs (BackgroundService)

public class OrderConsumer(IOptions<KafkaOptions> options, IServiceScopeFactory scopes, ILogger<OrderConsumer> log) : BackgroundService
{
    protected override Task ExecuteAsync(CancellationToken stoppingToken) =>
        Task.Run(() => Loop(stoppingToken), stoppingToken);      // Consume() is a blocking call

    private void Loop(CancellationToken ct)
    {
        var o = options.Value;
        var cfg = new ConsumerConfig
        {
            BootstrapServers = o.BootstrapServers, GroupId = o.GroupId,
            AutoOffsetReset = AutoOffsetReset.Earliest,
            EnableAutoCommit = false,
            PartitionAssignmentStrategy = PartitionAssignmentStrategy.CooperativeSticky
        };
        using var consumer = new ConsumerBuilder<string, string>(cfg).Build();
        consumer.Subscribe(o.Topic);
        try
        {
            while (!ct.IsCancellationRequested)
            {
                var cr = consumer.Consume(ct);
                using var scope = scopes.CreateScope();               // scoped services (DbContext...) per message
                var evt = JsonSerializer.Deserialize<OrderCreated>(cr.Message.Value)!;
                scope.ServiceProvider.GetRequiredService<IBillingService>().Charge(evt);   // idempotent
                consumer.Commit(cr);
            }
        }
        catch (OperationCanceledException) { log.LogInformation("Consumer stopping"); }
        finally { consumer.Close(); }
    }
}
  • Add health checks (for example AspNetCore.HealthChecks.Kafka) and expose lag metrics to Prometheus.
  • Run several instances (pods) of the worker with the same GroupId to scale out, up to the number of partitions.
  • For Aspire there is a Kafka integration (Aspire.Confluent.Kafka) that wires clients, health checks and telemetry.

producer.InitTransactions(TimeSpan.FromSeconds(30));

while (true)
{
    var cr = consumer.Consume(TimeSpan.FromMilliseconds(500));
    if (cr is null) continue;

    producer.BeginTransaction();
    try
    {
        producer.Produce("payments", new Message<string, string> { Key = cr.Message.Key, Value = Charge(cr.Message.Value) });
        producer.SendOffsetsToTransaction(
            new[] { new TopicPartitionOffset(cr.TopicPartition, cr.Offset + 1) },   // next offset to read
            consumer.ConsumerGroupMetadata, TimeSpan.FromSeconds(30));
        producer.CommitTransaction();      // output record + consumed offset become visible atomically
    }
    catch (Exception)
    {
        producer.AbortTransaction();
    }
}
// consumers of "payments" must use IsolationLevel.ReadCommitted
Exactly-once holds inside Kafka. For databases and APIs use idempotent writes (unique keys, upserts) or the outbox pattern.

22. Ordering Guarantees

Kafka guarantees order within a single partition only. Everything else must be designed.

QuestionAnswer
Is there global order across a topic?No. Only per partition.
How do I keep all events of one entity in order?Use the entity id as the record key.
Can retries break order?Yes without idempotence and with several in-flight requests. Idempotent producer (default) keeps order with up to 5 in-flight.
What if I add partitions?New records of a key may move to a different partition, so order across the change is not guaranteed.
Do consumer groups keep order?Yes per partition; but if you process records of one partition in parallel threads you lose it.
How to get strict global order?A single partition (limits throughput).
// all events of one order go to the same partition -> processed in order
await producer.ProduceAsync("orders", new Message<string, string> { Key = order.Id, Value = json });

23. Offset Commit Strategies

Committing an offset tells Kafka "I have finished everything before this offset". When you commit decides your delivery guarantee.

StrategyHowGuarantee / risk
Auto commitenable.auto.commit=true, every 5 sMay commit before processing finishes: possible loss or duplicates
Sync commit after batchcommitSync() after processingAt-least-once; blocks; simple and safe
Async commitcommitAsync() + callbackFaster; failed commit may re-process; commitSync on shutdown
Per-record commitCommit specific offsetsFine-grained, slower
TransactionalOffsets in the producer transactionExactly-once in Kafka
External storeSave offset in your DB with the resultExactly-once with that DB (seek on startup)
// Pattern 1: store the offset after processing; the client commits stored offsets in the background
var cfg = new ConsumerConfig { BootstrapServers = "localhost:9092", GroupId = "billing",
    EnableAutoCommit = true,            // background commit...
    EnableAutoOffsetStore = false };    // ...but ONLY offsets we store ourselves (after processing)

using var consumer = new ConsumerBuilder<string, string>(cfg).Build();
consumer.Subscribe("orders");
try
{
    while (!ct.IsCancellationRequested)
    {
        var cr = consumer.Consume(ct);
        Process(cr);
        consumer.StoreOffset(cr);                 // safe at-least-once, no per-message commit round trip
    }
}
catch (OperationCanceledException) { }
finally { consumer.Close(); }                      // commits stored offsets, then leaves the group

A message that fails must not block the partition or disappear. Classify errors, retry the transient ones without blocking, and park the rest in a dead letter topic (DLT).

.NET retries (Polly) + retry topic + DLT

// dotnet add package Polly
var quick = Policy.Handle<TransientException>()
                  .WaitAndRetryAsync(3, n => TimeSpan.FromMilliseconds(200 * Math.Pow(2, n)));   // short in-process retries

while (!ct.IsCancellationRequested)
{
    var cr = consumer.Consume(ct);
    var attempt = GetAttempt(cr.Message.Headers);                         // header "retry-count"
    try
    {
        await quick.ExecuteAsync(() => HandleAsync(cr.Message.Value));
    }
    catch (TransientException) when (attempt < 2)
    {
        // non-blocking retry: park the record on a delayed retry topic and keep consuming
        await producer.ProduceAsync(attempt == 0 ? "orders.retry.1m" : "orders.retry.10m",
            Copy(cr.Message, retryCount: attempt + 1));
    }
    catch (Exception ex)                                                  // permanent error or retries exhausted
    {
        var dead = Copy(cr.Message, retryCount: attempt);
        dead.Headers.Add("error", Encoding.UTF8.GetBytes(ex.Message));
        dead.Headers.Add("orig-topic", Encoding.UTF8.GetBytes(cr.Topic));
        dead.Headers.Add("orig-offset", Encoding.UTF8.GetBytes(cr.Offset.ToString()));
        await producer.ProduceAsync("orders.DLT", dead);                  // alert + redrive later
    }
    consumer.Commit(cr);                                                  // the main topic keeps flowing
}

32. Event-Driven Microservices on Kafka (Outbox + Saga)

A complete flow: the order service writes to its database and an outbox; Debezium publishes it to Kafka; payment, inventory and notification services react in a saga (choreography) and compensate on failure. Click each part.

  1. Customer places an order. Order service stores the order and an outbox row in one transaction.
  2. Debezium CDC reads the DB log and publishes OrderCreated to Kafka.
  3. Payment service consumes it, charges the card and publishes PaymentCompleted (or PaymentFailed).
  4. Inventory service reserves stock and publishes InventoryReserved (or OutOfStock).
  5. Notification service emails the customer; analytics updates dashboards.
  6. On failure, compensating events (refund, cancel order) undo earlier steps.

34. Idempotent Consumers & Deduplication

Because delivery is at-least-once, the same event can arrive twice. An idempotent consumer produces the same result however many times it processes an event.

TechniqueHow
Natural idempotencyUpsert / set-to-value instead of increment
Processed-id tableInsert eventId with a unique constraint in the same transaction as the effect
Conditional writeINSERT … ON CONFLICT DO NOTHING, DynamoDB conditional put
VersioningApply only if event version > stored version
Kafka transactionsExactly-once for Kafka-to-Kafka flows
public async Task HandleAsync(PaymentRequested e)
{
    await using var tx = await _db.Database.BeginTransactionAsync();
    if (await _db.ProcessedEvents.AnyAsync(p => p.EventId == e.EventId)) return;   // duplicate -> ignore

    _db.Ledger.Add(new LedgerEntry(e.CustomerId, -e.Amount));                      // the effect, same transaction

    await tx.CommitAsync();
}

41. Interview Q&A – Kafka Fundamentals

Each answer has a short answer you can say first, then the detail that proves you understand it. In practice mode (button above) the answers are hidden until you tap a question. Tap the 🔊 button next to the heading to hear everything read aloud.

Q1. What is Apache Kafka?

Short answer: Kafka is a distributed, fault-tolerant, high-throughput event streaming platform. Producers publish records to topics, Kafka stores them durably in a replicated log, and consumers read them, in real time or later.

Kafka was created at LinkedIn (2010) to move huge amounts of activity data between systems, was open-sourced in 2011 and is now an Apache top-level project. It combines three capabilities that used to need separate tools:

  • Messaging: publish/subscribe between applications, like a queue but with many independent readers.
  • Storage: records are written to disk, replicated and kept for a configurable time (days, forever, or latest-per-key). They are not deleted when read.
  • Stream processing: records can be filtered, joined and aggregated continuously with Kafka Streams, ksqlDB or Flink.

A Kafka cluster is a set of servers (brokers). Topics are split into partitions, and each partition is replicated on several brokers, which gives both scale and fault tolerance.

💡 Interview tip: Do not describe Kafka only as "a message queue". Say "a distributed commit log / event streaming platform", then mention retention and replay, because that is exactly what separates it from queues.

Q2. What are the main components of Kafka?

Short answer: Producers, consumers, brokers (the cluster), topics and partitions, replicas, consumer groups, the controller (KRaft), and the surrounding ecosystem (Connect, Streams, Schema Registry).

  • Producer: client that writes records to a topic.
  • Consumer / consumer group: client(s) that read records; a group shares partitions.
  • Broker: server that stores partitions and serves reads/writes. 3+ brokers form a cluster.
  • Topic: named stream; partition: ordered log inside a topic; offset: record position.
  • Replica: copy of a partition; one leader and several followers (the ISR is the in-sync subset).
  • Controller: manages metadata and leader election. In KRaft mode it is a Raft quorum built into Kafka; older versions used ZooKeeper.
  • Ecosystem: Kafka Connect (integration), Kafka Streams/ksqlDB (processing), Schema Registry (data contracts).

Flow in one sentence: producers append to partition leaders, followers replicate, consumers in a group pull from their assigned partitions and track progress with committed offsets.

💡 Interview tip: Draw it: producers → brokers (leader/follower partitions) → consumer groups. Interviewers like a quick sketch more than a list.

Q3. What are a topic, a partition and an offset?

Short answer: A topic is a named stream of records, a partition is one ordered, append-only log that makes up part of the topic, and an offset is the sequential position of a record inside one partition.

Think of a topic orders with 3 partitions as 3 separate notebooks. New records are only ever written at the end of a notebook, and every line gets the next number (offset 0, 1, 2 …). Key facts:

  • Order is guaranteed only inside a partition, not across the whole topic.
  • Offsets are unique per partition. "Partition 1, offset 42" identifies exactly one record.
  • Records are immutable; they are removed only by retention or compaction.
  • A consumer group stores, per partition, the offset it should read next (the committed offset).
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic orders --partitions 3 --replication-factor 3
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders --from-beginning \
  --property print.partition=true --property print.offset=true

💡 Interview tip: A frequent follow-up is "is there ordering across partitions?" Answer: no, so you choose a key that keeps related events in the same partition.

Q4. Why does Kafka use partitions?

Short answer: Partitions let Kafka scale horizontally (spread data and traffic over many brokers and consumers) while still preserving order within each partition.

A single log on a single server would be limited by one machine's disk, network and CPU. Splitting a topic into partitions gives:

  • Write scalability: different partitions can have their leaders on different brokers, so producers write in parallel.
  • Read scalability: in a consumer group each partition is read by one consumer, so adding consumers (up to the partition count) adds throughput.
  • Storage scalability: a topic can be larger than any single disk.
  • Fault tolerance: each partition is replicated independently.
  • Ordering with parallelism: records with the same key go to the same partition, so one entity's events stay in order while many entities are processed concurrently.

Trade-offs: too many partitions means more open files, more memory, slower leader elections and longer recovery; too few caps your parallelism. You can increase the count later but never decrease it.

💡 Interview tip: Mention the sizing rule: partitions ≥ target throughput ÷ per-partition throughput, and ≥ the maximum number of consumers you ever want in a group.

Q5. What is a broker?

Short answer: A broker is a single Kafka server. It stores partition data on disk and handles produce and fetch requests; several brokers form a cluster.

Each broker has a unique id. For a given partition one broker is the leader (serves all reads and writes) and others hold follower replicas. A broker is therefore leader for some partitions and follower for others, which spreads load evenly. Brokers also:

  • store data as segment files on local disk and lean on the OS page cache for speed;
  • serve clients with the binary Kafka protocol; any broker can answer metadata requests (this is why clients only need a few "bootstrap" addresses);
  • take part in replication by letting followers fetch from them;
  • in KRaft mode may also act as controllers (small clusters) or be dedicated brokers (large clusters).

If a broker fails, the controller elects new leaders for its partitions from the in-sync replicas on other brokers, and clients refresh metadata and carry on.

💡 Interview tip: Say that clients talk directly to partition leaders, not through a central router. It shows you know why Kafka scales.

Q6. What is the role of ZooKeeper, and what replaced it?

Short answer: In older Kafka, ZooKeeper stored cluster metadata and elected the controller. It is replaced by KRaft, a Raft-based metadata quorum built into Kafka; ZooKeeper support was removed in Kafka 4.0.

What ZooKeeper did: kept the list of brokers and topics, partition leaders and ISR, topic configs and ACLs, and ran the election of the active controller broker. Every metadata change went through ZooKeeper and then had to be pushed to brokers, which became a bottleneck and a second system to operate, secure and scale.

What KRaft changes:

  • Metadata lives in an internal log (__cluster_metadata) replicated by a quorum of controller nodes using Raft.
  • No separate ZooKeeper cluster: simpler deployment, one security model, one set of tools.
  • Much faster controller failover (standbys already hold the latest metadata) and support for millions of partitions.
  • Brokers fetch metadata updates from the controller quorum instead of being pushed state.
process.roles=broker,controller
node.id=1
controller.quorum.voters=1@b1:9093,2@b2:9093,3@b3:9093

💡 Interview tip: If asked "which version?": KRaft became production-ready in 3.3, ZooKeeper was deprecated in 3.5 and removed in 4.0.

Q7. How is Kafka different from a traditional message queue?

Short answer: Kafka is a persistent, replayable log; a traditional queue is a transient buffer. In Kafka consumers pull and track their own position, messages stay after being read, and many groups can read the same data independently.

  • Retention vs deletion: queues delete a message once it is acknowledged. Kafka keeps it for the retention period, so you can replay or add a new consumer later.
  • Multiple readers: with a queue each message goes to one worker. In Kafka each consumer group gets every message, and within a group partitions are shared (queue behaviour per group).
  • Ordering: Kafka orders per partition; queues usually order per queue but break order with competing consumers.
  • Throughput and scale: partitioning and sequential I/O give Kafka much higher throughput.
  • Smart client vs smart broker: Kafka brokers are simple; consumers track offsets. Brokers like RabbitMQ route, prioritise, delay and track per-message acks.

So use Kafka for event streaming, event sourcing, data pipelines and high-volume integration. Use RabbitMQ or SQS for simple task queues, per-message TTL, priorities or request/reply.

💡 Interview tip: Give one concrete example: "a new analytics service can start from offset 0 and rebuild its state; with a queue that history would be gone."

Q8. Why is Kafka so fast?

Short answer: Kafka turns disk into a fast sequential pipeline: append-only writes, OS page cache, zero-copy transfers, batching and compression, all spread across partitions.

  • Sequential I/O: appending to the end of a log file is far faster than random writes; reading is also sequential.
  • Page cache: Kafka relies on the operating system cache instead of its own heap cache, so recent data is served from RAM without GC pressure.
  • Zero-copy: sendfile moves data from the page cache directly to the network socket without copying through user space.
  • Batching: producers send batches and consumers fetch batches, amortising network and disk overhead.
  • Compression: whole batches are compressed (lz4/zstd) and stay compressed on disk until consumers decompress.
  • Partitioned parallelism: many partitions across many brokers and consumers work in parallel.
  • Simple protocol and dumb broker: no per-message bookkeeping on the broker.

💡 Interview tip: Name at least four reasons and make sure "sequential disk access" and "zero-copy" are among them.

Q9. Does Kafka delete a message after it is consumed?

Short answer: No. Consumption does not remove data. Records are deleted only by retention (time or size limits) or rewritten by log compaction.

The broker does not even know whether a message was "consumed"; it only knows each group's committed offset. Because of this, five different consumer groups can read the same topic at five different speeds, and any group can rewind its offset to reprocess history.

  • Default: retention.ms = 7 days; retention.bytes can also cap size.
  • cleanup.policy=compact keeps the latest record per key indefinitely.
  • Data older than retention may be deleted even if no consumer has read it, so slow consumers can lose data if lag exceeds retention.

💡 Interview tip: Bring up the failure mode: "if lag is bigger than retention, the oldest unread records disappear, so alert on lag before that happens."

Q10. What is the default retention period and how do you change it?

Short answer: The default is 7 days (log.retention.hours=168 on the broker, retention.ms=604800000 per topic). You can change it per topic at any time.

kafka-configs.sh --bootstrap-server localhost:9092 --entity-type topics --entity-name orders \
  --alter --add-config retention.ms=86400000        # 1 day

# size based, per partition
kafka-configs.sh ... --add-config retention.bytes=10737418240

Retention is applied to whole log segments, not individual records, and only closed (non-active) segments are deleted, so data can live a little longer than the setting. Tune segment.ms/segment.bytes for finer control. Whichever of time or size limit is hit first triggers deletion. For long-term history use tiered storage or sink the data to object storage with Kafka Connect.

💡 Interview tip: Mention that disk planning is throughput × retention × replication factor.

Q11. What is a Kafka record made of?

Short answer: A record has an optional key, a value, a timestamp and optional headers; once stored it also has a partition and an offset.

  • Key: decides the partition (hash) and is the identity used by log compaction; use the entity id such as orderId.
  • Value: the payload (JSON, Avro, Protobuf, bytes). Kafka itself only stores bytes.
  • Timestamp: creation time (set by producer) or log-append time (set by broker), per topic config.
  • Headers: key/value metadata like trace id, event type, schema version, correlation id.

Default maximum record size is about 1 MB (message.max.bytes). For big payloads (files, images) store them in object storage and send a reference (claim-check pattern).

💡 Interview tip: Add a unique event id in the payload or headers; it is what makes idempotent processing possible later.

Q12. What is log compaction?

Short answer: Log compaction is a cleanup policy (cleanup.policy=compact) that guarantees Kafka keeps at least the latest record for every key, discarding older values for the same key.

Instead of deleting by age, a background cleaner thread rewrites old segments and drops records that have a newer record with the same key. A record with a null value (a tombstone) marks the key as deleted and is removed after delete.retention.ms.

before: A:1  B:1  A:2  C:1  B:2  A:3
after : C:1  B:2  A:3          (latest per key survives)
  • Perfect for changelogs, reference data and state: __consumer_offsets, Kafka Streams state-store changelogs, KTables, CDC topics.
  • It is eventual: duplicates may remain until the cleaner runs; the active segment is never compacted.
  • Order of the remaining records is preserved and offsets are not changed.

💡 Interview tip: Contrast with time-based retention: "retention keeps the last N days of events; compaction keeps the last value of every key forever".

Q13. What is a consumer group?

Short answer: A consumer group is a set of consumers with the same group.id that divide the partitions of a topic among themselves, so each record is processed by one member of the group.

  • Scalability: add consumers to process faster, up to the number of partitions.
  • Fault tolerance: if a member dies, its partitions are reassigned (a rebalance).
  • Independence: each group keeps its own offsets, so billing and analytics read the same topic without affecting each other.
  • Queue vs pub/sub: one group sharing the work = queue; several groups each receiving everything = publish/subscribe.

Membership is coordinated by a broker called the group coordinator, using heartbeats. Progress is stored in the internal topic __consumer_offsets.

💡 Interview tip: Be ready for "what if consumers > partitions?" Answer: the extra consumers sit idle.

Q14. What is the maximum useful number of consumers in a group?

Short answer: It equals the number of partitions of the subscribed topics. A partition is assigned to at most one consumer in a group, so extra consumers receive nothing.

Example: topic with 6 partitions and 10 consumers in one group → 6 consumers get one partition each, 4 are idle (they are hot standbys that take over if a member fails). If you have 6 partitions and 3 consumers, each gets 2 partitions.

  • To scale beyond the limit you must add partitions (this changes key-to-partition mapping).
  • Parallelism inside one consumer (threads) is possible but you must keep per-partition order and manage offset commits carefully.
  • Different groups are not limited by each other.

💡 Interview tip: This is why partition count is a capacity-planning decision: pick it for your future peak consumer parallelism.

Q15. What is a bootstrap server?

Short answer: A bootstrap server is the address of any broker the client uses for its first connection to discover the whole cluster.

Clients are configured with bootstrap.servers=b1:9092,b2:9092. On connecting they request metadata: all brokers, topics, partitions and which broker leads each partition. After that they connect directly to the right brokers. Give two or three addresses so the client can still start if one broker is down; you do not need to list every broker.

  • A common production problem is a wrong advertised.listeners: the broker returns an address the client cannot reach, so bootstrapping works but later connections fail.
  • Behind a load balancer or in Kubernetes each broker still needs its own reachable advertised address.

💡 Interview tip: Mention advertised.listeners, it is the most common real-world connection issue.

Q16. What are the partition leader and followers?

Short answer: For every partition one replica is the leader and handles all reads and writes; the other replicas are followers that continuously copy the leader's log and take over if the leader fails.

  • Followers replicate by fetching from the leader, like consumers.
  • The leader tracks which followers are in sync (the ISR) and advances the high watermark when all ISR members have a record.
  • If the leader fails, the controller picks a new leader from the ISR, so no acknowledged data is lost (with the right settings).
  • Leadership is spread across brokers to balance load; a preferred leader is restored after recovery.

Consumers normally read from the leader, but since Kafka 2.4 they can fetch from the closest replica (KIP-392) to save cross-zone traffic.

💡 Interview tip: Link leaders to producer acks: "acks=all waits for the whole ISR, not just the leader."

Q17. What is the ISR (In-Sync Replicas)?

Short answer: The ISR is the set of replicas (leader plus followers) that are fully caught up with the leader within replica.lag.time.max.ms.

  • Only ISR members are eligible to become leader (unless unclean election is enabled).
  • A follower that lags too long is dropped from the ISR and rejoins when it catches up.
  • acks=all waits for every ISR member; min.insync.replicas sets the minimum ISR size needed to accept the write.
  • If the ISR shrinks below the minimum, producers get NotEnoughReplicas instead of risking data loss.
RF=3, min.insync.replicas=2
ISR = {1,2,3}  -> write ok            ISR = {1,2} -> write ok
ISR = {1}      -> acks=all write rejected (protects durability)

💡 Interview tip: Monitor UnderReplicatedPartitions (should be 0) and ISR shrink/expand rates; they are early warnings.

Q18. What is the maximum message size?

Short answer: About 1 MB by default (message.max.bytes on the broker, max.message.bytes per topic). It can be raised, but large records are discouraged.

To send bigger payloads you must align several settings: producer max.request.size, broker/topic max.message.bytes, replica replica.fetch.max.bytes and consumer max.partition.fetch.bytes. Big messages increase memory use, GC, replication time and latency, and can block a partition when slow to process.

  • Prefer the claim-check pattern: store the file in S3/Blob storage and put the URL/metadata in the Kafka record.
  • Compress records or split large payloads into chunks if you must.

💡 Interview tip: Interviewers like the claim-check pattern as the "right" answer.

Q19. What is event streaming?

Short answer: Event streaming is capturing data as a continuous flow of events in real time, storing it durably, and processing or routing it continuously instead of in periodic batches.

An event is a fact that something happened (order placed, sensor read, payment failed). Streaming platforms like Kafka let you: (1) publish and subscribe to events, (2) store them reliably for as long as needed, and (3) process them as they occur or retrospectively. This enables real-time dashboards, fraud detection, event-driven microservices, data pipelines and event sourcing.

💡 Interview tip: Contrast with batch: "nightly ETL answers yesterday's questions; streaming answers them now."

Q20. What are the typical use cases of Kafka?

Short answer: Event-driven microservices, real-time analytics, log and metrics aggregation, change data capture and data integration, stream processing, IoT/telemetry ingestion, and event sourcing.

  • Microservice backbone: services publish and react to domain events (orders, payments).
  • Real-time analytics and monitoring: clickstreams, live dashboards, fraud scoring.
  • Log aggregation: collect logs and metrics from thousands of hosts into one pipeline.
  • CDC / integration: stream database changes (Debezium) to search, cache, warehouse.
  • IoT: ingest very high event volumes from devices and vehicles.
  • Event sourcing and audit: immutable ordered history of what happened.

Where it is not a good fit: tiny low-volume workloads, request/reply, per-message priorities or delays, or when your team cannot operate a distributed system (use a managed service or a simpler queue).

💡 Interview tip: Pick one use case from your own experience and walk through topics, producers, consumers and failure handling.

42. Interview Q&A – Producers, Consumers & Reliability

Reliability is the most asked Kafka topic. Learn the settings and also why each exists.

Q1. Explain acks=0, acks=1 and acks=all.

Short answer: acks controls when a producer considers a write successful: 0 = do not wait, 1 = leader has written it, all = all in-sync replicas have written it.

  • acks=0: fastest; the producer does not know if the broker received it. Data can be lost silently. Use for metrics where loss is acceptable.
  • acks=1: the leader appended the record, but if the leader crashes before followers copy it, the record is lost although the producer was told "success".
  • acks=all (default since Kafka 3.0): the leader waits until every replica in the ISR has the record. Combined with min.insync.replicas=2 a record acknowledged to the producer survives the loss of any single broker.

Trade-off: stricter acks add latency (a round trip to followers) and can reduce availability when the ISR is too small.

var cfg = new ProducerConfig { BootstrapServers = "b1:9092", Acks = Acks.All, EnableIdempotence = true };

💡 Interview tip: Always connect acks to min.insync.replicas; acks=all alone with an ISR of one equals acks=1.

Q2. How do you guarantee that no data is lost?

Short answer: Replicate and acknowledge properly on the producer and broker side, and commit consumer offsets only after processing: RF≥3, min.insync.replicas≥2, acks=all, idempotence on, no unclean leader election, commit after processing.

  • Topic/broker: replication.factor=3, min.insync.replicas=2, unclean.leader.election.enable=false, brokers spread over availability zones (broker.rack).
  • Producer: acks=all, enable.idempotence=true, retries (default is effectively unlimited until delivery.timeout.ms), handle send failures in the callback.
  • Consumer: enable.auto.commit=false, process first then commit (at-least-once), make processing idempotent.
  • Operations: monitor under-replicated partitions, keep disks healthy, back up/mirror to another cluster for disaster recovery.

Remember "no data loss" is about acknowledged data. If a producer gives up after timeouts without a retry or a dead-letter path, that message is lost on the application side.

💡 Interview tip: Give the full recipe in order (topic → producer → consumer) and mention what you give up: latency and some availability.

Q3. What is an idempotent producer?

Short answer: An idempotent producer (enable.idempotence=true, default since Kafka 3.0) makes retries safe: the broker detects and discards duplicate batches so each record is written exactly once per partition.

How it works: the broker gives the producer a Producer ID (PID). Every batch carries a sequence number per partition. If a network error causes the producer to resend a batch the broker already wrote, the sequence number matches and the broker simply acknowledges it again without appending a duplicate. It also preserves ordering across retries (with up to 5 in-flight requests).

  • Scope: one producer session and partition. If the application restarts it gets a new PID, so cross-session de-duplication needs transactions or an idempotent consumer.
  • Requires acks=all and max.in.flight.requests.per.connection ≤ 5.

💡 Interview tip: Say clearly: idempotence stops producer retry duplicates; it does not stop duplicates caused by consumers reprocessing.

Q4. What are Kafka transactions and when do you use them?

Short answer: Transactions let a producer write to multiple partitions and topics atomically, together with consumer offsets, so a read-process-write cycle is all-or-nothing. They provide exactly-once semantics inside Kafka.

Typical flow: set a transactional.id; initTransactions(); beginTransaction(); send output records; sendOffsetsToTransaction() with the consumed offsets; commitTransaction() (or abortTransaction() on error). A transaction coordinator and an internal transaction log keep the state. Consumers using isolation.level=read_committed only see committed data.

  • Use for: stream processing (Kafka Streams exactly_once_v2), consume-transform-produce pipelines, financial flows between topics.
  • Do not expect it to make external side effects (database writes, HTTP calls) atomic; combine with idempotent writes or the outbox pattern.
  • Cost: a little extra latency and broker overhead; keep transactions short.

💡 Interview tip: Explain the "zombie fencing" idea: the same transactional.id lets Kafka fence off an old instance so two copies cannot both commit.

Q5. Explain at-most-once, at-least-once and exactly-once delivery.

Short answer: They describe how many times a message is processed: at-most-once (0 or 1, may lose), at-least-once (1 or more, may duplicate), exactly-once (effect happens once).

  • At-most-once: consumer commits the offset before processing (or producer uses acks=0 / no retries). A crash after the commit loses the message.
  • At-least-once: consumer processes, then commits. A crash before the commit re-delivers the message. This is the usual default and requires idempotent processing.
  • Exactly-once: idempotent producer + transactions + read_committed consumers (or Kafka Streams exactly_once_v2). The read-process-write cycle is atomic inside Kafka.

End-to-end exactly-once with a database is achieved by making the write idempotent (unique event id, upsert) or by storing the offset in the same DB transaction as the result.

💡 Interview tip: A strong answer ends with: "in practice I use at-least-once plus idempotent consumers, and transactions only for Kafka-to-Kafka pipelines."

Q6. How do you maintain message ordering?

Short answer: Kafka orders records only within a partition. Use the entity id as the record key so all its events go to one partition, keep idempotence on, and process each partition sequentially.

  • Key selection: orderId or customerId so related events stay together; the partition is murmur2(key) % partitions.
  • Retries: without idempotence a retried batch can land after a later one; idempotence (default) preserves order with ≤5 in-flight requests.
  • Consumers: do not process one partition with several threads in parallel, or order is lost; parallelise across partitions or by key.
  • Partition changes: adding partitions changes where keys map, so order for a key can break across the change.
  • Global order: only possible with a single partition, which limits throughput.

💡 Interview tip: Mention that retry topics also break order for the failed message; decide whether ordering or availability matters more.

Q7. How does a producer choose a partition?

Short answer: If a partition is specified it is used; otherwise with a key it uses murmur2(key) % numPartitions; with no key it uses sticky (batch-wise round-robin) partitioning; a custom Partitioner can override all of this.

  • Keyed: same key → same partition (as long as the partition count is unchanged). Gives per-key ordering but can create hot partitions with skewed keys.
  • Unkeyed: since Kafka 2.4 the "sticky partitioner" fills a batch for one partition, then switches, which improves batching and latency compared with pure round-robin.
  • Custom: implement Partitioner (Java) or a custom partitioner delegate (librdkafka/.NET) for tenant-aware or priority routing.

💡 Interview tip: Mention hot partitions and the fix: better keys, key salting, or more partitions.

Q8. What do linger.ms and batch.size do?

Short answer: batch.size is the maximum bytes per batch for a partition; linger.ms is how long the producer waits for more records before sending a not-yet-full batch. Together they trade latency for throughput.

Records are first placed in the producer's record accumulator, grouped per partition. A batch is sent when it is full or the linger time elapses. With linger.ms=0 batches are sent immediately (low latency, small batches). Raising linger to 5–20 ms and batch size to 64–256 KB, plus compression, can multiply throughput with only a few milliseconds extra delay.

  • Default batch.size = 16 KB; linger.ms = 0 (5 ms from Kafka 4.0).
  • Memory is bounded by buffer.memory; when full, send() blocks up to max.block.ms.

💡 Interview tip: Say which direction you would tune for throughput vs latency, it shows practical experience.

Q9. What happens during a consumer rebalance?

Short answer: A rebalance reassigns partitions among the members of a consumer group. With the classic eager protocol all members stop consuming, give up their partitions, rejoin and receive a new assignment; consumption pauses meanwhile.

Steps: the group coordinator notices a change → members send JoinGroup → one member (group leader) computes the assignment using the configured assignor → SyncGroup distributes it → members resume from their committed offsets. With the cooperative-sticky assignor only the partitions that must move are revoked, so the rest keep processing. The new consumer protocol (KIP-848, Kafka 4.0) moves assignment to the broker and avoids the global stop.

  • Uncommitted work of revoked partitions may be reprocessed by the new owner, hence idempotent handlers.
  • Commit offsets in the rebalance onPartitionsRevoked callback to minimise duplicates.
  • Long rebalances cause lag spikes and timeouts.

💡 Interview tip: Mention cooperative rebalancing and static membership as the cures.

Q10. What triggers a rebalance?

Short answer: A member joins or leaves, a member is considered dead (missed heartbeats or too slow polling), or the subscription/partition metadata changes.

  • Join: scale-out or a new deployment/pod starts.
  • Leave: graceful close() or crash.
  • Session timeout: no heartbeat within session.timeout.ms (45 s default), e.g. long GC pause or network partition.
  • Poll timeout: processing a batch takes longer than max.poll.interval.ms (5 min), so the consumer is removed.
  • Metadata change: partitions added or a new topic matches a regex subscription.
  • Rolling restarts: each restarted instance triggers rebalances.

💡 Interview tip: Distinguish heartbeat failures (background thread) from poll-interval failures (application thread). They have different fixes.

Q11. How do you reduce rebalances?

Short answer: Use the cooperative-sticky assignor, static membership (group.instance.id), well-tuned timeouts, fast message processing, and graceful shutdowns.

  • Static membership: a restarted consumer with the same group.instance.id returns within session.timeout.ms without any rebalance.
  • Cooperative sticky: incremental rebalances; only moved partitions pause.
  • Timeouts: raise session.timeout.ms and max.poll.interval.ms to fit realistic processing and GC pauses; reduce max.poll.records if batches are slow.
  • Keep poll loop short: offload long work to a worker pool and pause partitions if needed.
  • Deployments: rolling updates with surge limits, drain with close().
  • New KIP-848 protocol (Kafka 4.0) for lighter rebalances.

session.timeout.ms=45000
max.poll.interval.ms=300000

Q12. How are offsets committed and where are they stored?

Short answer: Consumers commit offsets with commitSync/commitAsync (or auto-commit); they are stored in the internal compacted topic __consumer_offsets keyed by group, topic and partition.

A committed offset means "the next record this group should read". On restart or rebalance the consumer asks the coordinator for the committed offset and continues from there. If none exists, auto.offset.reset decides (earliest/latest). The topic has 50 partitions by default and is compacted so only the latest commit per key is kept. Older clients stored offsets in ZooKeeper, which is no longer used.

  • The offset to commit is last processed offset + 1.
  • Commits are per partition; you can commit specific offsets.
  • External stores (a database) are also possible when you need atomicity with results.

💡 Interview tip: Mention that offsets are just data in a topic, so you can inspect and reset them with kafka-consumer-groups.

Q13. Auto commit vs manual commit?

Short answer: Auto commit (enable.auto.commit=true, every 5 s) commits what poll() returned regardless of whether processing succeeded; manual commit lets you commit only after successful processing.

  • Auto commit risks: if the app crashes after the commit but before finishing, those records are lost (at-most-once for them); if it crashes before the next commit, records are reprocessed (duplicates).
  • Manual sync commit: simple and safe, but blocks and adds latency.
  • Manual async commit: faster, with a callback; do a final commitSync on shutdown.
  • .NET pattern: EnableAutoCommit=true with EnableAutoOffsetStore=false and StoreOffset() after processing gives safe background commits.

💡 Interview tip: Recommend manual (or store-offset) commits for anything business-critical.

Q14. What is auto.offset.reset?

Short answer: It decides where a consumer group starts when it has no valid committed offset (new group, or the offset was deleted/out of range): earliest, latest (default) or none.

  • earliest: start from the beginning of the log (replay everything still retained). Use for new services that need history.
  • latest: only new records from now on; can silently skip data produced before the first poll completes.
  • none: throw an exception so you decide explicitly.

It does not apply when a committed offset exists. To re-read data for an existing group you must reset its offsets.

💡 Interview tip: A classic bug: first deploy with "latest" and "messages disappeared". Explain this.

Q15. What is consumer lag and how do you reduce it?

Short answer: Lag is the number of records a consumer group has not yet processed: log end offset − committed offset per partition. Rising lag means consumers are slower than producers.

  • Measure: kafka-consumer-groups.sh --describe, JMX records-lag-max, Burrow/exporters, Prometheus.
  • Add consumers up to the number of partitions; add partitions if you need more.
  • Speed up processing: batch DB writes, async I/O, avoid per-record network calls, tune max.poll.records and fetch.* settings.
  • Check rebalance loops, GC pauses and slow dependencies.
  • Protect: if lag exceeds retention, the oldest data is deleted before being read.

💡 Interview tip: Alert on lag trend (growing for N minutes) rather than a fixed number.

Q16. How do you replay messages?

Short answer: Reset the consumer group's offsets to the earliest position or a timestamp (group must be inactive), or call seek() in code, as long as the data is still within retention.

kafka-consumer-groups.sh --bootstrap-server b:9092 --group billing --topic orders \
  --reset-offsets --to-earliest --execute
kafka-consumer-groups.sh ... --reset-offsets --to-datetime 2025-03-14T10:00:00.000 --execute
kafka-consumer-groups.sh ... --reset-offsets --shift-by -1000 --execute
  • Replay is why Kafka is good for fixing bugs (reprocess after a fix) and for building new read models.
  • Make consumers idempotent so replays do not duplicate side effects.
  • For a brand-new consumer use a new group.id with auto.offset.reset=earliest.

💡 Interview tip: Add the caveat: external side effects (emails, payments) must be protected before replaying.

Q17. What is min.insync.replicas?

Short answer: The minimum number of in-sync replicas that must acknowledge a write when acks=all. If the ISR is smaller, the broker rejects the write with NotEnoughReplicasException.

It exists to stop "acks=all" from silently degrading to "only the leader has it". With RF=3 and min.insync.replicas=2 you tolerate one failed broker for both reads and writes; if two brokers fail, the partition becomes read-only for acks=all producers, trading availability for durability.

  • Rule of thumb: min.insync.replicas = RF − 1 (for RF=3 → 2).
  • Settable on broker or per topic.

💡 Interview tip: State the trade-off explicitly: durability over availability.

Q18. What is unclean leader election?

Short answer: Electing a replica that is not in the ISR as leader when no in-sync replica is available. It restores availability but can lose acknowledged data because that replica missed records.

Normally if every ISR member is down, the partition stays offline until one returns (consistency over availability). With unclean.leader.election.enable=true an out-of-date follower becomes leader, and records it never received are gone; when the old leader returns, its extra records are truncated. It is false by default and should stay false for important data; enable it only for topics where uptime matters more than completeness (for example metrics).

💡 Interview tip: This is the textbook CAP trade-off example in Kafka.

Q19. What is the high watermark?

Short answer: The high watermark (HW) is the highest offset that has been replicated to all in-sync replicas. Consumers can read only records below it.

The leader tracks each follower's fetched offset. The HW is the minimum across the ISR. Records beyond the HW exist on the leader but are not yet "committed"; if the leader failed now they could be lost, so hiding them guarantees consumers never see data that later disappears. Followers learn the HW through fetch responses. For transactional reads there is also the last stable offset (LSO).

💡 Interview tip: Relate it to log end offset (LEO = latest offset on a replica): HW ≤ LEO.

Q20. Do consumers push or pull?

Short answer: Consumers pull: they call poll()/Consume() and fetch batches from brokers using long polling.

  • Back-pressure: a slow consumer simply fetches less often; nothing overwhelms it.
  • Replay and control: the consumer chooses its offset and batch size.
  • Efficient batching: it fetches many records at once.
  • Long polling: the broker holds the request until fetch.min.bytes arrives or fetch.max.wait.ms passes, so there is no busy waiting.

The downside of pull (latency from polling) is hidden by long polling. Push systems (RabbitMQ) must manage consumer overload with prefetch limits.

💡 Interview tip: Mention back-pressure; it is the benefit interviewers expect.

Q21. How do you handle poison messages?

Short answer: Classify errors: retry transient failures with backoff (preferably non-blocking via retry topics), send permanent failures straight to a dead letter topic (DLT) with context, alert, and continue so the partition is never blocked.

  • Deserialisation errors: wrap deserializers (Spring ErrorHandlingDeserializer, or catch in .NET) so a bad payload becomes an error record instead of an endless crash loop.
  • Retries: bounded attempts with exponential backoff; use retry topics (orders.retry.1m, .10m) so one failing message does not stall the rest.
  • DLT: store original topic/partition/offset, error message and stack trace as headers; provide a way to redrive after the fix.
  • Observability: alert on DLT depth and retry rate.

💡 Interview tip: Mention that blocking retries preserve order but stall the partition; retry topics sacrifice order for throughput.

Q22. Is producer.send() synchronous?

Short answer: No. send() is asynchronous: it places the record in a buffer and returns immediately; a background sender thread batches and transmits it.

  • Java: returns a Future<RecordMetadata>; call get() to block or pass a callback.
  • .NET: ProduceAsync returns a Task you can await; Produce takes a delivery handler for maximum throughput.
  • Call flush() before shutting down or buffered records are lost.
  • Failures after retries surface in the callback or the task, so always handle them.

Blocking on every send (get/await immediately) destroys batching and throughput; send many records and wait for the group, or rely on callbacks.

💡 Interview tip: Mention flush() on shutdown; it is a common production bug.

43. Interview Q&A – Architecture, Ecosystem & EDA

These answers connect Kafka to architecture and design decisions, which is what senior interviews focus on.

Q1. What is event-driven architecture?

Short answer: A style where services communicate by publishing and reacting to events through a broker such as Kafka, instead of calling each other synchronously. It gives loose coupling, independent scaling and resilience.

When the order service places an order it publishes OrderCreated. Payment, inventory, email and analytics services subscribe and react in their own time. The producer does not know who consumes, so new consumers are added without changing it.

  • Benefits: decoupling in time and space, resilience (events wait if a consumer is down), independent scaling, replay and audit, easy extension.
  • Costs: eventual consistency, harder end-to-end tracing, duplicate delivery, schema/versioning discipline, more moving parts.
  • Core patterns: event notification, event-carried state transfer, event sourcing, CQRS, sagas, outbox.

💡 Interview tip: Always mention the trade-off (eventual consistency) after the benefits.

Q2. Event notification vs event-carried state transfer?

Short answer: Event notification sends a small event ("OrderShipped {id}") and consumers call back for details; event-carried state transfer puts the needed data in the event so consumers need no callback and can keep local copies.

  • Notification: very decoupled and small, but creates chatty call-backs and runtime dependency on the source service.
  • State transfer: consumers are autonomous and fast and survive the source being down; costs larger events and eventual consistency of the copies, plus careful schema evolution.
  • Many systems mix them: a thin event with an id plus a compacted topic of full entity state.

💡 Interview tip: Link state transfer to compacted topics and KTables for building local read models.

Q3. What is event sourcing?

Short answer: Event sourcing stores the state changes as an immutable ordered log of events; current state is derived by replaying them (often with snapshots).

Instead of updating a row balance=70, you append Deposited(100), Withdrawn(30). State = fold of events. Kafka (or an event store) is a natural log for it.

  • Benefits: complete audit trail, time travel, easy to build new projections, natural fit with CQRS.
  • Challenges: event schema evolution, rebuild time (use snapshots), eventual consistency of projections, learning curve, GDPR deletion needs crypto-shredding.

💡 Interview tip: Be honest that it is not needed everywhere; it shines in finance, ordering and audit-heavy domains.

Q4. What is CQRS?

Short answer: Command Query Responsibility Segregation separates the write model (handles commands, enforces rules) from one or more read models built from events and optimised for queries.

With Kafka: commands produce events to a topic; stream processors or consumers update read stores (Elasticsearch, Redis, SQL views). Reads are fast and shaped for the UI; writes stay simple and consistent. Read models are eventually consistent, so the UI must handle slightly stale data (for example "your order is being processed").

💡 Interview tip: CQRS and event sourcing are independent; you can use one without the other.

Q5. What is the saga pattern?

Short answer: A saga implements a business transaction that spans services as a sequence of local transactions, with compensating actions that undo earlier steps if a later step fails, because a distributed ACID transaction (2PC) is impractical.

  • Choreography: services react to each other's events (OrderCreated → PaymentCompleted → InventoryReserved). Simple and decentralised; the flow is implicit and harder to monitor as it grows.
  • Orchestration: a coordinator (orchestrator service or a workflow engine) tells each participant what to do and handles failures. Easier to see and test; adds a central component.
  • Compensations: refund payment, release stock, cancel order. They must be idempotent and eventually succeed.
OrderCreated -> PaymentCompleted -> InventoryReserved -> OrderConfirmed
                     |                   x OutOfStock
                     +<-- RefundPayment (compensation) <-- OrderCancelled

💡 Interview tip: Say that sagas give eventual consistency and need idempotent handlers and unique correlation ids.

Q6. What is the dual-write problem and how does the outbox pattern solve it?

Short answer: Writing to a database and to Kafka are two operations that cannot be made atomic; a crash between them leaves the systems inconsistent. The transactional outbox writes the event to an outbox table in the same DB transaction and publishes it afterwards.

Failure cases without the outbox: DB commit succeeds but Kafka send fails (event lost, other services never know) or Kafka send succeeds but DB commit fails (phantom event). With the outbox, business row and outbox row commit together or not at all. A separate relay then reads the outbox and publishes to Kafka. Delivery is at-least-once, so consumers must be idempotent.

  • Relay options: CDC with Debezium reading the database log (low latency, no polling load), or a polling publisher.
  • Add the event id, aggregate id and type as columns; clean up old rows.

💡 Interview tip: Mention "at-least-once, hence idempotent consumers" to complete the story.

Q7. What is CDC and Debezium?

Short answer: Change Data Capture streams row-level changes from a database's transaction log into Kafka. Debezium is the leading open-source CDC platform, running as Kafka Connect source connectors.

  • Reads the DB log (MySQL binlog, PostgreSQL WAL, SQL Server CDC, Oracle, MongoDB), so it captures committed changes in order without polling or triggers.
  • Emits events with before/after images, operation type and source metadata.
  • Typical uses: outbox publishing, keeping search/cache/warehouse in sync, building audit trails, migrating monoliths (strangler pattern).
  • Schema changes and snapshots need care; use Schema Registry and monitor connector lag.

💡 Interview tip: Compare with polling: lower latency, no extra queries, catches deletes.

Q8. What is Kafka Connect?

Short answer: Kafka Connect is a framework and runtime for scalable, reliable integration between Kafka and other systems using ready-made source and sink connectors, with no custom code.

  • Concepts: connector (job definition), task (unit of parallelism), worker (JVM process), converter (bytes ↔ data), SMT (single message transform).
  • Distributed mode: workers form a cluster; configs, offsets and status are stored in internal Kafka topics, so workers are stateless and failover is automatic.
  • REST API (port 8083) to create/pause/restart connectors.
  • Error handling: errors.tolerance and a dead letter queue topic for sink connectors.

💡 Interview tip: Give examples: Debezium source, JDBC source/sink, S3 sink, Elasticsearch sink.

Q9. What is Kafka Streams?

Short answer: Kafka Streams is a client library for building stateful stream-processing applications that read from and write to Kafka, running inside your own service without a separate cluster.

  • Abstractions: KStream (events), KTable (latest value per key), GlobalKTable (replicated table), windows (tumbling, hopping, session).
  • State is kept in local RocksDB stores backed by compacted changelog topics, so it can be rebuilt after failure.
  • Scaling: run more instances; tasks are distributed like consumer-group partitions.
  • Guarantees: exactly_once_v2 for read-process-write inside Kafka.
  • The official library is JVM-only; .NET teams use Streamiz.Kafka.Net, ksqlDB or Flink.

💡 Interview tip: Contrast with Flink: Streams is an embedded library tied to Kafka; Flink is a full engine and cluster.

Q10. KStream vs KTable?

Short answer: A KStream is an unbounded sequence of independent events (insert semantics); a KTable is the latest value per key (update semantics), i.e. a changelog view of a table.

records:  (A,1) (B,5) (A,2)
KStream : three events -> 1, 5, 2 are all kept
KTable  : A=2, B=5     (A=1 was overwritten)
  • Stream-table duality: a table is a stream of changes aggregated; a stream is the changelog of a table.
  • KStream-KTable joins enrich events with reference data (orders joined with customer profile).
  • Aggregations turn a KStream into a KTable.

💡 Interview tip: Use the "bank transactions vs account balances" analogy.

Q11. Kafka Streams vs Flink vs Spark Streaming?

Short answer: Kafka Streams is a lightweight library embedded in your app and tied to Kafka; Flink is a distributed stream engine with rich event-time features and many sources; Spark Structured Streaming is micro-batch oriented and strong when you already use Spark.

Q12. What is Schema Registry?

Short answer: A service that stores versioned schemas (Avro, Protobuf, JSON Schema) for Kafka topics, enforces compatibility rules and lets each record carry only a small schema id instead of the whole schema.

  • Producers register/look up a schema and write magic byte + 4-byte id + payload; consumers fetch the schema by id to deserialise.
  • Compatibility is checked per subject (usually <topic>-value), preventing breaking changes from being deployed.
  • Benefits: smaller messages, a documented data contract between teams, safe evolution.
  • It is not part of Apache Kafka core (Confluent Schema Registry, Apicurio, AWS Glue Schema Registry).

💡 Interview tip: Tie it to teamwork: it is the contract that lets teams deploy independently.

Q13. Explain schema compatibility modes.

Short answer: BACKWARD: consumers using the new schema can read data written with the previous schema. FORWARD: consumers on the old schema can read data written with the new one. FULL: both. NONE: no checks.

  • BACKWARD (default): allowed changes are deleting fields and adding optional fields with defaults. Upgrade consumers first.
  • FORWARD: add fields, delete optional fields. Upgrade producers first.
  • FULL: only add/remove optional fields with defaults; any upgrade order.
  • *_TRANSITIVE variants check against all previous versions, not only the last.

Breaking changes (rename/remove required fields, change types) need a new topic or a new event type/version.

💡 Interview tip: Give the example: adding coupon with default null is backward compatible.

Q14. Kafka vs RabbitMQ?

Short answer: Kafka is a distributed log for high-throughput event streaming with replay; RabbitMQ is a smart broker with flexible routing and per-message acknowledgement, best for task queues and RPC-style messaging.

  • Model: Kafka pull from partitioned log, consumers track offsets; RabbitMQ pushes messages from queues via exchanges/bindings.
  • Retention: Kafka keeps data and allows replay; RabbitMQ removes after ack (streams plugin adds log-like queues).
  • Throughput: Kafka scales to millions/s; RabbitMQ is great but lower.
  • Features: RabbitMQ has priorities, TTL, dead-lettering, complex routing; Kafka has partition ordering, compaction, stream processing ecosystem.
  • Consumer scaling: Kafka limited by partitions; RabbitMQ competing consumers are flexible.

💡 Interview tip: End with "I would choose by access pattern: streams and replay → Kafka; work queues and routing → RabbitMQ."

Q15. Kafka vs Amazon SQS?

Short answer: SQS is a fully managed queue with no operations and no replay; Kafka (or MSK) is a streaming log with replay, ordering per partition, higher throughput and a rich ecosystem, at the cost of operations (unless managed).

  • Retention/replay: SQS deletes after processing (max 14 days retention, no re-read); Kafka lets you rewind.
  • Ordering: SQS FIFO per message group with throughput limits; Kafka per partition at very high rates.
  • Consumers: SQS elastic competing consumers; Kafka bounded by partitions but many independent groups.
  • Operations: SQS zero; Kafka needs expertise or a managed service.
  • Often combined: Kafka as the event backbone, SQS/Lambda at the edges for simple tasks.

💡 Interview tip: Mention Amazon MSK if the interview is AWS-centred.

Q16. Kafka vs Azure Service Bus and Event Hubs?

Short answer: Service Bus is a managed enterprise message broker (queues, topics, sessions, peek-lock settlement, built-in dead-lettering); Event Hubs is Azure's partitioned streaming service that even speaks the Kafka protocol; Kafka is the open-source streaming platform you run yourself or consume as a managed service.

  • Kafka vs Service Bus: Kafka is a replayable log with consumers tracking offsets and very high throughput; Service Bus deletes messages once completed, gives per-message acknowledgement, scheduled delivery, duplicate detection, transactions and FIFO through sessions, but no replay and lower throughput.
  • Kafka vs Event Hubs: nearly the same model (namespace ≈ cluster, event hub ≈ topic, consumer groups, partitions, checkpoints instead of committed offsets). Event Hubs offers a Kafka-compatible endpoint so existing Kafka clients work; it is fully managed and has Capture to Blob/Data Lake, but lacks some Kafka features (for example full Kafka Streams state management and some admin APIs), and retention is shorter on lower tiers.
  • Event Grid is neither: it pushes discrete reactive events to handlers.
  • Choice: telemetry, logs, event streaming, analytics and replay → Kafka/Event Hubs; business commands, workflows, ordering by session and per-message control → Service Bus; platform notifications → Event Grid.

💡 Interview tip: Clarify the naming: there is no Azure product literally called "Event Bus", so ask which one the interviewer means and explain all three.

Q17. How do you scale Kafka?

Short answer: Scale storage and write/read capacity by adding brokers and partitions, scale consumption by adding consumers up to the partition count, and tune batching, compression and hardware.

  • Add brokers then reassign partitions (kafka-reassign-partitions, Cruise Control) to spread load.
  • More partitions for parallelism (plan ahead; cannot decrease).
  • Consumers: add instances to the group; make processing parallel per partition.
  • Producer tuning: larger batches, lz4/zstd compression, more in-flight within limits.
  • Storage: tiered storage for long retention; fast disks/NICs; page-cache-friendly RAM sizing.
  • Multi-cluster: separate clusters per domain or region with MirrorMaker 2 / Cluster Linking.

💡 Interview tip: Mention keeping controllers separate and monitoring partition/leader balance.

Q18. Can you reduce the number of partitions of a topic?

Short answer: No. Kafka allows only increasing partitions. To reduce, create a new topic with fewer partitions and migrate the data and consumers.

Why: removing a partition would mean deleting data and breaking offset/ordering guarantees. Increasing also has a catch: the mapping hash(key) % partitions changes, so new records for an existing key may land in a different partition and per-key order across the change is not guaranteed. Mitigate by over-provisioning moderately up front, using a new topic when ordering is critical, or pausing producers during the change.

💡 Interview tip: A good answer mentions both the "cannot decrease" rule and the key-mapping side effect of increasing.

Q19. How do you secure Kafka?

Short answer: Use TLS for encryption, SASL or mTLS for authentication, ACLs/RBAC for authorisation, quotas, network isolation and encrypted disks.

  • Encryption in transit: TLS on client-broker and inter-broker listeners (SASL_SSL).
  • Authentication: mTLS client certs, SASL/SCRAM, SASL/GSSAPI (Kerberos), OAUTHBEARER (OIDC), or cloud IAM (MSK IAM).
  • Authorisation: ACLs per principal, resource (topic/group/cluster) and operation; apply least privilege.
  • Quotas to stop noisy clients; network: private subnets, security groups.
  • At rest: volume/disk encryption (Kafka does not encrypt data on disk itself); consider payload encryption for sensitive fields.
  • Secrets & governance: rotate credentials, audit access, schema compatibility, PII tagging.

💡 Interview tip: Mention that producers need Write on the topic and consumers need Read on the topic and the group.

Q20. How do you do disaster recovery across regions?

Short answer: Replicate topics to a second cluster with MirrorMaker 2 or Cluster Linking, define RPO/RTO, translate consumer offsets, and rehearse failover.

  • Active-passive: standby cluster receives data; on failure clients switch bootstrap servers and resume from translated offsets.
  • Active-active: both accept writes and replicate to each other (topic prefixes avoid loops); needs conflict handling.
  • Stretch cluster: one cluster over 3 AZs/close regions with rack awareness (not for high-latency regions).
  • Replication across clusters is asynchronous, so some recent data may be lost (RPO > 0).
  • Also replicate schemas, ACLs and configs; test regularly.

💡 Interview tip: Distinguish AZ-level high availability (replication in one cluster) from region-level DR (mirroring).

Q21. What is tiered storage?

Short answer: Tiered storage moves older log segments from broker disks to cheap object storage (such as S3) while recent data stays local, allowing very long retention at lower cost and faster broker recovery.

  • Enabled with remote.storage.enable=true and local vs remote retention settings (local.retention.ms).
  • Consumers read old data transparently; reads of cold data are slower.
  • Brokers hold less data, so rebalancing and replacing brokers is faster.
  • Production-ready since Kafka 3.9.

💡 Interview tip: Use it to justify "retain history for months" without huge disks.

Q22. What are Kafka share groups (KIP-932)?

Short answer: A newer, queue-like consumption model (early access in Kafka 4.0) where multiple consumers can share the records of the same partition with per-record acknowledgement, removing the "consumers ≤ partitions" limit.

Classic consumer groups give each partition to exactly one consumer. With share groups, records are distributed among members, each acknowledged individually (accept, release, reject), with delivery counts and redelivery, which suits task-queue workloads that previously pushed teams to RabbitMQ or SQS. Ordering guarantees are weaker than in consumer groups.

💡 Interview tip: Say it is new/early access and verify the status for the current Kafka version.

Q23. What is Kafka Cruise Control?

Short answer: Cruise Control is an open-source tool (from LinkedIn) that monitors broker load and automatically rebalances partitions and leaders, and helps with adding or removing brokers.

  • Models cluster workload (CPU, disk, network, partition sizes) and proposes optimised replica placement.
  • Executes reassignments throttled so replication does not overload the cluster.
  • Supports self-healing after broker failure and rack-awareness goals.
  • Integrated in Strimzi and available in managed offerings.

💡 Interview tip: Mention it when asked how you keep a large cluster balanced.

44. Scenario-Based Interview Questions

For each scenario use the structure Cause → Measure → Fix → Prevent. The answers below follow it so you can reuse the pattern.

Q1. Consumer lag keeps growing. What do you do?

Short answer: First find out why consumers are slower than producers (processing time, too few consumers, rebalances, a slow dependency), then scale or optimise, and add alerts so it does not happen silently.

Measure: run kafka-consumer-groups.sh --describe --group billing to see lag per partition; check consumer CPU, processing time per record, downstream (database/API) latency, rebalance frequency and GC.

  • One partition lagging only → hot partition (skewed keys) or one slow/poisoned record.
  • All partitions lagging, consumers busy → processing is the bottleneck: batch database writes, use async I/O, remove per-record network calls, tune max.poll.records and fetch sizes.
  • Consumers idle but lag grows → group stuck in rebalance loops or consumers fewer than partitions.
  • Consumers == partitions and still slow → add partitions (plan key impact) or parallelise inside each partition while keeping per-key order.

Prevent: autoscale consumers on lag (KEDA), alert on lag trend and on lag vs retention, load test with realistic peaks, keep handlers idempotent so scaling and restarts are safe.

💡 Interview tip: Mention that lag larger than retention means data loss, so urgency depends on retention.

Q2. Orders of the same customer are processed out of order. Why, and how do you fix it?

Short answer: Kafka only guarantees order inside a partition, so out-of-order processing means the events were spread over partitions, retried without idempotence, or processed in parallel threads. Key by customer id, enable idempotence and process each partition sequentially.

  • No key / wrong key: events of one customer hash to different partitions. Use customerId as the record key.
  • Partitions were added: key-to-partition mapping changed mid-stream.
  • Producer retries with several in-flight requests and no idempotence can reorder: set enable.idempotence=true (default).
  • Consumer parallelism: handing records of one partition to a thread pool breaks order; shard the pool by key instead.
  • Retry topics / DLT deliberately delay failed messages and reorder them; decide whether that is acceptable or use blocking retries for that stream.
await producer.ProduceAsync("orders", new Message<string, string> { Key = customerId, Value = json });

💡 Interview tip: Ask which ordering is really required (per customer? per order?) before choosing the key.

Q3. You see duplicate payments. How do you prevent this?

Short answer: Duplicates are normal with at-least-once delivery, so make the payment handler idempotent: use an idempotency key (order or event id) with a unique constraint, perform the charge and the "processed" record in one transaction, and commit offsets only afterwards.

  • Where duplicates come from: producer retries after a lost ack, consumer crash/rebalance after processing but before commit, outbox relay at-least-once, upstream clients retrying HTTP calls.
  • Fix on the producer side: idempotent producer; unique eventId in every event.
  • Fix on the consumer side: table processed_events(event_id PRIMARY KEY) inserted in the same DB transaction as the ledger change; on conflict, skip.
  • Call external payment APIs with their idempotency key (for example the order id).
  • Disable auto-commit; commit after the transaction succeeds.
BEGIN;
INSERT INTO processed_events(event_id) VALUES ($1);   -- fails on duplicate
INSERT INTO ledger(customer_id, amount) VALUES ($2, -$3);
COMMIT;

💡 Interview tip: Explain that "exactly-once" in Kafka does not cover the payment database; idempotency does.

Q4. A broker crashed. What happens and what should you check?

Short answer: The controller detects the failure, elects new leaders for that broker's partitions from the in-sync replicas on other brokers, and clients refresh metadata and continue. You then verify replication health and restore the broker.

  • Producers get brief NotLeaderForPartition errors and retry against the new leader; with acks=all, RF=3 and min ISR=2, no acknowledged data is lost.
  • Consumers in the group continue from committed offsets; partitions led by the dead broker move leaders, no rebalance is needed unless a consumer died.
  • Check: UnderReplicatedPartitions, OfflinePartitionsCount (must be 0), ISR shrink events, broker logs and disk/network/OOM cause.
  • Recovery: restart the broker; it catches up as follower and rejoins the ISR; run preferred leader election to rebalance leaders; if the disk is lost, replace the node and let replication rebuild data (throttle it).
  • If min.insync.replicas was violated, producers with acks=all were rejected (by design).

💡 Interview tip: Mention that RF, min ISR and rack awareness decide how many simultaneous failures you survive.

Q5. How do you design a topic for 100,000 messages per second?

Short answer: Estimate message size and per-partition throughput, choose enough partitions (with headroom), key by the entity needing order, tune producers for batching and compression, size the cluster and disks, and plan consumers per partition.

Example: 100k msg/s × 1 KB = ~100 MB/s ingress; with RF=3 that is ~300 MB/s cluster write traffic plus replication reads. If one partition sustains ~10–20 MB/s you need at least 10 partitions; take 24–48 for headroom and consumer parallelism.

  • Producers: linger.ms 5–20, batch.size 64–256 KB, lz4/zstd, acks=all.
  • Brokers: 6–9 brokers over 3 AZs, SSD/NVMe, 10 GbE, RAM for page cache, tiered storage if long retention.
  • Topic: RF=3, min ISR=2, retention sized (throughput × retention × RF disk).
  • Consumers: ≥ expected parallelism, idempotent handlers, lag alerts.
  • Validate with kafka-producer-perf-test and consumer perf tests.

💡 Interview tip: Show your arithmetic; interviewers value the reasoning more than exact numbers.

Q6. A new service needs historical events. How do you provide them?

Short answer: Give it a new consumer group with auto.offset.reset=earliest so it reads from the start of the topic (within retention), or bootstrap from a compacted topic or a snapshot if history is longer than retention.

  • Within retention: a new group.id and earliest offset; process events idempotently and in order per key.
  • Beyond retention: use a compacted topic (latest state per key), tiered storage, or load a snapshot/backup from object storage (Kafka Connect S3 sink) and then switch to the live stream at a known offset.
  • Cut-over: avoid gaps and duplicates by recording the snapshot offset/timestamp.
  • Throttle backfill so it does not harm other consumers (quotas).

💡 Interview tip: Mention the advantage of Kafka over queues: replay without involving the producer.

Q7. How do you migrate a monolith to event-driven microservices on Kafka?

Short answer: Use the strangler fig approach: publish domain events from the monolith (outbox + CDC), move one capability at a time into new services that consume them, and retire the old code gradually.

  • Step 1: identify bounded contexts and the events they produce.
  • Step 2: add an outbox table or Debezium on the monolith database to emit events without rewriting it.
  • Step 3: build new services consuming those events with their own data stores; keep consumers idempotent.
  • Step 4: route traffic gradually; use schema registry and versioned events.
  • Step 5: remove the old module when parity and monitoring confirm it.
  • Keep observability from day one: correlation ids and distributed tracing.

💡 Interview tip: Warn against big-bang rewrites and against sharing the monolith database with new services.

Q8. A poison message blocks a consumer. What now?

Short answer: Do not let one bad record stall the partition: retry only transient errors a limited number of times, then move the record to a dead letter topic with context, alert, fix the cause and redrive.

  • Identify: logs show the same offset failing repeatedly; consumer lag stuck on one partition.
  • Deserialisation errors: use an error-handling deserializer (or catch and wrap in .NET) so bytes become an error record instead of crashing the poll loop.
  • Classify: validation/format problems are permanent; timeouts are transient.
  • Park: publish to orders.DLT with headers (original topic, partition, offset, exception) and commit the offset.
  • Recover: fix the bug or data, then redrive from the DLT with a replay tool.
  • Emergency: you can skip by committing offset+1 manually, but only with agreement because it drops the record.

💡 Interview tip: Mention alerting on DLT growth so parked messages are not forgotten.

Q9. You must update the schema of an event used by many teams. How?

Short answer: Evolve it with Schema Registry compatibility rules: make backward-compatible changes (add optional fields with defaults), coordinate upgrade order, and publish a new topic or event version for breaking changes.

  • Safe changes: add optional field with default, add enum symbols carefully, widen types allowed by the format.
  • Unsafe changes: rename/remove required fields, change types, change meaning.
  • Process: CI check that new schema is compatible; announce to consumers; upgrade consumers first for BACKWARD; keep deprecated fields for a period.
  • Breaking change: dual-publish to orders.v2 while consumers migrate, then retire v1.
  • Document the contract and ownership.

💡 Interview tip: Mention consumer-driven contract tests as a bonus.

Q10. How do you guarantee exactly-once from Kafka into a database?

Short answer: Kafka transactions cannot span your database, so make the database write idempotent (unique event id/upsert), or store the consumer offset in the same DB transaction as the result and seek to it on startup.

  • Idempotent write: INSERT ... ON CONFLICT DO NOTHING, MERGE/upsert keyed by event id or natural key.
  • Offsets in DB: in one transaction save the business result and (topic, partition, offset+1); on start/rebalance read it and seek. Disable Kafka offset commits.
  • Kafka Connect sinks (JDBC upsert mode) give effectively-once via idempotent upserts.
  • Inside Kafka only: transactions + read_committed give exactly-once.

💡 Interview tip: Use the phrase "effectively once" to show you understand the nuance.

Q11. Disk is filling up on brokers. What are the options?

Short answer: Find which topics grow, then reduce what is stored (retention/compaction), offload old data (tiered storage), or add capacity and rebalance, while protecting the cluster from filling completely.

  • Diagnose: kafka-log-dirs.sh, per-topic size, sudden traffic increase, compaction not running, a stuck consumer is not a cause (consumption does not hold data).
  • Quick relief: lower retention.ms/retention.bytes on big topics, delete unused topics, enable compression.
  • Structural: tiered storage, add brokers/disks and move partitions (Cruise Control, throttled), use compaction for state topics.
  • Safety: alert at 70–80% disk, set quotas, never let a broker reach 100% (it can crash and corrupt segments).

💡 Interview tip: Mention capacity formula: throughput × retention × RF.

Q12. Consumers rebalance every few minutes. How do you debug?

Short answer: Find which trigger is firing (heartbeat timeout, poll interval exceeded, restarts) from consumer logs and group state, then fix the specific cause: slow processing, GC pauses, short timeouts or pod churn.

  • Logs: "member ... has left", "session timeout", "max.poll.interval exceeded" messages; check kafka-consumer-groups --describe --state.
  • Poll interval exceeded: processing a batch takes longer than max.poll.interval.ms → lower max.poll.records, speed up handling, or move work off the poll thread and pause partitions.
  • Heartbeat/session timeouts: long GC pauses, CPU starvation, network issues → tune JVM/containers and raise session.timeout.ms.
  • Pod restarts/autoscaling: use static membership (group.instance.id) and cooperative sticky; avoid flapping autoscalers.
  • Subscription churn: regex subscriptions matching new topics.

💡 Interview tip: Mention that the new KIP-848 protocol reduces rebalance impact.

Structure every scenario answer as: cause → measure → fix → prevent.
