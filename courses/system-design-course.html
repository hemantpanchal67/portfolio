1. What is System Design?

System design is the process of defining the architecture, components, data flow and interfaces of a system so that it meets functional requirements (what it does) and non-functional requirements (how well it does it: scale, speed, reliability, cost). It turns a vague idea such as "build Instagram" into boxes, arrows, data models and decisions you can defend.

High-Level Design (HLD)Low-Level Design (LLD)
FocusArchitecture: services, databases, caches, queues, data flowClasses, interfaces, algorithms, schemas, design patterns
QuestionHow do the big pieces fit and scale?How is each piece implemented?
OutputArchitecture diagram, API list, capacity planClass diagram, method signatures, code
Interview"Design Twitter / URL shortener""Design a parking lot / LRU cache"
  • There is no single correct answer: every choice is a trade-off between consistency, latency, cost, complexity and time.
  • Good design starts with requirements and constraints, not with technology.
  • You design for the next 10× of load, not 1000×; over-engineering is also a failure.

A tiny example: "store and fetch user profiles"

// Version 1: one server, one database. Fine for 1,000 users.
app.MapGet("/users/{id}", async (int id, Db db) => await db.Users.FindAsync(id));

// Version 2: add a cache (system design thinking: reads dominate, profiles change rarely)
app.MapGet("/users/{id}", async (int id, IDistributedCache cache, Db db) =>
{
    var json = await cache.GetStringAsync($"user:{id}");
    if (json is not null) return Results.Text(json, "application/json");   // cache hit
    var user = await db.Users.FindAsync(id);                               // cache miss
    if (user is null) return Results.NotFound();
    await cache.SetStringAsync($"user:{id}", JsonSerializer.Serialize(user),
        new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10) });
    return Results.Ok(user);
});
Analogy: designing a system is like city planning. You decide roads (network), traffic lights (load balancers), warehouses (databases), shortcuts (caches) and what happens when a road is closed (failover).

3. Core Goals & Design Principles

Every system design discussion revolves around a small set of qualities. Learn them as a vocabulary; you will use them in every answer.

Principles to remember

  • Keep it simple (KISS): start with the simplest design that meets requirements.
  • Design for failure: everything fails; make failure a normal event.
  • Stateless services, stateful stores: keep servers disposable.
  • Separation of concerns: each component has one job.
  • Cache what is read often, queue what is slow, shard what is big, replicate what is critical.
  • Measure, do not guess: use numbers (QPS, p99, storage) to justify choices.

  • Choosing a technology because it is popular, not because of the access pattern.

6. How to Approach a System Design Problem (Framework)

Use the same six steps every time. The animation shows the order; time-box each step in an interview (about 45 minutes in total).

  1. Clarify requirements (5 min): functional (what features), non-functional (scale, latency, availability, consistency), out of scope. Ask questions; never assume.
  2. Estimate scale (5 min): users, QPS, read/write ratio, storage, bandwidth. Numbers drive decisions.
  3. Define APIs and data model (5 min): key endpoints, entities, relationships, access patterns.
  4. High-level design (10 min): draw clients, load balancer, services, databases, cache, queue; trace one read and one write.
  5. Deep dive (15 min): the hardest 2–3 parts: sharding key, consistency, fan-out, hot keys, ID generation.
  6. Bottlenecks and trade-offs (5 min): single points of failure, failure modes, monitoring, security, future growth.

Questions to ask first

  • Who are the users and what is the expected scale (DAU, QPS, data size)?
  • Is it read-heavy or write-heavy? What is the read:write ratio?
  • What latency and availability targets? Is eventual consistency acceptable?
  • Which features are in scope for the first version?
  • Global or single-region? Any compliance constraints?
Say your reasoning aloud. A clear trade-off explanation beats a perfect diagram.

7. Scalability: Vertical vs Horizontal

Scalability is the ability to handle more load by adding resources. There are two ways: make one machine bigger (vertical, scale up) or add more machines (horizontal, scale out).

Vertical (scale up)Horizontal (scale out)
HowBigger CPU, RAM, diskMore servers behind a load balancer
ComplexityLow: no code changeHigher: needs stateless design, data partitioning
LimitHardware ceiling, price grows non-linearlyNear-linear, practically unlimited
AvailabilitySingle point of failureRedundant: others take over
Downtime to scaleOften needs restartNone (add instances live)
Best forDatabases early on, quick fixWeb/app tiers, caches, workers

What makes a service horizontally scalable?

  • Stateless servers: no user session in local memory; use Redis or tokens.
  • Shared-nothing data partitioning (sharding) for storage.
  • Idempotent, retry-safe operations.
  • Load balancer + health checks + autoscaling.
  • Asynchronous work through queues so spikes are absorbed.

Estimator in code

public record Estimate(double AvgQps, double PeakQps, double StorageTbPerYear, double BandwidthGbps);

public static Estimate Calculate(long dau, int requestsPerUserPerDay, long writesPerDay,
                                 int bytesPerWrite, int bytesPerResponse, double peakFactor = 2.5)
{
    double avgQps = dau * (double)requestsPerUserPerDay / 86_400;
    double storageTb = writesPerDay * (double)bytesPerWrite * 365 / 1e12;
    double peakQps = avgQps * peakFactor;
    double gbps = peakQps * bytesPerResponse * 8 / 1e9;          // bits per second
    return new Estimate(avgQps, peakQps, storageTb, gbps);
}

// URL shortener: 100M new URLs/month, 100:1 read:write, 500 B per record
var e = Calculate(dau: 50_000_000, requestsPerUserPerDay: 4, writesPerDay: 3_300_000,
                  bytesPerWrite: 500, bytesPerResponse: 500);
Console.WriteLine(e);   // ~2.3k QPS avg, ~5.8k peak, ~0.6 TB/year
  • Powers of two: 2^10 ≈ 1 thousand, 2^20 ≈ 1 million, 2^30 ≈ 1 billion, 2^40 ≈ 1 trillion.
  • Always write units and keep a sanity check ("does 20 servers sound right?").
  • Interviewers care about reasoning and approximation, not exact digits.

10. CAP Theorem & PACELC

In a distributed data store, when a network partition happens you can keep Consistency (every read sees the latest write) or Availability (every request gets a response), not both. Click the corners and edges of the triangle.

ChoiceBehaviour during a partitionExamplesGood for
CPRefuses or delays requests that cannot be confirmedZooKeeper, etcd, HBase, Spanner, MongoDB (majority)Money, inventory counts, leader election, coordination
APAnswers from any node; data may be stale and reconciled laterCassandra, DynamoDB, Riak, CouchDB, DNSFeeds, carts, likes, caches, sessions
  • P is not optional: networks fail, so the real choice is C vs A.
  • PACELC: if Partition → A or C; Else (normal operation) → Latency or Consistency. Strong consistency costs latency even when nothing is broken.
  • CAP "consistency" means linearizability, different from the C in ACID.
  • Many databases are tunable per query (Cassandra QUORUM, Cosmos DB consistency levels).

    ConsistencyLevel = ConsistencyLevel.Session   // Strong > BoundedStaleness > Session > ConsistentPrefix > Eventual

12. Networking Basics: DNS, HTTP, TCP, REST, gRPC, WebSockets

Every system design relies on a few network concepts. Know what happens between typing a URL and seeing a page.

  1. DNS resolves the domain to an IP (cached by browser, OS, resolver).
  2. TCP three-way handshake (SYN, SYN-ACK, ACK), then TLS handshake for HTTPS.
  3. HTTP request sent; load balancer/CDN/gateway route it; server responds.
  4. Browser renders; further requests reuse the connection (keep-alive, HTTP/2 multiplexing).

How to read it

  • Left → right is a request: client → DNS/CDN → load balancer → API gateway → stateless app servers → cache/database.
  • Static files (images, JS) skip the app servers via the CDN.
  • Reads hit the cache first, then replicas; writes go to the primary and replicate.
  • Slow work goes to a queue and is done by workers.
  • Everything is observed: logs, metrics, traces and alerts.

Life of a Request (End to End)

Follow one request through the architecture. Each hop adds latency and a possible failure, which is why you add timeouts, caching and retries at the right places.

  1. DNS: the browser resolves shop.example.com (cached for the record TTL).
  2. CDN / Load balancer: static files are served from the edge; dynamic requests go to the load balancer, which picks a healthy server.
  3. API gateway: validates the JWT, applies rate limits and routes to the right service.
  4. App server: runs business logic; keeps no local state.
  5. Cache then database: a cache hit returns in about 1 ms; a miss reads the DB and fills the cache; writes go to the primary.
  6. Response: serialised and returned; side effects (emails, analytics) are queued asynchronously.

Cache-aside with Redis in .NET

public async Task<Product?> GetProductAsync(int id)
{
    var key = $"product:{id}";
    var cached = await _redis.StringGetAsync(key);
    if (cached.HasValue) return JsonSerializer.Deserialize<Product>(cached!);      // hit

    var product = await _db.Products.FindAsync(id);                                 // miss
    if (product is not null)
    {
        // TTL with jitter so many keys do not expire together (prevents stampede)
        var ttl = TimeSpan.FromMinutes(10) + TimeSpan.FromSeconds(Random.Shared.Next(0, 60));
        await _redis.StringSetAsync(key, JsonSerializer.Serialize(product), ttl);
    }
    return product;
}

public async Task UpdateProductAsync(Product p)
{
    _db.Update(p); await _db.SaveChangesAsync();
    await _redis.KeyDeleteAsync($"product:{p.Id}");      // invalidate after the DB commit
}

LRU cache in O(1)

public class LruCache<K, V> where K : notnull
{
    private readonly int _capacity;
    private readonly Dictionary<K, LinkedListNode<(K Key, V Value)>> _map = new();
    private readonly LinkedList<(K Key, V Value)> _order = new();      // head = most recent
    public LruCache(int capacity) => _capacity = capacity;

    public bool TryGet(K key, out V value)
    {
        if (_map.TryGetValue(key, out var node)) { _order.Remove(node); _order.AddFirst(node); value = node.Value.Value; return true; }
        value = default!; return false;
    }
    public void Put(K key, V value)
    {
        if (_map.TryGetValue(key, out var existing)) { _order.Remove(existing); _map.Remove(key); }
        else if (_map.Count >= _capacity) { var last = _order.Last!; _order.RemoveLast(); _map.Remove(last.Value.Key); }
        var node = _order.AddFirst((key, value)); _map[key] = node;
    }
}

Indexing

  • An index (usually a B-tree) turns a full scan O(n) into O(log n) lookups but slows writes and uses space.
  • Index columns used in WHERE, JOIN and ORDER BY; use composite indexes in the right column order; prefer covering indexes.
  • LSM trees (Cassandra, RocksDB) favour write-heavy workloads; B-trees favour reads.
-- find orders of a customer sorted by date: composite index matches the filter + sort
CREATE INDEX ix_orders_customer_created ON orders (customer_id, created_at DESC) INCLUDE (status, total);

EXPLAIN SELECT status, total FROM orders WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 20;

Normalisation vs denormalisation

  • Normalise (3NF) to avoid duplication and update anomalies: ideal for write-heavy transactional data.
  • Denormalise (duplicate data) to avoid joins and speed up reads: ideal for read-heavy, sharded or NoSQL stores; you must keep copies in sync.

Consistent hashing with virtual nodes (C#)

public class ConsistentHashRing
{
    private readonly SortedDictionary<uint, string> _ring = new();
    private readonly int _virtualNodes;
    public ConsistentHashRing(int virtualNodes = 100) => _virtualNodes = virtualNodes;

    private static uint Hash(string s) => BitConverter.ToUInt32(System.IO.Hashing.XxHash32.Hash(Encoding.UTF8.GetBytes(s)));

    public void AddNode(string node)    { for (int i = 0; i < _virtualNodes; i++) _ring[Hash($"{node}#{i}")] = node; }
    public void RemoveNode(string node) { for (int i = 0; i < _virtualNodes; i++) _ring.Remove(Hash($"{node}#{i}")); }

    public string GetNode(string key)
    {
        var h = Hash(key);
        foreach (var kv in _ring) if (kv.Key >= h) return kv.Value;     // first node clockwise
        return _ring.First().Value;                                      // wrap around the ring
    }
}

Token bucket in C#

public class TokenBucket(double capacity, double refillPerSecond)
{
    private double _tokens = capacity;
    private DateTime _last = DateTime.UtcNow;
    private readonly object _lock = new();

    public bool TryTake(int count = 1)
    {
        lock (_lock)
        {
            var now = DateTime.UtcNow;
            _tokens = Math.Min(capacity, _tokens + (now - _last).TotalSeconds * refillPerSecond);   // refill
            _last = now;
            if (_tokens < count) return false;                                                      // reject (429)
            _tokens -= count; return true;
        }
    }
}

Snowflake layout: 1 bit sign | 41 bits time (ms) | 10 bits machine | 12 bits sequence

public class SnowflakeGenerator(int machineId)            // 0..1023
{
    private const long Epoch = 1704067200000L;               // 2024-01-01 UTC in ms
    private long _lastMs = -1; private long _seq;
    private readonly object _lock = new();

    public long NextId()
    {
        lock (_lock)
        {
            long now = DateTimeOffset.UtcNow.ToUnixTimeMilliseconds();
            if (now < _lastMs) throw new InvalidOperationException("Clock moved backwards");
            if (now == _lastMs) { _seq = (_seq + 1) & 0xFFF; if (_seq == 0) while ((now = DateTimeOffset.UtcNow.ToUnixTimeMilliseconds()) <= _lastMs) { } }
            else _seq = 0;
            _lastMs = now;
            return ((now - Epoch) << 22) | ((long)machineId << 12) | _seq;     // 4096 ids per ms per machine
        }
    }
}

const string Alphabet = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";

26. Consensus, Leader Election & Distributed Locks

Nodes must sometimes agree on one value (who is leader, what is the next log entry) even though machines crash and messages are lost. This is the consensus problem.

ConceptWhat it givesUsed by
Paxos / RaftReplicated log agreed by a majority (quorum)etcd, Consul, ZooKeeper (ZAB), CockroachDB
Leader electionOne node coordinates; others followKafka controller, Kubernetes, databases
QuorumMajority (N/2 + 1) must agree; tolerates minority failure3 nodes survive 1 failure, 5 survive 2
GossipPeers spread state randomly; eventually consistentCassandra, Consul membership
Vector / Lamport clocksOrdering events without a global clockDynamo-style stores
Fencing tokenMonotonic number so a stale leader/lock-holder is rejectedSafe distributed locks

Raft in short

  1. Nodes are follower, candidate or leader. A follower that hears no heartbeat becomes a candidate and requests votes in a new term.
  2. A candidate with votes from a majority becomes leader.
  3. Clients write to the leader, which appends to its log and replicates; an entry is committed once a majority stored it.
  4. If the leader dies, a new election happens; the new leader always has all committed entries.

  • A lock with a TTL can expire while the holder is paused (GC, network); two holders may then work at once. Use fencing tokens checked by the resource, or a consensus store (etcd, ZooKeeper) when correctness matters.
  • Prefer designs that avoid locks: idempotent operations, optimistic concurrency (version/ETag), single-writer partitions.
  • Optimistic concurrency in SQL: UPDATE ... SET qty = qty - 1, version = version + 1 WHERE id = @id AND version = @v; zero rows updated means someone else won, retry.

27. Distributed Transactions: 2PC, Saga & Outbox

With database-per-service you lose a single ACID transaction across services. Two answers: 2PC (strict, blocking) and Saga (sequence of local transactions with compensations). Click the saga diagram.

The dual-write problem and the Outbox pattern

Saving to the database and publishing an event are two systems; if one fails you get inconsistency. The transactional outbox writes the event to an Outbox table in the same local transaction, and a relay publishes it later (at-least-once, so consumers dedupe).

public class OutboxRelay(IServiceScopeFactory sf, ServiceBusSender sender) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            using var scope = sf.CreateScope(); var db = scope.ServiceProvider.GetRequiredService<AppDb>();
            var batch = await db.Outbox.Where(m => m.SentAt == null).OrderBy(m => m.CreatedAt).Take(50).ToListAsync(ct);
            foreach (var m in batch)
            {
                await sender.SendMessageAsync(new ServiceBusMessage(m.Payload) { MessageId = m.Id.ToString(), Subject = m.Type }, ct);
                m.SentAt = DateTime.UtcNow;                         // consumers must be idempotent (at-least-once)
            }
            await db.SaveChangesAsync(ct);
            await Task.Delay(TimeSpan.FromSeconds(1), ct);
        }
    }
}

39. Best Practices, Trade-offs & Anti-patterns

Experienced designers differ from beginners mostly in judgement about trade-offs. Use this checklist.

Best practices

  • Clarify requirements and constraints before drawing; write down assumptions and numbers.
  • Start simple (monolith + one DB + cache); add complexity only when a measured need appears.
  • Keep services stateless; keep state in dedicated stores.
  • Design for failure: timeouts, retries with jitter, circuit breakers, redundancy in multiple zones.

40. Interview Q&A: Fundamentals

Q1. What is the difference between horizontal and vertical scaling?

Short answer: Vertical scaling makes one machine bigger; horizontal scaling adds more machines behind a load balancer.

Vertical scaling (scale up) is simple because nothing in the code changes, but it has a hard ceiling, gets expensive quickly, and the machine remains a single point of failure. Horizontal scaling (scale out) has practically no ceiling and gives redundancy, but the application must be stateless (sessions in a shared store), and you must deal with distributed concerns such as load balancing, data partitioning and consistency.

  • Typical path: scale up first while it is cheap, then scale out the stateless tier, then scale the data tier with replicas, caches and finally sharding.
  • Databases are the hard part: reads scale via replicas, writes need sharding.

💡 Interview tip: Always say the application tier is easy to scale horizontally and the data tier is the real challenge.

Q2. Explain latency vs throughput, and why percentiles matter.

Short answer: Latency is the time for one request; throughput is how many requests per second the system handles. Percentiles (p95/p99) reveal the slow tail that averages hide.

A system can have high throughput and poor latency (batching) or the reverse. Averages mislead: if 1% of requests take 5 seconds, the mean looks fine but those users suffer, and in a fan-out of 100 backend calls, a user will almost always hit one slow call (tail latency amplification). Set SLOs on p95/p99.

  • Reduce latency: caching, CDN, closer regions, async work, indexes, connection reuse.
  • Increase throughput: horizontal scaling, batching, queues, efficient serialization.

Q3. State the CAP theorem. What does it really say?

Short answer: During a network partition a distributed system must choose between consistency and availability; partition tolerance is not optional.

CAP says that when a partition splits the nodes, you can either refuse some requests to stay consistent (CP, e.g. etcd, ZooKeeper, HBase) or keep answering and risk stale or conflicting data (AP, e.g. Cassandra, DynamoDB default, Couchbase). When there is no partition you can have both, but there is still a trade-off between latency and consistency: that is PACELC.

  • Consistency in CAP means linearizability, not the "C" of ACID.
  • It is a per-operation choice in many systems (tunable consistency, quorum reads).
  • Banking ledger → CP; shopping cart, likes counter → AP.

💡 Interview tip: Mention PACELC and that modern databases let you choose per query.

Q4. What are the different consistency models?

Short answer: From strongest to weakest: linearizable, sequential, causal, read-your-writes / monotonic, eventual.

  • Strong (linearizable): every read sees the latest write; costs latency and availability.
  • Causal: causally related operations are seen in order.
  • Read-your-writes: a client always sees its own updates (route reads to the leader after writing).
  • Monotonic reads: never go back in time.
  • Eventual: replicas converge if updates stop; fast and available.

Choose the weakest model that keeps the business correct. Eventual consistency is fine for a like count but not for an account balance.

Q5. ACID vs BASE?

Short answer: ACID gives strict transactional guarantees; BASE (Basically Available, Soft state, Eventually consistent) trades them for availability and scale.

  • Atomicity all or nothing, Consistency invariants hold, Isolation concurrent transactions do not interfere (levels: read committed, repeatable read, serializable), Durability committed data survives crashes (write-ahead log).
  • Modern systems mix: ACID inside a service, sagas and eventual consistency between services.

Q6. How do you do capacity estimation in an interview?

Short answer: State assumptions, convert to per-second numbers, then derive storage, bandwidth and server counts using round numbers.

DAU 10M, 5 posts viewed/user/day -> 50M reads/day / 86,400 ≈ 600 reads/s, peak ×3 ≈ 2,000/s
Writes 1M/day ≈ 12/s. Post 1 KB -> 1 GB/day -> 365 GB/year; ×3 replication ≈ 1.1 TB/year
Bandwidth: 2,000 req/s × 10 KB ≈ 20 MB/s
Servers: one app server ≈ 1,000 req/s -> 2–3 servers + redundancy -> 6

The point is order of magnitude to choose the architecture (does it fit one DB? need cache? need sharding?), not exactness.

💡 Interview tip: Memorise 86,400 s/day, 2.5 M s/month, and latency numbers (memory 100 ns, SSD 100 µs, same-DC 0.5 ms, cross-continent 150 ms).

Q7. What is the difference between availability and reliability, and how do you calculate availability?

Short answer: Availability is the fraction of time the system is up; reliability is the probability it works correctly without failure over time.

Availability = uptime / total time. 99.9% allows ~8.8 h downtime a year; 99.99% ~53 min; 99.999% ~5 min. In series, availabilities multiply (0.999 × 0.999 = 99.8%); in parallel redundancy, failure probabilities multiply (two 99% nodes → 99.99%).

💡 Interview tip: Show you know dependencies in series reduce availability, so chains of synchronous calls are risky.

Q8. What happens when you type a URL in the browser?

Short answer: DNS resolves the name, a TCP/TLS connection is made (often to a CDN/load balancer), the HTTP request is routed to a server, and the response is rendered.

  1. Browser checks caches, DNS resolver returns the IP (recursive lookup, geo/latency-based routing).
  2. TCP handshake + TLS handshake (HTTP/2 or HTTP/3 over QUIC).
  3. CDN edge answers static content; otherwise the request goes to the load balancer → gateway → app server.
  4. App checks cache, queries the DB, builds a response.
  5. Browser parses HTML, fetches CSS/JS/images (more CDN hits), renders.

41. Interview Q&A: Building Blocks

Q1. How does a load balancer work, and what algorithms exist?

Short answer: It receives client traffic and forwards each request to a healthy backend chosen by an algorithm, checking health continuously.

  • Round robin, weighted round robin, least connections, least response time, IP hash / consistent hash, power of two choices.
  • L4 (TCP) is faster; L7 (HTTP) routes by path/header, terminates TLS, can do WAF/compression.
  • Health checks remove failing nodes; connection draining finishes in-flight requests during deploys.
  • Avoid sticky sessions; store sessions in Redis. Make the LB redundant (managed/active-passive; DNS or anycast for global).

Q2. Explain cache-aside, write-through and write-back. Which would you pick?

Short answer: Cache-aside: app checks the cache, loads from DB on a miss. Write-through: writes go to cache and DB together. Write-back: writes go to cache and are flushed to DB later.

I default to cache-aside with TTL for read-heavy data because it is simple and the cache can fail without data loss. Write-through suits data that must be fresh in cache. Write-back gives the fastest writes (counters, metrics) but can lose data if the cache node dies before flushing, so only use it with durability support.

var v = await cache.GetAsync(key); if (v is null) { v = await db.LoadAsync(key); await cache.SetAsync(key, v, ttl); }

Q3. What is a cache stampede and how do you prevent it?

Short answer: When a popular key expires, many requests miss at once and all hit the database together.

  • Request coalescing / single flight: only one request recomputes, others wait.
  • TTL jitter so keys do not expire together.
  • Early / background refresh (stale-while-revalidate).
  • Locks (with short TTL) around recompute; warm caches before traffic.
  • Also: penetration (missing keys) → negative caching, Bloom filter; avalanche (mass expiry or cache down) → jitter, replicas, circuit breaker.

Q4. Which eviction policy would you use?

Short answer: LRU is the common default; LFU suits stable popularity; TTL handles expiry by time.

LRU evicts the least recently used item (good for recency-based workloads), LFU the least frequently used (resists scans but slow to adapt), FIFO is simple but naive. Redis supports allkeys-lru, allkeys-lfu, volatile-ttl. Implementation of LRU is a hash map plus doubly linked list for O(1) get/put.

Q5. SQL or NoSQL?

Short answer: Pick by access pattern and consistency need: SQL for relational data and transactions, NoSQL for massive scale, flexible schema or simple key access.

  • SQL: joins, ad-hoc queries, strong ACID; scale with replicas, partitioning.
  • NoSQL: key-value (Redis/DynamoDB), document (Mongo/Cosmos), wide-column (Cassandra), graph (Neo4j).
  • Many systems use polyglot persistence: SQL as source of truth, Redis for cache, Elasticsearch for search.
  • Do not choose NoSQL merely for "scale"; modern relational databases scale very far.

Q6. How do indexes work, and what are their downsides?

Short answer: An index (usually a B-tree) keeps sorted pointers to rows so lookups are O(log n) instead of scanning the whole table.

  • Downsides: slower writes, extra storage, can be ignored by the optimizer if low selectivity.
  • Composite index order matters: (customer_id, created_at) serves filters on customer_id and customer_id+created_at, not created_at alone (leftmost prefix).
  • Covering index includes all needed columns to avoid table lookups.
  • LSM-tree stores favour writes; B-tree favours reads.

Q7. Explain replication and replication lag. How do you handle it?

Short answer: Replication copies data to other nodes for availability and read scaling; lag is the delay before replicas see a write.

  • Async replication risks stale reads and loss on failover; sync is safer but slower.
  • Handle lag: read-your-writes (route a user to the leader shortly after writing, or track write timestamps/versions), monotonic reads (stick a user to one replica), or tolerate staleness for non-critical views.
  • Failover: detect, elect, promote; use quorum and fencing to avoid split brain.

Q8. What is sharding, how do you choose a shard key, and what are the problems?

Short answer: Sharding splits data across nodes; the shard key decides which node owns a row.

  • Good key: high cardinality, even distribution, aligned with common queries (userId, tenantId).
  • Range sharding gives range scans but hot spots; hash sharding spreads load but kills range queries; directory-based is flexible.
  • Problems: cross-shard joins/transactions, resharding, hot shards (celebrity), uneven sizes.
  • Use consistent hashing with virtual nodes so adding a node moves only ~1/N keys.
  • Exhaust indexing, caching, read replicas and partitioning first.

Q9. Explain consistent hashing.

Short answer: Keys and nodes are hashed onto a ring; a key belongs to the first node clockwise. Adding or removing a node only affects its neighbours' keys.

With hash(key) % N, changing N remaps almost every key, causing a cache miss storm. With consistent hashing only ~K/N keys move. Virtual nodes (many points per physical node) smooth the distribution and let stronger machines own more points. Used by Dynamo, Cassandra, memcached clients and load balancers.

Q10. Message queue vs Kafka-style log: when to use which?

Short answer: Use a queue for tasks that are consumed once; use a log for events many consumers read independently and may replay.

  • Queue (RabbitMQ, SQS, Service Bus): per-message ack, delete after processing, competing consumers, DLQ, delayed delivery.
  • Log (Kafka, Event Hubs): partitioned append-only, retained, offsets, replay, high throughput, ordering per partition.
  • Both are at-least-once by default: make consumers idempotent.

Q11. How do you design a rate limiter?

Short answer: Choose an algorithm (token bucket is the usual answer), key it by user/IP/API key, keep counters in a shared fast store like Redis, and return 429 with Retry-After.

  • Token bucket: bursts allowed, memory-light. Sliding window counter: accurate and cheap. Fixed window: simplest but edge bursts.
  • Distributed: atomic Redis Lua/INCR+EXPIRE; or approximate with local limiters + periodic sync.
  • Place at the gateway/edge; decide fail-open vs fail-closed; separate limits per tier/route; communicate limits via headers.

💡 Interview tip: Mention both the algorithm and where it lives in the architecture.

Q12. REST vs gRPC vs GraphQL?

Short answer: REST is simple and cacheable; gRPC is fast, strongly typed and great between internal services; GraphQL lets clients ask for exactly the fields they need.

Q13. Offset vs cursor pagination?

Short answer: Offset (LIMIT/OFFSET) is simple but slow for deep pages and unstable when rows change; cursor (keyset) pagination is fast and stable.

SELECT * FROM posts WHERE (created_at, id) < (@lastCreated, @lastId) ORDER BY created_at DESC, id DESC LIMIT 20;

Q14. How do you generate unique IDs in a distributed system?

Short answer: Snowflake-style IDs (time + machine + sequence), UUIDv7/ULID, or ranges from a ticket server.

Snowflake gives 64-bit, roughly time-sortable IDs without coordination at runtime; the risks are clock skew/rollback and unique machine id assignment. UUID v4 is random and bad for index locality; v7 is time-ordered. Auto-increment is fine for a single DB but does not scale across shards.

Q15. What is a CDN and how does it handle dynamic content?

Short answer: A CDN caches content at edge locations near users; for dynamic content it speeds up the connection to the origin and can cache briefly or compute at the edge.

  • Use long TTL and fingerprinted file names for static assets, short TTL + stale-while-revalidate for semi-dynamic data.
  • Origin shield reduces origin load; purge by tag/URL for urgent invalidation.
  • Also gives TLS termination, DDoS protection, WAF, image optimisation.

42. Interview Q&A: Distributed Systems

Q1. When would you choose microservices over a monolith?

Short answer: When team size, independent scaling or independent release cadence outweigh the cost of distributed complexity; otherwise start with a modular monolith.

  • Benefits: independent deploy/scale, technology freedom, fault isolation, team autonomy.
  • Costs: network latency and failures, distributed data (no joins, no ACID across services), observability, versioning, operational overhead.
  • Split along bounded contexts; own your data; use async events to reduce coupling; migrate with the strangler fig.

💡 Interview tip: Warn about the distributed monolith. It shows maturity.

Q2. How do you handle transactions across multiple services?

Short answer: Avoid them by design where possible; otherwise use a saga (local transactions plus compensations) with the outbox pattern for reliable events.

  • 2PC gives atomicity but blocks and reduces availability, so it is rare across services.
  • Choreography vs orchestration; compensations must be idempotent; do the irreversible step last.
  • Outbox: write event with the data in one local transaction, a relay publishes (at-least-once); consumers dedupe with an inbox/idempotency table.

Q3. What is idempotency and why is it essential?

Short answer: An operation is idempotent if repeating it has the same effect as doing it once.

Networks and queues deliver at-least-once and clients retry, so duplicates are certain. GET, PUT and DELETE are idempotent by definition; POST is not, so use an idempotency key stored with the result, or natural keys/unique constraints, or conditional updates (INSERT ... ON CONFLICT DO NOTHING).

Q4. Explain the circuit breaker pattern.

Short answer: It stops calling a failing dependency for a while so failures do not cascade, then tests recovery.

  • Closed: calls flow, failures counted. Open: calls fail fast (fallback) for the break duration. Half-open: allow a few trial calls; success closes, failure re-opens.
  • Combine with timeouts, retries with backoff + jitter, bulkheads and fallbacks. Retry only idempotent calls and at a single layer to avoid retry storms.

Q5. How does leader election and consensus work (Raft)?

Short answer: Nodes vote for a leader with a majority in a numbered term; the leader replicates a log and commits entries once a majority stores them.

If heartbeats stop, a follower becomes a candidate and starts an election in a new term. A split vote retries with randomised timeouts. Quorum guarantees any two majorities overlap, so committed data survives. Odd cluster sizes (3, 5) are used because 4 nodes tolerate no more failures than 3. Fencing tokens protect against a stale leader.

Q6. How do you implement a distributed lock? What are the pitfalls?

Short answer: Use an atomic set-if-not-exists with a TTL and a unique token, release by compare-and-delete; for strict safety use fencing tokens or a consensus system.

A TTL lock can expire during a GC pause or network delay while the old holder still works, so two processes enter the critical section. Prefer idempotent design, optimistic concurrency or a single-writer queue. Redlock is controversial for correctness-critical cases.

Q7. What is eventual consistency and how do you make it user-friendly?

Short answer: Replicas converge over time if no new updates arrive; design the UI and flows to tolerate temporary staleness.

  • Read-your-writes by reading from the primary or caching the user's own change.
  • Optimistic UI, "processing" states, and background reconciliation.
  • Conflict resolution: last-write-wins (risky), version vectors, CRDTs, application-level merges.

Q8. What is the difference between orchestration and choreography?

Short answer: Choreography: services react to each other's events with no central controller. Orchestration: a central coordinator directs the steps.

Choreography is decoupled but the overall flow is hard to see and debug; orchestration centralises logic and makes failures and timeouts easier to handle but creates a coordinator to maintain. Use orchestration for complex business workflows (sagas).

Q9. How do you ensure ordering in a distributed message system?

Short answer: Guarantee ordering only per key: route all messages for a key to the same partition/session and process them sequentially.

Global ordering does not scale. In Kafka, order is per partition (use the entity id as the key); in Service Bus use sessions. Retries and parallel consumers can break order, so use sequence numbers and ignore stale updates.

Q10. How do you design for high availability?

Short answer: Remove single points of failure with redundancy at every tier, across zones/regions, plus health checks, automatic failover and graceful degradation.

  • Stateless app servers behind a redundant LB; replicated databases with automated failover; multi-AZ, optionally multi-region.
  • Timeouts, circuit breakers, bulkheads, load shedding; rate limiting.
  • Safe deploys (canary/blue-green), backups tested by restore, chaos testing, clear RTO/RPO.
  • Remember dependencies in series multiply failure probability.

Q11. How do you monitor and debug a distributed system?

Short answer: Use the three pillars (metrics, logs, traces) with correlation ids, define SLOs, and alert on user-visible symptoms.

Propagate the trace id (W3C traceparent) through every call and message. Use structured logs, RED/USE dashboards, distributed tracing to find which hop adds latency, and error budgets to balance reliability with releases.

Q12. How would you handle a hot partition / hot key?

Short answer: Detect it, then spread or isolate the load: salt the key, split the entity, cache locally, replicate reads, or give the big tenant its own shard.

Example: a celebrity's like counter → shard the counter into N sub-counters and sum on read; or batch increments in memory and flush periodically.

Q13. How do you migrate a database or service without downtime?

Short answer: Use incremental, backward-compatible steps: expand, dual-write or CDC, backfill, switch reads, then contract.

  • Schema: add nullable column → deploy code writing both → backfill → switch reads → drop old.
  • Service: strangler fig, traffic shifting by percentage, shadow traffic, feature flags, easy rollback.
  • Verify with data comparison before the final cutover.

43. Interview Q&A: Scenario & Design Questions

Use this framework for any "Design X" question, then see the questions below.

  1. Clarify functional and non-functional requirements, scale and constraints (5 min).
  2. Estimate traffic, storage, bandwidth (3 min).
  3. API and data model (5 min).
  4. High-level design: draw the main flow end to end (10 min).
  5. Deep dive into the 1–2 hardest parts: bottlenecks, scaling, consistency (15 min).
  6. Failure, monitoring, security, trade-offs, and what you would improve (5 min).

Q1. Design a URL shortener. Key points?

Short answer: Unique id → base62 code, key-value store sharded by code, Redis cache for hot links, 302 redirect, async click analytics.

  • Scale: ~100:1 read to write; 7 chars of base62 give 3.5 trillion codes.
  • Id generation via Snowflake/ticket ranges avoids collisions; custom alias needs a unique constraint.
  • Protect against abuse: rate limits and malware checks; expire links; use 302 to keep analytics.

Q2. Design a chat application.

Short answer: WebSocket gateways with a session registry, chat service assigning ordered ids, write-optimised message store, queue/push for offline users, presence via heartbeats.

  • Delivery receipts via acks; client-generated message ids make sends idempotent.
  • Groups fan out on the server; large channels use pull.
  • Media in blob storage via pre-signed URLs; end-to-end encryption keeps content private.

Q3. Design Twitter's timeline.

Short answer: Hybrid fan-out: push posts to followers' Redis feed lists for normal users, pull celebrity posts at read time and merge.

  • Feed = sorted set of post ids; hydrate from post cache; cursor pagination.
  • Fan-out via queue workers; skip inactive users.
  • Ranking service and CDN for media; counters approximate.

Q4. Design a rate limiter as a service.

Short answer: Gateway middleware calling a Redis-backed token bucket via Lua for atomicity, with rules per client/route and 429 + Retry-After.

Discuss rule storage and hot reload, fail-open vs fail-closed, multi-region sync trade-offs (approximate local limits), and metrics on rejected traffic.

Q5. Design a notification system.

Short answer: API → preferences + template → per-channel queues → workers → provider adapters, with dedupe keys, retries, DLQ and delivery tracking.

Q6. Design Uber / nearby driver search.

Short answer: Stream driver GPS into a geo index (geohash/S2/H3 cells), query the rider's cell and neighbours, match with an atomic claim, shard by city.

Q7. Design a distributed cache.

Short answer: Partition keys with consistent hashing over cache nodes, replicate for availability, use LRU eviction and TTL, a client library or proxy for routing.

  • Handle node failure (replicas, rehash only affected keys), hot keys (local cache), stampede (coalescing), consistency (invalidate on write).
  • Memcached (simple, multithreaded) vs Redis (data structures, persistence, clustering).

Q8. Design a file storage / sharing service (Dropbox).

Short answer: Split files into chunks, deduplicate by hash, upload chunks to blob storage with resumable pre-signed URLs, store metadata in a database, sync clients via change notifications.

  • Only changed chunks are uploaded (delta sync); versioning and conflict copies.
  • Metadata DB sharded by user; notifications via long polling/WebSocket; CDN for downloads; virus scan asynchronously.

Q9. Design a video streaming platform (YouTube/Netflix).

Short answer: Upload to blob storage, transcode asynchronously into multiple resolutions/bitrates, split into small segments (HLS/DASH), serve from CDN with adaptive bitrate.

Queue + worker fleet for transcoding, metadata DB + search index, recommendations offline, CDN edge caching with popular content pre-positioned (Open Connect style).

Q10. Design a search autocomplete.

Short answer: Trie or prefix index of top queries per prefix, precomputed offline from query logs, served from memory/cache with very low latency.

  • Cache top-K suggestions at each prefix node; update periodically (hourly/daily).
  • Debounce client requests, personalise lightly, filter offensive terms.

Q11. Design a payment system.

Short answer: Idempotent payment API, state machine (created → authorised → captured → settled/refunded), double-entry ledger, reconciliation with the provider, and strong consistency.

  • Never store card data (use the provider's tokens, PCI scope).
  • Idempotency key per attempt; webhooks for async results; outbox for events.
  • Audit log immutable; retry safely; daily reconciliation catches mismatches.

Q12. Your system is slow. How do you investigate?

Short answer: Measure first: check dashboards for which tier and which percentile, use traces to find the slow hop, then fix the biggest contributor.

  1. Is it all requests or a subset (endpoint, region, tenant)? When did it start (deploy, traffic, dependency)?
  2. Look at saturation: CPU, memory, connection pools, thread pool, DB locks, queue depth, GC.
  3. Trace: DB query (missing index, N+1), downstream call, network, serialization.
  4. Mitigate: roll back, scale out, shed load, enable cache; then fix root cause and add alerts.

Q13. How would you scale a system from 1 user to 100 million?

Short answer: Evolve step by step: single server → separate DB → LB + stateless servers → cache + CDN → read replicas → queues → sharding → multi-region.

Each step is triggered by a measured bottleneck. Stress that you would not build the 100 M design on day one.
