1. What is AWS Lambda?

AWS Lambda is a serverless, event-driven compute service. You upload a small piece of code (a function) and AWS runs it whenever an event happens: a file upload, an HTTP request, a message in a queue or a timer. You never create, patch or scale servers, and you pay only while your code is running. Lambda was launched in 2014 and is the core of serverless computing on AWS.

  • You supply code + configuration (memory, timeout, permissions); AWS supplies everything else.
  • Billing is per request and per millisecond of execution (GB-seconds). Idle time costs nothing.
  • Supports Python, Node.js, Java, .NET, Ruby, custom runtimes (Go, Rust) and container images up to 10 GB.
  • Scales automatically from zero to thousands of parallel executions.

The smallest Lambda function

def lambda_handler(event, context):
    name = event.get("name", "World")
    return {"message": f"Hello, {name}!"}
Analogy: Lambda is like a taxi. You do not own or maintain a car; you pay only for the ride.

2. What is Serverless Computing?

Serverless does not mean there are no servers. It means you do not manage them. The provider handles provisioning, patching, scaling, availability and capacity; you only write business logic. Billing follows actual usage instead of reserved capacity.

Traditional (EC2)Serverless (Lambda)
ServersYou provision and patchFully managed by AWS
ScalingYou configure auto scalingAutomatic, per request
CostPay while the server is onPay per request and millisecond
IdleStill billedZero cost
Start-upAlways runningOn demand (cold start possible)
  • Other serverless AWS services: S3, DynamoDB, API Gateway, SQS, SNS, EventBridge, Step Functions, Fargate, Aurora Serverless.
  • Four traits: no server management, automatic scaling, pay for value, built-in high availability.

5. Problems, Limitations & When NOT to Use

Lambda is powerful but not perfect. Knowing the trade-offs is a classic interview topic.

ProblemWhy it happensMitigation
Cold startsA new environment must start the runtime and run init codeProvisioned concurrency, SnapStart, smaller packages, lighter runtimes

Limited resources10 GB memory, 6 vCPU, 10 GB /tmpUse containers or EC2 for heavy workloads
Hard to debug locallyDepends on cloud events and IAMSAM local, unit tests, structured logs, X-Ray
Vendor lock-inEvents and integrations are AWS specificKeep business logic separate from handler glue code

Avoid Lambda when…

  • Work runs longer than 15 minutes without being split.
  • You need predictable ultra-low latency for every request (cold starts) and cannot pay for provisioned concurrency.
  • The workload is steady, high-throughput and 24x7, where reserved containers are cheaper.
  • You need special hardware (GPU) or a specific OS kernel.

7. Event-Driven Architecture

In an event-driven architecture (EDA) components communicate by producing and reacting to events instead of calling each other directly. An event is a record that something happened, such as OrderPlaced or ObjectCreated. Lambda is the most common consumer.

  • Producer emits the event and moves on.
  • Router (EventBridge, SNS, SQS, Kinesis) delivers it to interested consumers.
  • Consumer (Lambda) reacts, then goes back to sleep.
  • Benefits: loose coupling, independent scaling, easy to add new consumers, natural buffering.
  • Challenges: eventual consistency, debugging flows across services, duplicate events (design for idempotency).

      "bucket": { "name": "my-uploads" },

8. Execution Flow

The execution flow describes what happens from the moment an event occurs until a result is returned. Press play-through by watching the highlighted step.

  1. Event arrives from a trigger (API request, S3 upload, queue message…).
  2. Lambda service authenticates the call and checks permissions.
  3. It looks for a warm environment; if none is free it creates a new one (cold start).
  4. The handler runs with the event and context objects.
  5. The response is returned (sync) or the event is marked processed (async); logs and metrics go to CloudWatch and the environment is frozen for reuse.

9. Request Life Cycle: Cold Start vs Warm Start

Every execution environment goes through three phases: Init (once), Invoke (many times) and Shutdown. Click any block to learn more.

PhaseWhat happensNotes
InitDownload code, start runtime, run extensions and your global codeCold start delay; up to 10 s; billed
InvokeHandler runs with the eventRepeats for every request; billed per ms
ShutdownEnvironment removed after idle timeExtensions may flush data

Make warm starts count

import boto3, os

# Init phase: runs once per environment (cold start only)
s3 = boto3.client("s3")
TABLE = os.environ["TABLE_NAME"]

def lambda_handler(event, context):
    # Invoke phase: runs for every request; reuses s3 and TABLE
    obj = s3.get_object(Bucket="my-bucket", Key=event["key"])
    return {"size": obj["ContentLength"]}
Rule: put expensive setup (SDK clients, DB connections, config) outside the handler.

11. Handler Function

The handler is the function Lambda calls for every event. You tell Lambda where it is with the format file.function (Python/Node) or package.Class::method (Java). It receives an event (the input) and a context (runtime information).

Python

import json

def lambda_handler(event, context):
    # event: dict with the trigger data   context: runtime info
    body = json.loads(event.get("body") or "{}")
    return {
        "statusCode": 200,
        "headers": {"Content-Type": "application/json"},
        "body": json.dumps({"hello": body.get("name", "world"),
                            "request_id": context.aws_request_id})
    }

Node.js

export const handler = async (event, context) => {
  const body = JSON.parse(event.body ?? "{}");
  return {
    statusCode: 200,
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ hello: body.name ?? "world", requestId: context.awsRequestId })
  };
};

Java

public class Handler implements RequestHandler<Map<String,Object>, String> {
    @Override
    public String handleRequest(Map<String,Object> event, Context context) {
        return "Hello from " + context.getFunctionName();
    }
}
  • The shape of event depends on the trigger: always log it once to inspect it.
  • The return value is the response for synchronous callers and is ignored for asynchronous ones.
  • Raise an exception to signal failure so retries and DLQs can work.

12. Invocation Types (sync, async, poll-based)

How a function is invoked decides who waits, who retries and where failures go. Click the lanes, boxes and arrows for details.

TypeHow it worksExamplesErrors / retries
SynchronousCaller waits for the responseAPI Gateway, ALB, Function URL, SDK RequestResponseNo retry; caller handles errors
AsynchronousLambda queues the event and returns 202S3, SNS, EventBridge, SDK Event2 automatic retries; DLQ / destinations
Poll-based (event source mapping)Lambda polls a queue/stream and invokes with batchesSQS, Kinesis, DynamoDB Streams, MSK, KafkaRetries until success or expiry; partial batch response

Invoke from code

import boto3, json
lam = boto3.client("lambda")

# Synchronous: waits for the result
r = lam.invoke(FunctionName="my-func", InvocationType="RequestResponse",
               Payload=json.dumps({"name": "Asha"}))
print(json.loads(r["Payload"].read()))

# Asynchronous: returns immediately with 202
lam.invoke(FunctionName="my-func", InvocationType="Event",
           Payload=json.dumps({"name": "Asha"}))

Follow an Event End to End

Example: a user uploads cat.jpg and a thumbnail appears. Follow the numbered steps on the architecture diagram above.

  1. User uploads the file to the S3 bucket.
  2. S3 sends an ObjectCreated notification to Lambda asynchronously.
  3. The Lambda service queues the event, authorises S3 through the resource-based policy and returns 202 to S3.
  4. It finds a warm execution environment (or creates one: Init phase).
  5. The handler downloads the image using the execution role, resizes it and writes the thumbnail to another bucket.
  6. Logs and metrics are written to CloudWatch; the REPORT line shows duration and memory.
  7. If the handler throws, Lambda retries twice, then sends the event to the DLQ/destination.

13. Steps to Create a Lambda Function

You can create a function from the console, the AWS CLI, SAM, CDK or Terraform. Start with the console to learn, then move to infrastructure as code.

Console

  1. Open AWS Console → Lambda → Create function.
  2. Choose Author from scratch (or a blueprint / container image).
  3. Enter a function name, e.g. HelloLambda.
  4. Select the runtime (e.g. Python 3.12) and architecture (arm64 or x86_64).
  5. Under permissions choose Create a new role with basic Lambda permissions (logs).
  6. Click Create function, write code in the editor and press Deploy.
  7. Create a test event and press Test; read the result and the logs.

AWS CLI

# 1. package the code
zip function.zip lambda_function.py

# 2. create the function (role must already exist)
aws lambda create-function \
  --function-name HelloLambda \
  --runtime python3.12 \
  --handler lambda_function.lambda_handler \
  --role arn:aws:iam::123456789012:role/lambda-basic-role \
  --zip-file fileb://function.zip

# 3. invoke it
aws lambda invoke --function-name HelloLambda \
  --payload '{"name":"Asha"}' --cli-binary-format raw-in-base64-out out.json
cat out.json

# 4. update code later
aws lambda update-function-code --function-name HelloLambda --zip-file fileb://function.zip

17. Sample Lambda Code (Python & Node.js)

Complete, copy-paste examples for the most common cases.

1. HTTP API with validation and errors (Python)

import json, logging
log = logging.getLogger(); log.setLevel(logging.INFO)

def response(status, body):
    return {"statusCode": status, "headers": {"Content-Type": "application/json"}, "body": json.dumps(body)}

def lambda_handler(event, context):
    log.info("event=%s", json.dumps(event))
    try:
        data = json.loads(event.get("body") or "{}")
        if "name" not in data:
            return response(400, {"error": "name is required"})
        return response(200, {"message": f"Hello, {data['name']}!", "request_id": context.aws_request_id})
    except json.JSONDecodeError:
        return response(400, {"error": "invalid JSON"})
    except Exception:
        log.exception("unexpected error")
        return response(500, {"error": "internal error"})

2. Write to DynamoDB (Python)

import os, uuid, boto3
table = boto3.resource("dynamodb").Table(os.environ["TABLE_NAME"])   # created once

def lambda_handler(event, context):
    item = {"id": str(uuid.uuid4()), "name": event["name"]}
    table.put_item(Item=item)
    return item

19. Trigger: API Gateway

API Gateway exposes Lambda as an HTTP endpoint (REST, HTTP or WebSocket API). It is a synchronous trigger: the client waits for the function result. It adds authentication (Cognito, JWT, IAM, authorizers), throttling, validation and caching.

Event received by the function (proxy integration, trimmed)

  "routeKey": "GET /orders/{id}",

  "pathParameters": { "id": "42" },
  "queryStringParameters": { "expand": "items" },

Handler

import json

def lambda_handler(event, context):
    order_id = event["pathParameters"]["id"]
    return {"statusCode": 200,
            "headers": {"Content-Type": "application/json"},
            "body": json.dumps({"order": order_id})}
  • Integration timeout is 29 seconds by default, so long work must be asynchronous.
  • HTTP API is cheaper and simpler; REST API has usage plans, API keys, WAF and caching.
  • Alternative: a Function URL gives a built-in HTTPS endpoint with no API Gateway.

20. Trigger: Amazon S3

S3 can notify Lambda when objects are created, removed or restored. It is an asynchronous trigger. The event carries the bucket and object key, and your function then reads the file.

import boto3, urllib.parse
s3 = boto3.client("s3")

def lambda_handler(event, context):
    for rec in event["Records"]:
        bucket = rec["s3"]["bucket"]["name"]
        key = urllib.parse.unquote_plus(rec["s3"]["object"]["key"])   # keys are URL-encoded
        obj = s3.get_object(Bucket=bucket, Key=key)
        data = obj["Body"].read()
        print(f"processed {key}: {len(data)} bytes")
Warning: never write results into the same bucket/prefix that triggers the function. That creates an infinite loop and a huge bill.
  • Use prefix/suffix filters (for example only uploads/*.jpg).
  • S3 delivers at least once: handle duplicates.
  • Large files: stream or use byte ranges instead of reading everything into memory.

21. Trigger: DynamoDB Streams

A DynamoDB stream records every item change (INSERT, MODIFY, REMOVE) in order for 24 hours. Lambda polls the stream with an event source mapping and delivers changes in batches, one concurrent batch per shard.

def lambda_handler(event, context):
    for rec in event["Records"]:
        action = rec["eventName"]                      # INSERT | MODIFY | REMOVE
        keys = rec["dynamodb"]["Keys"]
        new = rec["dynamodb"].get("NewImage")
        old = rec["dynamodb"].get("OldImage")
        print(action, keys)
  • Use cases: audit trail, replication, search indexing, aggregate tables, welcome emails.
  • A failing batch blocks its shard: set MaximumRetryAttempts, BisectBatchOnFunctionError and an on-failure destination.
  • Use event filtering to invoke only for matching changes.

23. Trigger: Amazon SNS

SNS uses publish/subscribe: a publisher sends one message to a topic and SNS pushes a copy to every subscriber (Lambda, SQS, email, HTTP). With Lambda as subscriber the invocation is asynchronous.

import json

def lambda_handler(event, context):
    for rec in event["Records"]:
        sns = rec["Sns"]
        msg = json.loads(sns["Message"])
        print(sns["Subject"], msg)
  • Fan-out: one order event triggers billing, inventory and email functions at the same time.
  • Use message filtering so a function only receives relevant messages.
  • Add an SQS queue between SNS and Lambda when you need buffering and a DLQ.

24. Trigger: Amazon SQS

SQS is a managed queue. Lambda polls it and invokes the function with batches of messages. It protects downstream systems from traffic spikes.

def lambda_handler(event, context):
    failures = []
    for rec in event["Records"]:
        try:
            process(rec["body"])
        except Exception:
            failures.append({"itemIdentifier": rec["messageId"]})
    return {"batchItemFailures": failures}      # only these messages are retried
  • Enable ReportBatchItemFailures on the mapping to use partial batch responses.
  • Set the queue visibility timeout to at least 6 times the function timeout.
  • Configure a DLQ with maxReceiveCount on the queue.
  • Use MaximumConcurrency on the mapping to limit how many functions run at once.
  • FIFO queues keep order per message group.

26. IAM Roles, Execution Role & Permissions

Lambda security answers two questions: who can invoke my function and what can my function access. Both use IAM roles and policies. Everything is denied by default.

Execution role

The role the function assumes at runtime. Lambda gives your code short-lived credentials automatically, so no keys are stored in code.

Trust policy (who may assume the role)

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "lambda.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}

Permissions policy (what the function may do)

{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": ["logs:CreateLogGroup","logs:CreateLogStream","logs:PutLogEvents"], "Resource": "*" },
    { "Effect": "Allow", "Action": ["dynamodb:GetItem","dynamodb:PutItem"],
      "Resource": "arn:aws:dynamodb:ap-south-1:123456789012:table/Orders" }
  ]
}
  • Managed policy for logs: AWSLambdaBasicExecutionRole; for VPC: AWSLambdaVPCAccessExecutionRole; for X-Ray: AWSXRayDaemonWriteAccess.
  • AccessDeniedException in a function almost always means the execution role is missing a permission.

Cost calculator

def lambda_cost(invocations, avg_ms, memory_mb, arm64=False):
    gb_seconds = invocations * (avg_ms / 1000) * (memory_mb / 1024)
    price = 0.0000133334 if arm64 else 0.0000166667
    free_gb_s, free_req = 400_000, 1_000_000
    compute = max(0, gb_seconds - free_gb_s) * price
    requests = max(0, invocations - free_req) / 1_000_000 * 0.20
    return round(compute + requests, 2)

print(lambda_cost(10_000_000, 200, 512))   # 10 M calls, 200 ms, 512 MB -> about $6.4

Optimization tips

  • Right-size memory with Lambda Power Tuning; use arm64.
  • Reduce duration: reuse connections, cache, run independent calls in parallel.
  • Batch records from SQS/Kinesis; use event filtering to avoid useless invocations.
  • Set log retention and log levels; avoid recursion; set budgets and alarms.
  • Use provisioned concurrency only where latency requires it; consider Compute Savings Plans.

Common mistakes ❌

  • Default 3-second timeout or too little memory.
  • Creating SDK clients and DB connections inside the handler on every call.

45. Interview Q&A – Fundamentals

Each answer starts with a short answer you can say first, then the detail that proves you understand it. Use practice mode (button above) to hide answers until you tap a question, and tap 🔊 next to the heading to hear them read aloud.

Q1. What is AWS Lambda?

Short answer: AWS Lambda is a serverless, event-driven compute service. You upload a function; AWS runs it in response to events, scales it automatically and bills only for the requests and the milliseconds it actually runs.

Instead of provisioning servers, patching operating systems and planning capacity, you supply code and a few settings (memory, timeout, permissions, trigger). Lambda handles placement, scaling, high availability across Availability Zones, and operating-system and runtime patching for managed runtimes.

  • Event-driven: triggered by API calls, S3 uploads, queue messages, schedules and 200+ other sources.
  • Stateless and short-lived: each invocation runs in an isolated execution environment that can be created or destroyed at any time (max 15 minutes per run).
  • Pay-per-use: no cost when idle; free tier of 1M requests and 400,000 GB-seconds per month.
  • Runtimes: Python, Node.js, Java, .NET, Ruby, custom runtimes (Go, Rust) and container images up to 10 GB.

💡 Interview tip: Open with the definition, then give one concrete example, for example "an S3 upload triggers a function that creates a thumbnail".

Q2. What does "serverless" mean?

Short answer: Servers still exist, but you do not provision, patch, scale or pay for them while idle. The provider runs them and you pay for actual usage.

Serverless is a responsibility split. In a traditional setup you choose instance types, configure auto scaling, patch the OS and keep capacity ahead of demand. In serverless the cloud provider takes over those tasks. The defining properties are:

  • No server management (no SSH, no AMIs, no patching).
  • Automatic, fine-grained scaling including scaling to zero.
  • Pay for value (per request / per millisecond) instead of paying for reserved capacity.
  • Built-in availability and fault tolerance.

Other serverless AWS services include S3, DynamoDB, API Gateway, SQS, SNS, EventBridge, Step Functions, Fargate and Aurora Serverless.

💡 Interview tip: Avoid saying "no servers"; say "no server management".

Q3. What are the main benefits of Lambda?

Short answer: No server management, automatic scaling, pay-per-use pricing, built-in high availability, faster development and deep integration with the rest of AWS.

  • Cost efficiency: idle time is free; spiky workloads are much cheaper than always-on servers.
  • Elastic scale: from zero to thousands of concurrent executions without capacity planning (up to account limits).
  • Faster delivery: developers write business logic and attach a trigger; no infrastructure design.
  • Lower operational burden: AWS patches the OS and managed runtimes and replaces failed hardware.
  • Security: strong isolation (Firecracker microVMs) and IAM integration.
  • Integration: native triggers from S3, DynamoDB, SQS, EventBridge, API Gateway and more.

💡 Interview tip: Balance the answer with one limitation (cold starts or the 15-minute limit); it shows judgement.

Q4. What are the limitations of Lambda?

Short answer: Cold starts, a 15-minute maximum run time, limited memory/CPU/storage, statelessness, harder local debugging, vendor lock-in and concurrency limits.

  • Cold starts: first request after idle or scale-out pays environment creation and init time. Mitigate with provisioned concurrency, SnapStart, smaller packages.
  • 15 minutes: use Step Functions, Fargate or AWS Batch for longer work.
  • Resource caps: up to 10 GB memory (about 6 vCPU), 10 GB /tmp, 6 MB sync payload.
  • Stateless: keep state in S3, DynamoDB, ElastiCache or EFS.
  • Connections: many concurrent environments can exhaust database connections; use RDS Proxy.
  • Observability/debugging: distributed and event-driven; needs good logging, tracing and local tools (SAM).
  • Lock-in: triggers and integrations are AWS-specific; keep business logic separate from handler glue.

💡 Interview tip: For each limitation, name the mitigation. That turns a list of problems into engineering judgement.

Q5. What is the maximum timeout, memory and package size?

Short answer: Timeout 15 minutes; memory 128 MB to 10,240 MB; package 50 MB zipped (direct upload) / 250 MB unzipped including layers, or a container image up to 10 GB.

  • Default timeout is only 3 seconds; default memory 128 MB.
  • CPU and network bandwidth scale with memory (about 1,769 MB equals one vCPU, up to 6 vCPUs).
  • /tmp ephemeral storage 512 MB by default, configurable to 10,240 MB.
  • Environment variables: 4 KB total. Layers: up to 5 per function.
  • Payload: 6 MB for synchronous request and response.

💡 Interview tip: Say the defaults too (3 seconds, 128 MB); interviewers often ask why a new function times out.

Q6. What is a handler?

Short answer: The handler is the entry-point function Lambda calls for every event, configured as file.function (for example app.lambda_handler) or Namespace.Class::Method in .NET/Java.

Lambda loads your code, runs your init code once per environment, then calls the handler with two arguments: event (the trigger data as JSON) and context (runtime information). The return value goes back to the caller for synchronous invocations and is ignored for asynchronous ones; raising an exception signals failure so retries and DLQs can work.

def lambda_handler(event, context):
    print(context.aws_request_id, context.get_remaining_time_in_millis())
    return {"statusCode": 200, "body": "ok"}

💡 Interview tip: Mention that the shape of event depends entirely on the trigger, so log it once when integrating a new source.

Q7. What is in the event and context objects?

Short answer: event is the JSON input from the trigger; context exposes runtime metadata such as the request id, function name, memory limit and the time left.

  • event examples: API Gateway (route, headers, body), S3 (bucket and key), SQS (records with messageId and body), EventBridge (source, detail-type, detail).
  • context (Python): aws_request_id, function_name, memory_limit_in_mb, get_remaining_time_in_millis(), log_group_name.
  • Use get_remaining_time_in_millis() to stop long loops gracefully before the timeout.

💡 Interview tip: Use the request id as a correlation id in logs so you can trace one invocation across services.

Q8. Which languages does Lambda support?

Short answer: Python, Node.js, Java, .NET and Ruby as managed runtimes; Go, Rust and others through the OS-only/custom runtime (provided.al2023); anything via container images.

Managed runtimes are patched and updated by AWS and have version support/deprecation schedules, so keep versions current. Custom runtimes poll the Lambda Runtime API. Choose by team skills and workload: Python/Node.js start fast; Java/.NET start slower (use SnapStart or Native AOT); Go/Rust give very small, fast binaries. Architectures: x86_64 or arm64 (Graviton, about 20% cheaper per GB-second).

💡 Interview tip: Mention arm64; it is an easy cost optimisation interviewers like to hear.

Q9. Is Lambda stateless? How do you persist data?

Short answer: Yes. Each environment is disposable, so anything you must keep goes to an external service: S3, DynamoDB, RDS, ElastiCache or EFS.

Global variables and /tmp survive between warm invocations of the same environment, which is useful for caching, but there is no guarantee: Lambda can recycle environments at any time, and concurrent requests run in different environments, each with its own memory and /tmp.

  • Cache clients, config and small lookup data in global scope.
  • Never rely on local memory or files for correctness or sharing between requests.
  • Use idempotent writes so retries and re-executions are safe.

💡 Interview tip: A nice follow-up: "state in global scope is an optimisation, never a source of truth."

Q10. How are you billed for Lambda?

Short answer: You pay for requests and for duration x memory measured in GB-seconds, billed per millisecond, plus optional extras (provisioned concurrency, extra ephemeral storage, data transfer).

  • Requests: about $0.20 per million.
  • Compute: about $0.0000166667 per GB-second on x86 and about 20% less on arm64.
  • Free tier each month: 1 million requests and 400,000 GB-seconds.
  • Init time is billed for managed runtimes as well.
  • Related costs: CloudWatch logs, API Gateway, data transfer, NAT gateways for VPC functions.
gb_seconds = invocations * (avg_ms / 1000) * (memory_mb / 1024)
cost = gb_seconds * 0.0000166667 + invocations / 1_000_000 * 0.20   # before free tier

💡 Interview tip: Explain the memory-cost trade-off: more memory can reduce duration enough to lower the total.

Q11. What is the default concurrency limit?

Short answer: 1,000 concurrent executions per Region per account by default; it is a soft limit that can be increased through AWS Support.

Concurrency is the number of requests being processed at the same moment (roughly requests per second × average duration). All functions in the Region share this pool unless you set reserved concurrency on some. When the limit is reached new synchronous invocations are throttled with HTTP 429, asynchronous events are retried for up to 6 hours, and event source mappings back off. Each function can also scale by at most 1,000 new execution environments every 10 seconds.

💡 Interview tip: Mention reserved concurrency as the tool to protect critical functions or limit a noisy one.

Q12. Lambda vs EC2: when would you use which?

Short answer: Use Lambda for event-driven, short-running, spiky workloads with no server management; use EC2 when you need full OS control, long-running processes, special hardware or steady high utilisation.

Q13. Lambda vs containers (Fargate/ECS/EKS)?

Short answer: Lambda is best for spiky, short, event-driven workloads with zero operations; containers suit long-running, steady or custom-runtime workloads without Lambda's 15-minute and size limits.

  • Lambda: scales to zero, per-ms billing, built-in triggers, concurrency model of one request per environment.
  • Fargate/ECS: long-running services and batch, multiple concurrent requests per container, more control over networking and runtime.
  • EKS: Kubernetes ecosystem, portability, more operational effort.
  • Lambda can run container images too, but they are still event-driven functions with Lambda limits.
  • Many architectures mix them: Lambda for glue and events, containers for core services.

💡 Interview tip: Mention portability and cost at constant high load as reasons to pick containers.

Q14. What is a cold start and a warm start?

Short answer: A cold start happens when Lambda must create a new execution environment (download code, start the runtime, run init code) before running the handler; a warm start reuses an existing initialised environment and skips Init.

  • When cold starts happen: first invoke, after scaling out, after idle time, after deployments or configuration changes.
  • Typical size: tens of milliseconds to a few seconds, depending on runtime, package size, VPC networking and your init code.
  • Reduce: smaller deployment package, lazy imports, arm64, SnapStart, provisioned concurrency, avoid unnecessary work in global scope.
  • Visible in logs as Init Duration in the REPORT line.

💡 Interview tip: Add that only a small percentage of requests are cold in steady traffic; measure p99 before optimising.

Q15. What are the phases of the Lambda lifecycle?

Short answer: Init (download code, start runtime, run your global/init code and extensions), Invoke (the handler runs, repeated for each request) and Shutdown (the environment is removed after idle time).

  • Init: happens once per new environment; up to 10 seconds; billed.
  • Invoke: runs up to the configured timeout; billed per millisecond; between invocations the environment is frozen.
  • Shutdown: extensions can receive a short shutdown signal to flush data; do not rely on it for correctness.

💡 Interview tip: Link lifecycle to practice: expensive setup goes in Init, per-request logic in Invoke.

Q16. What environment variables does Lambda provide?

Short answer: Lambda injects runtime information and credentials as environment variables, for example AWS_REGION, AWS_LAMBDA_FUNCTION_NAME, AWS_LAMBDA_FUNCTION_MEMORY_SIZE, AWS_LAMBDA_LOG_GROUP_NAME, and the temporary role credentials (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN).

You add your own configuration as function environment variables (4 KB total) such as TABLE_NAME. They can be encrypted with KMS; for real secrets prefer Secrets Manager or SSM Parameter Store (SecureString) and cache the value in global scope.

💡 Interview tip: Mention that the SDK picks the credentials up automatically; you never hardcode keys.

Q17. Why should you create SDK clients outside the handler?

Short answer: Code outside the handler runs once per execution environment, so clients, connections and config are reused across warm invocations, which reduces latency and avoids repeated connection setup.

import boto3, os
dynamodb = boto3.resource("dynamodb")            # created once (Init phase)
table = dynamodb.Table(os.environ["TABLE_NAME"])

def lambda_handler(event, context):
    table.put_item(Item={"id": event["id"]})     # reused on warm invocations
  • Faster warm invocations and fewer TLS handshakes.
  • Fewer database connections when you reuse a pool.
  • Beware: heavy init increases cold-start time, so lazy-initialise rarely used resources.

💡 Interview tip: Mention lazy initialisation as the counterweight.

Q18. What is a Lambda layer?

Short answer: A layer is a zip archive of libraries, a custom runtime or data that is mounted at /opt and can be shared by many functions.

  • Up to 5 layers per function; total unzipped size (function + layers) ≤ 250 MB.
  • Layers are versioned and immutable; functions reference a specific version.
  • Great for shared dependencies, Powertools, monitoring agents.
  • Container images are the alternative when you need more than 250 MB.
aws lambda publish-layer-version --layer-name common-libs --zip-file fileb://layer.zip --compatible-runtimes python3.12

💡 Interview tip: Note the Python path convention: libraries must be under python/ inside the layer zip.

Q19. What are versions and aliases?

Short answer: A version is an immutable snapshot of code and configuration; an alias is a named pointer (for example prod) to a version that can split traffic between two versions for canary releases.

  • $LATEST is mutable and meant for development.
  • Publishing creates numbered versions (1, 2, 3).
  • Aliases give stable ARNs for triggers and clients and allow instant rollback by re-pointing.
  • Weighted aliases (for example 90/10) plus CodeDeploy automate canary or linear deployments with alarms and automatic rollback.
aws lambda publish-version --function-name api
aws lambda update-alias --function-name api --name prod --function-version 2 \
  --routing-config AdditionalVersionWeights={"3"=0.1}

💡 Interview tip: Production triggers should point to an alias, never to $LATEST.

Q20. What is a Function URL?

Short answer: A built-in HTTPS endpoint for a Lambda function, with optional IAM authentication, CORS configuration and response streaming, created without API Gateway.

  • Auth type AWS_IAM (SigV4-signed requests) or NONE (public).
  • Good for simple webhooks and internal tools; no throttling plans, API keys or request validation like API Gateway.
  • The URL has the form https://<id>.lambda-url.<region>.on.aws.

💡 Interview tip: Compare with API Gateway: Function URL is simpler and cheaper; API Gateway has more features (auth, throttling, caching, WAF).

46. Interview Q&A – Triggers & Architecture

Know how each trigger invokes Lambda (sync, async or polled) because retries, errors and scaling all follow from that.

Q1. Explain synchronous, asynchronous and poll-based invocation.

Short answer: Synchronous: the caller waits for the result (API Gateway). Asynchronous: Lambda queues the event, returns 202 immediately and retries failures (S3, SNS, EventBridge). Poll-based: Lambda reads from a queue or stream and invokes the function with batches (SQS, Kinesis, DynamoDB Streams).

  • Sync: result or error goes straight back; no automatic retry; the caller (or API Gateway timeout of 29 s) controls waiting.
  • Async: an internal queue holds the event; 2 automatic retries (configurable 0–2), max event age up to 6 hours, failures go to a DLQ or on-failure destination; order is not guaranteed.
  • Poll-based: an event source mapping polls the source and invokes synchronously with a batch; on error the batch is retried until success or expiry; partial batch responses avoid re-processing successes.
lam.invoke(FunctionName="f", InvocationType="RequestResponse", Payload=b"{}")  # sync
lam.invoke(FunctionName="f", InvocationType="Event", Payload=b"{}")            # async (202)

💡 Interview tip: Draw three lanes and mark who waits, who retries and where failures go.

Q2. How many times are async invocations retried?

Short answer: By default twice after the first failure (three attempts total), with delays of about 1 minute then 2 minutes; configurable from 0 to 2, with a maximum event age of 60 seconds to 6 hours.

If every attempt fails, or the event ages out, Lambda discards it unless you configured a dead-letter queue (SQS/SNS) or an on-failure destination (SQS, SNS, Lambda, EventBridge). Destinations also support on-success routing and include richer context (the error and the original event). Because retries run the same code again, handlers must be idempotent.

aws lambda put-function-event-invoke-config --function-name worker \
  --maximum-retry-attempts 1 --maximum-event-age-in-seconds 3600 \
  --destination-config '{"OnFailure":{"Destination":"arn:aws:sqs:...:worker-failures"}}'

💡 Interview tip: State that synchronous invocations are not retried by Lambda at all.

Q3. What is an event source mapping?

Short answer: An event source mapping is a Lambda resource that polls a stream or queue (SQS, Kinesis, DynamoDB Streams, MSK, self-managed Kafka) and invokes your function with batches of records.

  • Settings: BatchSize, MaximumBatchingWindowInSeconds, MaximumConcurrency, FilterCriteria, retry limits, bisect-on-error, on-failure destination, partial batch response.
  • Scaling: SQS pollers scale with queue depth; stream mappings scale with shards (parallelization factor up to 10).
  • There is no charge for polling itself, only for invocations.
  • Filtering drops records that do not match before invoking, saving cost.

💡 Interview tip: Mention that the mapping, not your code, owns the polling and deletion/checkpointing.

Q4. How do you process SQS messages with partial failures?

Short answer: Enable ReportBatchItemFailures on the event source mapping and return the ids of failed messages in batchItemFailures, so only those messages become visible again.

def lambda_handler(event, context):
    failures = []
    for rec in event["Records"]:
        try:
            process(rec["body"])
        except Exception:
            failures.append({"itemIdentifier": rec["messageId"]})
    return {"batchItemFailures": failures}

Without this feature, one bad message makes the whole batch fail and every message (including successful ones) is retried, causing duplicates. Combine it with a queue DLQ (redrive policy with maxReceiveCount) so poison messages end up parked.

💡 Interview tip: Add that handlers should still be idempotent because standard queues are at-least-once.

Q5. What should the SQS visibility timeout be?

Short answer: At least six times the function timeout (AWS recommendation) so a message is not delivered again while a function is still processing it.

When Lambda receives a batch the messages become invisible for the visibility timeout. If processing takes longer (or Lambda retries after a timeout), messages reappear and are processed twice, or end up in the DLQ prematurely. The six-times rule leaves room for retries and polling behaviour. Also set the queue DLQ maxReceiveCount high enough for transient failures, and use MaximumConcurrency on the mapping to protect downstream systems.

💡 Interview tip: A classic gotcha question: "messages processed twice even though no error occurred" → visibility timeout too short.

Q6. What happens when a stream record keeps failing?

Short answer: Lambda retries the whole batch and blocks that shard until it succeeds or the data expires. Configure maximum retries, bisect-on-error and an on-failure destination to move the poison record aside.

  • MaximumRetryAttempts: stop retrying after N attempts.
  • MaximumRecordAgeInSeconds: skip records older than a limit.
  • BisectBatchOnFunctionError: split the batch in halves to isolate the bad record.
  • On-failure destination: send the failure metadata to SQS/SNS for inspection.
  • IteratorAge metric shows how far behind the consumer is; alarm on it.

💡 Interview tip: Mention that order is preserved per shard, which is why one poison record blocks progress.

Q7. How does API Gateway invoke Lambda and what is its timeout?

Short answer: API Gateway invokes Lambda synchronously (proxy or custom integration) and waits for the result; the default integration timeout is 29 seconds.

With Lambda proxy integration API Gateway passes the full request (method, path, headers, query string, body) as the event and expects a response object with statusCode, headers and a string body. If the function exceeds 29 seconds the client gets a 504 even though the function may keep running, so long operations should return 202 and continue asynchronously (SQS, Step Functions) with a status endpoint or webhook.

💡 Interview tip: Mention authorizers (Cognito, JWT, Lambda authorizer) and throttling/caching as API Gateway value-adds.

Q8. REST API vs HTTP API in API Gateway?

Short answer: HTTP APIs are cheaper, faster and simpler with JWT/OIDC and Lambda proxy support; REST APIs have more features such as usage plans and API keys, request validation, caching, WAF integration and edge-optimised endpoints.

  • HTTP API: lower latency and cost (roughly 70% cheaper), CORS, JWT authorizers, auto deploy.
  • REST API: API keys/usage plans, request/response transformation (VTL), caching, WAF, resource policies, private endpoints.
  • Choose HTTP API by default; choose REST API when you need its extra features.
  • WebSocket APIs exist for two-way communication.

💡 Interview tip: A good answer says "default to HTTP API unless I need X".

Q9. How do you run a function on a schedule?

Short answer: Create an EventBridge (formerly CloudWatch Events) rule or EventBridge Scheduler schedule with rate() or cron() that targets the function, and grant EventBridge permission to invoke it.

aws events put-rule --name nightly --schedule-expression "cron(0 2 * * ? *)"      # 02:00 UTC daily
aws lambda add-permission --function-name report --statement-id eb --action lambda:InvokeFunction \
  --principal events.amazonaws.com --source-arn arn:aws:events:...:rule/nightly
aws events put-targets --rule nightly --targets "Id"="1","Arn"="arn:aws:lambda:...:function:report"

Cron expressions in EventBridge have six fields and use UTC. Scheduler adds time zones, one-time schedules and flexible time windows. The invocation is asynchronous, so failures retry and can go to a DLQ.

💡 Interview tip: Mention idempotency: scheduled runs can occasionally overlap or repeat.

Q10. What are the gotchas of the S3 trigger?

Short answer: Object keys are URL-encoded, delivery is at-least-once, events can arrive out of order, and writing output to the same bucket and prefix causes an infinite loop.

  • Decode keys: use urllib.parse.unquote_plus(key) (spaces arrive as +).
  • Duplicates and ordering: handle idempotently; do not assume events arrive in upload order.
  • Recursive loops: write results to another bucket or prefix and use prefix/suffix filters; Lambda now also detects some recursive loops and stops them.
  • Large files: stream or use byte ranges; consider S3 multipart upload events and presigned URLs for uploads.
  • Permissions: a resource policy lets S3 invoke the function, scoped by SourceArn and SourceAccount.

💡 Interview tip: Describe the loop bug and its fix; it is the most common real-world S3 mistake.

Q11. SNS vs SQS vs EventBridge?

Short answer: SNS pushes one message to many subscribers (fan-out); SQS is a durable queue consumers pull from (buffering); EventBridge routes events by content-based rules and schedules, with SaaS and AWS service sources.

  • Delivery: SNS push; SQS pull (Lambda polls); EventBridge push to targets.
  • Ordering/dedup: SNS/SQS FIFO variants keep order; EventBridge has none.
  • Filtering: SNS attribute filters; EventBridge rich JSON patterns.
  • Typical combo: SNS or EventBridge fan-out → one SQS queue per consumer → Lambda, giving buffering, retries and a DLQ per consumer.

💡 Interview tip: Mention the fan-out-to-queues pattern; it shows real design experience.

Q12. What is the fan-out pattern?

Short answer: Fan-out delivers one event to many independent consumers, typically an SNS topic or EventBridge bus with several subscribed Lambda functions or SQS queues.

Example: an OrderPlaced event goes to a topic; billing, inventory, email and analytics functions each receive a copy and process it independently, so they can fail, retry and scale separately. Putting an SQS queue between the topic and each function adds buffering, controlled concurrency and a DLQ per consumer. Use message filtering so consumers only get relevant events.

💡 Interview tip: Contrast with a single queue where consumers compete for messages.

Q13. How do you preserve ordering?

Short answer: Use sources that guarantee it per key: SQS FIFO (message group id), Kinesis or DynamoDB Streams (per shard/partition key). Standard SQS, SNS and asynchronous invocations do not guarantee order.

  • SQS FIFO: ordering within a message group; Lambda processes one batch per group at a time.
  • Kinesis/DynamoDB Streams: order within a shard; parallelization factor allows concurrency across key hashes while keeping order per key.
  • Order forces sequential processing, so it limits throughput; design keys to spread load.
  • Make handlers idempotent anyway, because retries can still replay records.

💡 Interview tip: Ask what ordering is really needed (per customer? per order?) before choosing a source.

Q14. What is a DLQ vs destinations?

Short answer: A DLQ (SQS or SNS) captures events that failed all retries of an asynchronous invocation; destinations are the newer mechanism that routes both success and failure results (to SQS, SNS, Lambda or EventBridge) with richer context.

  • DLQ messages contain the original event and limited attributes; destinations include the request/response payload and error details.
  • Destinations support on-success chaining without code.
  • For SQS event sources configure the DLQ on the queue; for streams use the mapping's on-failure destination.
  • AWS recommends destinations for new designs.

💡 Interview tip: Mention alarms on DLQ depth so failures are noticed.

Q15. How do you invoke a function from another function?

Short answer: Use the SDK Invoke API (sync or async), but prefer decoupling through queues, events or Step Functions instead of chaining synchronous calls.

Synchronous chaining makes the caller wait (and pay) while the callee runs, doubles cold-start latency risks and can cascade failures. Better options: publish to SNS/EventBridge/SQS; use Step Functions to orchestrate multi-step workflows with retries and error handling; or use destinations for success/failure chaining. If you must invoke directly, set timeouts so that caller timeout > callee timeout and avoid recursive loops.

💡 Interview tip: Mention the "Lambda calling Lambda" anti-pattern and its alternatives.

Q16. What is Lambda@Edge?

Short answer: Lambda@Edge runs Lambda functions at CloudFront edge locations to customise requests and responses (auth, redirects, header rewrites, A/B tests, SEO), closer to users.

  • Triggers: viewer request/response and origin request/response.
  • Limits are tighter than normal Lambda and the function must be created in us-east-1.
  • CloudFront Functions are lighter and cheaper for simple JavaScript logic at massive scale (sub-millisecond), while Lambda@Edge supports more runtime power and network access.

💡 Interview tip: Pick CloudFront Functions for simple header/URL tweaks, Lambda@Edge for heavier logic.

Q17. How do you expose a function without API Gateway?

Short answer: Use a Function URL or put Lambda behind an Application Load Balancer target group.

  • Function URL: simple HTTPS endpoint with IAM or no auth, CORS and streaming.
  • ALB: routes by path/host to Lambda targets, supports WAF, Cognito/OIDC auth and mixed targets (EC2, ECS, Lambda).
  • Choose API Gateway when you need throttling plans, API keys, request validation, caching or usage plans.

💡 Interview tip: State the trade-off: fewer features and lower cost versus a managed API layer.

Q18. What is Step Functions and when do you use it with Lambda?

Short answer: Step Functions is a serverless workflow orchestrator that coordinates multiple steps (Lambda, ECS, SDK integrations) with retries, branching, parallelism, waits and error handling.

  • Use it for processes longer than 15 minutes, human-approval waits, saga/compensation flows, ETL pipelines and anything where you would otherwise chain Lambdas.
  • Standard workflows: up to a year, exactly-once execution semantics, audit history. Express: high volume, short, at-least-once.
  • The state machine owns retry/backoff and catch logic, keeping individual functions simple.
  • Distributed Map processes millions of S3 items in parallel.

💡 Interview tip: Say that orchestration belongs in Step Functions and business logic in Lambda.

Q19. How does Lambda connect to a VPC?

Short answer: You configure subnets and security groups on the function; Lambda creates shared elastic network interfaces (Hyperplane ENIs) so the function can reach private resources like RDS or ElastiCache.

  • For internet access from a VPC function put it in private subnets with a NAT gateway.
  • For AWS services prefer VPC endpoints (gateway endpoints for S3/DynamoDB, interface endpoints for others).
  • Cold-start overhead of VPC attachment is small today; the real cost is NAT/endpoint charges and misconfiguration.
  • Only attach to a VPC when you need private resources; public AWS APIs do not require it.

💡 Interview tip: A classic bug: "function in a VPC cannot reach the internet" → missing NAT or route.

Q20. How do you connect Lambda to a relational database safely?

Short answer: Use RDS Proxy for connection pooling, store credentials in Secrets Manager or use IAM authentication, reuse connections in global scope, and cap concurrency so you do not exhaust database connections.

  • Each concurrent environment may open its own connection; 500 concurrent invocations can overwhelm max_connections.
  • RDS Proxy multiplexes many Lambda connections onto a smaller pool and handles failover quickly.
  • Create the connection outside the handler and validate it before use.
  • Use reserved concurrency or an SQS queue with limited mapping concurrency to throttle load.
  • Consider DynamoDB or Aurora Data API when relational features are not required.

💡 Interview tip: Mention that Lambda and RDS must be in the same VPC for RDS Proxy.

47. Interview Q&A – Security, Monitoring & Performance

Security and performance questions reward precise vocabulary and awareness of trade-offs.

Q1. Execution role vs resource-based policy?

Short answer: The execution role defines what the function can access (outbound); a resource-based policy attached to the function defines who can invoke it (inbound).

  • Execution role: IAM role with a trust policy for lambda.amazonaws.com and permission policies such as dynamodb:PutItem. Lambda assumes it through STS and gives the code temporary credentials.
  • Resource-based policy: statements like "S3 bucket X may call lambda:InvokeFunction". Added with aws lambda add-permission or automatically when you add a trigger in the console.
  • Cross-account invocation needs the resource policy (or an IAM role in the caller account).

💡 Interview tip: Use the "two gates" picture: gate 1 is can the caller start the function, gate 2 is can the function reach the service.

Q2. What is the minimum permission a function needs?

Short answer: Permission to write logs to CloudWatch: logs:CreateLogGroup, logs:CreateLogStream, logs:PutLogEvents, provided by the managed policy AWSLambdaBasicExecutionRole.

  • Add AWSLambdaVPCAccessExecutionRole for VPC functions (ENI permissions).
  • Add AWSXRayDaemonWriteAccess for tracing.
  • Add only the specific actions and resource ARNs your code uses (for example one DynamoDB table).
  • Event source mappings need extra read permissions (for example sqs:ReceiveMessage, sqs:DeleteMessage) on the execution role.

💡 Interview tip: If logs are missing, check these three log permissions first.

Q3. How do you give a function secure access to secrets?

Short answer: Store secrets in AWS Secrets Manager or SSM Parameter Store (SecureString), grant the execution role read access, fetch the value once and cache it in global scope; never hardcode secrets or keep them in plain environment variables.

import boto3, json
sm = boto3.client("secretsmanager")
_secret = None
def get_secret():
    global _secret
    if _secret is None:                                  # cached across warm invocations
        _secret = json.loads(sm.get_secret_value(SecretId="prod/db")["SecretString"])
    return _secret
  • Encrypt with KMS; restrict kms:Decrypt to the role.
  • The AWS Parameters and Secrets Lambda Extension caches values with a local HTTP endpoint.
  • Rotate secrets automatically with Secrets Manager rotation functions.
  • Prefer IAM roles/IAM auth over passwords wherever the service supports it.

💡 Interview tip: Mention caching and rotation: they are what make this answer production-grade.

Q4. What is least privilege and how do you apply it to Lambda?

Short answer: Grant only the actions and resources a function needs, nothing more: one role per function, specific ARNs instead of *, and conditions where possible.

  • Start narrow, run the function, and add permissions from AccessDenied messages.
  • Use IAM Access Analyzer policy generation from CloudTrail activity to right-size roles.
  • Separate read and write functions; avoid sharing a powerful role across functions.
  • Use permission boundaries and SCPs as guardrails for teams.

💡 Interview tip: Contrast a bad policy (Action: *, Resource: *) with a good one for a concrete answer.

Q5. What is the confused deputy problem?

Short answer: A service that acts on your behalf can be tricked into accessing your resource for another party. Mitigate it by restricting resource policies with AWS:SourceArn and AWS:SourceAccount conditions.

Example: a resource policy allows s3.amazonaws.com to invoke your function. Without a condition, a bucket in someone else's account could invoke it too. Adding SourceArn = arn:aws:s3:::my-bucket and SourceAccount ensures only your bucket can. The same applies to SNS topics, EventBridge rules and cross-account role trusts (use ExternalId).

💡 Interview tip: This is a security-aware answer that stands out.

Q6. How do you debug AccessDenied?

Short answer: Read the error message for the denied action and resource, fix the execution role or the resource policy, and check other layers such as KMS key policies, S3 bucket policies, permission boundaries and SCPs; CloudTrail shows the denied call.

  • Reproduce with the same role (IAM policy simulator).
  • Remember explicit Deny overrides Allow; implicit deny is the default.
  • Cross-account access needs permission on both sides.
  • KMS-encrypted objects need kms:Decrypt in addition to s3:GetObject.

💡 Interview tip: Mention checking all policy types, not only the role.

Q7. Where do Lambda logs go and how do you control logging cost?

Short answer: To CloudWatch Logs, in the log group /aws/lambda/<function>; control cost with retention periods, log levels, structured logging and sampling.

  • Everything printed to stdout/stderr becomes a log event; each execution environment writes its own stream.
  • Default retention is never expire: set 7–30 days (or export to S3).
  • Use JSON logs and the advanced logging controls (log level filtering) of Lambda.
  • Avoid logging full payloads or secrets/PII; sample verbose logs.
  • Logs Insights lets you query without exporting.

💡 Interview tip: Mention that logging can cost more than compute at high volume.

Q8. What is in the REPORT log line?

Short answer: Duration, Billed Duration, Memory Size, Max Memory Used and, on cold starts, Init Duration.

REPORT RequestId: 4f1c...  Duration: 183.42 ms  Billed Duration: 184 ms
       Memory Size: 512 MB  Max Memory Used: 211 MB  Init Duration: 346.88 ms
  • Duration vs timeout reveals timeouts close calls.
  • Max Memory Used vs Memory Size shows if you are over- or under-provisioned or near OOM.
  • Init Duration is the cold-start cost.
  • Logs Insights can aggregate these across invocations.

💡 Interview tip: Say that it is the first thing you read when tuning.

Q9. Which metrics do you alarm on?

Short answer: Errors, Throttles, Duration (p95/p99), IteratorAge for streams, DLQ depth/DeadLetterErrors and ConcurrentExecutions approaching the limit.

  • Errors: Sum ≥ 1 for critical functions, or error-rate math (Errors / Invocations).
  • Throttles: any non-zero value deserves attention.
  • Duration p99 near the timeout predicts failures.
  • IteratorAge: stream consumers falling behind.
  • AsyncEventAge / queue age: events waiting too long.
  • Route alarms through SNS to chat or paging.

💡 Interview tip: Add that you alarm on business outcomes too (orders processed) not only infrastructure.

Q10. CloudWatch vs X-Ray vs CloudTrail?

Short answer: CloudWatch gives logs and metrics (what happened and how much); X-Ray traces a request across services (where time is spent); CloudTrail audits API calls (who changed or invoked what).

  • CloudWatch: debugging, dashboards, alarms.
  • X-Ray: distributed tracing and service maps; enable Active tracing and instrument SDK calls.
  • CloudTrail: security and compliance; management events on by default, data events optional.
  • They complement each other; OpenTelemetry (ADOT) is an alternative for tracing.

💡 Interview tip: One-liner: logs say what, traces say where, audit says who.

Q11. How do you reduce cold starts?

Short answer: Make initialisation lighter and avoid it when it matters: smaller packages, lighter runtimes/arm64, lazy imports, SnapStart, provisioned concurrency, and avoiding needless VPC or heavy init.

  • Package: tree-shake/bundle (esbuild), remove unused dependencies, use layers carefully.
  • Init code: lazy-load rarely used modules; avoid synchronous network calls at init.
  • SnapStart: snapshots the initialised environment and resumes from it (Java and newer runtimes).
  • Provisioned concurrency: pre-initialised environments, billed while configured; use with scheduled auto scaling.
  • Memory: more memory gives more CPU, which speeds up init.
  • Measure first with Init Duration and p99 latency.

💡 Interview tip: Mention that keep-warm pings are an old workaround; provisioned concurrency is the supported solution.

Q12. What is SnapStart?

Short answer: SnapStart takes a snapshot of the memory and disk state of an initialised execution environment when you publish a version and resumes new environments from that snapshot, cutting cold-start time dramatically.

  • Works on published versions/aliases (not $LATEST).
  • Originally for Java; now available for additional runtimes (Python, .NET) in supported regions.
  • Be careful with uniqueness: random seeds, temporary credentials and connections created during init must be refreshed after restore (runtime hooks).
  • Billed per restore and snapshot storage; no extra provisioned cost when idle.

💡 Interview tip: Mention the uniqueness caveat; it shows depth.

Q13. Reserved vs provisioned concurrency?

Short answer: Reserved concurrency guarantees and caps a function's share of the account concurrency (free). Provisioned concurrency keeps environments initialised and ready to avoid cold starts (extra cost).

  • Reserved: protects critical functions from starvation and protects downstream systems from overload; setting 0 disables the function.
  • Provisioned: applied to a version/alias; can be scheduled or auto-scaled; billed for the provisioned time.
  • Provisioned does not raise the account limit; it uses it.
  • Use both: reserve capacity and provision a baseline.
aws lambda put-function-concurrency --function-name worker --reserved-concurrent-executions 50
aws lambda put-provisioned-concurrency-config --function-name api --qualifier prod --provisioned-concurrent-executions 10

Q14. How does memory affect performance and cost?

Short answer: CPU and network scale with memory, so more memory can make code run faster; because you pay for GB-seconds, a faster run can cost the same or less despite the higher price per millisecond.

Example: a CPU-bound function takes 800 ms at 512 MB (0.4 GB-s) but 200 ms at 2,048 MB (0.4 GB-s): same cost, four times faster. Use AWS Lambda Power Tuning (a Step Functions tool) to test several memory sizes and graph cost vs duration. I/O-bound functions benefit less. Check Max Memory Used to avoid out-of-memory errors.

💡 Interview tip: Always say "measure with Power Tuning".

Q15. What happens when concurrency is exhausted?

Short answer: New synchronous invocations are throttled (HTTP 429 TooManyRequestsException); asynchronous events are retried for up to 6 hours; poll-based sources slow down or retry.

  • Alarm on the Throttles metric.
  • Callers must retry with exponential backoff and jitter.
  • Fixes: request a higher account limit, set reserved concurrency to isolate noisy functions, put SQS in front to smooth bursts.
  • API Gateway usage plans/throttling can protect the backend.

💡 Interview tip: Mention that throttles are a feature protecting downstream systems, not just a problem.

Q16. How fast does Lambda scale?

Short answer: It creates one execution environment per concurrent request and can add up to 1,000 new environments every 10 seconds per function, up to the account concurrency limit.

Each new environment may incur a cold start. Scaling is per function, so many functions share the account pool. For predictable spikes pre-warm with provisioned concurrency or scheduled scaling. Event source mappings have their own scaling rules (SQS pollers scale automatically with queue depth; stream mappings scale with shards).

💡 Interview tip: Mention the interplay between scaling rate and downstream limits.

Q17. How do you optimise cost?

Short answer: Right-size memory, use arm64, reduce duration, avoid unnecessary invocations (batching, event filtering), control logging, and use provisioned concurrency only where latency requires it.

  • Power Tuning for memory; arm64 for about 20% savings.
  • Duration: reuse connections, cache, parallelise independent calls.
  • Invocations: batch SQS/Kinesis, filter events at the source, avoid recursion.
  • Logs: retention, log level, avoid chatty logs.
  • Architecture: use Step Functions Express or containers where cheaper at scale; Compute Savings Plans.
  • Budgets and anomaly detection to catch runaway loops.

💡 Interview tip: Mention recursion detection and budgets as safety nets.

Q18. How do you make a function idempotent?

Short answer: Derive an idempotency key from the event, record it atomically (for example a DynamoDB conditional put), and skip processing if it already exists. Powertools for AWS Lambda provides this as a ready-made utility.

try:
    table.put_item(Item={"id": event["id"], "ttl": expiry},
                   ConditionExpression="attribute_not_exists(id)")      # first time only
except ClientError as e:
    if e.response["Error"]["Code"] == "ConditionalCheckFailedException":
        return "duplicate"
    raise
do_work(event)
  • Use a TTL so the dedupe table does not grow forever.
  • For multi-step work store the result so duplicates get the same response.
  • Also use idempotency keys when calling external APIs.

💡 Interview tip: Say why: all async and poll-based sources are at-least-once.

Q19. How do you handle a function that needs more than 15 minutes?

Short answer: Split the work into smaller units, orchestrate with Step Functions (including Distributed Map), fan out with SQS, or move the job to Fargate/AWS Batch.

  • Chunking: process pages/ranges and re-enqueue the continuation using get_remaining_time_in_millis().
  • Step Functions: loop, wait and parallelise steps with retries and state.
  • Containers/Batch: for genuinely long-running or heavy jobs.
  • Keep each Lambda step idempotent and small.

💡 Interview tip: Mention checkpointing progress in DynamoDB/S3 so work can resume.

Q20. How do you do safe deployments?

Short answer: Publish versions, shift traffic gradually with an alias (canary or linear via CodeDeploy), monitor alarms, and roll back automatically if they trip.

  • Pre-traffic and post-traffic hook functions validate the new version.
  • CloudWatch alarms on errors/latency feed CodeDeploy rollback.
  • IaC (SAM DeploymentPreference, CDK) makes it repeatable.
  • Use feature flags to separate deploy from release.

48. Scenario-Based Interview Questions

Use the structure cause → measure → fix → prevent for every scenario answer.

Q1. Your API Lambda is slow only on the first request after quiet periods. What do you do?

Short answer: That is a cold start. Confirm with Init Duration in the REPORT line, shrink and simplify initialisation, then use SnapStart or provisioned concurrency for the latency-critical path.

  • Measure: compare p50 vs p99 latency, count REPORT lines with Init Duration, check package size and import time.
  • Reduce: bundle and tree-shake, lazy-load heavy modules, use arm64 and a lighter runtime, move SDK client creation to init but defer rarely used ones.
  • Eliminate: SnapStart (supported runtimes) or provisioned concurrency on the prod alias, scaled by schedule.
  • Prevent: add a latency alarm on p99 and review dependencies in code review.

💡 Interview tip: Say that cold starts affect a small share of requests, but p99 and spiky traffic make them visible.

Q2. Thousands of images are uploaded at once and your database runs out of connections. Fix?

Short answer: Buffer the load and limit concurrency: put SQS between S3 and Lambda, cap concurrency with reserved concurrency or the mapping's MaximumConcurrency, and use RDS Proxy for pooling.

  • Cause: each concurrent execution opens a DB connection; S3 triggers scale with the upload burst.
  • Fix: S3 event → SQS → Lambda (batch, controlled concurrency) → RDS Proxy → database.
  • Also: reuse connections in global scope; consider DynamoDB if relational features are not needed.
  • Prevent: alarms on DB connections, Throttles and queue age; load test bursts.

💡 Interview tip: Show you understand that throttling on purpose protects downstream systems.

Q3. A bad message keeps failing and blocks processing. What do you do?

Short answer: Isolate the poison record: enable partial batch response and a DLQ for SQS, or max retries, bisect-on-error and an on-failure destination for streams; then alarm, fix and redrive.

  • SQS: batchItemFailures + redrive policy with maxReceiveCount → DLQ.
  • Kinesis/DynamoDB Streams: MaximumRetryAttempts, MaximumRecordAgeInSeconds, BisectBatchOnFunctionError, on-failure destination.
  • Recover: inspect DLQ messages, fix code or data, then redrive (SQS redrive-to-source).
  • Prevent: input validation, schema checks and DLQ-depth alarms.

💡 Interview tip: Explain why a stream blocks (per-shard ordering).

Q4. You see duplicate orders. Why and how do you prevent them?

Short answer: All Lambda event sources deliver at least once and callers retry, so duplicates happen; prevent them with an idempotency key and conditional writes.

  • Causes: async retries, SQS visibility timeout expiry, stream batch retries, client retries, S3 duplicate events.
  • Fix: derive a key (order id/event id), put it in DynamoDB with attribute_not_exists (or a unique constraint) in the same transaction as the effect.
  • Powertools idempotency utility automates this.
  • Prevent: design every handler to be safe to run twice; add duplicate-detection metrics.

💡 Interview tip: Mention that exactly-once delivery does not exist in practice; exactly-once effect is the goal.

Q5. Lambda in a VPC cannot reach the internet. Why?

Short answer: Functions in a VPC use your subnets and have no public IP, so they need a route to a NAT gateway in a public subnet (or VPC endpoints for AWS services) and permissive security-group egress.

  • Check: function is in private subnets, route table points 0.0.0.0/0 to a NAT gateway, NAT is in a public subnet with an internet gateway, security group egress allows the traffic, NACLs.
  • For AWS APIs: use gateway endpoints (S3, DynamoDB) or interface endpoints to avoid NAT cost.
  • Question first: does the function really need the VPC? Remove it if it only calls public AWS services.

💡 Interview tip: Mention NAT cost and endpoints as the optimisation.

Q6. Costs doubled this month. How do you investigate?

Short answer: Use Cost Explorer and CloudWatch to find which function, then look for recursion, retries, higher traffic, memory increases, verbose logging or provisioned concurrency left on.

  • Find: Cost Explorer by tag/service; Lambda metrics (Invocations, Duration) per function; CloudWatch Logs ingestion; NAT data processing.
  • Common causes: S3 loop writing to the same bucket, retry storms, a bug raising duration, memory raised without benefit, DEBUG logging, forgotten provisioned concurrency.
  • Fix: remove the loop, add reserved concurrency as a cap, tune memory, set log levels/retention, filter events.
  • Prevent: AWS Budgets and Cost Anomaly Detection alarms, tags per function, recursion detection.

💡 Interview tip: Mention anomaly detection and tagging as proactive controls.

Q7. How would you build a thumbnail service?

Short answer: S3 upload event → Lambda resizes the image → writes the thumbnail to another bucket/prefix, with a DLQ, least-privilege role, idempotency by object key and alarms.

S3 bucket "uploads" --ObjectCreated--> Lambda make-thumbnail --PutObject--> S3 bucket "thumbs"
                                             |  on failure
                                             +--> SQS DLQ  --> alarm
  • Filter by prefix/suffix (uploads/, .jpg).
  • Increase memory for faster image processing; use /tmp and streaming for big files; use a Pillow layer.
  • Write output to a different bucket to avoid loops; make keys deterministic for idempotency.
  • For heavy workloads use SQS in between to control concurrency.

💡 Interview tip: Cover failure handling and the loop pitfall.

Q8. How do you release a risky change safely?

Short answer: Publish a new version, send a small percentage of alias traffic to it (canary) with CodeDeploy, watch error and latency alarms, and let it roll back automatically if they trip.

  • AutoPublishAlias with DeploymentPreference: Canary10Percent5Minutes in SAM.
  • Pre-traffic hook function runs smoke tests.
  • Alarms on Errors and Duration decide rollback.
  • Feature flags decouple deployment from release; keep database changes backward compatible.

💡 Interview tip: Mention that rollback is just re-pointing the alias.

Q9. A function times out calling a third-party API. What now?

Short answer: Set client timeouts shorter than the function timeout, retry with exponential backoff and jitter, use idempotency keys, and move slow or unreliable calls to an asynchronous path with a DLQ.

  • Measure: X-Ray subsegments and logs show where time goes.
  • Fix: connect/read timeouts, circuit breaker, bulkhead via reserved concurrency, cache responses.
  • Architecture: queue the work (SQS) and process with controlled concurrency; notify on failure.
  • Prevent: alarms on Duration p99 and error rates; contract tests.

💡 Interview tip: Mention that a Lambda timeout should be longer than the sum of client timeouts and retries.

Q10. How do you secure an internal API exposed via Lambda?

Short answer: Put it behind API Gateway or an ALB with IAM/Cognito/JWT authorisation, restrict network access (private API or VPC endpoint, resource policies), add WAF and throttling, and keep the function role least-privilege.

  • AuthN/Z: IAM (SigV4) for service callers, Cognito/JWT or a Lambda authorizer for users.
  • Network: private API Gateway via VPC endpoint, resource policy limiting source VPC/IPs.
  • Protection: WAF rules, usage plans, throttling, request validation.
  • Function: validate input, no secrets in env vars, minimal IAM, structured audit logs and CloudTrail.

💡 Interview tip: Structure the answer in layers: identity, network, edge protection, function hardening.

Structure every scenario answer as: cause → measure → fix → prevent.
