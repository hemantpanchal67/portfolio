Kubernetes ☸️ (K8s)

Simple-language notes · Concepts → Architecture → Objects → Networking → Storage → Scaling → Security → Interview

1. What is Kubernetes?

Kubernetes (say "koo-ber-NET-eez", often written K8s because there are 8 letters between K and s) is an open-source system that runs and manages containers across many machines. It was created by Google, based on their internal system called Borg, and donated to the Cloud Native Computing Foundation (CNCF) in 2014. Imagine you have hundreds of containers, each one a small packaged application. Starting them by hand, restarting those that crash, spreading them over machines, and updating them without downtime would be a nightmare. Kubernetes is the manager or "captain of the ship" (the word comes from the Greek for helmsman) that does all of this automatically.

  • You tell Kubernetes the desired state: "I want 3 copies of my web app running"
  • Kubernetes continuously compares the desired state with the actual state and fixes any difference
  • This is called self-healing and the loop doing it is called a control loop / reconciliation loop

2. Why do we need it? (The problem)

Docker lets you package an app into a container and run it on one machine. But real production systems have many problems that Docker alone does not solve: What if the machine dies? What if traffic suddenly increases? How do containers on different machines talk to each other? How do you release a new version without users noticing? Kubernetes is the answer to these questions.

3. Containers vs VMs vs Kubernetes

A virtual machine carries a whole operating system, so it is heavy and slow to start. A container shares the host's OS kernel and packages only the app and its libraries, so it is light and starts in seconds. Kubernetes is not a replacement for containers; it is the orchestrator that sits above them and manages many containers over many machines.

4. Key Features of Kubernetes

  • Self-healing – restarts failed containers
  • Auto-scaling – up/down on CPU or custom metrics
  • Load balancing – spreads traffic across Pods
  • Rolling updates & rollbacks
  • Service discovery & DNS
  • Storage orchestration – mount cloud/local disks
  • Secret & config management
  • Portable – runs on cloud, on-prem, laptop
  • Extensible – CRDs, operators, plugins
  • Declarative – everything described in YAML

6. Kubernetes Architecture

A Kubernetes cluster has two kinds of machines. The Control Plane (the "brain" or "manager") makes all decisions: what should run, where, and whether everything is healthy. The Worker Nodes (the "muscle" or "employees") actually run your containers. You, the user, never talk to nodes directly; you send commands with kubectl to the control plane's API server, and it takes care of the rest.

Only the API server talks to etcd. Everyone else talks to the API server.

7. Control Plane Components (the brain)

ComponentWhat it does (simple)
kube-apiserverThe front door. Every request (from kubectl, nodes, controllers) goes through it. It checks who you are (authentication), whether you are allowed (authorization), validates the request and then stores it.
etcdA reliable key-value database that stores the whole state of the cluster (what objects exist and their settings). If etcd is lost, the cluster forgets everything, so it is backed up regularly.
kube-schedulerWatches for new Pods with no node assigned and chooses the best node by looking at free CPU/memory, rules like affinity, taints and tolerations.
kube-controller-managerRuns many control loops (Node controller, ReplicaSet controller, Job controller…). Each loop compares desired vs actual state and acts to fix it.
cloud-controller-managerConnects Kubernetes to the cloud provider: creating load balancers, disks and nodes.

8. Worker Node Components (the muscle)

ComponentWhat it does (simple)
kubeletThe agent on every node. It receives Pod specs from the API server, tells the container runtime to start the containers, and reports back their health.
kube-proxyMaintains network rules (iptables/IPVS) on the node so that traffic sent to a Service reaches one of its Pods.
Container runtimeThe software that really runs containers: containerd, CRI-O (Docker Engine is no longer used directly since v1.24).

9. What happens when you run kubectl apply? (Flow)

This is the most useful flow to understand, and a favourite interview question. Notice how each component does only one small job and communicates through the API server; this loose design is what makes Kubernetes robust.

10. Pod – the smallest unit

Kubernetes does not run containers directly; it runs Pods. A Pod is like a small apartment in which one or more containers live together. All containers in a Pod share the same IP address, network ports and storage volumes, and are always placed on the same node. Normally a Pod has one main container; extra containers called sidecars are added for helper jobs like log shipping or a proxy. Pods are mortal: when one dies it is not repaired, it is replaced with a brand-new Pod that has a new IP. That is why we never depend on a Pod's IP directly and use Services instead.

Simple Pod YAML

apiVersion: v1
kind: Pod
metadata:
  name: my-pod
  labels: { app: web }
spec:
  containers:
  - name: web
    image: nginx:1.25
    ports: [{ containerPort: 80 }]

11. Pod Lifecycle

A Pod moves through phases: Pending (accepted, waiting for a node or for images to download), Running (at least one container is running), Succeeded (all containers finished OK, used for jobs), Failed (a container ended with error) and Unknown (node unreachable). Common status messages you will see: CrashLoopBackOff (app keeps crashing and K8s waits longer between restarts), ImagePullBackOff (cannot download image) and OOMKilled (used more memory than its limit).

12. ReplicaSet & Deployment

Because a bare Pod is not replaced if its node dies, we use higher-level managers. A ReplicaSet guarantees that a given number of identical Pods are always running; if one disappears it creates another. A Deployment sits on top of a ReplicaSet and adds updates and rollbacks. In daily work you almost always create a Deployment and let it create the ReplicaSet and Pods for you.

Deployment YAML

apiVersion: apps/v1
kind: Deployment
metadata: { name: web }
spec:
  replicas: 3
  selector: { matchLabels: { app: web } }
  template:
    metadata: { labels: { app: web } }
    spec:
      containers:
      - name: web
        image: myrepo/web:1.0
        resources:
          requests: { cpu: 100m, memory: 128Mi }
          limits:   { cpu: 500m, memory: 256Mi }

13. Rolling Update & Rollback

When you change the image version, the Deployment does not stop everything at once. It creates one new Pod, waits until it is ready, then removes one old Pod, and repeats until all Pods are new. Users never see downtime. Two knobs control the speed: maxSurge (how many extra Pods may exist temporarily) and maxUnavailable (how many may be missing). If the new version is broken, kubectl rollout undo deployment web goes back to the previous ReplicaSet in seconds.

15. Services – stable network address

Pods are temporary and their IPs change, so how does the frontend find the backend? Through a Service. A Service gets a fixed virtual IP (ClusterIP) and a DNS name such as backend.default.svc.cluster.local. It uses a label selector to find all matching healthy Pods and load-balances traffic between them. If Pods come and go, the Service updates automatically. Think of it as the permanent phone number of a company's reception desk: the staff behind it can change, but the number stays the same.

16. Ingress – smart HTTP routing

Creating one cloud LoadBalancer per Service is expensive. An Ingress lets you use one entry point for many Services, routing by host name or URL path (for example /shop to the shop Service and /api to the API Service) and handling HTTPS certificates. The Ingress is only a set of rules; the real work is done by an Ingress Controller (such as NGINX, Traefik or the AWS ALB controller) that you must install. The newer Gateway API is the more flexible successor.

17. Cluster Networking Rules

Kubernetes has a simple but powerful networking model: (1) every Pod gets its own IP address; (2) any Pod can talk to any other Pod directly without NAT, even on different nodes; (3) agents on a node can talk to all Pods on it. These rules are implemented by a CNI plugin (Calico, Flannel, Cilium, AWS VPC CNI). CoreDNS runs in the cluster and turns Service names into IPs. If you want to restrict who can talk to whom, create a NetworkPolicy (like a firewall for Pods, enforced by the CNI).

  • Container ↔ Container in same Pod → localhost
  • Pod ↔ Pod → Pod IP (but use a Service instead)
  • Pod ↔ Service → ClusterIP / DNS name
  • External ↔ Service → NodePort / LoadBalancer / Ingress

18. Configuration: ConfigMap & Secret

Good practice is to keep configuration outside the container image, so the same image can run in dev, test and production. A ConfigMap stores normal settings (URLs, feature flags, config files). A Secret stores sensitive data (passwords, tokens, certificates). Both can be injected into a Pod as environment variables or mounted as files. Important: by default Secrets are only base64-encoded, not encrypted, so enable encryption at rest, restrict access with RBAC, or use an external secret manager.

19. Storage: Volumes, PV, PVC, StorageClass

A container's own file system disappears when it restarts. To keep data, Kubernetes provides volumes. A PersistentVolume (PV) is a piece of real storage (an AWS EBS disk, NFS share, etc.). A PersistentVolumeClaim (PVC) is the request a developer makes: "I need 10 GB, read-write". Kubernetes matches the claim to a volume, and the Pod simply mounts the claim. With a StorageClass the volume is created dynamically when the claim appears, so admins don't create disks by hand.

  • Access modes: RWO (one node read-write), ROX (many read-only), RWX (many read-write)
  • Reclaim policy: Retain keeps data, Delete removes the disk with the claim

20. Resource Requests, Limits & Probes

Each container should declare how much CPU and memory it needs. A request is the amount the scheduler reserves when deciding which node to use; a limit is the maximum it may use. If a container exceeds its memory limit it is killed (OOMKilled); if it exceeds its CPU limit it is merely slowed (throttled). Probes let Kubernetes check the health of your app: liveness (is it alive? if not, restart it), readiness (can it take traffic? if not, remove from the Service) and startup (give slow apps time to boot).

ProbeQuestion askedIf it fails
LivenessIs the app stuck or dead?Container is restarted

21. Scaling

Kubernetes can scale at three levels. Manual: kubectl scale deployment web --replicas=5. Horizontal Pod Autoscaler (HPA) automatically changes the number of Pods based on CPU, memory or custom metrics (needs metrics-server). Vertical Pod Autoscaler (VPA) adjusts the size (CPU/memory) of Pods. When Pods have no room left on the nodes, the Cluster Autoscaler (or Karpenter on AWS) adds new nodes.

22. Scheduling Controls

By default the scheduler places Pods wherever there is room, but you can guide it. nodeSelector and node affinity say "run on nodes with this label" (for example GPU nodes). Pod affinity / anti-affinity says "put me near / away from other Pods" (spread replicas across nodes for high availability). Taints are marks on a node that repel Pods, and tolerations on a Pod let it ignore the mark; together they reserve nodes for special workloads.

FeatureMeaning in plain words
nodeSelector / affinity"I want a node with label disk=ssd"
Pod anti-affinity"Don't put two copies of me on the same node"
Taint (on node)"Keep out unless you tolerate me"
Toleration (on Pod)"I'm allowed on tainted nodes"
Topology spread"Spread me evenly over zones"

23. Namespaces, Labels & Annotations

Namespaces divide one cluster into virtual sections, for example dev, test, prod or one per team; names only need to be unique inside a namespace, and you can apply quotas and access rules per namespace. Default namespaces are default, kube-system (K8s components), kube-public and kube-node-lease. Labels are key/value tags (app=web, env=prod) used by selectors; Services, Deployments and many commands find objects through labels. Annotations are extra notes for tools and humans that are not used for selection.

24. Security: RBAC & more

Every request to the API server passes three gates: Authentication (who are you?), Authorization (are you allowed? usually RBAC) and Admission control (are the contents acceptable? policies can modify or reject). RBAC (Role-Based Access Control) uses four objects: a Role (a list of permissions inside one namespace), a ClusterRole (cluster-wide permissions), and RoleBinding / ClusterRoleBinding that attach those roles to users, groups or ServiceAccounts (identities for Pods).

  • Use least privilege; avoid cluster-admin for apps
  • Run containers as non-root, read-only filesystem, drop capabilities (securityContext)
  • Use NetworkPolicies, Pod Security Standards, image scanning, private registries, encrypt etcd/Secrets

26. Full Example – Deploy a Web App

Putting it together: a Deployment runs three Pods of the app, a Service gives them one stable address, and an Ingress exposes it to the internet. Save the following into one file and run kubectl apply -f app.yaml.

apiVersion: apps/v1
kind: Deployment
metadata: { name: web }
spec:
  replicas: 3
  selector: { matchLabels: { app: web } }
  template:
    metadata: { labels: { app: web } }
    spec:
      containers:
      - { name: web, image: nginx:1.25, ports: [{containerPort: 80}] }
---
apiVersion: v1
kind: Service
metadata: { name: web-svc }
spec:
  selector: { app: web }
  ports: [{ port: 80, targetPort: 80 }]
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: web-ing }
spec:
  rules:
  - host: example.com
    http:
      paths:
      - { path: /, pathType: Prefix,
          backend: { service: { name: web-svc, port: { number: 80 } } } }

27. Troubleshooting Guide

  • Service not reachable? check kubectl get endpoints – empty means selector labels don't match or Pods aren't Ready
  • Always read the Events at the bottom of kubectl describe

28. Helm, Operators & the Ecosystem

  • Helm – the "package manager" for Kubernetes: bundles many YAML files into a reusable chart with configurable values
  • Kustomize – customise YAML per environment without templates (built into kubectl)
  • Operators / CRDs – teach Kubernetes new object types (e.g. a "PostgresCluster") with custom controllers
  • Service mesh (Istio, Linkerd) – secure, observe and control service-to-service traffic
  • GitOps (Argo CD, Flux) – Git is the source of truth; the cluster syncs itself from it
  • Monitoring – Prometheus + Grafana, logging with Loki / EFK, tracing with Jaeger / OpenTelemetry
  • Managed Kubernetes – Amazon EKS, Google GKE, Azure AKS (cloud runs the control plane for you)
  • Local practice – minikube, kind, Docker Desktop, k3s

29. Best Practices

  • Always use Deployments (not bare Pods) and keep YAML in Git
  • Set resource requests/limits and probes on every container
  • Use specific image tags (never latest) and scan images
  • Run at least 2-3 replicas spread across nodes/zones; add PodDisruptionBudget
  • Separate environments with namespaces; apply RBAC and NetworkPolicy
  • Keep secrets out of images and Git; keep apps stateless, store data in volumes/databases

30. Interview Questions & Answers

Q1. What is Kubernetes? An open-source container orchestration platform that automates deployment, scaling, networking and healing of containerised apps across a cluster.

Q2. Explain the architecture. Control plane (API server, etcd, scheduler, controller-manager, cloud-controller-manager) makes decisions; worker nodes (kubelet, kube-proxy, container runtime) run Pods.

Q3. What is a Pod? Why not run containers directly? Smallest deployable unit; one or more containers sharing network and storage, scheduled together as one unit.

Q4. Deployment vs ReplicaSet vs StatefulSet? ReplicaSet keeps N Pods; Deployment adds rolling updates/rollback on top; StatefulSet gives stable identity and storage for stateful apps.

Q5. How do Services work? Types? A Service provides a stable IP/DNS and load-balances to Pods matched by a selector; ClusterIP, NodePort, LoadBalancer, ExternalName, Headless.

Q6. Service vs Ingress? Service exposes Pods at L4; Ingress routes external HTTP/HTTPS (L7) to many Services by host/path and needs an Ingress Controller.

Q7. What happens when a node fails? Node controller marks it NotReady; after a timeout its Pods are evicted and controllers recreate them on healthy nodes.

Q8. Liveness vs readiness probe? Liveness failure restarts the container; readiness failure removes the Pod from Service endpoints without restarting.

Q9. Requests vs limits? Requests are used by the scheduler for placement (guaranteed minimum); limits are the maximum (memory over limit → OOMKilled, CPU over limit → throttled).

Q10. How does HPA work? It reads metrics, compares with the target and adjusts Deployment replicas between min and max.

Q11. ConfigMap vs Secret? ConfigMap for non-sensitive config; Secret for sensitive data (base64 by default, enable encryption at rest and RBAC).

Q12. PV, PVC, StorageClass? PV is actual storage, PVC is a request for it, StorageClass enables dynamic provisioning.

Q13. What is etcd? Distributed key-value store holding all cluster state; back it up and run an odd number of members (3 or 5).

Q14. What is a DaemonSet? Ensures one Pod runs on every (or selected) node, e.g. logging or monitoring agents.

Q15. Taints & tolerations vs affinity? Taints repel Pods from nodes unless tolerated; affinity attracts Pods to nodes/Pods. Taints are node-driven, affinity is Pod-driven.

Q16. How do you do a zero-downtime release? Rolling update with readiness probes, enough replicas, maxUnavailable 0, PodDisruptionBudget; roll back with rollout undo.

Q17. What is a CrashLoopBackOff? Container repeatedly crashes; kubelet restarts with increasing delay. Check logs --previous, config, probes and memory limits.

Q18. What is Helm? Package manager that templates and versions sets of Kubernetes manifests (charts, releases).

Pod Creation & IP Assignment ⚙️

Watch what happens, step by step, from kubectl to a running Pod. The highlighted line and the moving dot show the current step, and the Pod card at the bottom changes live: first Pending with no node and no IP, then a node is chosen, then ContainerCreating, and finally the CNI plugin creates the Pod IP and the status becomes Running. Notice that components never talk to each other directly; they all go through the API server.

What each step means

  1. kubectl sends POST /api/v1/pods (via a Deployment → ReplicaSet → Pod) to the API server, which authenticates, authorises and validates it.
  2. The API server writes the Pod object into etcd. Status is Pending and nodeName is empty.
  3. The scheduler is watching the API server and is notified of a Pod that has no node.
  4. It filters nodes (resources, taints, affinity), scores them and binds the Pod to node2 by writing nodeName back through the API server.
  5. The kubelet on node2 watches for Pods assigned to it and notices the new one.
  6. The kubelet asks containerd to create the Pod sandbox, pull the image from the registry and start the containers.
  7. While creating the sandbox, the CNI plugin creates a veth pair and takes the next free address from the node's podCIDR (10.244.2.0/24): Pod IP 10.244.2.7 is born.
  8. The kubelet reports status Running and the podIP to the API server; it is stored in etcd and the Pod is added to Service endpoints once Ready.
Remember: scheduler decides where, kubelet decides how, CNI decides which IP.

A New Node Joins the Cluster 🔌

Adding capacity means adding a node. The animation shows a brand-new machine (left) connecting to the control plane (right). Orange dashed lines are the live connections; the dots show the messages. Watch the status badge at the bottom of the node: it starts as NotReady (red) and turns Ready (green) only after the certificate, the podCIDR and the network pods are in place. Only then does the scheduler start sending Pods to it, and they get IPs from the node's own range.

What each step means

  1. The machine gets containerd, kubelet and kubeadm installed and a node IP (192.168.1.14) from your network or cloud.
  2. kubeadm join: kubelet contacts the API server using a bootstrap token and the cluster CA hash (to verify it is talking to the real cluster).
  3. TLS bootstrap: a CSR is approved and the cluster issues the kubelet a client certificate; from now on it authenticates with that certificate.
  4. The kubelet registers a Node object (stored in etcd). It starts as NotReady because networking is not set up yet.
  5. The controller manager (node IPAM) allocates a podCIDR (10.244.4.0/24) for the node. Pods here will get IPs from this range.
  6. DaemonSets place a kube-proxy pod and the CNI pod (Calico/Flannel) on the node, which sets up the pod network.
  7. The kubelet sends heartbeats (Lease renewed ~every 10 s) and the node turns Ready.
  8. The scheduler now includes worker-4 and starts placing Pods on it; each gets a Pod IP from 10.244.4.0/24.
