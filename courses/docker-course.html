1. What is Docker?

Docker is an open-source platform that lets you package an application together with everything it needs to run, such as the runtime, libraries, system tools and settings, into a single unit called an image. When you start that image, it becomes a container, an isolated process that behaves the same on a developer laptop, a test server and a production cloud. The slogan is "build once, run anywhere", and its real value is that it removes the old problem of "it works on my machine".

Before containers, teams installed an application directly on a server, and every server slowly became different: another version of Python, another library, another configuration. Virtual machines helped by bundling a whole operating system, but they are heavy and slow to start. Docker uses features of the Linux kernel to isolate processes instead, so a container starts in about a second, uses little memory and shares the host's kernel.

Your first container

docker run hello-world                    # pulls the image if needed and runs it
docker run -d -p 8080:80 --name web nginx # run nginx in the background, publish port 8080
curl http://localhost:8080                # the nginx welcome page
docker ps                                 # list running containers
docker logs web                           # see its output
docker stop web && docker rm web          # stop and remove it

These few commands show the whole idea: an image is downloaded from a registry, a container is created from it, and your machine needs nothing installed except Docker itself.

2. Containers vs Virtual Machines

A virtual machine emulates a complete computer. A hypervisor such as VMware, Hyper-V or KVM runs on the hardware, and each VM contains its own full guest operating system with its own kernel. A container has no guest operating system. It is a normal process on the host that the kernel isolates with namespaces and limits with control groups, so many containers share one kernel.

The trade-off is isolation. Because containers share the kernel, a kernel bug can affect all of them, so untrusted code is often run in a VM or in a sandboxed runtime such as gVisor or Kata Containers. In practice many companies run containers inside VMs in the cloud, combining both. On Windows and macOS, Docker Desktop runs a small Linux VM, because containers need a Linux kernel.

3. History, Features & Benefits

Docker was released in 2013 by dotCloud, which later became Docker Inc. It did not invent containers, since Linux already had LXC, namespaces and cgroups, but it made them easy with a simple command line, a build format (the Dockerfile) and a public registry (Docker Hub). In 2015 the industry created the Open Container Initiative (OCI) to standardise the image and runtime formats, and Docker donated its runtime, which became containerd and runc.

Main features

Docker gives you images built in cached layers, containers with a defined lifecycle, registries for sharing, networks with built-in DNS, volumes for persistent data, Compose for multi-container applications, BuildKit for fast parallel builds, resource limits, health checks, logging drivers and a rich command line and API.

Benefits

The first benefit is consistency: the same image runs in development, testing and production. The second is speed: containers start in about a second, and layer caching makes rebuilds fast. The third is efficiency: many containers share one machine. The fourth is isolation: each app has its own dependencies, so two apps needing different versions of a library do not conflict. The fifth is easy scaling and rollback: you start more containers from the same image, or redeploy the previous tag. The sixth is a large ecosystem: nearly every database, tool and language publishes official images. Finally, Docker makes onboarding easy, because a new developer can run the whole stack with one command.

4. Problems, Limits & Use Cases

Docker is not a perfect tool, and a good engineer knows where it hurts. Security is the first concern: containers share the host kernel, running as root is the default, and anything with access to the Docker socket controls the host. Persistent data is the second: container storage is ephemeral, so databases need volumes and backups, and many teams still run databases outside containers. Image bloat and vulnerabilities are the third, because large base images carry many packages that need patching. Networking can be confusing, with port publishing, NAT and DNS rules. Orchestration complexity appears at scale, where Kubernetes brings its own learning curve. Docker Desktop licensing requires a paid plan for larger companies, which pushed some teams to Podman or Rancher Desktop. Debugging is harder when containers are short-lived and have no shell. There is also a Linux dependency: Windows containers exist but are far less common.

Use cases

Docker fits microservices, where each service ships as its own image, local development environments with Compose, CI pipelines that need clean and repeatable build agents, testing with real databases through Testcontainers, legacy application packaging, batch jobs, machine-learning model serving and sandboxed tools. It is a poor fit for desktop GUI applications and for workloads that need a different operating-system kernel.

6. How Containers Work: Namespaces, cgroups & More

A container is not a special kind of object in the Linux kernel. It is an ordinary process that has been given limits and a restricted view, using four kernel features. Namespaces control what the process can see: its own process ids, network interfaces, mount points, hostname, users and inter-process communication. Control groups (cgroups) control what it can use: CPU, memory, disk I/O and number of processes. A union filesystem such as overlay2 stacks the read-only image layers and a writable layer into one view. Capabilities and seccomp reduce what the process is allowed to do: Docker drops many root powers by default and blocks dangerous system calls.

docker run -d --name limited --memory 256m --cpus 1.0 --pids-limit 100 nginx     # cgroup limits
docker run --rm --cap-drop ALL --security-opt no-new-privileges alpine id        # fewer powers
docker inspect limited --format '{{.HostConfig.Memory}}'                         # see the limit
docker stats --no-stream                                                         # live usage per container

If a container uses more memory than its limit, the kernel's out-of-memory killer ends it, and Docker records exit code 137. Understanding these four features is what separates someone who only uses Docker from someone who can explain it.

8. Images, Layers & Registries

An image is a read-only package made of layers. Every step that changes the filesystem in a Dockerfile adds a layer, and each layer is identified by a hash of its content. This design has two big benefits: layers are shared between images, so ten images based on the same base image store the base only once, and they are cached, so a rebuild reuses every layer whose inputs did not change. When a container starts, Docker adds a thin writable layer on top, using copy-on-write: a file stays in the read-only layer until it is modified, and only then is it copied up.

Names, tags and digests

An image name has the form registry/repository:tag, for example ghcr.io/acme/orders:1.4.2. A tag is a movable label, so latest can point to a different image tomorrow. A digest such as orders@sha256:ab12… identifies exact content and never changes, so pinning by digest guarantees you run what you tested. A registry stores images: Docker Hub is the default, and companies use private ones such as Azure Container Registry, Amazon ECR, GitHub Container Registry or Harbor.

docker pull nginx:1.27-alpine
docker image ls
docker history nginx:1.27-alpine           # see each layer and its size
docker tag myapp:1.0 ghcr.io/acme/myapp:1.0
docker login ghcr.io
docker push ghcr.io/acme/myapp:1.0
docker image inspect myapp:1.0 --format '{{.Id}}'
docker image prune -a                      # remove unused images

Images can be built for several CPU architectures, such as amd64 and arm64, and published under one name using a manifest list, which is why the same docker pull works on an Intel server and an Apple-silicon laptop. docker buildx build --platform linux/amd64,linux/arm64 creates them.

9. Writing a Dockerfile

A Dockerfile is a text file of instructions that Docker runs top to bottom to build an image. The most common instructions are FROM (the base image), WORKDIR (the working folder), COPY (add files), RUN (execute a command during build), ENV (set an environment variable), EXPOSE (document a port), USER (the user to run as), ENTRYPOINT and CMD (what runs when the container starts), plus ARG, LABEL and HEALTHCHECK. Only RUN, COPY and ADD create filesystem layers; the others add metadata.

# a small Node.js service
FROM node:22-alpine
WORKDIR /app

COPY package*.json ./                 # copy only the dependency files first
RUN npm ci --omit=dev                 # this layer is cached until package.json changes

COPY . .                              # then the source, which changes often
ENV NODE_ENV=production
EXPOSE 3000
USER node                             # do not run as root
HEALTHCHECK --interval=30s CMD wget -qO- http://localhost:3000/health || exit 1
CMD ["node", "server.js"]             # exec form: the app is PID 1 and receives signals

ENTRYPOINT versus CMD, COPY versus ADD

ENTRYPOINT defines the executable and CMD supplies default arguments that docker run can override, so together ENTRYPOINT ["java","-jar","app.jar"] and CMD ["--port=8080"] work as a program with default options. Always prefer the exec form (a JSON array) over the shell form, because the shell form starts /bin/sh -c as PID 1, which does not forward signals, so docker stop would wait ten seconds and then kill the app. Prefer COPY to ADD: ADD can also unpack archives and download URLs, which is surprising and less safe.

Layer order and .dockerignore

Because Docker caches layers from the top and invalidates everything below a changed step, put things that change rarely first (the base image, system packages, dependency files) and things that change often last (your source code). A .dockerignore file keeps the build context small and prevents files such as .git, node_modules and .env from entering the image.

10. Multi-stage Builds, BuildKit & Smaller Images

Compilers, package managers and test tools are needed to build an application but not to run it. A multi-stage build uses several FROM lines in one Dockerfile: early stages compile the code, and the final stage copies only the result into a small runtime image. The result is a much smaller and safer image, because the final image contains no compiler and no source code.

# ---- stage 1: build ----
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY *.csproj .
RUN dotnet restore                       # cached unless the project file changes
COPY . .
RUN dotnet publish -c Release -o /out --no-restore

# ---- stage 2: runtime ----
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS final
WORKDIR /app
COPY --from=build /out .                 # take only the published output
USER app
ENTRYPOINT ["dotnet", "Shop.Api.dll"]

The same idea works for Go (build a static binary and copy it into scratch or distroless), Java (JDK to build, JRE to run) and Node (build the frontend, serve it with nginx). You can build a specific stage with docker build --target build ., which is useful for running tests.

BuildKit and cache tricks

BuildKit is the modern builder and the default today. It builds independent stages in parallel, skips unused stages, and supports cache mounts and secrets. A cache mount keeps a package cache between builds without storing it in the image, and a secret mount provides a credential during one RUN step without leaving it in any layer.

# syntax=docker/dockerfile:1
FROM python:3.12-slim
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt
RUN --mount=type=secret,id=npmrc cp /run/secrets/npmrc ~/.npmrc && npm ci && rm ~/.npmrc
docker build -t shop:1.0 .
docker build --secret id=npmrc,src=$HOME/.npmrc -t shop:1.0 .
docker buildx build --platform linux/amd64,linux/arm64 -t acme/shop:1.0 --push .
docker image ls shop                     # compare the size before and after multi-stage

Making images smaller

Choose a small base (-slim, alpine or distroless), combine related RUN commands and clean caches in the same command, install only what you need, and use multi-stage builds. Remember that Alpine uses the musl C library, which can behave differently from glibc for some software.

11. Running Containers & the Lifecycle

docker run is the command you use most, and it combines pull, create and start. A container moves through a lifecycle: it is created, running, sometimes paused, then stopped (exited) and finally removed. The container lives only as long as its main process (PID 1): when that process ends, the container stops. That is why a container that runs a service must keep it in the foreground.

docker run -d --name api \
  -p 8080:8080 \
  -e ASPNETCORE_ENVIRONMENT=Production \
  -v api-data:/data \
  --memory 512m --cpus 1 \
  --restart unless-stopped \
  --network shop-net \
  myapp:1.0

docker stop api            # SIGTERM, then SIGKILL after 10 s
docker kill api            # immediate SIGKILL
docker rm -f api           # remove, even if running
docker run --rm alpine echo hi          # remove automatically when it exits
docker exec -it api sh                  # extra process inside a running container

Important flags are -d (detached), -it (interactive terminal), -p (publish port), -e (environment variable), -v (volume or bind mount), --name, --rm, --restart, --network, --user, --memory, --cpus and --read-only. A restart policy (no, on-failure, always, unless-stopped) gives basic self-healing on one host. A graceful application handles SIGTERM by finishing current work before exiting, which is important during deployments.

12. Docker Networking

Docker networking connects containers to each other and to the outside world. Each network uses a driver. The default bridge driver creates a virtual switch on one host. The host driver removes isolation and shares the host's network stack. none gives no network at all. overlay connects containers across several hosts, which Swarm uses. macvlan gives a container its own MAC and IP on the physical network.

The most useful feature is the embedded DNS of user-defined bridge networks: containers on the same network reach each other by name, for example db or redis, because Docker's DNS resolves it. The default bridge does not offer this, so always create your own network. Publishing a port with -p 8080:80 maps a host port to a container port using NAT, and without it a container port is reachable only from other containers on the same network.

docker network create shop-net
docker run -d --name db --network shop-net -e POSTGRES_PASSWORD=secret postgres:16
docker run -d --name api --network shop-net -p 8080:8080 myapp:1.0     # the app connects to host "db"
docker network ls
docker network inspect shop-net
docker network connect shop-net other-container
// inside the "api" container the connection string uses the container name as the host
var cs = "Host=db;Port=5432;Database=shop;Username=postgres;Password=secret";

Common mistakes are using localhost to reach another container (it means the container itself), publishing database ports to the whole internet, and forgetting that a service must listen on 0.0.0.0 and not only 127.0.0.1 to be reachable through a published port.

13. Volumes, Bind Mounts & Data

The writable layer of a container disappears when the container is removed, and it is slower than a proper volume. To keep data you mount storage into the container. A volume is managed by Docker, lives outside the container lifecycle, is portable and is the preferred choice for databases and uploads. A bind mount maps a specific host folder, which is ideal during development to share source code but depends on the host layout. A tmpfs mount keeps data only in memory, which suits temporary or sensitive files.

docker volume create pgdata
docker run -d --name db -v pgdata:/var/lib/postgresql/data postgres:16     # named volume
docker run -d -v "$(pwd)":/app:ro node:22 sleep infinity                   # bind mount, read-only
docker run -d --tmpfs /tmp:rw,size=64m myapp:1.0                           # memory-backed

# backup a volume
docker run --rm -v pgdata:/data -v "$(pwd)":/backup alpine tar czf /backup/pgdata.tgz -C /data .
docker volume ls
docker volume inspect pgdata

Use volumes for data you care about, back them up, and consider a managed database for production. In Kubernetes the same idea becomes PersistentVolumes. Deleting the container does not delete a named volume, but docker compose down -v and docker volume prune do.

14. Docker Compose for Multi-container Apps

Real applications have several parts: a web app, a database, a cache. Docker Compose describes the whole stack in one YAML file, compose.yaml, and docker compose up builds, creates networks and volumes and starts everything. Compose creates a default network where each service is reachable by its service name, so the web service connects to the database at host db.

services:
  api:
    build: .                              # build from the Dockerfile in this folder
    ports: ["8080:8080"]
    environment:
      ConnectionStrings__Default: Host=db;Database=shop;Username=postgres;Password=secret
    depends_on:
      db: { condition: service_healthy }  # wait until the database is really ready
    restart: unless-stopped
  db:
    image: postgres:16
    environment: { POSTGRES_PASSWORD: secret }
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 10
  cache:
    image: redis:7-alpine
volumes:
  pgdata:
docker compose up -d --build       # start everything in the background, rebuilding images
docker compose ps
docker compose logs -f api
docker compose exec db psql -U postgres
docker compose down                # stop and remove containers and the network (keeps volumes)
docker compose down -v             # also remove volumes

Compose is excellent for local development and simple single-host deployments. Use profiles to start optional services, override files (compose.override.yaml) for development settings, and an .env file for variables. Remember that depends_on without a health condition only waits for the container to start, not for the service to be ready. For production at scale, use an orchestrator.

15. Configuration, Secrets, Health Checks & Logging

A container image should be the same in every environment, with differences supplied from outside. The usual way is environment variables (-e, --env-file or Compose environment), or configuration files mounted as volumes, following the twelve-factor app approach. Secrets such as passwords and API keys must never be written into the Dockerfile, an ENV line or the image, because anyone with the image can read them with docker history or docker inspect. Use BuildKit secret mounts for build-time secrets, and Docker or Kubernetes secrets, mounted files or a vault for runtime secrets.

docker run --env-file prod.env myapp:1.0
docker run -v /run/secrets/db_password:/run/secrets/db_password:ro myapp:1.0     # a mounted secret file
docker inspect api --format '{{json .Config.Env}}'                              # env vars are visible here!

Health checks

A HEALTHCHECK runs a command inside the container at an interval, and Docker marks the container healthy or unhealthy. Orchestrators and Compose use it to decide when a service is ready and whether to restart it. A running process is not the same as a working service, so health checks should test the real endpoint.

HEALTHCHECK --interval=30s --timeout=3s --start-period=20s --retries=3 \
  CMD curl -fsS http://localhost:8080/health/live || exit 1

Logging

Containers should write logs to stdout and stderr, not to files inside the container. Docker captures them, and docker logs shows them. A logging driver (json-file by default, or syslog, fluentd, gelf, awslogs and others) ships them to a central system. Set rotation so a chatty container does not fill the disk.

{ "log-driver": "json-file", "log-opts": { "max-size": "10m", "max-file": "3" } }

Resource limits

Without limits one container can use all memory or CPU on the host. Set --memory and --cpus (and --pids-limit) so a leak in one service cannot take down the others. A container that exceeds its memory limit is killed by the out-of-memory killer with exit code 137.

16. Docker Security

Security in Docker is about reducing what an attacker can do if the application is compromised, and about keeping bad things out of the image in the first place. Think in layers. The image: use a small trusted base, scan it, and keep secrets out. The container: run as a non-root user, drop capabilities, use a read-only filesystem and never use --privileged. The host and daemon: protect the Docker socket, keep the engine updated and consider rootless mode. The supply chain: pull only from trusted registries, pin versions or digests, and sign images.

FROM gcr.io/distroless/nodejs22-debian12
WORKDIR /app
COPY --chown=nonroot:nonroot . .
USER nonroot
CMD ["server.js"]
docker run -d --read-only --tmpfs /tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --pids-limit 200 --memory 256m \
  -u 10001:10001 myapp:1.0

trivy image myapp:1.0                     # scan for vulnerabilities
docker scout cves myapp:1.0
cosign sign ghcr.io/acme/myapp@sha256:...  # sign by digest

17. Docker in CI/CD & Registries

Docker turns a build into a versioned artifact. A typical pipeline builds the image on every commit, tests it, scans it for vulnerabilities, pushes it to a registry and deploys it. The same image that passed the tests is the one that reaches production, which removes a whole class of "works in staging" surprises. Tag images with the commit SHA and a version so that every deployment is traceable and a rollback is simply deploying the previous tag.

# .github/workflows/docker.yml
name: docker
on: { push: { branches: [main] } }
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with: { registry: ghcr.io, username: ${{ github.actor }}, password: ${{ secrets.GITHUB_TOKEN }} }
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ghcr.io/acme/shop:${{ github.sha }},ghcr.io/acme/shop:1.4.2
          cache-from: type=gha
          cache-to: type=gha,mode=max
      - run: docker run --rm aquasec/trivy image --exit-code 1 --severity CRITICAL ghcr.io/acme/shop:${{ github.sha }}

Use a private registry for company images, set retention rules so old tags are cleaned up, enable vulnerability scanning in the registry, and sign images. For integration tests, start real dependencies in containers using Compose or libraries such as Testcontainers.

18. Orchestration: Swarm, Kubernetes & Managed Services

Docker alone manages containers on one host. Real systems need to run containers across many machines, restart failed ones, scale up and down, roll out new versions without downtime and balance traffic. This is the job of an orchestrator, and the central idea is desired state: you declare what you want, such as "three copies of this image", and the system continually works to make reality match.

Docker Swarm is built into Docker and is simple to start: docker swarm init creates a cluster, and docker service create --replicas 3 runs a service. Kubernetes is the industry standard, with a richer model (pods, deployments, services, ingress, config maps, autoscaling) and a huge ecosystem, and it runs Docker-built images through containerd or CRI-O. Managed services such as AWS ECS and Fargate, Azure Container Apps and Google Cloud Run run your images without you managing a cluster.

docker swarm init
docker service create --name web --replicas 3 -p 80:80 nginx:1.27
docker service scale web=5
docker service update --image nginx:1.27.1 web          # rolling update
# the same idea in Kubernetes
apiVersion: apps/v1
kind: Deployment
metadata: { name: web }
spec:
  replicas: 3
  selector: { matchLabels: { app: web } }
  template:
    metadata: { labels: { app: web } }
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports: [ { containerPort: 80 } ]
          readinessProbe: { httpGet: { path: /, port: 80 } }

Choose Compose for development and small single-host apps, a managed service when you want containers without cluster operations, and Kubernetes when you need its flexibility and ecosystem and have the skills to run it or use a managed offering.

19. Troubleshooting & Best Practices

When a container misbehaves, follow a short routine. First, docker ps -a shows whether it is running and its exit code: 0 is a normal exit, 1 an application error, 125 to 127 a Docker or command problem, 137 a kill (often out of memory) and 143 a normal SIGTERM stop. Second, docker logs shows the output. Third, docker inspect shows the configuration, environment, mounts and network. Fourth, docker exec -it name sh lets you look inside, and docker run --rm -it image sh lets you explore an image. Fifth, docker stats, docker top and docker events show resource use and activity.

Best practices checklist

Use small, specific base images with pinned versions. Order Dockerfile steps for caching and use multi-stage builds. Run one main process per container and run it as a non-root user. Use exec form for CMD and handle SIGTERM. Keep images stateless and put data in volumes. Pass configuration through environment variables and secrets through a secret store, never in the image. Add health checks, log to stdout and set resource limits. Use .dockerignore, scan images in CI, tag with versions and commit SHAs and never rely on latest. Clean up unused objects regularly with docker system prune.

Common anti-patterns

Avoid putting an SSH server in a container, running several unrelated services in one container, baking secrets or environment-specific settings into images, using latest, mounting the Docker socket, running as root and treating containers like pets by logging in to change things instead of rebuilding the image.

20. Interview Q&A: Docker Basics & Images

Q1. What is Docker and what problem does it solve?

Short answer: Docker packages an application and its dependencies into an image that runs the same everywhere as an isolated container.

It solves "works on my machine" by making the environment part of the artifact. It also makes deployments fast, because containers start in about a second, and makes scaling and rollback simple.

Q2. What is the difference between a container and a virtual machine?

Short answer: A VM emulates hardware and runs its own guest operating system, while a container is an isolated process sharing the host kernel.

Containers are smaller, start faster and allow higher density, but have weaker isolation because the kernel is shared. Untrusted workloads often use VMs or sandboxed runtimes.

Q3. What is the difference between an image and a container?

Short answer: An image is a read-only template, and a container is a running instance of it with a writable layer.

Many containers can start from one image. Changes made in a container are lost on removal unless stored in a volume.

Q4. Explain Docker architecture.

Short answer: The CLI talks through a REST API to the Docker daemon, which uses containerd and runc to create containers.

The daemon manages images, networks, volumes and builds. containerd manages container lifecycle and image transfer, and runc creates the isolated process using namespaces and cgroups according to the OCI runtime spec.

Q5. How do containers achieve isolation?

Short answer: With Linux namespaces (what a process sees), cgroups (what it can use), a union filesystem and security features such as capabilities and seccomp.

Namespaces isolate process ids, network, mounts, hostname, users and IPC. cgroups limit CPU, memory and I/O. Together they make an ordinary process behave like a separate machine.

Q6. What are image layers and why do they matter?

Short answer: Layers are read-only filesystem changes created by Dockerfile steps, shared and cached by content hash.

Sharing saves disk and bandwidth, and caching speeds builds. Ordering steps so rarely changing ones come first keeps the cache valid longer.

Q7. How does the build cache work and how do you invalidate it?

Short answer: Docker reuses a layer if the instruction and its inputs are unchanged, and all layers after a changed step are rebuilt.

Copy dependency files and install dependencies before copying the source code. Changing a file copied earlier invalidates everything below it. --no-cache forces a full rebuild.

Q8. CMD versus ENTRYPOINT?

Short answer: ENTRYPOINT sets the executable, and CMD sets default arguments that can be overridden at run time.

Used together they make a container behave like a command with default options. Prefer the exec form so the process is PID 1 and receives signals.

Q9. COPY versus ADD?

Short answer: COPY copies files, while ADD can also unpack archives and fetch URLs, so COPY is preferred.

ADD behaviour can be surprising and less safe, so use it only when you need automatic extraction.

Q10. What is a multi-stage build and what are its benefits?

Short answer: It uses several FROM stages so build tools stay in early stages and only the result is copied into a small final image.

The final image is smaller, faster to pull and has a smaller attack surface because it contains no compiler or source code.

Q11. What is .dockerignore for?

Short answer: It excludes files from the build context.

It speeds up the build, keeps images small and prevents secrets and unnecessary files such as .git from being copied into the image.

Q12. Why avoid the latest tag?

Short answer: It is mutable, so you cannot tell what version runs or reliably roll back.

Use explicit version tags, the commit SHA or an image digest for reproducible deployments.

Q13. What is an image digest?

Short answer: A sha256 hash of the image content that never changes, unlike a tag.

Pinning by digest guarantees the exact tested image is deployed, and prevents a tag from being silently replaced.

Q14. ARG versus ENV?

Short answer: ARG exists only at build time, while ENV persists in the image and the running container.

Neither is safe for secrets, since both can be seen in the image history or inspection. Use BuildKit secrets instead.

Q15. What is the OCI?

Short answer: The Open Container Initiative defines standards for the image format and the runtime.

It makes images and runtimes interchangeable across tools such as Docker, Podman, containerd and Kubernetes.

Q16. How do you reduce the size of an image?

Short answer: Use a small base, multi-stage builds, combine and clean RUN steps, install only what is needed and use .dockerignore.

Distroless or slim bases help. Check layers with docker history and compare sizes after each change.

21. Interview Q&A: Containers, Networking, Storage & Compose

Q1. What happens when you run docker run nginx?

Short answer: Docker pulls the image if missing, creates a container with a writable layer, sets up network and storage, and starts the main process.

The CLI sends the request to the daemon, which asks containerd and runc to create the namespaces and cgroups and run the process as PID 1.

Q2. Why does a container stop immediately?

Short answer: Because its main process (PID 1) finished or crashed.

A container lives only as long as PID 1. Run the service in the foreground, check docker logs and the exit code.

Q3. What do the exit codes 0, 1, 137 and 143 mean?

Short answer: 0 is success, 1 is an application error, 137 means killed (often out of memory) and 143 means stopped by SIGTERM.

Check docker inspect for OOMKilled when you see 137.

Q4. docker stop versus docker kill?

Short answer: stop sends SIGTERM and waits (10 s by default) before SIGKILL, while kill sends the signal immediately.

Handle SIGTERM in your application to finish work cleanly.

Q5. What is the difference between docker exec and docker attach?

Short answer: exec starts a new process inside a running container, while attach connects to the main process streams.

Use exec for shells and debugging because leaving an attach session can stop the container.

Q6. How do containers communicate?

Short answer: Over Docker networks; on a user-defined network they resolve each other by name through the embedded DNS.

The default bridge has no name resolution. Ports are only reachable from outside when published.

Q7. Explain the network drivers.

Short answer: bridge (default, single host), host (shares host stack), none (no network), overlay (multi-host) and macvlan (own MAC and IP).

Choose bridge for most apps, host for performance-sensitive tools, overlay for Swarm and macvlan for legacy integration.

Q8. What does -p 8080:80 mean?

Short answer: It publishes container port 80 on host port 8080.

Without it, the container port is reachable only from other containers on the same network.

Q9. Why can a container not reach another with localhost?

Short answer: Localhost inside a container means the container itself.

Use the other container's name on a shared user-defined network, or the service name in Compose.

Q10. Volume versus bind mount versus tmpfs?

Short answer: A volume is managed by Docker and preferred for persistent data, a bind mount maps a host path, and tmpfs is memory-only.

Use bind mounts in development for source code, volumes for databases and tmpfs for temporary or sensitive files.

Q11. What happens to data when a container is removed?

Short answer: Data in the writable layer is lost, while data in named volumes stays.

Back up volumes, because docker volume prune and compose down -v delete them.

Q12. How do you back up a volume?

Short answer: Run a temporary container that mounts the volume and an output folder and archives the data.

For databases prefer the database's own dump tools or managed backups, since copying files of a running database may be inconsistent.

Q13. What is Docker Compose and when do you use it?

Short answer: A tool and YAML format for defining and running multi-container applications on one host.

It is ideal for local development and testing and simple single-host deployments, not for large production clusters.

Q14. Does depends_on wait until a service is ready?

Short answer: Only with a healthcheck and condition service_healthy; otherwise it waits only for the container to start.

Applications should also retry connections, because dependencies can restart at any time.

Q15. What is a restart policy?

Short answer: A setting that tells Docker when to restart a container: no, on-failure, always or unless-stopped.

It gives basic self-healing on one host, but it does not check health, and orchestrators do this better.

Q16. How do you limit resources?

Short answer: With --memory, --cpus and --pids-limit, which set cgroup limits.

Without limits one container can starve others. Exceeding the memory limit gets the container OOM-killed.

Q17. How do you handle logs?

Short answer: Write to stdout and stderr, and use a logging driver and rotation to ship and limit them.

docker logs reads them, and drivers such as fluentd or awslogs forward them to a central system.

Q18. What is a health check?

Short answer: A command Docker runs inside the container periodically to mark it healthy or unhealthy.

Compose and orchestrators use it for readiness and restarts, and it should test the real service endpoint.

22. Interview Q&A: Security, CI/CD, Orchestration & Scenarios

Q1. How do you secure Docker containers?

Short answer: Use trusted minimal images, scan them, run as non-root, drop capabilities, use a read-only filesystem, never use privileged mode and keep secrets out of images.

Also protect the daemon socket, update the engine, apply resource limits, restrict networks and sign images.

Q2. Why is mounting /var/run/docker.sock dangerous?

Short answer: It gives the container full control of the Docker daemon, which is effectively root on the host.

A process with the socket can start a privileged container that mounts the host filesystem. Avoid it or use rootless mode or a restricted proxy.

Q3. What does --privileged do and why avoid it?

Short answer: It gives the container almost all host capabilities and access to devices, and disables most isolation.

Add only the specific capability you need with --cap-add instead.

Q4. How do you manage secrets?

Short answer: Never in the Dockerfile, ENV or image; use BuildKit secret mounts at build time and secret stores, mounted files or a vault at run time.

Anything in an image layer can be recovered with docker history or by anyone who pulls the image.

Q5. What is rootless Docker?

Short answer: Running the daemon and containers without root privileges on the host.

It limits the damage of a breakout, with some feature limitations such as privileged ports and certain network drivers.

Q6. How do you scan images for vulnerabilities?

Short answer: Use Trivy, Grype or Docker Scout in CI and in the registry, and fail the build on critical findings.

Rescan regularly, because new vulnerabilities appear in old packages, and rebuild with updated base images.

Q7. Describe a CI/CD pipeline with Docker.

Short answer: Build and tag the image, test it, scan it, push to a registry and deploy it, using the same image in every environment.

Tag with the commit SHA for traceability, cache layers for speed and deploy with rolling updates and health checks. Rollback means redeploying the previous tag.

Q8. Why is docker build slow and how do you speed it up?

Short answer: Usually because the cache is invalidated early or the context is large.

Order layers well, use .dockerignore, BuildKit and cache mounts, multi-stage builds and a remote cache in CI.

Q9. What is Docker Swarm and how does it compare with Kubernetes?

Short answer: Swarm is Docker's built-in, simple orchestrator, while Kubernetes is a more powerful and widely adopted standard.

Swarm is easy to start; Kubernetes has a richer model and ecosystem. Most new production work uses Kubernetes or a managed service.

Q10. Why did Kubernetes remove dockershim and does it still run Docker images?

Short answer: Kubernetes needs only a CRI runtime, and containerd provides it directly, so the Docker layer was unnecessary; images built with Docker still run.

Images follow the OCI standard, so any compliant runtime can run them.

Q11. What is desired state?

Short answer: You declare what you want, such as three replicas, and the orchestrator continually works to make reality match.

If a container dies it is replaced, which is the basis of self-healing and scaling.

Q12. How do you do zero-downtime deployments with containers?

Short answer: Use rolling updates with readiness checks, so new containers receive traffic only when healthy and old ones are removed gradually.

Blue-green and canary releases are alternatives. Applications should handle SIGTERM and finish requests.

Q13. A container keeps restarting. How do you investigate?

Short answer: Check docker ps for the exit code, read docker logs, inspect the configuration and run the image interactively.

Common causes are a crashing application, missing configuration, an out-of-memory kill (137), a wrong CMD or a failing health check.

Q14. A container is slow or uses too much memory. What do you do?

Short answer: Use docker stats to see usage, set limits, profile the application and check for leaks.

Memory limits protect other containers, and an OOM kill shows exit code 137.

Q15. How do you persist a database in Docker and is it a good idea in production?

Short answer: Use a named volume, backups and a health check; for production many teams prefer a managed database.

Containers are ephemeral and databases need careful storage, backups and tuning, so run them in containers mainly for development, testing or when you operate a proper stateful platform.

Q16. How do you keep an image the same across environments?

Short answer: Build once, tag immutably, push to a registry and promote the same image, with differences supplied through configuration.

Rebuilding per environment would produce different artifacts and defeat the point.

Q17. What are Docker alternatives?

Short answer: Podman (daemonless and rootless), containerd with nerdctl, CRI-O, Buildah and Kaniko for builds.

They use the same OCI images, so skills and images transfer.

Q18. How would you containerise an existing application?

Short answer: Identify dependencies and configuration, write a Dockerfile with a small base, externalise config and data, add health checks and logging to stdout, then test with Compose.

Then add CI to build and scan images and deploy to an orchestrator or managed service.
