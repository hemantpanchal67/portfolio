1. How Do You Scale a Database? Vertical vs Horizontal

A database becomes a bottleneck when one machine can no longer keep up with reads, writes, storage or connections. The right response is not to jump straight to an exotic architecture. It is to climb a scaling ladder, taking the cheapest effective step first: measure to find the real bottleneck, tune queries and indexes, cache repeated reads, scale up the machine, add read replicas for read traffic, and only then partition or shard to scale writes and storage. Each step adds capacity but also adds complexity, so you stop as soon as the problem is solved.

Vertical versus horizontal scaling

Vertical scaling (scale up) means giving the single database server more CPU, memory and faster disks. It is simple, needs no application change and is often a one-click operation on managed services, but it has a hardware ceiling, costs rise steeply near the top, and you still have a single point of failure. Horizontal scaling (scale out) means spreading the work across several machines, either by replicating the same data for reads or by sharding different data across nodes for writes and storage. It scales much further and improves resilience, but it brings consistency, routing and operational complexity.

Benefits, problems and a practical order

The benefit of this ordering is that you spend effort where the return is highest. Query tuning and caching often remove most of the load for little cost, and they make every later step last longer. The usual mistakes are scaling before measuring, adding replicas to a write-bound system, and sharding too early, which locks you into a hard-to-change design.

-- 1. Measure: top statements by total time (PostgreSQL)
SELECT query, calls, round(total_exec_time::numeric, 0) AS total_ms, round(mean_exec_time::numeric, 2) AS mean_ms
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;

-- 2. What is the database waiting on right now?
SELECT wait_event_type, wait_event, count(*) FROM pg_stat_activity WHERE state = 'active' GROUP BY 1, 2 ORDER BY 3 DESC;

-- 3. Cache hit ratio (should be above 99 percent for OLTP)
SELECT sum(blks_hit) * 100.0 / nullif(sum(blks_hit) + sum(blks_read), 0) AS cache_hit_pct FROM pg_stat_database;

2. Replication, Read Replicas and Replication Lag

Database replication keeps copies of the same data on several servers. The primary accepts all writes and records every change in a log. That log, the write-ahead log in PostgreSQL or the binlog in MySQL, is shipped to replicas, which replay it in order. Replication gives you read scaling, high availability (a replica can be promoted), disaster recovery, and a safe place for reports that would otherwise slow the primary.

Primary versus read replica

The primary is the source of truth and takes reads and writes. A read replica is a follower that normally serves only reads and is kept up to date by replaying the primary's log. Replication can be asynchronous (the primary does not wait, so writes are fast but a replica may lag and a failover can lose the last commits) or synchronous (the primary waits for at least one replica, so data is safe but writes are slower). Physical replication copies storage-level changes; logical replication copies row changes and allows selective tables and cross-version targets.

When should you introduce read replicas?

Add replicas when the workload is read heavy, when primary CPU or IO is mostly spent on reads, when reporting or analytics queries disturb transactional traffic, when you need a standby for availability, or when users in another region need lower read latency. Do it after query tuning and caching, and do not expect it to help a write-bound system, because every write still lands on the single primary.

How do you handle replication lag?

Replication lag means a replica is a little behind, so a read there may return stale data. Handle it by design rather than hope. Give users read-your-writes by sending their reads to the primary for a few seconds after they write, or by making a replica wait until it has replayed their write position. Use smart routing so only tolerant reads go to replicas and critical reads (balances, permissions) stay on the primary. Monitor lag and automatically remove replicas that fall too far behind. Where freshness is vital, use synchronous or quorum replication and accept slower writes. Finally, find the cause: long-running replica queries, heavy write bursts, slow disks or network.

-- on the primary: lag per replica
SELECT application_name, state, sync_state, write_lag, flush_lag, replay_lag,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)) AS bytes_behind
FROM pg_stat_replication;

-- on a replica: how old is the data it shows?
SELECT now() - pg_last_xact_replay_timestamp() AS replica_delay;

3. Database Partitioning

Partitioning splits one large table into smaller physical pieces called partitions, while it still looks like a single table to your queries. In PostgreSQL this is declarative partitioning: you define the key and the partitions, and the database routes inserts and prunes reads. All partitions live in the same database server, so it improves manageability and speed but does not add servers.

Types of partitioning

Range partitioning divides by ranges, most often dates, and is perfect for logs, events and orders. List partitioning groups by explicit values such as region or status. Hash partitioning spreads rows evenly using a hash of the key when there is no natural range. A table can also be partitioned in two levels, for example by month then by region.

When should you use partitioning?

Use it when a table has grown to tens or hundreds of millions of rows or hundreds of gigabytes, when queries usually filter on the partition key (so partition pruning skips most partitions), when you have retention rules (dropping an old partition is instant, unlike a massive DELETE), and when vacuum and index maintenance on one huge table has become painful.

Benefits and problems

The benefits are faster queries through pruning, smaller indexes, cheap archiving and deletion, easier maintenance and better cache use. The problems are that queries without the partition key scan every partition, the partition key must be part of primary and unique keys, too many partitions slow query planning, foreign keys and some features have limits, and cross-partition operations cost more.

Partitioning versus sharding

Partitioning divides data inside one server; sharding divides data across several servers. Partitioning helps with size and maintenance but all writes still go to one machine. Sharding adds capacity for writes and storage but needs routing and handles cross-shard queries. Many designs use both: each shard holds partitioned tables. (Some people use the word "partitioning" loosely for sharding, so clarify which one is meant.)

4. Sharding, Shard Keys and Cross-Shard Queries

Sharding splits data horizontally across independent database servers, called shards, so each holds only a subset of the rows. It is the main way to scale writes and total storage beyond one machine, because each shard handles its own slice of traffic. A router (application code or a proxy) uses the shard key to send each query to the right shard.

When should you use sharding?

Shard when, after tuning, caching, scaling up, read replicas and partitioning, a single primary still cannot handle the write rate or the data size or working set. It also helps with tenant isolation and data residency. Do not shard early: it makes joins, transactions, schema changes and operations much harder, and it is difficult to undo.

How do you choose a shard key?

The shard key is the most important decision. A good key has high cardinality, spreads data and load evenly, appears in most queries so each query hits one shard, and rarely changes. In SaaS systems the tenant or customer id is the classic choice, in consumer systems the user id. Avoid monotonically increasing keys such as timestamps or auto-increment ids with range sharding, because new writes pile onto one shard, and avoid low-cardinality columns such as country or status. Watch for hot keys (one huge tenant) and give them a dedicated shard. Common strategies are hash sharding (even), range sharding (good for ordered scans, risk of hotspots), and directory sharding (a lookup table gives full flexibility). Use consistent hashing or many logical shards mapped to fewer servers so you can rebalance by moving whole logical shards.

How do you handle cross-shard queries?

First, design to avoid them: co-locate related data by using the same shard key for related tables (orders and order items under the same customer id), so joins stay inside a shard. Copy small reference tables to every shard. When a query truly needs several shards, use scatter-gather: send it to all shards in parallel and merge the results, accepting higher latency and cost. Keep a global lookup table for secondary keys (find the shard for an email). Send analytics to a separate store such as a warehouse using CDC. For writes that span shards, avoid distributed transactions and use sagas with idempotent steps.

Replication versus sharding: when do you use which?

Replication copies the same data to more nodes, so it scales reads and availability. Sharding divides different data across nodes, so it scales writes and storage. Use replication when reads dominate or you need HA, use sharding when one primary cannot take the writes or the data. In large systems you use both: every shard has its own primary and replicas.

5. Indexes, Slow Queries and Query Optimisation

An index is a separate, sorted structure that lets the database find rows without scanning the whole table. It is the single biggest lever for read performance, but it has a price, so you need to understand both sides.

How do indexes affect performance?

Indexes speed up reads that filter, join or sort on the indexed columns, because a lookup touches a few pages instead of the whole table. They slow down writes, because every insert, update or delete must also update each index, and they use memory and disk. Columns with low selectivity (such as a boolean) rarely benefit from a plain index. Composite indexes follow the left-prefix rule, so put equality columns first and range columns last. Covering indexes (INCLUDE) allow index-only scans, and partial indexes index only the rows you query.

What happens when an index becomes too large?

A huge index no longer fits in memory, so lookups fall through to disk reads, the cache hit ratio drops and latency rises. Writes get slower because each change touches big index pages, bloat accumulates, and vacuum and rebuilds take much longer. The fixes are to drop unused and duplicate indexes (check idx_scan in pg_stat_user_indexes), use partial indexes and narrower data types, use BRIN for naturally ordered data such as timestamps, partition the table so each index is smaller, and rebuild bloated indexes with REINDEX CONCURRENTLY.

How do you optimise a slow database query?

Follow a loop: find the query that matters by total time, read its plan with EXPLAIN (ANALYZE, BUFFERS), fix the cause, and verify the result. Typical causes and fixes are a missing or unsuitable index, a function on an indexed column (rewrite the predicate), SELECT star pulling unneeded columns, OFFSET pagination on large pages (use keyset pagination), N+1 queries from the ORM (batch or join), stale statistics (run ANALYZE), poor join order or missing join indexes, and sorts or hashes spilling to disk (tune work_mem carefully). For heavy aggregations, consider a materialised view or a summary table.

-- find the offenders
SELECT query, calls, mean_exec_time, total_exec_time FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 5;
-- read the plan: look for Seq Scan on big tables, big gaps between rows= estimates and actual rows
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE customer_id = 42 AND status = 'open' ORDER BY created_at DESC LIMIT 20;

-- fix 1: a composite index matching filter + sort, built without blocking writes
CREATE INDEX CONCURRENTLY idx_orders_cust_status_created ON orders (customer_id, status, created_at DESC);
-- fix 2: partial index for a hot subset
CREATE INDEX CONCURRENTLY idx_orders_open ON orders (customer_id, created_at DESC) WHERE status = 'open';
-- fix 3: keyset pagination instead of OFFSET 100000
SELECT id, created_at FROM orders WHERE customer_id = 42 AND (created_at, id) < ('2026-05-01 10:00', 98765) ORDER BY created_at DESC, id DESC LIMIT 20;
-- find unused indexes (candidates to drop)
SELECT relname, indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid)) AS size FROM pg_stat_user_indexes WHERE idx_scan = 0 ORDER BY pg_relation_size(indexrelid) DESC LIMIT 20;
REINDEX INDEX CONCURRENTLY idx_orders_cust_status_created;

6. Connection Pooling, Connection Exhaustion and Heavy Load

In PostgreSQL every client connection is a separate operating-system process with its own memory, so connections are expensive and the server can only run a limited number efficiently. When an application opens too many, you see errors such as remaining connection slots are reserved and throughput actually drops from contention.

What is connection pooling and why is it important?

A connection pool keeps a small set of open database connections and lends them to requests, instead of opening and closing one per request. It saves the cost of TCP, TLS and authentication, caps the number of real connections, and lets thousands of clients share a few dozen database connections. Pool in the application (for example HikariCP, Npgsql or SQLAlchemy pools) and, when there are many clients such as microservices or Lambda, add an external pooler such as PgBouncer or RDS Proxy. In transaction pooling mode a server connection is held only for the duration of a transaction, which gives the best sharing but disables session-level features (temp tables, advisory locks, session variables).

How do you handle connection exhaustion?

First find the cause: connection leaks (not closed), long or idle-in-transaction sessions, too many app instances times pool size (autoscaling can multiply it suddenly), or serverless functions opening a connection per invocation. Then fix it: close and return connections properly, set idle_in_transaction_session_timeout and statement_timeout, size pools so instances times pool size stays under max_connections with room for admin, add PgBouncer or RDS Proxy, queue or reject excess requests instead of letting them pile up, and only then raise max_connections, remembering the memory cost. A good pool size is surprisingly small, roughly a few times the number of CPU cores.

How do you optimise a database under heavy load?

Identify the saturated resource first (CPU, IO, locks, connections). Then apply, in roughly this order: cache hot and expensive reads, fix the top queries, pool connections, queue and batch writes to smooth spikes (SQS, Kafka, COPY or multi-row inserts), offload reports and search to replicas, a warehouse or a search engine, protect the database with timeouts, rate limits, circuit breakers and load shedding, and finally scale up or out. Failing fast is better than a slow collapse.

7. Handling 500M+ Records and Scaling PostgreSQL

Hundreds of millions of rows are not unusual for a well-designed database. What matters is that queries touch only a small hot slice of the data. The strategy is to keep the working set small, structure the table so the planner can skip most of it, and move what is not needed online elsewhere.

How do you handle 500 million records?

Partition the table by time or tenant so each piece is manageable and pruning skips most of it. Use few, selective indexes, with partial indexes and BRIN for naturally ordered data, so indexes stay in memory. Define a retention and archive policy: detach old partitions and export them to S3 as Parquet, keeping summary tables online. Always filter on indexed keys and avoid full scans, use keyset pagination, load with COPY, run backfills, deletes and migrations in small batches with short transactions, tune autovacuum for large tables, and move heavy analytics to a columnar store (Redshift, ClickHouse, BigQuery). If a single primary still cannot cope, add replicas for reads and finally shard.

How would you scale PostgreSQL for a high-traffic application?

Combine the ladder with PostgreSQL specifics. Start with query and index tuning using pg_stat_statements and EXPLAIN, fix N+1 queries and tune autovacuum. Add connection pooling (PgBouncer or RDS Proxy). Add a cache (Redis) for hot reads. Scale up the instance and use fast storage. Add read replicas and route reads. Partition big tables. Offload analytics via logical replication or CDC. If writes still exceed one node, use Citus or application-level sharding, or move to Aurora for faster failover and many readers. Keep HA (Patroni or managed Multi-AZ), backups with PITR and monitoring throughout.

8. Failover, Multi-Region Design and Transactions Across Microservices

Availability and consistency across machines, Regions and services is where database architecture gets hard. Three questions come up again and again: how to fail over safely, how to span Regions, and how to keep data consistent across microservices.

How do you design database failover and high availability?

Define your RPO (how much data you can lose) and RTO (how long you can be down) first. Run a primary with at least one standby in another Availability Zone; use synchronous or quorum replication if you cannot lose acknowledged data. Automate failure detection and promotion with Patroni plus a consensus store (etcd) or a managed service such as RDS Multi-AZ or Aurora. Make clients find the new primary through a stable endpoint, proxy or virtual IP and retry with backoff. Fence the old primary so it cannot accept writes, which prevents split brain, and rejoin it as a replica with pg_rewind. Take backups with point-in-time recovery, monitor replication, and test failovers regularly.

How do you design a multi-region database architecture?

Start from the goal: disaster recovery, low latency for global users or data residency. The simplest pattern is active-passive: one Region takes writes and an asynchronous replica in another Region is promoted during an outage (Aurora Global Database, cross-Region replicas), accepting an RPO equal to the replication lag. Active-active lets several Regions accept writes and gives the lowest latency, but concurrent writes can conflict, so you need conflict resolution (last-writer-wins, CRDTs) or a consensus system (Spanner, CockroachDB, DynamoDB global tables with their own rules). Geo-partitioning gives each user a home Region that owns their data, which fits residency laws. Remember that cross-Region synchronous writes add tens to hundreds of milliseconds, so choose consistency per data type: strong for money and inventory, eventual for profiles and feeds. Route users with latency or geo DNS, and rehearse Regional failover.

How do you handle transactions across microservices?

Each microservice should own its data, so a single ACID transaction cannot span them. Instead use the saga pattern: each service commits a local transaction and publishes an event, and if a later step fails, earlier steps are undone with compensating transactions. Sagas can be choreographed (services react to events) or orchestrated (a coordinator drives the steps). To publish events reliably, use the transactional outbox: write the event to an outbox table in the same local transaction as the data change, and let a relay or CDC tool such as Debezium deliver it at least once. Because delivery can repeat, every handler and compensation must be idempotent, using idempotency keys or an inbox table. Two-phase commit is generally avoided across services because it locks resources, blocks on failure and couples availability. Accept eventual consistency and design the user experience for it.

9. Interview Q&A: Database Architecture (All 25 Questions)

Q1. What is database replication?

Short answer: Replication keeps copies of the same data on several database servers, by shipping the primary's change log to followers that replay it.

It gives read scaling, high availability and disaster recovery. It can be asynchronous (fast writes, possible lag and small data loss on failover) or synchronous (no loss, slower writes), and physical (storage level) or logical (row changes, selective tables, cross-version).

Q2. Primary database vs read replicas — what is the difference?

Short answer: The primary accepts reads and writes and is the source of truth; read replicas are followers that serve read queries and follow the primary's log.

A replica may be slightly behind, so it can return stale data, and it can be promoted to primary during failover. Replicas scale reads but not writes.

Q3. When should you introduce read replicas?

Short answer: When the workload is read heavy and reads are saturating the primary, when reports disturb transactional traffic, or when you need a standby or lower read latency in another region.

Introduce them after query tuning and caching, and not for a write-bound system, because replicas do not reduce write load. You also need an application that can route reads and tolerate lag.

Q4. How do you handle replication lag?

Short answer: Design for it: give read-your-writes by pinning a user to the primary briefly after writes, send only tolerant reads to replicas, monitor lag and remove replicas that fall behind, and use synchronous or quorum replication where freshness is critical.

Also find the cause, such as long queries on the replica, write bursts, slow disks or network, and fix it. Use pg_stat_replication or cloud metrics for visibility.

Q5. What is database partitioning?

Short answer: Splitting a large table into smaller physical partitions inside one database server, while queries still see one logical table.

Types are range, list and hash. The planner uses partition pruning to scan only relevant partitions, and old partitions can be dropped or archived quickly.

Q6. When should you use partitioning?

Short answer: When a table is very large (tens to hundreds of millions of rows), most queries filter on a natural key such as date or tenant, you have retention requirements, or maintenance like vacuum and index builds has become painful.

Do not partition small tables or when queries rarely include the partition key, because too many partitions slow planning and unfiltered queries scan all of them.

Q7. Partitioning vs sharding — what is the difference?

Short answer: Partitioning splits data within one server; sharding splits data across multiple servers.

Partitioning improves manageability and query speed but writes still hit one machine. Sharding scales writes and storage but needs routing, a shard key and handling of cross-shard queries. Systems often use both.

Q8. What is database sharding?

Short answer: Sharding is horizontal partitioning of data across independent database servers (shards), each owning a subset of the rows, with a router that sends each query to the right shard by the shard key.

Each shard has its own resources, so write and storage capacity scale with the number of shards, at the cost of complexity.

Q9. When should you use sharding?

Short answer: When a single primary cannot handle the write throughput or data size even after tuning, caching, scaling up, replicas and partitioning, or when you need tenant isolation or data residency.

It should be a late step: it complicates joins, transactions, schema changes, backups and operations, and is hard to reverse.

Q10. How do you choose a shard key?

Short answer: Choose a high-cardinality column that distributes data and load evenly, appears in most queries, and rarely changes, such as tenant id or user id.

Avoid monotonically increasing keys that create hot shards, and low-cardinality columns. Prefer hash or many logical shards for easy rebalancing, and isolate very large tenants on their own shard.

Q11. How do you handle cross-shard queries?

Short answer: Avoid them by co-locating related data with the same shard key, copying small reference tables to every shard, and sending analytics to a separate store.

When unavoidable, use scatter-gather and merge, a global lookup table for secondary keys, and sagas instead of distributed transactions for writes across shards.

Q12. Replication vs sharding — when do you use which?

Short answer: Use replication to scale reads and improve availability, and sharding to scale writes and storage.

Replication copies the same data to every node; sharding divides different data across nodes. Large systems combine them, with replicas for each shard.

Q13. How do you scale a database?

Short answer: Climb a ladder: measure the bottleneck, tune queries and indexes, add caching, scale up, add read replicas, then partition and shard.

Take the cheapest effective step first, because each step adds operational complexity. Also pool connections and move heavy analytics off the primary.

Q14. Vertical vs horizontal database scaling — what is the difference?

Short answer: Vertical scaling adds resources to one server; horizontal scaling adds more servers.

Vertical is simple but has a ceiling and a single point of failure. Horizontal (replicas for reads, sharding for writes and storage) scales further but adds consistency, routing and operational complexity.

Q15. How would you scale PostgreSQL for a high-traffic application?

Short answer: Tune queries and indexes, add PgBouncer or RDS Proxy, cache hot reads, scale up, add read replicas, partition big tables, offload analytics, and shard with Citus or application logic when writes exceed one node.

Alternatively use Aurora PostgreSQL for faster failover and many readers. Maintain HA, backups with PITR, autovacuum tuning and monitoring throughout.

Q16. How do indexes affect database performance?

Short answer: Indexes make reads that filter, join or sort on the indexed columns much faster, but they slow writes and consume memory and storage.

Index the columns you query, use composite indexes in the right order, covering indexes for index-only scans and partial indexes for hot subsets, and avoid indexing low-selectivity columns or having many unused indexes.

Q17. What happens when an index becomes too large?

Short answer: It no longer fits in memory, so lookups cause disk reads and cache misses, writes slow down, bloat grows, and vacuum and rebuilds take much longer.

Fix it by dropping unused or duplicate indexes, using partial indexes, BRIN for ordered data and narrower types, partitioning the table, and rebuilding with REINDEX CONCURRENTLY.

Q18. How do you optimize a slow database query?

Short answer: Find it with pg_stat_statements or slow logs, read the EXPLAIN (ANALYZE, BUFFERS) plan, fix the cause, and verify.

Common fixes are matching indexes, removing functions on indexed columns, selecting only needed columns, keyset pagination, fixing N+1 queries, refreshing statistics with ANALYZE, adjusting joins, and using materialised views or summary tables for heavy aggregates.

Q19. How do you optimize a database under heavy load?

Short answer: Find the saturated resource, then cache hot reads, fix top queries, pool connections, queue and batch writes, offload reports and search, protect with timeouts and load shedding, and scale up or out.

Failing fast with rate limits and circuit breakers is better than letting the database collapse slowly.

Q20. How do you handle database connection exhaustion?

Short answer: Find leaks, long or idle-in-transaction sessions and oversized pools, then size pools so instances times pool size stays below max_connections, add PgBouncer or RDS Proxy, set timeouts, and queue or reject excess load.

Raise max_connections only as a last step because each connection costs memory. Cap autoscaling so connection counts cannot multiply suddenly.

Q21. What is connection pooling and why is it important?

Short answer: A pool keeps a limited set of open database connections and reuses them across many requests or clients.

It avoids the cost of establishing connections (TCP, TLS, authentication), limits the load on the database, and lets many clients share few connections. Use application pools plus PgBouncer or RDS Proxy, and understand that transaction pooling disables session-level features.

Q22. How do you handle 500M+ database records?

Short answer: Partition by time or tenant, keep a small hot set, use few selective indexes (partial and BRIN), archive cold data to cheap storage, filter on indexed keys, and run changes in small batches.

Use keyset pagination and COPY for loads, tune autovacuum, move analytics to a columnar store, and add replicas or shards only if a single primary still cannot cope.

Q23. How do you design database failover and high availability?

Short answer: Define RPO and RTO, run a primary with at least one standby in another AZ, automate detection and promotion with Patroni or a managed service, route clients through a stable endpoint, fence the old primary, and test regularly.

Use synchronous or quorum replication when you cannot lose acknowledged data, take PITR backups, and make applications retry with backoff. Prevent split brain with quorum and fencing.

Q24. How do you handle transactions across microservices?

Short answer: Avoid distributed ACID; use sagas with local transactions and compensating actions, the transactional outbox for reliable events, and idempotent handlers.

Choose choreography or orchestration, avoid two-phase commit across services because it blocks and couples availability, and design the user experience for eventual consistency.

Q25. How do you design a multi-region database architecture?

Short answer: Choose by goal: active-passive with an asynchronous cross-Region replica for disaster recovery, geo-partitioned data for residency and latency, or active-active with conflict resolution or consensus for global writes.

Remember cross-Region latency, pick consistency per data type, route users with latency or geo DNS, and rehearse Regional failover and recovery.
