1. The AI Loan Assistant: Use Case and End-to-End Flow

A customer asks, "What is the current status of my loan application LA12345, and why is it still pending?" A traditional chatbot would need a hard-coded flow for this exact question. An AI agent can instead understand the question, decide which tools will answer it, call them through a controlled interface such as the Model Context Protocol (MCP), and combine the results into a clear reply: "Your application LA12345 is currently pending because the latest income verification document has not yet been submitted." The value is that the language model is decoupled from the Loan Origination System (LOS), CRM, workflow engine, document system and databases, so each can change without rebuilding the assistant.

What the assistant must and must not do

It must give accurate, grounded answers, respect privacy and ownership (a customer sees only their own loans), explain things in plain language, suggest a next step, and hand over to a person when unsure. It must not invent statuses or reasons, reveal credit scores or model internals, change data in this first release, or promise an outcome. Starting read-only keeps risk low and value high, because status questions are among the most common support contacts.

Features, benefits and problems

Benefits: 24 by 7 answers, lower call-centre load, consistent wording, faster resolution, and a reusable tool layer for other assistants. Problems to manage: wrong or stale data, privacy leaks, prompt injection through documents or notes, regulated explanations of credit decisions, downstream outages and latency, and the need for evaluation and monitoring. Each of these has a design answer in the following lessons.

2. The Architecture: Layers and Responsibilities

The design separates concerns into layers. Channels (web chat, mobile app, WhatsApp, IVR, a staff screen) are thin and authenticate the user. Identity and session establishes who is asking and issues tokens carrying that identity. The orchestration layer is the agent runtime: it holds the model, instructions and policy, selects tools, manages context, retries and limits, and composes the answer. The MCP gateway is the controlled entry point for every tool call: it validates tokens, authorises per user, rate-limits, routes and audits. MCP servers are split by domain (loan application, documents, decisions, customer data) and expose a few task-oriented tools. Behind them sit the systems of record: LOS, CRM, workflow or BPM, document management and databases, reached through existing service APIs.

3. Designing the Loan Tools and the MCP Server

Four read-only tools answer the example question. get_loan_application returns a minimal, masked view of the application (product, requested amount, submission date, current stage) after verifying the caller owns it. get_application_status returns the workflow stage, its state, timestamps and the next expected step from the system of record. get_pending_documents lists what is still required, why and by when; it returns metadata only, never file contents. get_credit_decision is the sensitive one: it returns the decision state and approved, customer-safe reason codes, never scores or model internals, and has stricter authorisation and logging.

ToolReturnsNever returnsNotes
get_loan_applicationProduct, amount, submitted date, stage, masked applicantFull ID numbers, internal notesOwner check first
get_application_statusStage, state, timestamps, next stepInferred or guessed statusFrom workflow as source of truth
get_pending_documentsMissing document types, reason, due date, received flagDocument content or file links of othersUsually the real reason for "pending"
get_credit_decisionDecision state, approved reason codesScore, model features, policy thresholdsRestricted, extra audit

Fine-grained tools or one composite tool?

Four narrow tools are easy to authorise, test and reuse, and the agent can fetch only what a question needs. A single composite tool such as get_loan_status_summary reduces model round trips and latency but returns more data than some questions need. A balanced design keeps the narrow tools and adds a composite one for the most common question, with the same authorisation inside. Test both with evals on tool-selection accuracy and latency.

# loan_server.py - MCP server (Python SDK) for the loan application domain
from mcp.server.fastmcp import FastMCP
mcp = FastMCP("loan-applications")

def caller():                       # identity comes from the VALIDATED access token, never from tool arguments
    return auth.current_customer()

def owned_application(application_id: str):
    app = los.get_application(application_id)
    if app is None or app.customer_id != caller().id:           # object-level authorisation
        audit.log("denied", tool="owned_application", application_id=application_id, customer=caller().id)
        raise PermissionError("Application not found for this customer.")      # same message whether it exists or not
    return app

@mcp.tool()
def get_loan_application(application_id: str) -> dict:
    """Core details of ONE loan application belonging to the signed-in customer. Use first to confirm the application exists."""
    a = owned_application(application_id)
    return {"application_id": a.id, "product": a.product, "requested_amount": a.amount, "currency": a.currency,
            "submitted_on": a.submitted_on.isoformat(), "stage": a.stage}

@mcp.tool()
def get_application_status(application_id: str) -> dict:
    """Current workflow stage and state for the application, with timestamps and the next expected step."""
    owned_application(application_id)
    s = workflow.status(application_id)
    return {"stage": s.stage, "state": s.state, "since": s.since.isoformat(), "next_step": s.next_step}

@mcp.tool()
def get_pending_documents(application_id: str) -> dict:
    """Documents still required for the application (type, reason, due date, whether anything was received). Metadata only."""
    owned_application(application_id)
    return {"pending": [{"type": d.type, "reason": d.reason, "due": d.due.isoformat(), "received": d.received} for d in dms.pending(application_id)]}

@mcp.tool()
def get_credit_decision(application_id: str) -> dict:
    """Decision state and customer-safe reason codes. Never returns scores or model details."""
    owned_application(application_id)
    d = decisions.latest(application_id)
    return {"state": d.state, "reason_codes": [c for c in d.reason_codes if c in CUSTOMER_SAFE_CODES]}

if __name__ == "__main__":
    mcp.run(transport="streamable-http")        # remote server behind the gateway

4. Orchestration: Choosing Tools, Parallel Calls, Retries and Answers

The orchestration layer turns a question into a reliable answer in five steps. Plan: extract and validate the application id (and ask for it if missing); ownership is verified by the tools, not trusted from the text. Call tools in parallel: once the application is confirmed, status, pending documents and decision are independent, so they run concurrently with individual timeouts. Retry and fall back: retry transient errors, use circuit breakers, and if one system is down answer with what is known and say what is unavailable instead of guessing. Manage context: keep the validated id and key facts in session state for follow-ups, trim history and redact sensitive values. Compose the answer: state the status, the factual reason and the next action, in plain, approved wording, using only tool data.

import asyncio, re
APP_ID = re.compile(r"\bLA\d{5}\b")

async def handle_question(question, session):
    m = APP_ID.search(question) or session.get("application_id")
    if not m:
        return "Could you share your application number (it looks like LA12345)?"
    app_id = m.group(0) if hasattr(m, "group") else m

    app = await mcp.call("get_loan_application", {"application_id": app_id})          # also proves ownership
    if app.is_error:
        return "I could not find that application on your account. Please check the number or I can connect you to an agent."
    session["application_id"] = app_id

    status, docs, decision = await asyncio.gather(                                     # independent: run in parallel
        mcp.call("get_application_status",  {"application_id": app_id}, timeout=6),
        mcp.call("get_pending_documents",   {"application_id": app_id}, timeout=6),
        mcp.call("get_credit_decision",     {"application_id": app_id}, timeout=6),
        return_exceptions=True)                                                        # one failure must not kill the answer

    facts = {"application": app.data, "status": ok(status), "pending_documents": ok(docs), "decision": ok(decision),
             "unavailable": [n for n, r in [("status", status), ("documents", docs), ("decision", decision)] if failed(r)]}

    return await llm_answer(facts, system=ANSWER_RULES)

ANSWER_RULES = """Answer the customer using ONLY the facts provided. State the status, the reason it is pending,
and the next step. If a fact is listed as unavailable, say it is temporarily unavailable and offer a callback.
Never mention scores or internal codes. Never promise approval. Be brief and polite."""

5. Security, Privacy and Compliance

Lending data is highly sensitive, so security is designed in, not added later. The central control is ownership authorisation: every tool verifies, using the identity from the validated token, that the application belongs to the signed-in customer, and refuses otherwise, regardless of what the model asks. This is object-level authorisation, enforced in the server, never in the prompt. Data minimisation means tools return only the fields needed, masked where appropriate, and logs are redacted. Prompt injection can arrive through document names, free-text notes or the customer message, so the assistant is read-only, treats all text as data, and any future write action needs an approval step. Credit explanations are regulated: use approved reason codes and wording, never invent reasons, and route disputes to humans. An audit trail records who asked what, which tools ran, and what was said.

6. Reliability, Observability and Scaling

The assistant depends on several enterprise systems, and any of them can be slow or down. Protect it with per-call timeouts, retries with backoff, circuit breakers and bulkheads so that one failing system cannot stall every conversation, and answer with partial data when that is safe. Cache only stable data (tool definitions, static content, the stable prompt prefix) and be careful with customer-specific status. Trace each conversation end to end across the model and tools with OpenTelemetry-style tracing, and watch tool latency and errors, model latency and token cost, containment and escalation rates. Make human handoff easy and early, passing a summary. Scale with stateless workers, state in a store, autoscaling and per-customer and per-system rate limits that protect the LOS from bursts.

# Per-system circuit breaker around tool calls (simplified)
class Breaker:
    def __init__(self, failures=5, cooldown=30): self.f, self.cool, self.n, self.opened = failures, cooldown, 0, 0
    async def call(self, fn, *a, **k):
        if self.n >= self.f and time.time() - self.opened < self.cool:
            raise Unavailable("system temporarily unavailable")        # fail fast, no pile-up
        try:
            r = await asyncio.wait_for(fn(*a, **k), timeout=6); self.n = 0; return r
        except Exception:
            self.n += 1; self.opened = time.time(); raise
breakers = {"los": Breaker(), "dms": Breaker(), "decisions": Breaker()}

7. Testing, Evaluation and Safe Rollout

You cannot ship an assistant like this on faith. Build golden conversations: realistic questions with fixtures for every system, expected tool calls and expected answers, graded for factual accuracy against the data. Add negative and attack tests: someone else's loan, a missing or malformed id, injected text in a note or document name, a downstream outage, a request for a restricted explanation and an attempt to make the assistant change data. Each must produce a safe refusal or an escalation, and none may leak data. Roll out in stages: shadow mode beside human agents, a small pilot, then gradual expansion with a kill switch. Track accuracy, containment without harm, escalation quality, handle time, satisfaction and cost per resolved query.

8. Why Decouple with MCP and Alternatives

The main architectural benefit is decoupling. The model sees only tool contracts, so you can change or upgrade the model without touching systems, and when the LOS, CRM or document system changes, only the adapter behind the MCP server changes while the contract stays stable. The same servers can serve a customer assistant, a staff copilot and other agents, each with its own tool subset and permissions enforced at the gateway.

MCP or equivalent standards

Native function calling is enough for one application and one model. MCP is the better choice when several clients need the same tools, when you want governance through a gateway and registry, or when different teams own the systems. OpenAPI-described tools let an agent call existing REST APIs directly, and A2A is relevant when independent agents, for example a loan-assistant agent and a document-processing agent from another team, must delegate tasks to each other. Keep business logic in services with thin adapters for each protocol, so you can adopt or replace standards without rewriting logic.

NeedChoice
One chatbot, one model, a few toolsNative function calling
Many assistants and teams sharing tools, central governanceMCP servers behind a gateway and registry
Agent calling an existing REST API quicklyOpenAPI tool definition or MCP wrapper
Agents from different teams collaboratingA2A
Stateful, approval-heavy multi-step flowsOrchestration framework (LangGraph, Semantic Kernel, Microsoft Agent Framework)

10. Interview Q&A: The AI Loan Assistant

Q1. Walk me through the architecture of your AI loan assistant.

Short answer: Channels authenticate the customer, an orchestration layer runs the agent, a gateway enforces authentication, per-user authorisation and audit on every tool call, domain MCP servers expose narrow tools, and those wrap the LOS, CRM, workflow, document and database systems.

The model never touches the systems directly, which decouples both sides.

Q2. How does the agent decide which tools to call for "status of LA12345 and why pending"?

Short answer: The model reads the question and the tool descriptions, extracts the application id and requests the application, status, pending-documents and decision tools; the orchestration layer validates each request against policy.

Independent calls run in parallel after the application is confirmed.

Q3. Why did you use MCP rather than calling the APIs directly?

Short answer: MCP gives a standard, discoverable tool interface that several assistants and clients can reuse with central governance, while keeping the model decoupled from internal systems.

For a single app, native function calling could be enough; business logic stays in services either way.

Q4. How do you ensure a customer can only see their own application?

Short answer: Every tool verifies, using the identity from the validated token, that the application belongs to the caller, in the server and independent of the prompt, returning the same error for not found and not yours.

Rate limits and audit logs help detect id guessing.

Q5. How do you handle authentication and authorisation end to end?

Short answer: The customer authenticates in the channel, a token carries identity to the gateway, the gateway validates audience, scope and policy, and the server performs object-level authorisation before calling the system.

Tokens are never passed through to downstream systems; service credentials or token exchange are used instead.

Q6. What does the orchestration layer do?

Short answer: It runs the agent loop, selects and validates tool calls, manages context and state, applies timeouts, retries and limits, enforces policy and composes the grounded answer.

It is the harness around the model.

Q7. How do you manage context in a multi-turn conversation?

Short answer: Store the validated application id and key facts in session state, trim and summarise history, redact sensitive fields, expire the session and re-fetch volatile data when needed.

Follow-up questions then reuse state without re-asking.

Q8. How do you handle retries and failures?

Short answer: Per-call timeouts, retries with backoff for transient errors, circuit breakers and bulkheads per system, and partial answers that state what is unavailable, with handoff when key data is missing.

Writes, if any are added later, must be idempotent.

Q9. What if the document system is down but the LOS is up?

Short answer: Answer with the status from the LOS, say that document details are temporarily unavailable, and offer a callback or a human agent, instead of guessing the reason.

Track partial-answer rate as a metric.

Q10. How do you prevent the model from inventing a status or reason?

Short answer: Instruct it to use only the structured tool results, return explicit fields, validate the reply against them, forbid speculation, and test with golden conversations.

If data is missing or conflicting, escalate.

Q11. How do you handle the credit decision tool?

Short answer: It returns only the decision state and approved customer-safe reason codes, never scores or model internals, with stricter authorisation, step-up authentication and logging.

Disputes and adverse decisions go to humans, and wording is confirmed with compliance.

Q12. What are the prompt-injection risks and defences?

Short answer: Injected text can arrive in document names, agent notes or the customer message; defend with read-only tools, treating all text as data, output validation, approvals for any write and attack cases in the evals.

Do not give the status assistant tools that can change data.

Q13. How do you protect personal data?

Short answer: Return minimal masked fields, never send raw documents or full identifiers to the model, redact logs, limit retention and apply data-protection rules confirmed with compliance.

Data minimisation also reduces cost.

Q14. What do you log for audit and compliance?

Short answer: Customer and session, each tool call with redacted arguments, authorisation decisions, result summaries, model and prompt versions, the final answer and latency.

Logs are tamper-resistant and retained per policy.

Q15. How do you monitor the assistant in production?

Short answer: End-to-end traces across model and tools, tool latency and error rates, token cost, containment and escalation rates, and sampled human review of answer quality.

Alert on error spikes, cost spikes and breaker openings.

Q16. How do you test it before release?

Short answer: Golden conversations with fixtures for each system, negative and attack cases, fault injection for outages, and shadow mode alongside human agents.

Run the suite on every prompt, tool or model change.

Q17. How would you roll it out safely?

Short answer: Shadow mode with human review, a small pilot, gradual expansion with metrics, a kill switch and easy human handoff.

Review failures weekly and add them to the eval set.

Q18. Four narrow tools or one composite tool?

Short answer: Narrow tools are easier to authorise, test and reuse; a composite summary tool reduces round trips for the most common question; use both and compare with evals on accuracy and latency.

Authorisation is identical inside each.

Q19. How would you extend it to take actions, such as uploading a document or booking a callback?

Short answer: Add separate write tools with idempotency keys, explicit customer confirmation, stricter authorisation, approval policy where needed and extra audit, and test for injection.

Keep the read-only assistant stable and release writes incrementally.

Q20. How does this design survive a change of LOS vendor?

Short answer: Only the adapter behind the loan MCP server changes; the tool contracts, gateway policy and assistant remain the same.

Version tools if a contract must change.

Q21. Can the same tools support a staff copilot?

Short answer: Yes, with a different audience policy at the gateway granting more tools and different data scopes, reusing the same servers.

Each audience gets its own authorisation and audit.

Q22. How do you reduce latency and cost?

Short answer: Parallel tool calls, concise structured results, prompt caching of the stable prefix, a smaller model for simple classification and avoiding unnecessary tool calls.

Track cost per resolved conversation.

Q23. What would you do differently next time?

Short answer: Describe a real lesson, for example merging overly fine-grained tools after evals showed wrong tool choices, or adding injection tests earlier.

Specific lessons show real experience.

Q24. Which metrics prove the assistant is working?

Short answer: Answer accuracy against the data, containment without harm, escalation quality, handle time saved, customer satisfaction and cost per resolved query.

Do not optimise deflection at the expense of accuracy.
