1. What is the Model Context Protocol (MCP) and Why It Exists

The Model Context Protocol (MCP) is an open standard for connecting AI applications to tools, data and prompts. Before MCP, every AI application needed a custom integration for every system it wanted to use, which is an N times M problem. With MCP, a system is wrapped once as an MCP server and any MCP-compatible client can use it, turning the problem into N plus M. A common analogy is a universal port: one connector that many devices and accessories can share.

The architecture

Three roles matter. The host is the AI application the user works with, such as a chat app, an IDE or your own agent; it owns the model, the user relationship and the security policy. The host creates an MCP client for each server, and each client keeps a one-to-one stateful session with its MCP server. Servers expose capabilities from real systems: databases, SaaS APIs, file systems and internal services. Messages use JSON-RPC 2.0 over a transport: standard input and output for local servers, or Streamable HTTP for remote servers.

Features and benefits

MCP gives you reuse (write a server once), a consistent way to discover capabilities at run time, a growing ecosystem of ready-made servers, a clear separation of concerns (tool owners build servers, application teams build hosts), and portability between models and clients.

Problems and limits

MCP does not make tools safe by itself. Security is a real concern (prompt injection, malicious servers, over-broad permissions), tool descriptions and results consume context window, poorly designed tools confuse models, remote servers need authentication and operations, and the specification keeps evolving, so always check the current revision. MCP also standardises tool access, not agent behaviour: you still need good orchestration, evaluation and guardrails.

2. Protocol Primitives: Tools, Resources, Prompts, Sampling, Roots, Elicitation

MCP defines three server features and several client features. The key idea is who controls each one. Tools are functions the model decides to call, such as running a query or creating a ticket. Resources are read-only data identified by URIs that the application chooses to attach as context. Prompts are reusable, parameterised templates that the user selects, often as slash commands. On the client side, sampling lets a server ask the host to run a model completion, roots tell a server which directories it should stay within, and elicitation lets a server ask the user for missing input.

3. Lifecycle, Messages and Transports

An MCP session follows a clear lifecycle. The client sends initialize with the protocol version it supports and its capabilities; the server replies with its own version, capabilities and information; the client confirms with a notifications/initialized message. Both sides now know which features are available. The client lists tools, resources or prompts, calls or reads them, and may receive notifications such as tools/list_changed. Requests can report progress and be cancelled, and the session ends when the transport closes. Protocol versions are identified by date (for example 2025-06-18), so negotiating the version matters.

Transports

stdio launches the server as a subprocess and exchanges newline-delimited JSON-RPC messages over standard input and output; it is simple and ideal for local tools. Streamable HTTP uses HTTP POST for client messages and can stream responses and server messages; it is designed for remote servers, which must handle authentication, scaling and security. It replaced the earlier HTTP with Server-Sent Events transport.

// 1. client -> server
{ "jsonrpc": "2.0", "id": 1, "method": "initialize",
  "params": { "protocolVersion": "2025-06-18", "capabilities": { "roots": { "listChanged": true }, "sampling": {}, "elicitation": {} },
              "clientInfo": { "name": "my-host", "version": "1.0.0" } } }
// 2. server -> client
{ "jsonrpc": "2.0", "id": 1, "result": { "protocolVersion": "2025-06-18", "capabilities": { "tools": { "listChanged": true }, "resources": {} },
              "serverInfo": { "name": "tickets-server", "version": "0.3.0" } } }
// 3. client -> server (notification, no id)
{ "jsonrpc": "2.0", "method": "notifications/initialized" }
// 4. call a tool
{ "jsonrpc": "2.0", "id": 2, "method": "tools/call", "params": { "name": "search_tickets", "arguments": { "query": "refund", "limit": 5 } } }
// 5. result: tool failures use isError, not a JSON-RPC error
{ "jsonrpc": "2.0", "id": 2, "result": { "content": [ { "type": "text", "text": "3 tickets found: T-101, T-118, T-120" } ], "isError": false } }

4. Building an MCP Server (Python and C#)

Building a server has four stages. Design the tools first: think in user tasks, keep the set small and write descriptions the model can act on. Implement with an official SDK, which handles the protocol and transports so you write only the tool logic. Test with the MCP Inspector (npx @modelcontextprotocol/inspector), unit tests and evals with a real model. Package and deploy as a local command or as a remote HTTPS service behind authentication.

# server.py - Python SDK (FastMCP). Run: python server.py   |  inspect: npx @modelcontextprotocol/inspector python server.py
from mcp.server.fastmcp import FastMCP
mcp = FastMCP("tickets")

@mcp.tool()
def search_tickets(query: str, status: str = "open", limit: int = 5) -> str:
    """Search support tickets. Use for questions about existing tickets. Does not modify anything."""
    rows = db.search(query, status, min(limit, 25))                 # hard cap protects the context window
    return "\n".join(f"{r.id}: {r.title} [{r.status}]" for r in rows) or "No tickets found."

@mcp.tool()
def close_ticket(ticket_id: str, resolution: str) -> str:
    """Close one ticket with a resolution note. Destructive: only call after the user confirms."""
    if not db.exists(ticket_id):
        raise ValueError(f"Unknown ticket {ticket_id}. Use search_tickets to find valid ids.")   # surfaces as isError
    db.close(ticket_id, resolution); return f"Closed {ticket_id}"

@mcp.resource("ticket://{ticket_id}")
def ticket_resource(ticket_id: str) -> str:
    """Full text of one ticket."""
    return db.get(ticket_id).as_text()

@mcp.prompt()
def triage(ticket_id: str) -> str:
    return f"Read ticket://{ticket_id}, classify severity (P1-P4), and propose next steps."

if __name__ == "__main__":
    mcp.run(transport="stdio")           # use transport="streamable-http" for a remote server

5. Building a Client and Integrating with an Agent

A host integrates MCP by running a client per server. The flow has four steps. Connect and discover: launch or connect to the server, initialise the session and list its tools. Expose to the model: convert each MCP tool into the model provider's function-calling format (name, description and the input schema map directly) and namespace names by server. Route the call: when the model requests a tool, apply user approval and policy, then send tools/call to the right server. Return the result: trim it, keep the error flag and send it back to the model as a tool result, treating the content as untrusted data.

# Minimal MCP-aware agent: discover tools from a stdio server, give them to Claude, route tool calls back
import asyncio, anthropic
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

llm = anthropic.Anthropic()
MODEL = "claude-sonnet-5-5"

async def main(question: str):
    params = StdioServerParameters(command="python", args=["server.py"])
    async with stdio_client(params) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()                                        # handshake + capability negotiation
            listed = await session.list_tools()
            tools = [{"name": t.name, "description": t.description or "", "input_schema": t.inputSchema} for t in listed.tools]

            messages = [{"role": "user", "content": question}]
            for _ in range(8):                                                # always cap the loop
                resp = llm.messages.create(model=MODEL, max_tokens=1024, tools=tools, messages=messages)
                if resp.stop_reason != "tool_use":
                    return "".join(b.text for b in resp.content if b.type == "text")
                messages.append({"role": "assistant", "content": resp.content})
                results = []
                for block in resp.content:
                    if block.type == "tool_use":
                        if not policy_allows(block.name, block.input):         # host-level policy / user approval
                            results.append({"type": "tool_result", "tool_use_id": block.id, "content": "Blocked by policy", "is_error": True}); continue
                        out = await session.call_tool(block.name, block.input)
                        text = "".join(c.text for c in out.content if c.type == "text")[:4000]
                        results.append({"type": "tool_result", "tool_use_id": block.id, "content": text, "is_error": bool(out.isError)})
                messages.append({"role": "user", "content": results})

print(asyncio.run(main("Which tickets mention refunds?")))

6. Design Principles for MCP Servers and Tools

Good MCP design is mostly good tool design for a model. Make tools task-oriented: one tool that completes a user task beats six thin wrappers over API endpoints. Write precise schemas with enums, ranges and descriptions that say when to use each argument, and add an output schema when results are structured. Return small, relevant results, paginate or give links instead of dumping data, and make error messages instructive so the model can recover. Be safe by design: idempotent operations, confirmation for destructive ones and honest annotations, with real enforcement on the server. Finally, operate the server: log calls, measure latency and errors, rate limit, version tools and document changes.

7. Security and Authorization

Because MCP connects models to real systems, security needs a clear threat model. Prompt injection is the central threat: tool results and resource content are untrusted and may contain instructions that hijack the model, and combining tools (read private data plus send a message) can create exfiltration paths. Tool poisoning hides malicious instructions in tool descriptions, and a rug pull changes definitions after a user approved them. Remote servers use OAuth-based authorization: the server acts as a resource server, validates tokens, audiences and scopes on every request, and must never pass client tokens through to downstream APIs, which is the confused deputy problem. Local servers run code with the user permissions and need consent, sandboxing and review.

ThreatMitigation
Prompt injection via tool outputTreat output as data, least privilege, human approval for risky actions, separate read and send capabilities
Tool poisoning, rug pullsAllow-list and pin servers, review and hash tool definitions, alert on changes
Excessive scopesMinimal OAuth scopes, short-lived audience-bound tokens
Token passthrough, confused deputyValidate audience, use on-behalf-of token exchange for downstream calls
Malicious local server or commandShow the exact command, require consent, sandbox, prefer vetted packages
SSRF and data exfiltrationEgress allow-lists, block internal addresses, log and rate limit
No accountabilityPer-user identity on every call and full audit logs
# Host-side policy gate in front of every tools/call
SENSITIVE = {"close_ticket", "send_email", "handle_refund_request"}
def policy_allows(server, tool, args, user):
    if (server, tool) not in ALLOW_LIST:                          # only approved, pinned tools
        return False
    if tool in SENSITIVE:
        return ui.confirm(user, f"Allow {server}.{tool} with {args}?")   # human approval with the real arguments shown
    return True

# Server-side: validate the token on EVERY request (remote server)
def authenticate(request):
    claims = jwt.decode(bearer(request), key=JWKS, audience="https://mcp.example.com/crm", algorithms=["RS256"])   # audience must be THIS server
    require_scopes(claims, ["tickets:read"])
    return claims["sub"]          # use the user identity for downstream authorisation; never forward this token
Authorization requirements are part of the specification and have changed between revisions. Read the authorization section of the current MCP specification before implementing it.

8. Enterprise Architecture and Equivalent Orchestration Standards

At enterprise scale you manage many servers, clients and teams. An MCP gateway centralises authentication, authorisation, policy, rate limiting, logging and routing, and hides server details from clients. A registry or catalogue lists approved, reviewed and versioned servers with owners, preventing shadow integrations. Observability traces every model request and tool call with user identity, arguments and outcome, and OpenTelemetry-based conventions help standardise it. Compose these with orchestration frameworks (LangGraph, Semantic Kernel, Microsoft Agent Framework, vendor agent SDKs) that add state, graphs and approvals.

Equivalent and complementary standards

MCP is not the only way to connect tools. Native function calling with JSON Schema is supported by all major model APIs; OpenAPI-described tools let an agent call REST APIs; frameworks have their own plugin or tool models. Agent2Agent (A2A) is a separate open protocol for independent agents to discover each other through agent cards and exchange tasks. A useful rule of thumb is that MCP connects an agent to tools and data, while A2A connects an agent to other agents. Design tools so they are portable: business logic in a service, thin adapters for MCP, OpenAPI and function calling.

10. Interview Q&A: MCP and AI Orchestration

Q1. What is MCP and what problem does it solve?

Short answer: An open protocol for connecting AI applications to tools, data and prompts, replacing custom N by M integrations with servers written once and reused by any compatible client.

It standardises discovery and invocation of capabilities, not agent behaviour.

Q2. Explain the host, client and server roles.

Short answer: The host is the AI application that owns the model and security policy, it creates one client per server, and each client keeps a stateful session with one server that exposes capabilities.

Trust decisions and user consent live in the host.

Q3. What are tools, resources and prompts?

Short answer: Tools are model-controlled functions, resources are application-controlled read-only data identified by URIs, and prompts are user-controlled parameterised templates.

Who controls each one is the key distinction.

Q4. What are sampling, roots and elicitation?

Short answer: Client features: sampling lets a server request a model completion through the host, roots declare the directories a server should stay in, and elicitation lets a server ask the user for input.

All keep the host and user in control.

Q5. Which transports does MCP support?

Short answer: stdio for local servers launched as subprocesses and Streamable HTTP for remote servers, with the older HTTP and SSE transport superseded.

Messages are JSON-RPC 2.0 on both.

Q6. Describe the session lifecycle.

Short answer: Initialize with version and capability negotiation, an initialized notification, discovery with list methods, invocation with call and read methods, and shutdown.

Notifications such as list_changed, progress and cancellation can occur throughout.

Q7. How are tool errors reported?

Short answer: A failing tool returns a normal result with isError true and a message the model can read, while protocol-level problems use JSON-RPC errors.

Make error text instructive so the model can recover.

Q8. How do you design good MCP tools?

Short answer: Task-oriented tools with precise schemas, compact and paginated outputs, instructive errors, idempotency and confirmation for destructive actions.

Treat descriptions like prompts and test them.

Q9. What is structured tool output?

Short answer: A tool can declare an output schema and return structured content alongside text so clients can validate and parse results reliably.

It arrived in later spec revisions, so check the current version.

Q10. How do you test an MCP server?

Short answer: Use the MCP Inspector for manual exploration, unit tests for tool logic and schemas, and evals with a real model for tool selection and argument accuracy.

Test security cases such as injection and unauthorised calls too.

Q11. How do you integrate MCP tools into an agent?

Short answer: Connect and list tools, convert them to the model provider function-calling format, route tool calls through policy and approval to the right server, then return trimmed results.

Namespace tool names by server.

Q12. Local or remote MCP server?

Short answer: Local stdio servers are simple and run with user permissions; remote servers centralise credentials, updates and governance but need authentication, scaling and monitoring.

Enterprises usually prefer remote servers behind a gateway.

Q13. What are the main MCP security risks?

Short answer: Prompt injection through tool output, tool poisoning and rug pulls, over-broad scopes, confused deputy and token passthrough, and malicious local servers.

Mitigate with least privilege, approvals, allow-lists, audience-bound tokens and sandboxing.

Q14. What is tool poisoning?

Short answer: Hiding malicious instructions in tool metadata that the model reads, or silently changing tool definitions after approval.

Pin versions, review definitions and alert on changes.

Q15. How is a remote MCP server authorised?

Short answer: With OAuth-based authorization: the client gets an access token for that server, and the server validates the token, audience and scopes on every request.

Follow the authorization section of the current specification.

Q16. What is the token passthrough anti-pattern?

Short answer: Accepting a token that was not issued for the MCP server and forwarding it to a downstream API, which breaks audience validation and accountability.

Use a token exchange or separate downstream credentials instead.

Q17. What is a confused deputy problem here?

Short answer: A server with more authority than the user performs actions on the user behalf without proper checks, letting a user or attacker exceed their rights.

Always authorise against the user identity.

Q18. Why use an MCP gateway and registry?

Short answer: A gateway centralises authentication, policy, rate limits, routing and audit; a registry lists approved, versioned and owned servers.

Together they give governance and prevent shadow integrations.

Q19. MCP versus A2A?

Short answer: MCP connects an agent to tools and data; A2A lets independent agents discover each other and exchange tasks.

They are complementary, not competing.

Q20. What are equivalent orchestration standards to MCP?

Short answer: Native function calling with JSON Schema, OpenAPI-described tools, framework plugin models and A2A for agent collaboration.

Keep business logic in a service with thin adapters so tools stay portable.

Q21. How do you handle large or long-running tool calls?

Short answer: Paginate or return resource links, send progress notifications, support cancellation, set timeouts and make operations idempotent.

Newer spec revisions add asynchronous task patterns, so check the current spec.

Q22. What do you monitor on MCP servers?

Short answer: Call counts, latency, error rates, usage per user and client, security events and traces linking model requests to tool calls.

Redact sensitive arguments in logs.

Q23. How would you describe your MCP experience in an interview?

Short answer: Present a real project with design decisions, security measures, evals and trade-offs, using a situation, action and result structure and only claiming what you can defend.

Mention failures and what you changed, which shows depth.
