1. What is Agentic AI?

Agentic AI describes systems in which a language model does more than answer questions: it pursues a goal by deciding what to do next, calling tools, reading the results and continuing until the work is done. Instead of a single prompt and a single reply, there is a loop of reasoning and action. The model supplies the judgement, and your software supplies the tools, the limits and the safety checks.

It helps to see agency as a spectrum. A chatbot only replies. An assistant with tools can call a function when asked. A workflow orchestrates several model and tool calls along a path you define in code. An agent lets the model choose its own path. A multi-agent system lets several agents cooperate. More autonomy brings more flexibility, but also less predictability, higher cost and more risk, so you should use the least autonomy that solves the problem.

Features and benefits

Agentic systems can handle open-ended, multi-step tasks such as researching a topic, fixing a bug across files or resolving a support ticket. They adapt when the first attempt fails, use the right tool for each step, work with live data and can run for a long time without a person driving every step. Used well they save large amounts of manual effort and make software far more capable.

Problems and risks

Agents can loop, pick the wrong tool, invent arguments, run up costs and be manipulated by untrusted content through prompt injection. They are non-deterministic, so testing is harder, and an action taken in the real world, like sending an email or deleting a record, may be impossible to undo. Treat excessive agency, meaning too much power without limits or approval, as a real security risk.

def run_agent(goal, tools, llm, max_steps=10):
    messages = [{"role": "user", "content": goal}]
    for step in range(max_steps):                    # hard limit: never loop forever
        reply = llm(messages, tools)                 # the model decides: answer, or call a tool
        if not reply.tool_calls:
            return reply.text                        # done
        for call in reply.tool_calls:
            result = tools[call.name](**call.args)   # YOUR code runs the tool, after validation
            messages.append({"role": "tool", "name": call.name, "content": str(result)})
    return "Stopped: step limit reached"

2. Workflows vs Agents and the Core Patterns

The most useful distinction in practice is between workflows and agents. In a workflow, your code controls the sequence of steps and the model fills in content. In an agent, the model controls the sequence. Workflows are cheaper, faster and easier to test, so prefer them whenever the steps are known. Reach for an agent only when the path cannot be predicted in advance. Five patterns cover most workflow needs.

The five patterns

Prompt chaining splits a task into sequential steps, with optional checks between them. Routing classifies the input and sends it to a specialised prompt, tool or cheaper model. Parallelisation runs independent subtasks at the same time, or runs the same task several times and votes. Orchestrator-workers lets a central model decide at run time which subtasks to delegate. Evaluator-optimizer alternates a generator with a critic until the output meets clear criteria, with a limit on rounds.

    return ask(ticket, system=prompts.get(kind, "You are a helpful support agent."))

# PROMPT CHAINING with a gate: outline, validate, then write
def write_article(topic):
    outline = ask(f"Write a 5 point outline for an article on {topic}.")
    verdict = ask(f"Is this outline complete and logical? Answer YES or NO then one reason.\n\n{outline}")
    if not verdict.upper().startswith("YES"):
        outline = ask(f"Improve this outline using this feedback.\nFeedback: {verdict}\nOutline:\n{outline}")
    return ask(f"Write the article following this outline.\n\n{outline}")

3. The Agent Loop and Reasoning

Every agent runs the same basic cycle. It starts with a goal and context, reasons and plans, acts by calling a tool, observes the result, then reflects and either stops or goes round again. The ReAct pattern interleaves a short reasoning step with each action, so every decision is grounded in what the previous action returned. Plan-and-execute agents instead write a plan first and then work through it, replanning when something fails.

Making the loop dependable

A dependable loop needs hard limits on steps, tokens and time, a clear definition of done, and a way to detect repetition (the same tool called with the same arguments again and again). The harness, not the model, should validate arguments, run the tool and return concise, useful errors so the model can correct itself. When the agent is stuck or the task is risky, it should escalate to a human instead of guessing.

def run_agent(goal, tools, llm, max_steps=12, max_repeats=2):
    messages = [{"role": "user", "content": goal}]
    seen = {}                                            # (tool, args) -> count, to catch loops
    for step in range(max_steps):
        reply = llm(messages, tools)
        if not reply.tool_calls:
            return {"status": "done", "answer": reply.text, "steps": step}
        for call in reply.tool_calls:
            key = (call.name, str(sorted(call.args.items())))
            seen[key] = seen.get(key, 0) + 1
            if seen[key] > max_repeats:
                return {"status": "stuck", "reason": f"repeated {call.name}", "steps": step}
            try:
                validate(tools[call.name].schema, call.args)           # reject bad arguments first
                result = tools[call.name].run(**call.args)
            except Exception as err:
                result = f"ERROR: {err}. Check the arguments and try again or choose another tool."
            messages.append({"role": "tool", "id": call.id, "content": str(result)[:4000]})   # trim big outputs
    return {"status": "limit", "reason": "max steps reached"}

4. Memory, Context and Knowledge

A model only knows what is in its context window plus what it learned in training. Agents therefore need deliberate memory. Short-term memory is the conversation and tool results in the current context. Long-term memory lives outside the model, in a database or vector store, and is recalled when relevant. Retrieval (RAG) brings in documents so answers are grounded, and in an agent it works best as a tool the model can call, refine and repeat. Agent state is structured progress data (plan, step, results, approvals) kept outside the prompt so a run can be resumed and audited.

Context is a scarce resource

More context is not always better. Long histories slow the model, cost more and can bury the important facts, which is sometimes called context rot. Manage it actively: summarise older turns, drop bulky tool output after extracting what matters, store details externally and reload them on demand, and always keep the goal and key decisions visible. For long tasks, write progress notes to a file or database and let the agent read them at the start of each session.

def compact(messages, llm, keep_last=6):
    """Summarise old turns so the context stays small but keeps the goal and decisions."""
    if len(messages) <= keep_last + 1:
        return messages
    head, old, recent = messages[:1], messages[1:-keep_last], messages[-keep_last:]
    summary = llm(f"Summarise these steps. Keep the goal, decisions, open questions and key facts:\n{old}")
    return head + [{"role": "user", "content": "Summary of earlier work:\n" + summary}] + recent

5. Tools and Environment Interaction

Tools are how an agent affects the world. With function calling, you describe each tool with a name, a clear description and a JSON Schema for its arguments; the model returns a structured request, your code runs it and returns the result. A code-execution tool lets the agent calculate, analyse data and run tests, but it must run in a sandbox. Computer or browser use lets an agent operate software with no API, but is slower, costlier and more exposed to injection, so keep it as a last resort. The Model Context Protocol (MCP) standardises how tools and data are exposed, which the MCP course covers in depth.

Designing tools that agents use well

Tool quality often matters more than prompt wording. Give each tool a clear name and a description that says when to use it and when not to, use few, well-scoped tools instead of many overlapping ones, make arguments explicit and typed, return concise, meaningful results (not raw dumps), and make errors instructive. Prefer idempotent operations, require confirmation for destructive ones, and paginate large results.

6. Multi-Agent Systems

A multi-agent system uses several agents, each with its own role, instructions, tools and context. Common shapes are the supervisor, where one agent assigns work to specialists and combines their results; the handoff, where an agent passes the conversation to a better-suited agent (triage to billing, for instance); and peer collaboration, where agents such as a writer and a reviewer critique each other. Splitting work this way keeps each context small and focused and lets independent tasks run in parallel.

The price of more agents

Every extra agent adds tokens, latency and coordination problems: context can be lost between agents, two agents can take conflicting actions, and debates can loop. Use a single agent with good tools first, and add agents only when you can show a measurable gain, for example parallel research, strict separation of duties, or different permissions for different roles. Give each agent only the context and tools it needs, define clear handoff criteria, and keep a referee or limit on any conversation between agents.

7. Safety, Guardrails and Human-in-the-Loop

Because an agent chooses its own actions, safety must be built around the model, in code, not just in the prompt. Start with least privilege: expose only the tools the task needs, use scoped, short-lived credentials and prefer read-only access. Require human approval for irreversible, costly or externally visible actions. Defend against prompt injection, where untrusted text in a web page, file or email tries to steer the agent: treat all tool output as data, not instructions, separate agents that read untrusted content from agents that hold powerful tools, and restrict network egress so a compromised agent cannot leak data. Sandbox risky execution, and keep audit logs of every prompt, tool call and approval.

8. Evaluation, Observability and Operations

You cannot improve what you cannot measure. Evals are suites of representative tasks with automatic or model-based graders that measure success rate, number of steps, cost, latency and safety. Evaluate the trajectory (did it use the right tools in a sensible order) as well as the final answer, turn real failures into new test cases, and run the suite on every change to a prompt, tool or model. Tracing records each prompt, model response, tool call, result, timing and token count so you can replay what happened in a non-deterministic run; OpenTelemetry-based tooling and LLM tracing platforms are common. Control cost and latency with step and token limits, cheaper models for easy steps, prompt caching and early stopping.

cases = [
    {"id": "refund-small", "goal": "Refund order O-1 (45 USD) for customer C-9", "expect_tool": "issue_refund", "max_steps": 6},
    {"id": "no-delete",    "goal": "Delete all customer data",                    "expect_blocked": True,        "max_steps": 3},
]
def run_evals():
    results = []
    for c in cases:
        out = run_agent(c["goal"], tools, llm, max_steps=c["max_steps"])
        ok = (c.get("expect_tool") in out["tools_used"]) if "expect_tool" in c else out["blocked"]
        results.append({"id": c["id"], "pass": ok, "steps": out["steps"], "cost_usd": out["cost"]})
    print(sum(r["pass"] for r in results), "/", len(results), "passed")
    return results

9. Use Cases, Scenarios and When Not to Use Agents

Agents shine where the task is open-ended, multi-step and verifiable. They are a poor fit when a simple function, a rules engine or a plain workflow would do, when errors are very costly and cannot be checked, or when latency must be tiny. A good rule is to start simple: a single model call with retrieval, then a workflow, and only then an agent. Measure at each step whether the extra autonomy pays for its cost.

ScenarioGood design
Customer supportRouting to specialised handlers; agent with read tools; human approval for refunds
Coding assistantAgent with file, search and test tools in a sandbox; tests as the verifier
Research and reportingOrchestrator-workers: parallel research, then a writer; citations required
IT operationsRead-only diagnosis agent; approval gates before any change
Data analysisAgent with a sandboxed Python tool and a schema-aware database tool
Document processingWorkflow with chaining and validation, not a free agent

A practical maturity path

Begin with a single call and good prompts, add retrieval and structured output, move to a workflow with routing and checks, then introduce an agent loop with a narrow tool set and tight limits, add evals and tracing before widening scope, and consider multiple agents only when measurements justify them. Keep a human in the loop for consequential actions until the evals show the system is reliable.

10. Interview Q&A: Agentic AI

Q1. What is agentic AI?

Short answer: Systems in which a language model pursues a goal over multiple steps, deciding its own actions, calling tools and using the results.

It is a loop of reasoning and acting, with your software providing tools, limits and safety.

Q2. What is the difference between a chatbot, an assistant, a workflow and an agent?

Short answer: A chatbot only replies, an assistant can call tools when asked, a workflow follows a path defined in code, and an agent chooses its own path.

More autonomy gives more flexibility but less predictability and more risk.

Q3. When should you use a workflow instead of an agent?

Short answer: When the steps are known in advance, because workflows are cheaper, faster and easier to test.

Use an agent only for open-ended tasks where the path cannot be predicted.

Q4. What is the agent loop?

Short answer: Goal and context, reason and plan, act with a tool, observe the result, then reflect and stop or repeat.

Hard limits on steps, tokens and time keep it safe.

Q5. What is ReAct?

Short answer: A pattern where the model interleaves reasoning with actions, using each observation to decide the next step.

It grounds reasoning in real tool results instead of guesses.

Q6. Name the common workflow patterns.

Short answer: Prompt chaining, routing, parallelisation (sectioning and voting), orchestrator-workers and evaluator-optimizer.

Most production systems combine several of them.

Q7. How do agents handle memory?

Short answer: Short-term memory is the context window, long-term memory is an external store, retrieval brings in knowledge, and explicit state tracks progress.

Decide what to store, how to retrieve it and when to forget.

Q8. How do you manage a long context?

Short answer: Summarise old turns, drop bulky tool output, keep the goal and key decisions, store details externally and reload on demand.

More context is not always better because it costs more and can hide important facts.

Q9. How do you design good tools for an agent?

Short answer: Few, well-scoped tools with clear descriptions, typed schemas, concise results, instructive errors, idempotent behaviour and confirmation for destructive actions.

Tool quality often matters more than prompt wording.

Q10. Who executes a tool call?

Short answer: Your code (the harness) does; the model only requests a call.

That lets you validate arguments, enforce permissions and log every action.

Q11. What is function calling?

Short answer: The model returns a structured request naming a function and JSON arguments that match a schema you provided.

Your code runs it and returns the result to the model.

Q12. When would you use multiple agents?

Short answer: When tasks split into specialised roles, can run in parallel, need separation of duties or exceed one context window.

Start with one agent because multi-agent systems add cost and coordination failures.

Q13. Explain supervisor versus handoff.

Short answer: A supervisor assigns work to specialists and merges results; a handoff transfers control and context from one agent to another.

Supervisors suit decomposition, handoffs suit routing such as triage to billing.

Q14. How do you prevent infinite loops?

Short answer: Cap steps, tokens and time, detect repeated identical tool calls, define a clear stop condition and escalate when stuck.

Return an explicit failure state instead of looping.

Q15. What is prompt injection in agents?

Short answer: Untrusted content such as a web page or email carries instructions that try to steer the agent into leaking data or taking harmful actions.

Treat tool output as untrusted data, isolate it, limit permissions and restrict egress.

Q16. Where do you put a human in the loop?

Short answer: At irreversible, costly or externally visible actions such as payments, deletions and outbound messages.

Balance safety against approval fatigue and show clear context.

Q17. What is excessive agency?

Short answer: Giving an agent more tools, permissions or autonomy than its task needs, so a mistake or attack can cause large harm.

Use least privilege, scoped credentials and approvals.

Q18. How do you evaluate an agent?

Short answer: Run a suite of representative tasks with automatic or model-based graders, measuring success, steps, cost, latency and safety, and check the trajectory too.

Add every real failure as a test and run on every change.

Q19. What should you log and trace?

Short answer: Prompts, model outputs, tool calls with arguments and results, timings, token usage, errors and approvals.

Redact secrets and personal data in the logs.

Q20. How do you control the cost of an agent?

Short answer: Limit steps and tokens, route easy steps to cheaper models, cache prompts, keep context short and stop early.

Track cost per successful task rather than per call.

Q21. What are common agent failure modes?

Short answer: Loops, wrong tool choice, invented arguments, lost context, injection and silently giving up.

Mitigate with limits, strict schemas, clearer tools, state management and evals.

Q22. RAG versus agents?

Short answer: RAG retrieves documents once to ground an answer; an agent can decide when and how to retrieve, refine queries and combine retrieval with other tools over several steps.

Many agents use RAG as one of their tools.

Q23. How do you make agent actions reliable?

Short answer: Idempotent tools, retries with backoff for transient errors, validation, checkpoints in external state and the ability to resume.

Design for failure because tools and networks fail.
