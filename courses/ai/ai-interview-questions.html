1. What AI and Agent Interviews Look Like and How to Answer

Interviews for AI engineering and agent roles usually combine five kinds of questions: fundamentals (how models, context and retrieval work), agent and MCP concepts (loops, tools, protocols), system design (design an agent or an integration platform), coding (implement a loop, a registry, a retry wrapper) and behavioural or experience questions (tell me about a system you built). Strong candidates answer in a repeatable structure and always bring up safety, evaluation and cost without being asked.

A five-step answer framework

First clarify the problem: users, goals, scale, how costly a wrong answer is and which data and tools are involved. Second, choose the architecture with the least autonomy that works (single call, retrieval, workflow, agent, multi-agent) and justify each piece. Third, define the tools, data and integration, including schemas, permissions and how MCP or APIs connect them. Fourth, cover safety, quality and operations: guardrails, human approval, injection defence, evals, tracing and cost controls. Fifth, close with trade-offs and evolution: alternatives, remaining risks and how you would measure and improve.

Never claim experience you cannot explain in detail. Interviewers probe with "why that choice?" and "what went wrong?", and honest, specific answers score higher than polished but vague ones.

2. LLM Fundamentals Interviewers Check

Even agent-focused interviews begin with fundamentals, because every agent design decision rests on them. The context window limits the tokens per request and drives cost and latency, so everything an agent needs must fit and be managed. Sampling parameters such as temperature control randomness, and low values suit tool use and extraction. RAG retrieves relevant content at query time to ground answers in current, private data. Fine-tuning changes weights for consistent style or specialised behaviour; try prompting and RAG first. Hallucination is confident but wrong output, reduced by grounding, citations, schemas and verification.

3. System Design Problems with Solutions

System design questions ask you to design an agent or an integration platform end to end. Use the five-step framework and keep the design as simple as the problem allows. Here are five frequent problems with a solution outline for each; open the diagram popups for follow-up questions.

Problem 1: customer support agent

Requirements: answer order questions, handle small refunds, escalate the rest, respect privacy. Solution: a router classifies intent; an agent with narrow read tools and a refund tool behind a policy layer (ownership check, amount limit, per-conversation cap); an approval step above the threshold; conversation state in a database; tracing; evals with wrong-user and injection cases; escalation with a summary. Key point: limits live in code, not in the prompt.

Problem 2: coding agent

Solution: sandboxed tools for search, read, edit and run tests on a scratch branch; loop until tests pass or a limit is reached; tests and linters as the objective verifier; repository roots to limit scope; context management for large repos (search first, read only what is needed); human review before merge.

Problem 3: enterprise knowledge assistant

Solution: MCP servers per system (documents, tickets, wiki) behind a gateway; user identity propagated to every retrieval and tool call; results filtered by the user permissions at the source; retrieval with reranking and citations; audit logs. Key point: never rely on the prompt for access control.

Problem 4: multi-tenant MCP gateway

Solution: OAuth authentication, tenant and user mapped to policy, a registry of approved and versioned servers, routing, per-tenant rate limits and quotas, approval rules for write tools, audit logging, isolation between tenants, health checks and metrics. Never pass tokens through to downstream systems; use token exchange.

Problem 5: research agent

Solution: an orchestrator plans sub-questions, worker agents search and read in parallel with a small tool set, a verifier checks claims against the sources, and a writer produces a cited report; budgets for steps, tokens and time; source-quality checks.

4. Coding Exercises with Solutions

Coding rounds usually ask you to implement small, realistic pieces without a framework. Practise these five until you can write them cleanly and explain every choice.

Exercise 1: agent loop with limits

What they look for: correct message history, executing every tool call, returning errors to the model, a step limit, repeat detection and clean termination.

def run_agent(goal, llm, registry, max_steps=10, max_repeats=2):
    messages, seen = [{"role": "user", "content": goal}], {}
    for step in range(max_steps):
        resp = llm(messages, registry.schemas())
        if not resp.tool_calls:
            return {"status": "done", "answer": resp.text}
        messages.append(resp.as_message())
        results = []
        for call in resp.tool_calls:
            key = (call.name, json.dumps(call.args, sort_keys=True))
            seen[key] = seen.get(key, 0) + 1
            if seen[key] > max_repeats:
                return {"status": "stuck", "reason": f"repeated call to {call.name}"}
            results.append(registry.execute(call))               # never raises: returns an error result instead
        messages.append({"role": "user", "content": results})
    return {"status": "limit"}

Exercise 2: tool registry with validation

import jsonschema, inspect
class Registry:
    def __init__(self): self.tools = {}
    def register(self, fn, schema, description):
        self.tools[fn.__name__] = {"fn": fn, "schema": schema, "description": description}
        return fn
    def schemas(self):
        return [{"name": n, "description": t["description"], "input_schema": t["schema"]} for n, t in self.tools.items()]
    def execute(self, call):
        tool = self.tools.get(call.name)
        if not tool:
            return {"type": "tool_result", "tool_use_id": call.id, "content": f"Unknown tool {call.name}", "is_error": True}
        try:
            jsonschema.validate(call.args, tool["schema"])                      # validate BEFORE running
            return {"type": "tool_result", "tool_use_id": call.id, "content": str(tool["fn"](**call.args))}
        except Exception as err:
            return {"type": "tool_result", "tool_use_id": call.id, "content": f"Error: {err}", "is_error": True}

Exercise 3: retry with exponential backoff, jitter and a deadline

import time, random
def retry(fn, attempts=5, base=0.4, deadline_s=20, transient=(TimeoutError, ConnectionError)):
    start = time.monotonic()
    for i in range(attempts):
        try:
            return fn()
        except transient:
            delay = base * (2 ** i) + random.uniform(0, base)
            if i == attempts - 1 or time.monotonic() - start + delay > deadline_s:
                raise                                          # out of attempts or time
            time.sleep(delay)
# Discussion: retry only transient errors; writes need idempotency keys; honour Retry-After headers.

Exercise 4: context compaction

def compact(messages, summarise, keep_last=6):
    if len(messages) <= keep_last + 1:
        return messages
    cut = len(messages) - keep_last
    while cut < len(messages) and has_tool_result(messages[cut]):      # never split a tool_use / tool_result pair
        cut -= 1
    old, recent = messages[1:cut], messages[cut:]
    summary = summarise(old, keep=["goal", "decisions", "constraints", "open questions"])
    return [messages[0], {"role": "user", "content": "Summary of earlier work:\n" + summary}] + recent

Scenario questions test judgement under realistic problems. A good answer follows a method: look at the trace first, form a hypothesis, make one change, and verify with evals. Here are five common scenarios and how to handle them.

Experience questions probe whether you have really built and operated these systems. Prepare three stories with a situation, your actions and measurable results, plus one failure with what you learned. Below are common prompts and the points a strong answer includes.

Sample answer outline: experience with MCP

Situation: several teams had each built their own integrations for internal copilots, which duplicated work and had inconsistent security. Actions: I designed a small set of task-oriented MCP servers on top of a shared service layer, added a gateway with OAuth, per-user identity, approvals for write tools and audit logging, tested tools with the Inspector and an eval suite for tool selection and injection cases, and documented tool design guidelines. Results: fewer duplicate integrations, higher tool-selection accuracy after rewriting descriptions, and a complete audit trail. Lesson: an early version exposed too many fine-grained tools and the model chose poorly, so we merged them into workflow-level tools.

Replace this outline with your own real project. Specific numbers, failures and trade-offs you can explain are far more convincing than a generic story.

7. Interview Q&A: Agentic AI, Agents and MCP (Questions with Solutions)

Q1. [Concepts] What is an AI agent and how does it differ from a chatbot?

Short answer: An agent pursues a goal over several steps by choosing actions, calling tools and using the results, while a chatbot only replies to messages.

Autonomy and tool use are the difference, not the underlying model.

Q2. [Concepts] Workflow or agent: how do you decide?

Short answer: Use a workflow when the steps are known in advance because it is cheaper, faster and easier to test; use an agent when the path cannot be predicted.

Start simple and add autonomy only when measurements justify it.

Q3. [Concepts] Explain the agent loop.

Short answer: Goal and context, reason and plan, act with a tool, observe the result, reflect, then stop or repeat, bounded by limits.

The harness executes tools and enforces step, token and time limits.

Q4. [Concepts] What is ReAct?

Short answer: Interleaving short reasoning with tool actions so each decision uses the latest observation.

Plan-and-execute is the alternative that writes a plan first.

Q5. [Concepts] What are the common workflow patterns?

Short answer: Prompt chaining, routing, parallelisation, orchestrator-workers and evaluator-optimizer.

Name one use case for each.

Q6. [Concepts] When would you use multiple agents?

Short answer: For specialised roles, parallel work, separation of duties or when one context cannot hold the task, accepting extra cost and coordination risk.

Start with one agent and split only with evidence.

Q7. [Tools] How does tool calling work?

Short answer: You send tool schemas, the model returns a structured request, your code validates and runs it, and you send the result back until the model finishes.

The model never executes anything itself.

Q8. [Tools] How do you design a good tool?

Short answer: Task-oriented, one clear purpose, precise schema, compact output, instructive errors, idempotent behaviour and confirmation for destructive actions.

Treat the description like a prompt.

Q9. [Tools] Why should you validate tool arguments?

Short answer: Model output is untrusted and can be wrong or malicious, so arguments must match the schema and policy before execution.

Return clear errors so the model can correct itself.

Q10. [Memory] How do you handle memory and context?

Short answer: Short-term in the context window, long-term in an external store, retrieval for knowledge, explicit state for progress, with summarisation and trimming to keep context useful.

More context is not always better.

Q11. [Memory] How do you resume a long-running agent after a crash?

Short answer: Checkpoint messages and state in a durable database after each step, keep workers stateless and make side effects idempotent.

Use idempotency keys for writes.

Q12. [MCP] What is MCP and what problem does it solve?

Short answer: An open protocol connecting AI apps to tools, data and prompts, replacing N by M custom integrations with reusable servers.

It standardises discovery and invocation, not agent behaviour.

Q13. [MCP] Explain host, client and server.

Short answer: The host owns the model and policy, creates one client per server, and each client keeps a stateful session with one server exposing capabilities.

Consent and security decisions live in the host.

Q14. [MCP] Tools vs resources vs prompts?

Short answer: Tools are model-controlled functions, resources are application-controlled read-only data by URI, prompts are user-controlled templates.

Who controls each one is the key distinction.

Q15. [MCP] Which transports exist and when do you use each?

Short answer: stdio for local subprocess servers and Streamable HTTP for remote servers needing authentication and scaling.

Both carry JSON-RPC 2.0 messages.

Q16. [MCP] How would you secure a remote MCP server?

Short answer: OAuth-based authorization with token validation, audience and scope checks on every request, no token passthrough, rate limits, audit logs and approvals for sensitive tools.

Follow the authorization section of the current specification.

Q17. [MCP] What is tool poisoning and how do you defend against it?

Short answer: Malicious instructions hidden in tool metadata, or definitions changed after approval; defend by trusting only reviewed servers, pinning versions and alerting on definition changes.

Treat tool descriptions as untrusted input.

Q18. [MCP] MCP versus function calling versus OpenAPI?

Short answer: Function calling is the model API mechanism, OpenAPI describes REST APIs, and MCP is a protocol for exposing reusable tools, resources and prompts to many clients.

Keep logic in a service with thin adapters for each.

Q19. [MCP] MCP versus A2A?

Short answer: MCP connects an agent to tools and data; A2A lets independent agents discover each other and exchange tasks.

They are complementary.

Q20. [MCP] Why use a gateway and a registry?

Short answer: Central authentication, policy, rate limits, routing and audit, plus a catalogue of approved, versioned servers.

They prevent shadow integrations and give governance.

Q21. [Safety] What is prompt injection and how do you mitigate it?

Short answer: Untrusted content carrying instructions that try to steer the agent; mitigate with least privilege, treating output as data, isolation, approvals, egress control and monitoring.

No single filter is enough.

Q22. [Safety] What is excessive agency?

Short answer: Giving an agent more tools, permissions or autonomy than the task needs so mistakes or attacks cause large harm.

Use minimal tools, scoped credentials and human approval.

Q23. [Safety] Where should humans approve actions?

Short answer: At irreversible, costly or externally visible steps such as payments, deletions and outbound messages.

Show the exact action and arguments.

Q24. [Safety] How do you enforce access control in a RAG or agent system?

Short answer: Propagate user identity to every retrieval and tool call and filter results at the source, never relying on the prompt.

Audit access.

Q25. [Quality] How do you evaluate an agent?

Short answer: A suite of representative tasks with graders for outcome and trajectory, plus safety and injection cases, run on every change.

Add production failures as new tests.

Q26. [Quality] How do you reduce hallucinations?

Short answer: Ground with retrieval and tools, require citations, use schemas, verify programmatically and allow the system to say it does not know.

Measure with evals.

Q27. [Ops] How do you control cost and latency?

Short answer: Cap steps and tokens, route easy steps to cheaper models, cache prompts, shorten context, parallelise independent work and stop early.

Track cost per successful task.

Q28. [Ops] How do you make agents reliable in production?

Short answer: Retries with backoff for transient errors, timeouts and budgets, schema validation, idempotency, checkpoints, escalation and observability.

Design for failure.

Q29. [Design] Design a customer-support agent.

Short answer: Router, narrow read and write tools behind a policy layer with ownership and limits, approval above thresholds, state, tracing, evals and escalation.

Limits live in code, not in the prompt.

Q30. [Design] Design an enterprise assistant that respects permissions.

Short answer: MCP servers per system behind a gateway, user identity propagated to every call, permission filtering at the source, citations and audit.

The model must never see data the user could not.

Q31. [Debug] The agent keeps repeating the same tool call. What do you do?

Short answer: Read the trace, make tool results more informative, clarify the stop condition, add step limits and repeat detection, and escalate.

Add the case to the evals.

Q32. [Experience] How do you present your experience with MCP or orchestration standards?

Short answer: Describe a real project with design decisions, security and evals, using situation, action and result, with trade-offs and failures, claiming only what you can defend.

Concrete details build credibility.
